# Security Policy

**Last Updated: October 16, 2026**

## 1. Overview

IDEAZES POS AI is committed to maintaining the highest standards of security to protect your business data and your customers' information. This document outlines our security practices, infrastructure, and commitments.

## 2. Infrastructure Security

### 2.1 Cloud Infrastructure

| Aspect | Implementation |
|--------|---------------|
| **Provider** | Cloudflare (CDN, DDoS protection) |
| **Server** | VPS with dedicated resources |
| **Locations** | Malaysia and Singapore data centers |
| **Uptime** | 99.9% SLA target |

### 2.2 Network Security

- **Firewall**: Cloudflare WAF with custom rules
- **DDoS Protection**: Automatic mitigation up to 10Gbps
- **Network Segmentation**: Separate networks for web, API, and database
- **VPN**: Required for administrative access
- **Ports**: Only necessary ports exposed (80, 443)

### 2.3 Server Security

- **Operating System**: Latest stable Linux with security patches
- **SSH**: Key-based authentication only, no password access
- **Updates**: Automatic security updates applied within 24 hours
- **Monitoring**: Real-time server monitoring and alerting
- **Backups**: Daily incremental, weekly full backups

## 3. Data Encryption

### 3.1 Data in Transit

```
All data transmitted between users and our services is encrypted using:
- TLS 1.3 (Transport Layer Security)
- 256-bit SSL certificates
- Perfect Forward Secrecy (PFS)
- HSTS (HTTP Strict Transport Security)
```

### 3.2 Data at Rest

| Data Type | Encryption |
|-----------|------------|
| Passwords | bcrypt (cost factor 12) |
| Payment Card Data | Handled by Stripe (PCI DSS compliant) |
| Business Data | AES-256 encryption |
| Backup Data | Encrypted with separate keys |

### 3.3 Encryption Key Management

- Keys are stored securely using environment variables
- Production keys are never committed to code repositories
- Key rotation performed annually or after suspected compromise

## 4. Authentication and Access Control

### 4.1 User Authentication

| Feature | Implementation |
|---------|---------------|
| **Password Policy** | Minimum 6 characters, complexity not enforced |
| **Password Storage** | bcrypt with salt |
| **Session Management** | JWT tokens with 30-day expiry |
| **Multi-Factor Auth** | 2FA support for admin accounts |

### 4.2 Role-Based Access Control (RBAC)

| Role | Permissions |
|------|------------|
| Owner | Full access, billing, user management |
| Admin | Full operational access, no billing |
| Manager | Operational access, limited settings |
| Staff | Limited to assigned functions |
| Kitchen | Order viewing and updates only |

### 4.3 API Authentication

- API keys for programmatic access
- Keys are hashed in storage
- Rate limiting: 100 requests/minute per key

## 5. Application Security

### 5.1 Secure Development

| Practice | Implementation |
|---------|---------------|
| **Code Review** | All changes reviewed before deployment |
| **Dependency Scanning** | Automated scanning for vulnerabilities |
| **Static Analysis** | Linting and security-focused static analyzers |
| **Penetration Testing** | Annual third-party testing |
| **Bug Bounty** | Not currently active |

### 5.2 Input Validation

- All user input is validated and sanitized
- SQL injection prevention via parameterized queries
- XSS prevention via output encoding
- CSRF tokens on all state-changing operations

### 5.3 Error Handling

- Generic error messages shown to users
- Detailed errors logged server-side only
- No sensitive data in error responses

## 6. Payment Security

### 6.1 PCI DSS Compliance

- We do NOT store card data locally
- All payment processing handled by Stripe
- Stripe is PCI DSS Level 1 compliant

### 6.2 Our Payment Infrastructure

```
Payment Flow:
1. Card details entered in Stripe's secure iframe
2. Stripe returns payment token to our system
3. We process payments using tokens only
4. Original card data never touches our servers
```

### 6.3 Supported Payment Methods

| Method | Provider |
|--------|----------|
| Credit/Debit Cards | Stripe |
| ABA Payway | ABA Bank (Cambodia) |
| Touch 'n Go | Not currently integrated |
| GrabPay | Not currently integrated |

## 7. Data Protection

### 7.1 Backup Strategy

| Type | Frequency | Retention | Location |
|------|-----------|-----------|----------|
| Incremental | Daily | 7 days | Local + Remote |
| Full | Weekly | 4 weeks | Remote only |
| Monthly | Monthly | 12 months | Remote only |

### 7.2 Disaster Recovery

- **RTO (Recovery Time Objective)**: 4 hours
- **RPO (Recovery Point Objective)**: 24 hours
- **Recovery Procedures**: Documented and tested annually

### 7.3 Data Isolation

- Each customer's data is logically isolated
- Database uses customer_id for segregation
- No cross-customer data access

## 9. Incident Response

### 9.1 Incident Classification

| Severity | Description | Response Time |
|----------|-------------|---------------|
| **Critical** | Data breach, service down | 1 hour |
| **High** | Potential breach, partial outage | 4 hours |
| **Medium** | Non-critical vulnerability | 24 hours |
| **Low** | Minor issue, optimization | 72 hours |

### 9.2 Response Procedure

```
1. IDENTIFY - Detect and confirm the incident
2. CONTAIN - Isolate affected systems
3. ERADICATE - Remove the threat
4. RECOVER - Restore normal operations
5. DOCUMENT - Record lessons learned
6. NOTIFY - Inform affected parties if required
```

### 9.3 Notification

- Affected customers notified within 72 hours of breach discovery
- Regulatory bodies notified as required by law
- Updates provided until resolution

## 13. Your Security Responsibilities

### 13.1 Account Security

- Use strong, unique passwords
- Enable two-factor authentication (2FA)

- Regularly review account activity

### 13.2 Best Practices

- Log out when using shared devices
- Keep your devices updated
- Report suspicious activity immediately
- Review connected applications regularly

## 14. Reporting Security Issues

### 14.1 How to Report

If you discover a security vulnerability, please contact us immediately:

**Email**: security@ideazes.com
**Response Time**: Within 24 hours
**Expected Response**: We will acknowledge receipt and provide updates

### 14.2 What to Include

- Description of the vulnerability
- Steps to reproduce
- Potential impact
- Suggested remediation (if any)

### 14.3 Out of Scope

- Social engineering attacks
- Physical security testing
- Denial of service attacks
- Issues in third-party applications
