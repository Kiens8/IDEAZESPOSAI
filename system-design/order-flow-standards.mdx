# Order Flow Standards — the machine, the business types, and the tenant setup

**Document Version:** 3.0 (the clean rewrite)
**Owner:** Ideazes POS AI
**Status:** Proposal — the standard, the scenarios and the implementation order. Nothing is built yet.

> This document consolidates the earlier drafts (`takeaway-ordering.mdx`,
> `business-type-standards.mdx`) — both remain as stubs so old links still land somewhere
> sensible. The design has not changed; it has been reorganised, the duplication cut, and
> the tenant scenarios and the implementation order added.

---

## 1. The summary — the whole thing on one page

**One status machine for every business type and every order type:**

```
pending → confirmed → preparing → ready → served
```

**Three things vary:**

| What | The options | Decided by |
|---|---|---|
| The order type | dine_in / takeaway / delivery | the tenant's **mix** (which types are offered) — the **flow** comes from the type |
| The anchor | the table / the token / the customer name | the order type + the business type |
| The payment timing | prepay / postpay / either | the tenant's setting, per order type |

**One thing never varies:** the price, the tax, the currency, the receipt, the tenant
isolation.

**One exception:** the **delivery** adds exactly one step to the machine
(`out_for_delivery` → `delivered`). The dine-in and takeaway machines are untouched. See
`delivery-app.mdx`.

**The business type is a PRESET.** It *seeds* the settings; it is never a branch in the code.

## 2. The shapes

### 2.1 The order types

| Order type | The flow | The anchor | The bill |
|---|---|---|---|
| dine_in | the table service | the table | the table's orders |
| takeaway | the counter handover | the token or the name | the one order |
| delivery | dispatched | the address + the name | the one order |

**The delivery is one app and one process for EVERY business type** — it is not a business
type's flow. Its rules (the address, the fee, the driver, the payment) live in the delivery
app and are the same for everyone.

### 2.1a What already exists — the order type column

**The `orders` table already carries the order type:**

```python
# Order type: dine_in, takeaway, delivery
order_type = Column(String(20), default="dine_in") # models.py:216-217
```

**It is a plain `String(20)` — not an enum, not a CHECK constraint — so a new value needs no
migration.** The same is true of `status` (a `String(20)`) → the delivery's
`out_for_delivery` also needs no migration.

| The piece | Where | The state |
|---|---|---|
| the column | `models.py:217` | `String(20)`, default `dine_in` |
| the create | `order.py:181` (`order_type: str = "dine_in"`) | **no whitelist — any string is accepted✗** |
| the dine-in table rule | `order.py:303` | a table is required for a dine-in, not for the others |
| the staff chips | `StaffOrder.jsx:359-362` + the kiosk `790-792` | the three chips exist and honour `allow_dine_in / allow_takeaway / allow_delivery` |
| the reports | `reportsConfig.js:233-235` | the three types are already split |
| the PWA | `customer-app/js/app.js:1518` | it sends `order_type` — **and it has a delivery chip (`app.js:1144`) that must go** (the delivery is a separate app; a chip with no address and no fee is a broken flow) |
| `delivery_address` | `models.py:239` | **the column exists and is plumbed** (the create, the read, six response sites) |

**The three gaps this leaves**
1. **no whitelist✗** → a typo ("takeway") is stored silently → add
 `Literal["dine_in", "takeaway", "delivery"]` to the schema (tiny);
2. **the delivery's fee and driver are missing** — the address is there, the fee and the
 driver need a column (a `delivery` JSON on the order, or the tenant's JSON in the
 settings);
3. **the in-venue PWA must lose its delivery chip** — the delivery belongs to the
 delivery app. **DONE(Nov 5, 2026)** — the chip, the visibility rule and the
 "no type at all" rule are gone from `customer-app/js/app.js`.

**A hawker's counter is not a fourth order type** — the fulfilment is the same as a
takeaway; what differs is the anchor and the payment timing.

### 2.2 The status machine — one for all

- the cancellation rule — pending / confirmed / preparing (`order.py:969`)
- the kitchen's filter — everything that is not served/cancelled (`Kitchen.jsx:545`)
- the reports — the three types are already split (`Reports.jsx:122`)
- the reminder — `order_reminder_minutes`

**Only the wording of the last step varies**, and it is a translation:

| The business | The last step reads |
|---|---|
| Restaurant | **Served** |
| Cafe | **Collected** |
| Fast Food | **Collected** |
| Bar | **Served** |
| Stall | **Collected** |

→ **No new status value for the dine-in or the takeaway** — no migration, no data change, no
API change. **The one exception:** the delivery adds `out_for_delivery` — and because
`status` is a plain `String(20)`, **that needs no migration either**; it costs **about
seven places** in the frontend: the queue's flow array (`OrderQueue.jsx:132`), its icon
switch (`125`), its labels (`944`), the "all served" rule (`935` — a dispatched order is not
served), the kitchen's filter (`Kitchen.jsx:545` — an out-for-delivery order must leave the
kitchen), the unpaid-served list (`OrderSearchPanel.jsx:34`) and the report's status counts.

### 2.3 The anchor — what identifies the order

Every order needs something to point at: the counter, the kitchen and the bill.

| The order is | The anchor is | The bill rolls up |
|---|---|---|
| dine-in | the **table** | the table's orders |
| takeaway at a counter | the **token** ("A12") | the one order |
| takeaway with a name | the **customer name** | the one order |
| delivery | the **address** + the name | the one order |

**The anchor priority: the table → the token → the name.** The name is the fallback for the
counter orders that have no token.

**A takeaway may carry a table or carry none — the table is a HINT, not the anchor.**
The guest scans the table QR and then orders a takeaway: the order carries T5, and the
staff know the food is going to that table. The guest orders from the app: there is no
table. **Both are valid.** The staff may attach a table to a takeaway. **All of these are
valid** — the table is optional, never required.

**What an attached table does** — it puts the takeaway in the table's bill, so the
customer settles the table and the takeaway **in one payment** (§2.7).

**The takeaway's name lives on the order** (decided Nov 5, 2026): a `customer_name`
column on `orders`, nullable — a safe migration. The staff type it; the PWA asks for it
when the guest is not logged in. Not on the dining customer: that would mean creating a
customer record for every walk-in, which cuts against the walk-in principle.

**The token is nearly free** — the order number already exists (`order_prefix` — "ORD-00042")
→ "A12" is a short form of it → no new table, no new field.

### 2.4 The walk-in principle

**For the counter businesses the customer is a walk-in.** The fast food, the stall and the
cafe's counter customer have no account, no login and no loyalty — they are not a returning
customer we recognise, they are somebody standing at the till.

**What that means in the design:**
- the **token** is the natural anchor (the customer takes a number and waits for it to be
 called) → the fast food and the stall lead with the token, not the name;
- the **name** is the fallback when there is no token (a table-order cafe, a counter drink);
- the **walk-in customer id** stays the placeholder it is today — the POS must not invent a
 customer identity for a walk-in.

### 2.5 The payment timing

`prepay` / `postpay` / `either` — a setting, never a business-type constant (a stall does
both and a restaurant does both).

**Where it lives** — per order type, in the same JSON-map pattern the codebase already uses
for `payment_methods`:

```json
// OutletSettings.payment_timing
{ "dine_in": "postpay", "takeaway": "postpay", "delivery": "prepay" } // the restaurant preset
```

**The rules of a prepay order**
1. it is created with `payment_status = 'pending'` and `status = 'pending'`;
2. **it stays out of the kitchen** until the money lands;
3. **the payment webhook confirms it** → `payment_status = 'paid'` and `status = 'confirmed'`
 → the kitchen sees it;
4. the staff can still force it (`auto_confirm_orders`) — with a logged override;
5. **if the payment never lands** — **there is no auto-cancel today** (the
 `order_reminder_minutes` is a reminder, not a cancellation) → **an explicit expiry rule is
 needed**: the staff cancels it, or a scheduled cleanup does it. No new status — the wait
 lives in `payment_status`.

**Why prepay matters — the ghost order:** a hawker takes the order → the customer walks off
→ the food is made → nobody comes. The waste is real; prepay ends it.

**The delivery is the exception to the per-type map.** The delivery's timing belongs to the
delivery app's own tenant setting (`prepaid_only` — prepay or cash on delivery), not to the
business type. The fast food's delivery, for example, is **not** prepay: the driver collects.

**Where it is today** — the PWA has no online payment at all (it creates the order → the
success modal → the customer pays at the counter) → **postpay everywhere**. Prepay needs the
PWA to call `POST /api/orders/{order_id}/payments` (the endpoint already exists —
`order.py:809`) and to render a **DuitNow QR** — the HitPay DuitNow QR is the same service
the SaaS billing already uses.

### 2.6 The PWA's takeaway — the outlet is the venue, the table is only the dine-in anchor

**The principle**
> **A takeaway needs the OUTLET— only a dine-in needs the TABLE.** The table is
> the dine-in anchor; the outlet is the tenant's identity.

**How the customer arrives**

| How they arrive | The venue | The table | The state |
|---|---|---|---|
| **the table QR** | from the uuid | known | **works today** → they switch to Takeaway → **the table comes along as a hint** (the takeaway is its own order) |
| **a deep link** (`?outlet=<id>&type=takeaway`) | from the link | **none** | **broken today ✗✗** → `tableNumber = tableParam || 'T1'` invents a table ✗ → the uuid lookup fails ✗ → `venueResolved` is false ✗ → the venue picker opens on a takeaway order ✗ |
| **the installed app** (no QR) | the picker | **mandatory ✗✗** | **broken today ✗✗** → the picker is group → outlet → **table** → a counter-only outlet (a fast food, a stall) has **no tables** → *"No tables available" ✗* |

**The three fixes(small)**
1. **the picker must offer "Takeaway — no table"** at the outlet step → the venue is
 then resolved with **an outlet and no table** → `/pwa/venues` already returns the
 groups + the outlets + the address(`pwa.py:51`) — **no table needed**;
2. **the deep link must not invent a table** → `tableNumber = tableParam || null` →
 and `venueResolved` is true when the outlet is known;
3. **the link carries the type** → `?type=takeaway` → the PWA's `orderType` starts as
 `dine_in` ✗ → it must respect the link.

**The login changes two things and nothing else**
- **the `dining_customer_id`** → the customer (logged in) or the **walk-in
 placeholder** (not logged in) → **the order is identical either way** (the
 placeholder exists precisely so a walk-in still has an id);
- **the name** → a logged-in customer already has a name and a phone → **the
 takeaway's anchor can come from the account**; **not logged in** → the PWA must
 ask for the name (and the phone for the "your order is ready");
- **the login must never gate the takeaway✗** → a takeaway customer is a **walk-in**
 (the walk-in principle) → **no login, no problem**.

**The gap that matters most**
> **There is no customer-name field on the order✗** — neither the model nor the
> PWA → **a PWA takeaway is anonymous** → the kitchen sees an order with **no
> identifier ✗** → **that is exactly what Phase 4's tokenfixes**
>.

**The safety** — the PWA's `table_uuid` is the venue trust boundary → a takeaway has
**no uuid** → **the outlet becomes the anchor** → the backend verifies that the outlet
belongs to the claimed tenant(`order.py:340` — *"This customer does not belong to the
restaurant you are ordering from"*) → **so a takeaway without a uuid is safe**
.

**The staff side** — the takeaway lands in the staff's OrderQueue → **Phase 4b's
Takeaway view** (the code already computes `takeawayOrders` and never renders it
) → **the token identifies it at the counter**.

### 2.7 The one bill — the orders stay separate, the settlement is one

**The question (Nov 5, 2026).** The customer sits at T1, orders a dine-in, finishes
eating, then orders a takeaway. Two bills — is that convenient? The customer may want to
settle in one.

**The answer: the orders stay separate, the settlement becomes one.**

**Why the orders must not be merged**
- **two different states** — the dine-in is *served*, the takeaway is *ready* or
 *collected* — one order cannot be in two states, and the status machine cannot express
 it;
- **two different payment rules** — a prepay takeaway is paid before the kitchen starts, a
 dine-in is settled at the table;
- **the reports split by order type** — merging loses the dine-in/takeaway split, which
 is the number the business actually watches;
- **two different anchors** — the table, and the name or the token;
- **the industry does the same** — Toast, Square and Clover all keep them as separate
 checks and orders. What the mature systems offer is *settling them together*, not
 merging them.

**What the customer actually wants is "pay once", not "one order" — and that we can give.**

The machinery is already there:
- the staff search a table in the Orders screen → **"settle T5 (2 orders)"** → one payment,
 one receipt (`OrderSearchPanel.jsx:119` → `usePaymentFlow.js:282` — the bulk loop; the
 receipt already handles a bulk settlement, `StaffOrder.jsx:358`);
- the settle list is **served + unpaid + the same table number**, with **no order_type
 filter** (`OrderSearchPanel.jsx:32` and `:90`) → **a takeaway that carries T5 is already
 inside that settle action.**

**The two gaps — both closed (Nov 5, 2026)**
1. **the table is now OPTIONAL for a takeaway** — the staff may attach T5, and then the
 takeaway joins the table's bill and the one settlement covers both. The Phase 1 rule
 changed from "the picker is hidden for a takeaway" to "the picker is there, the table is
 optional" — the button was already enabled without a table.
2. **the two totals now agree** — the table's bill card in the Orders queue holds the
 dine-in orders **and** the takeaways attached to that table, which is exactly the set
 the search panel settles (the payable orders with that table number, no order_type
 filter). The card's total and the settlement can no longer disagree.

**The prepaid takeaway** — it is already paid, so it cannot join the table's settlement
(the money has moved). The customer gets two receipts. That is correct and stays.

## 3. The business types

### 3.1 The presets

`business_type` seeds these, and the tenant can override every one of them.

| Knob | Restaurant | Cafe | Fast Food | Bar | Stall |
|---|---|---|---|---|---|
| `table_required` | **true** | false | false | **true** | false |
| `allow_dine_in` | true | true | false | true | false |
| `allow_takeaway` | true | true | true | true | **true** |
| `allow_delivery` | **false** | false | **false** | false | false |
| `auto_confirm_orders` | false | **true** | **true** | false | **true** |
| `tips_enabled` | true | true | false | true | false |
| `split_bill_enabled` | true | false | false | true | true |
| the last step's wording | Served | Collected | Collected | Served | Collected |
| the anchor | table | table / name | **token** | table / tab | **token** |
| the stations (deferred — §3.5) | 1 | 2 (kitchen + bar) | 1 | 1 (bar) | 1 |

**`allow_delivery` is false everywhere in the presets.** The delivery flow is not built (the
address, the fee, the driver) → the type must not switch it on → it is switched on **per
tenant**, deliberately.

**`business_type` today** — a column on the outlet settings (`models.py:385`) that the
Settings page writes (`Settings.jsx:1190-1200`) and **nothing reads** — it is a label today.

### 3.2 The payment timing per type

| The type | dine_in | takeaway | delivery |
|---|---|---|---|
| **Restaurant** | **postpay** | **postpay** | the delivery app's setting |
| **Cafe** | postpay (the table service) | **prepay** | the delivery app's setting |
| **Fast Food** | — (no seating) | **prepay** | the delivery app's setting |
| **Bar** | **postpay** | postpay | the delivery app's setting |
| **Stall** | — | **either** | the delivery app's setting |

**The daily shapes**

| The type | The shape |
|---|---|
| **Restaurant** | the order → the kitchen → the payment at the table (the current flow, unchanged) |
| **Cafe** | order at the till → **pay** → wait → collect (the Starbucks shape) |
| **Fast Food** | order → **prepaid** → wait → collect (the KFC shape) |
| **Bar** | the order → the drink → pay at the end |
| **Stall** | the token → **pay first or when collected** |

**A cafe that takes table orders** — that is the dine-in order type → the restaurant flow →
postpay. **The same POS, both flows**, chosen by the order type and not by the business type.
A cafe has both flows, so the business type cannot decide the flow — the order type must.

**The sharp distinction** — it is not really "prepay vs postpay". The axis that matters is
**"must the money be in before the kitchen starts?"**

- **money first** — the kitchen waits for the payment → no ghost order (the cafe, the fast
 food);
- **kitchen first** — the food starts immediately, the money comes after or during (the
 restaurant, the bar).

Both are the same mechanic: the order is created → the payment is a separate event → the
webhook confirms it → **the only difference is whether the kitchen's view is gated on the
payment.**

**The Malaysian nuance** — "postpay" at a stall is usually the customer scanning the
merchant's **DuitNow QR** at the counter → the money lands in seconds → it is postpay with a
very fast payment. We already default the payment method to `duitnow_qr` (`models.py:279`) —
the local standard is already our default.

### 3.3 The food court — a set of independent stalls

**The food court is calculated as one stall.** A food court sells drinks and its own food,
and **every other stall has its own payment** → the stalls are independent businesses.

**In our model that needs nothing new:**

| The food court's | In the model |
|---|---|
| a stall | **an outlet** (the menu, the tables, the orders, the takings are all per-outlet) |
| a stall's payment | the payment sits on the **order** → the order carries `outlet_id` → the takings per stall come from the `payment-stats/{outlet_id}` report that already exists |
| the stall's kitchen | the kitchen display **already filters by outlet** (`Kitchen.jsx:103-105`) |
| the stalls' owners | **either their own tenant** (independent businesses → their own login and DuitNow) **or an outlet of the operator's tenant** (if the operator owns them → one account, and the internal split is the operator's commercial business, not a POS feature) |

**Both arrangements work today — no new concept.**

**And the scope saving:** the multi-stall split ticket is **not** needed. An order belongs to
exactly one outlet → one stall → one ticket. The "one order, two tickets" idea is dropped.
The stations work is therefore **deferred** (it was a food-court requirement; it remains a
real need for a single outlet with a grill and a bar — the cafe — but not for the food court).

### 3.4 The stall type — the hawker

A single stall is not a food court → **the business type is `stall`**: counter-only,
token-based, pay-first-or-later.

→ **The five business types:** restaurant, cafe, fast_food, bar, **stall** — and **`food_court`
is dropped**. A food court is not a business type; it is a set of independent stall outlets.
The Settings dropdown becomes five entries.

### 3.5 The stations — deferred

The gap: `kitchen_printer_ip` is a single printer → a cafe's bar and a restaurant's grill
have nowhere to live.

- (a) **the category is the station** — zero migration → the kitchen display filters by
 category → the interim answer;
- (b) **a real `stations` table + `menu_items.station_id`** — a nullable column (a safe
 migration) → the grill, the fryer, the bar → the kitchen display per station.

**Deferred** — it is not a food-court requirement any more → it drops to the end of the
queue.

## 4. The tenant setup — the scenarios

### 4.0 Phase 1 — what was implemented (Nov 5, 2026)

**The bug✗** — the staff screen's **Place order** button was disabled without a table
**whatever the order type was** ✗ (`canSubmit={!!selectedTable && settings?.table_required !== false}`)
→ **a takeaway could not be rung up at all ✗** (the handler and the backend
were already correct).

**The rule— one place:**

```jsx
// A table is the anchor of a DINE-IN order only.
const needsTable = orderType === 'dine_in' && settings?.table_required !== false
```

**What it changed**
- `canSubmit` → `!needsTable || !!selectedTable` (the desktop button and the kiosk's
 two buttons — `CartPanel.jsx:128` and `:165`);
- the submit guard → the same rule;
- **the table picker is hidden for a takeaway** — the desktop card, the mobile row
 and the kiosk's chip → **the kiosk's modal too** *(corrected below)*;
- **the type falls back** — if the tenant switches a type off, the screen does not stay on
 a type that no longer exists (a `useEffect` on the settings);
- **the PWA** — the delivery chip is gone; **the takeaway keeps its table** (a
 guest who scanned the QR carries T5 — the table is a hint, not the anchor);
- **the PWA's delivery chip is gone** — the delivery is a separate app.

**The correction (Nov 5, 2026) — the table is optional, not hidden**
Kens: *"for takeaway allow table no or don't have also can — using pwa can have table
no, if using staff order then no need table number, can input name."* The first cut hid
the picker for a takeaway, which was wrong: **the table may be attached or left empty.**

- the picker is always there — the desktop card, the mobile row, the kiosk's chip and the
 kiosk's modal;
- the heading says **"Select Table (optional)"** when the table is not required (a new
 i18n key in en/zh/km);
- **switching the type keeps the table** (`changeOrderType`) → a takeaway with an attached
 table settles with the table's bill, in one payment;
- the order's `table_id` / `table_number` are sent as they are — the takeaway carries the
 table when there is one.

**And the totals reconciled** — the table's bill card holds the dine-in orders *and* the
takeaways attached to that table, so it matches the set the search panel settles.

**The flow test** — `/tmp/phase1_takeaway_test.sh`→ **14/14**:
a takeaway with no table → **200** with no table · a dine-in with no table → **400
"A table is required for a dine-in order"** · a dine-in with a table → **200** with the
table · the cleanup cancels the test orders (there is no DELETE `/orders/{id}`—
the API's own way is `PATCH /{id}/cancel`).

### 4.1 How the setup happens — the mechanic

1. **Settings → Business** → the tenant picks the business type;
2. **a confirmation appears** — *"Apply the cafe preset? This changes your order settings"*
 → the preset never silently overwrites a tuned tenant;
3. **the preset seeds the knobs** — the table rule, the order types, the tips, the
 auto-confirm, the split bill, the payment timing;
4. **the tenant then tweaks anything** — the settings are always the source of truth (the
 code reads the settings, never the business type);
5. **the staff sees the effect immediately** — the type chips, the table picker, the wording,
 the payment timing.

### 4.2 A restaurant

**The type:** `restaurant`
**The settings:** `table_required=true` · `allow_dine_in=true` · `allow_takeaway=true` ·
`allow_delivery=false` (the delivery is off everywhere in the presets) · `auto_confirm=false`
· `tips=true` · `split_bill=true` · the last step **"Served"** · 1 station · the anchor: the
table · **the payment: postpay** (dine-in and takeaway)

**A day**
- a guest walks in → the staff opens the **Staff Order screen** → the type chips → **Dine
 In** → the table picker → **T5** → the order → the kitchen → the status flow → **the
 table's bill** → the payment;
- a takeaway → **Takeaway** → **the table picker disappears** → the token or the customer's
 name → the kitchen → **"Collected"** → the customer pays at the counter (**postpay**).

### 4.3 A cafe

**The type:** `cafe`
**The settings:** `table_required=false` (the tables are optional) · `allow_dine_in=true` (a
few tables) · `allow_takeaway=true` · `allow_delivery=false` · `auto_confirm=true` (the
drinks flow) · `tips=true` · `split_bill=false` · the last step **"Collected"** · 2 stations
(the bar + the kitchen) · the anchor: the token or the name · **the payment: prepay** (the
takeaway; the table service stays postpay)

**A day** — the customer orders at the counter (a **walk-in**) → the **coffee goes to the
bar station** and the pastry to the kitchen → the bar's display shows only the drinks →
**"Collected"** → the customer picks it up — **the money came first**: they paid at the till
→ **the kitchen waited for the payment**.

### 4.4 A fast-food outlet

**The type:** `fast_food`
**The settings:** `table_required=false` · `allow_dine_in=false` (no seating) ·
`allow_takeaway=true` · `allow_delivery=false` · `auto_confirm=true` · `tips=false` ·
`split_bill=false` · the last step **"Collected"** · 1 station · **the anchor: the token** ·
**the payment: prepay**

**A day**
- the customer comes to the counter (a **walk-in**) → the staff takes the order → **the
 token "A12"** → the customer waits;
- **prepay** → the customer scans the **DuitNow QR** at the till → the money lands in
 seconds → **the webhook confirms it** → **the kitchen starts** → **no ghost order**;
- the food is ready → **"A12!"** is called → **"Collected"**;
- **and a delivery, when the tenant switches it on** — the delivery is **a separate app and
 a separate process for every business type** (§8 / `delivery-app.mdx`) — and for a fast
 food the delivery is **not** prepay: **the driver collects** (cash on delivery).

### 4.5 A bar

**The type:** `bar`
**The settings:** `table_required=true` · `allow_dine_in=true` · `allow_takeaway=true` (a
bottle to go) · `allow_delivery=false` · `auto_confirm=false` (a bartender confirms) ·
`tips=true` · `split_bill=true` · the last step **"Served"** · 1 station (the bar) · the
anchor: the table **or the tab** · **the payment: postpay**

**A day** — the guest sits → the **table** (or a **tab** — the running bill, Phase 7) → the
drinks → the bar station → **"Served"** → the bill.

### 4.6 A food-court stall (the hawker)

**The type:** `stall` — **each stall is its own tenant (or its own outlet) with its own
payment**
**The settings:** `table_required=false` · `allow_dine_in=false` · `allow_takeaway=true` ·
`allow_delivery=false` · `auto_confirm=true` · `tips=false` · `split_bill=true` · the last
step **"Collected"** · 1 station (the stall's own) · **the anchor: the token** · **the
payment: either**

**A day**
- the customer comes to the stall (a **walk-in**) → the staff takes the order → **the token
 "A12"** (the short order number) → the customer waits;
- **pay first or when collected** → for **pay first** the customer scans the DuitNow QR →
 the webhook confirms → **the kitchen starts** → **no ghost order**;
- the food is ready → **"A12!"** is called → **"Collected"** → the customer pays (if they did
 not already).

## 6. The rails

1. **The backend is the authority** — `order.py:303` requires a table for a dine-in order and
 allows a null `table_id` otherwise → the frontend stops contradicting it;
2. **a takeaway may carry a table, or none** — the PWA's guest has one (they scanned the
 QR), the staff's takeaway does not (the staff enter a **name** instead). No model
 change (`models.py:202`); the takeaway never joins the table's bill;
3. **the money path does not move** — the price, the discount, the tax and the currency are
 identical for every type;
4. **the isolation does not move** — the tenant, the outlet, the table and the customer are
 derived exactly as today;
5. **the kitchen is not a table-bound surface**;
6. **a takeaway is not a "no-table dine-in"** — it is its own type and it is countable
 separately (`Reports.jsx:122`);
7. **the status machine is shared** — **no new status for the dine-in and the takeaway** (no
 migration, no API change); **the delivery adds exactly one** (`out_for_delivery`);
8. **the business type never links to the order type** — it seeds the mix and the knobs; the
 **flow comes from the order type**;
9. **the payment timing is a setting**, never a business-type constant — and any tenant may
 set it for any order type, whatever their business type (the type only seeds it), so a
 cafe can run postpay and a bar can run prepay;
10. **the delivery's timing belongs to the delivery app's own tenant setting** — not to the
 business type;
10b. **a customer-facing payment route is its own route** — the staff payment endpoint is
 a staff route; the PWA's prepay needs the ownership proof, not a staff session;
11. **a prepay order must never reach the kitchen unpaid** — the webhook confirms it and the
 kitchen filters on the payment — no new order status — **and it needs an expiry rule**
 (there is no auto-cancel today);
12. **the preset never overwrites a tuned tenant** — only on the type change, with a
 confirmation;
13. **every type stays available to every plan** — the type is a configuration, not a product;
14. **a stall is an outlet and its payment is its own** — the payment sits on the order → the
 order carries the outlet → the takings split per stall (no multi-stall order);
15. **a walk-in is a walk-in** — the counter businesses do not invent a customer identity;
 the token leads and the name is the fallback.

## 8. The delivery PWA → the full design is in `delivery-app.mdx`

**One separate PWA for the delivery business** — approved, with one condition: **one API, two
PWAs — not two systems.**

**Why a second PWA is right**
- the delivery customer is **not at the venue** → the surface is different (the address, the
 fee, the driver, the live tracking);
- the **in-venue PWA** (the QR table ordering) stays exactly what it is — a restaurant's
 dine-in + takeaway, the current flow, unchanged;
- **the delivery is one app and one process for every business type** — it is not a
 business type's flow.

**The condition — one backend**
- the same menu, prices, orders, kitchen and tenant → **the delivery PWA is a second client
 of the same API** — a fork here would duplicate the whole system;
- the delivery's rules (the address, the fee, the payment) belong in the **core**, not in the
 PWA.

**A delivery-only tenant (a ghost kitchen)** — no new business type: it is a restaurant whose
preset has `allow_dine_in=false`, `allow_takeaway=false` and `allow_delivery=true` — the
preset machinery already covers it.

**→ the full design:** `delivery-app.mdx` — the white-label storefront (one codebase, one
deployment, one API, one branded PWA per tenant), the scope boundary (**the tenant owns its
delivery operation; we own the commerce** — no marketplace, no driver app, no GPS, no
commission), the fee settings (one nullable JSON column), the **driver assignment** (a name +
a phone — the whole "tracking" for the price of a phone number), the **one delivery-specific
status** (`out_for_delivery`), the plan gating (the core in every plan; the zones, the
scheduling and the analytics are the paid "Delivery Ops" tier — the adoption argument wins: a
tenant who switches to us *for* the delivery must not be charged for it), and the four audit
gates for the PWA's public routes.

## 9. The market standard — how the mature POS do it

| System | The order types | The payment timing | The payment object |
|---|---|---|---|
| **Toast** | Dine In / Takeout / Delivery / Kiosk | a setting (Pay Ahead or pay at the counter) | separate |
| **Square** | none (the fulfilment sits on the customer) | native — pay later, split tender, pay at the table | separate |
| **Clover** | none | native (Pay Now / Pay Later) | separate |
| **Lightspeed** | Dine In / Takeaway | a setting (Pay Now / Pay Later) | separate |
| **Ours** | dine_in / takeaway / delivery | a setting, per order type | **separate** |

**Three conclusions**
1. **The payment is a separate object — in every mature POS — and we already are.** `Payment`
 (`models.py:273` — the amount, the method, the status, the transaction id, the paid-at)
 and `OrderPayment` for the split bill; the `payment_status` on the order is only a
 summary → **the architecture is already standard and needs no rework**.
2. **The payment timing is a setting in every one of them** — never a business-type constant
 → the per-type values are presets and every tenant can override them.
3. **The payment method defaults to `duitnow_qr`** (`models.py:279`) → the Malaysian standard
 is already our default — the local market's norm, not a Western import.

**One cleanup note** — there are two payment tables (`Payment` and `OrderPayment`) → they
should be one (with a `payment_type`) → a cleanup, not a rebuild.
