> **Why this document exists.** Kens: *"the current menu management is too simple —
> ingredients/toppings, size, modifiers, optional, remarks. If we change the menu
> structure it touches the kitchen printing and the recipe management, which involves
> costing. Example: a chicken mee soup — the customer chooses the noodle (mee,
> bihun, flat rice noodle), the size (big or small)."*
>
> So: the structure of the menu changes, and the three things that depend on it
> change with it — **the kitchen ticket**, **the recipe (the stock)** and **the
> costing (the margin)**. This document says what the menu looks like after, what
> each of those three becomes, and in which order it is safe to build.

## 1. The summary — one page

**Today the menu is a flat list of dishes.** A dish has a name, a price, a
category, a picture and a **flat list of free-text modification strings**
(`menu_items.modifications`). There are no sizes, no option groups, no prices on a
choice, no ingredient deltas and no remark on the order line.

**The gap, in the words of the example:**

| The guest wants | Today |
|---|---|
| Chicken mee soup | one menu item, one price |
| Big or small | **not possible** — no size concept anywhere |
| Mee, bihun or kway teow | **not possible** — no choice, no ingredient swap |
| Extra egg / no coriander | **not possible** — and the kitchen would never see it |
| "Less spicy, no celery" | the counter staff types it — **and the note is silently dropped** (see §3.4) |
| The right cost and the right margin | one flat cost per dish, whatever the guest chose |

**The proposal — three layers on top of the dish:**

```
menu_items                      the dish            (today)
  ├── menu_item_variants        the size            (NEW)  "Big", "Small"  → its own price, its own recipe
  └── menu_option_groups        the choice group    (NEW)  "Noodle", "Topping", "Spice"
        └── menu_options        one choice          (NEW)  "Mee", "Bihun", "Extra egg" → a price delta, an ingredient delta, a kitchen note
```

**and the sold line keeps a snapshot of the choice** (`order_item_options`, NEW) so
that the receipt, the kitchen ticket, the stock and the margin all speak about the
same thing.

**The four rules the proposal rests on:**

1. **The guest posts ids, never prices.** The server resolves the price from the
   menu. *(Today it does not — see §3.6, that is a live money hole.)*
2. **The choice changes three things at once, or it is not a choice:** the price,
   the ingredients (stock + cost) and the kitchen ticket. A group that does not
   move all three is a free-text remark, not an option.
3. **The sold line is a snapshot.** The history never changes when the menu does.
4. **The tenant can build it.** The sizes, the groups and the choices are not
   only readable — the tenant **creates** them (phase 4b, §7.1e), and the
   rules of the menu are enforced by the server, never by the browser.
   **And the screen is proved by a browser** — not by an API probe
   (§7.1f), because the API cannot see a missing button.
   **And both pickers are built** — the counter's (phase 5) and the
   guest's (phase 6, §7.1h) — each proved by a browser and each
   **asking** the server for the price, never working it out.
5. **Nothing breaks.** The tables are additive, the existing items keep working,
   the old `modifications` list stays as the legacy remark group. **A dish with no
   variant and no group takes the old code path exactly** — and the **compatibility
   probe** (§4.4) proves it on every phase, against the live menu: the same price,
   the same cost, the same grams, the same ticket lines.

## 3. What breaks, or is already broken

### 3.1 The kitchen ticket — the browser and the PDF lose the choices

`frontend/src/pages/Kitchen.jsx` has **two** ticket builders and they disagree:

| Builder | Used for | The choices |
|---|---|---|
| `generateKitchenTicketHTML()` (line 360) | the browser print and the PDF | **dropped** — it prints only `menu_item_name` and `x{quantity}` |
| `generateKitchenTicket()` (the ESC/POS, line 425) | the network printer | printed — `> ${mod}` per modification |

So on the browser printer the kitchen sees "Chicken Mee Soup x1" and nothing else —
not the noodle, not the size, not "no coriander". This is the single most
dangerous gap in the menu today, and it is **independent** of the new structure: it
is worth fixing on its own, this week, even if the whole options project is
deferred.

### 3.2 The recipe — one per dish, so a size cannot cost differently

`backend/app/models/inventory.py`:

```python
class Recipe:            menu_item_id, outlet_id          # ONE recipe per dish
class RecipeIngredient:  recipe_id, ingredient_id, quantity, unit_override
```

`backend/app/routes/inventory.py` → `GET /api/inventory/cost/{menu_item_id}`
(line 540) walks the recipe and multiplies `ri.quantity * ing.unit_cost`. One
dish, one cost.

Consequence: "Big chicken mee" and "Small chicken mee" would share **one** cost
and **one** stock deduction — the margin of the big one would be wrong, and the
noodle choice would not change the stock at all.

### 3.3 The stock — the deduction follows the dish, not the choice

`backend/app/routes/order.py` → `auto_decrement_stock()` (line ~92) deducts the
recipe's ingredients when the order is marked **ready**; the add-to-cart stock
check (line ~50) walks the same recipe. With a choice, the deduction has to be
`the variant's recipe + the chosen options' ingredient deltas` — otherwise a bowl
of mee and a bowl of bihun take the same noodles out of the shelf.

### 3.4 The remark is silently dropped

`frontend/src/pages/StaffOrder.jsx:310` sends `notes` **per cart line**.
`OrderItemCreate` (`backend/app/routes/order.py:185`) has **no `notes` field** and
`order_items` has **no `notes` column** — so the remark is accepted by the
browser, sent to the server and dropped by the schema. The only `notes` that
survives is the **order-level** one (`OrderCreate.notes`, line 206) — one note for
the whole order, not per line.

So the "less spicy, no celery" of a hawker is typed by the staff and never
reaches the kitchen nor the receipt.

### 3.5 The margin is a flat number per dish

`backend/app/routes/reports.py` (the menu mix, lines 89–186) joins the cost of the
sold lines to the menu and reports the margin per dish. The cost is chosen **per
tenant**, not per dish (`_menu_item_cost`, line 395): the tenant has the **Inventory**
feature → the **recipe** (the real cost) — otherwise `MenuItem.estimated_cost` (the
hand-written estimate) — otherwise **nothing is known** (`cost_known: false`, *a
dash, not a lie*).

With choices, the cost of a line is `the base + the options` — so the margin has to be
computed **per sold line**, under the same rule (the recipe's cost when the plan is
on, the estimate when it is not, a dash when neither is known) — and the
**frozen** cost of the line when the line has one (§5.2a).

### 3.6 The add-on's price is trusted from the client — a live money hole

`backend/app/services/order_service.py` (line ~109):

```python
provided_price = item_data.get("unit_price") if trust_client_money else None
item_unit_price = provided_price if provided_price is not None else menu_item.price
add_ons_price = sum(a.get("price", 0) for a in add_ons)      # <- ALWAYS from the client
item_total = (item_unit_price + add_ons_price) * quantity
```

The **unit price** is protected (a guest's price is the menu's price), but the
**add-on's price is not** — the guard `trust_client_money` covers only the unit
price. A guest who posts `add_ons: [{"name": "x", "price": -5.0}]` lowers their
own total.

**Verified** with `scripts/addon_price_probe.py` (against a copy of the database,
Nov 9): an order for a 3.00 dish, posted by a "guest" (`trust_client_money =
False`) with a `-5.00` add-on, came out at

```
the item total     : -2.0
the order subtotal : -2.0
the order total    : -2.16
```

**A guest can make their order negative.** This is a **priority 1** fix and it does
not wait for the options project: the price of an add-on must come from the menu,
never from the request. The patch is in §7.1.

## 4. The proposal — the structure

### 4.1 The seven new tables (all additive)

```python
# ── the size ────────────────────────────────────────────────────────────────
class MenuItemVariant(Base):
    """A size (or another whole variation) of a dish.
    Big / Small / Half / Regular / the lunch set."""
    __tablename__ = "menu_item_variants"
    id, outlet_id, menu_item_id
    name = Column(String(100), nullable=False)        # "Big", "Small"
    price = Column(Float, nullable=True)              # null -> the dish's price
    price_delta = Column(Float, default=0.0)          # or a delta on the dish's price
    cost_multiplier = Column(Float, default=1.0)      # or a multiplier on the dish's recipe
    # Its OWN recipe is NOT a row of the `recipes` table - it lives in
    # `menu_item_variant_recipes` (below), keyed by this variant's id.
    sku = Column(String(50), nullable=True)
    is_default = Column(Boolean, default=False)
    is_available = Column(Boolean, default=True)
    sort_order = Column(Integer, default=0)
    created_at, updated_at

# ── the group of choices ───────────────────────────────────────────────────
class MenuOptionGroup(Base):
    """A named group of choices: Size, Noodle, Topping, Spice, Side, Add-on."""
    __tablename__ = "menu_option_groups"
    id, outlet_id
    name = Column(String(100), nullable=False)        # "Noodle"
    min_select = Column(Integer, default=0)           # 0 = optional, 1 = required
    max_select = Column(Integer, default=1)           # 1 = single choice, >1 = multiple
    sort_order = Column(Integer, default=0)
    is_active = Column(Boolean, default=True)
    print_group_name = Column(Boolean, default=False) # does the kitchen read the group's name?
    station = Column(String(50), nullable=True)        # "Soup", "Grill", "Fry" (the split is deferred)
    created_at, updated_at

# ── the link between the dish and the group ───────────────────────────────
class MenuItemOptionGroup(Base):
    __tablename__ = "menu_item_option_groups"
    id, menu_item_id, group_id
    variant_id = Column(Integer, nullable=True)        # null -> the group applies to every variant
    sort_order = Column(Integer, default=0)
    required = Column(Boolean, default=False)          # overrides the group's min_select
    created_at

# ── one choice ────────────────────────────────────────────────────────────
class MenuOption(Base):
    """One choice inside a group."""
    __tablename__ = "menu_options"
    id, outlet_id, group_id
    name = Column(String(100), nullable=False)        # "Mee", "Bihun", "Extra egg"
    price_delta = Column(Float, default=0.0)          # the money
    ingredient_id = Column(Integer, nullable=True)     # the stock (nullable = no stock effect)
    ingredient_qty = Column(DECIMAL(12, 4), default=0.0)   # may be negative ("No egg" = -1)
    kitchen_note = Column(String(100), nullable=True)  # "NO CORIANDER" - printed in CAPS
    sku = Column(String(50), nullable=True)
    is_default = Column(Boolean, default=False)
    is_available = Column(Boolean, default=True)
    sort_order = Column(Integer, default=0)
    created_at, updated_at

# ── the snapshot of what was sold ──────────────────────────────────────────
class OrderItemOption(Base):
    """What was chosen, frozen at the moment of the sale."""
    __tablename__ = "order_item_options"
    id, order_item_id
    group_name = Column(String(100))                  # the name at the time
    option_name = Column(String(100))                 # the name at the time
    variant_name = Column(String(100), nullable=True) # "Big"
    price_delta = Column(Float, default=0.0)          # the money at the time
    ingredient_delta = Column(JSON, default=list)     # [{name, qty}] - the stock at the time
    kitchen_note = Column(String(100), nullable=True) # what the kitchen reads
    print_group_name = Column(Boolean, default=False) # the flag, frozen at the sale
    option_id = Column(Integer, nullable=True)        # null if the option was deleted since
    variant_id = Column(Integer, nullable=True)
    created_at
```

The **relationships** that were built with them: `MenuItem.variants` and
`MenuItem.option_group_links`, `MenuItemVariant.links` and `.recipe`
(`uselist=False` — a variant has **one** recipe), `MenuOptionGroup.options`
and `.links`, `MenuItemOptionGroup.group` / `.variant` / `.menu_item`,
`MenuOption.group` / `.ingredient`, `OrderItem.order_item` and
`OrderItem.option_snapshot`.

# ── the variant's recipe — its OWN tables ─────────────────────────────────
class MenuItemVariantRecipe(Base):
    """The recipe of a variant - the exact grams of the Large.

    It is NOT a row of the `recipes` table. That table holds **one recipe per
    dish** and thirteen places take it by `menu_item_id` (the stock check, the
    deduction, the cost, the menu's stock status, the reports' cost, the AI's
    predictions...). A second row for the same dish would be picked up by
    `.first()` in the wrong place - the wrong cost and the wrong stock, with
    no error to show for it.

    So the dish's recipe stays exactly where it is, untouched, and the
    variant's recipe lives here. The lookup is by `variant_id`, so it can
    never be mistaken for the dish's.
    """
    __tablename__ = "menu_item_variant_recipes"
    id, outlet_id
    variant_id = Column(Integer, ForeignKey("menu_item_variants.id"), nullable=False)
    created_at, updated_at

class MenuItemVariantRecipeIngredient(Base):
    __tablename__ = "menu_item_variant_recipe_ingredients"
    id, recipe_id, ingredient_id
    quantity = Column(DECIMAL(12, 4), nullable=False) # the same shape as the dish's
    unit_override = Column(String(50), nullable=True) # the same shape as the dish's

Plus **three columns** on the order line (`order_items`) — all nullable, all
additive:

| The column | What it holds | Why |
|---|---|---|
| `notes` (Text) | the per-line remark | the field the browser already sends and the server already drops (§3.4) |
| `variant_id` (Integer) | the size of the line ("Big") | a line may have a **size and no choice at all** — the snapshot rows hold the OPTIONS, so the size needs its own place |
| `variant_name` (String(100)) | the name of the size, frozen | the menu may be renamed tomorrow — the ticket of yesterday must still say "Big" |

> **This is a change to the first draft**: the draft said **one** column. The
> two size columns were added in phase 2, when the write path showed that a
> line with a size and no choice would lose its size. **Nothing was rewritten**
> — the three columns are nullable and the 502 old lines have none of them.

**Seven tables, not five** — and every one of them is additive (§4.4).

### 4.2 The rules of a group

| Rule | Where it lives | What it means |
|---|---|---|
| `min_select` | the group | 0 = optional, 1 = required (the guest must choose) |
| `max_select` | the group | 1 = one choice, n = up to n choices |
| `price_delta` | the option | the money it adds (may be negative) |
| `ingredient_id` + `ingredient_qty` | the option | the stock it takes (may be negative → "No egg") |
| `kitchen_note` | the option | what the kitchen reads, in CAPS |
| `variant_id` on the link | the link | the group's choices can differ per variant ("Big" offers a bigger topping set) |

### 4.3 The example, end to end — chicken mee soup

**The dish** (one menu item, as today):

| Field | Value |
|---|---|
| name | Chicken Mee Soup |
| price | 9.00 (the base) |
| recipe | 200 g chicken, 100 g mee, 1 piece chicken, soup base |

**The variants** (the size):

| Variant | price_delta | recipe | The cost |
|---|---|---|---|
| Small | -1.00 | the dish's recipe × 0.7 | ~2.10 |
| Regular | 0.00 | the dish's recipe | ~3.00 |
| Large | +2.00 | the dish's recipe × 1.4 | ~4.20 |

**The groups**:

| Group | min | max | Options (price / ingredient / kitchen note) |
|---|---|---|---|
| Noodle | 1 | 1 | Mee (0 / mee 100 g) · Bihun (0 / bihun 100 g) · Kway teow (0 / kway teow 100 g) · Flat rice noodle (+1.00 / flat rice 100 g) |
| Topping | 0 | 3 | Extra egg (+2.00 / egg +1 / EXTRA EGG) · Extra chicken (+4.00 / chicken +80 g / EXTRA CHICKEN) · No coriander (0 / coriander -1 g / NO CORIANDER) · Extra sprouts (+0.50 / sprouts +50 g) |
| Spice | 0 | 1 | Mild (0 / -) · Hot (+0.50 / chilli +2 g / HOT) · Extra hot (+0.50 / chilli +4 g / EXTRA HOT) |

**What the guest orders:** "Large Chicken Mee Soup, bihun, extra egg, no coriander, less spicy".

**What the server computes:**

```
the base            9.00
the size           +2.00
the noodle          0.00   (a swap, not a cost)
the topping        +2.00   (the extra egg)
                     ------
the unit price     13.00
```

**What the kitchen reads (the ticket):**

```
*** KITCHEN ***
      12
--------------------------------
[TAKEAWAY] 21:14
Guest: Ah Seng
--------------------------------

1x CHICKEN MEE SOUP
   > LARGE
   > BIHUN
   > EXTRA EGG
   > NO CORIANDER
   > LESS SPICY
--------------------------------
```

**What the stock takes:** `chicken +140 g (the large recipe), bihun 100 g, egg +1,
coriander -1 g` — the dish's recipe is replaced by the variant's, and the options
add their deltas.

**What the margin is:** `13.00 - (4.20 + 0.60 + 0.40) = 7.80` — a real number per
line, not the dish's flat 3.00.

## 4.4 The compatibility guarantee — the existing menu does not move

**Kens's rule:** *"make sure the new proposal won't impact the existing menu."*

The rule of the whole proposal: **a dish that has no variant and no group takes the
old code path exactly.** The new tables are additive, every new field of the API is
optional, and **nothing that exists today is rewritten** — not a row of the menu, not
a row of the recipes, not an order of yesterday.

| The thing | Today | After the proposal | Why it cannot move |
|---|---|---|---|
| the dish's price | `menu_items.price` | the same | the resolver adds nothing when there is no variant and no option |
| the dish's recipe | `recipes` + `recipe_ingredients` — **one row per dish** | **the same rows, untouched** | the variant's recipe lives in its own tables (§4.1) |
| the cost of the dish | `Σ quantity × unit_cost` | the same | a line with no choice costs exactly what the dish costs |
| the stock | the dish's recipe | the same | the snapshot's deltas are added **on top of** the base, never instead of it |
| the tile's stock status | the dish's recipe | the same | the menu route still asks for the dish's recipe |
| `menu_items.modifications` | a free-text list | the same, printed as it is | the write path still accepts it |
| the order lines (502 today) | `order_items.modifications` | untouched | the snapshot rows are written only for the new lines |
| the order line's API | `menu_item_id, quantity, unit_price, modifications, add_ons` | the same **plus** the optional `variant_id`, `option_ids`, `notes` | an old client posts the old body and gets the old answer |
| the customer app | the modal hides the options | the same, and the choices are **optional** | the PWA posts the old body **and** the new one — a dish with no choices is untouched |
| the tenant's internals (`estimated_cost`, `cost_multiplier`, `sku`, the ingredient links) | the guest's key could read them | **the guest's key reads none of them** | the stripper **fails closed** — only a staff key keeps them (phase 6, §7.1h) |
| the reports' cost | the dish's recipe, live | the same for the old lines | a line with no frozen cost falls back to the dish's recipe |
| the ticket | the dish's name | the same | a line with no choice is the line of today |
| the promotions and the voucher | the subtotal | the same | a dish with no choice has the same subtotal |
| the tax | the subtotal | the same | unchanged |

**The rule in code — three "if there is nothing, do exactly what you did" branches:**

```python
# the price: no variant, no option -> the dish's price, unchanged
unit_price = menu_item.price
if variant:  unit_price += variant.price_delta
unit_price += sum(option.price_delta for option in chosen_options)

# the cost: no variant -> the dish's recipe, unchanged
cost = dish_recipe_cost()
if variant and variant.has_own_recipe: cost = variant_recipe_cost()
elif variant:                           cost = dish_recipe_cost() * variant.cost_multiplier
cost += sum(option.ingredient_qty * ingredient.unit_cost for option in chosen_options)

# the stock: no choice -> the dish's recipe, unchanged
ingredients = dish_recipe_ingredients()
if variant and variant.has_own_recipe: ingredients = variant_recipe_ingredients()
ingredients += the option's deltas
```

**The proof — the compatibility probe.** It is **the acceptance gate of every phase**,
not a test at the end. For every dish of the live menu (16 today) the **old path**
and the **new path** are run side by side, and the answers must be **identical**:

- the price of the line,
- the cost of the line,
- the grams the stock would take,
- the lines of the kitchen ticket.

**A dish with no variant and no group may not move by one cent, one gram or one
line.** The probe is the answer to "will this impact the existing menu" — it is not a
promise, it is a number that has to stay the same.

**And the tenant's data:** the probe runs against a **copy** of the database (the
pattern the other probes use), so the live menu is never the thing being tested.

## 5. The three dependents — what each one becomes

### 5.1 The kitchen printing

**One formatter, three sinks.** Today there are two builders that disagree (§3.1).
The proposal is a single pure function that takes the order and returns the lines:

```
printLines(order) -> [
  { name: "Chicken Mee Soup", qty: 1, variant: "Large",
    options: ["BIHUN", "EXTRA EGG", "NO CORIANDER"], note: "less spicy" }
]
```

and then:
- the **browser/PDF** ticket renders it as HTML (the same shape it renders today, plus the lines);
- the **ESC/POS** ticket renders it as `> ` lines (the shape it already has);
- the **customer app's** ticket (if it ever prints) renders the same lines.

**The rules:**
- the choices are printed in CAPS, one per line, under the item;
- the group name is **not** printed when the option name says it all ("Bihun") but **is** printed when it is ambiguous ("Noodle: Bihun") — a per-group flag `print_group_name` (**built** — and **frozen** into the snapshot, so the kitchen reads the ticket as it was written);
- the **remark** prints under the item in italics ("less spicy");
- a "no" choice prints in CAPS with a NO ("NO CORIANDER") — the kitchen must never read "No coriander" as "add coriander";
- **the item's name is never rewritten** ("Chicken Mee Soup (Large, Bihun)") — the name stays searchable and the choices stay on their own lines.

> **Two decisions the build made**:
> - **the kitchen note wins over the name** — when a choice carries a note
> ("NO CORIANDER"), the note is what the kitchen reads; the name is what
> the guest picked and it is printed when there is no note;
> - **the remark is a row of its own** — marked as a remark (the HTML prints
> it in italics, the ESC/POS prints it in italic) so the kitchen never
> reads a remark as a choice.

**The station split (the deferred "stations" feature).** When the stations arrive,
a group can carry a `station` ("Soup", "Grill", "Fry") → the ticket router sends
the soup station only the soup lines. The options structure is the natural place
to hang that — worth one column now (`menu_option_groups.station`), even if the
router itself waits.

### 5.2 The recipe and the stock — inside the recipe management that exists

**Kens's second rule:** *"the proposal also has to be compatible in the current
recipes management, because the ingredients inside will use to calculate the actual
cost."*

**The recipe management today (Nov 9, 2026 — the live code):**

| The piece | Where | What it does |
|---|---|---|
| the two tables | `backend/app/models/inventory.py` | `recipes` (one row per dish — `menu_item_id` NOT NULL) and `recipe_ingredients` (`recipe_id, ingredient_id, quantity, unit_override`) |
| the three routes | `backend/app/routes/inventory.py` | `GET` / `PUT` / `DELETE /api/inventory/recipes/{menu_item_id}` — the PUT **replaces** the ingredient rows and sets `menu_item.has_recipe = True` |
| the cost | `backend/app/routes/inventory.py` → `calculate_item_cost` (line 542) | `Σ ri.quantity × ing.unit_cost` — the same arithmetic the reports use (`reports.py:395` `_menu_item_cost`) |
| the stock | `backend/app/routes/order.py` → `auto_decrement_stock` (line 133) | the dish's recipe, at the moment the order is marked **ready**, with a `StockMovement` row per ingredient |
| the stock check | `backend/app/routes/order.py` (line 59) | the dish's recipe, at the moment the item is added to the cart |
| the editor | `frontend/src/pages/Inventory/RecipeBuilder.jsx` | **one** recipe per dish — the dish's list on the left, the ingredients on the right |

**The live shape (Nov 9, 2026):** 16 dishes · 11 with a recipe · **never more than
one recipe row for a dish** · 502 order lines · 38 ingredients, **all** with a unit
cost.

**The rule: the dish's recipe does not move.** The proposal adds the choices to the
**side** of it — it never rewrites it, never re-keys it and never puts a second row
for the same dish into `recipes`.

**The thirteen places that take the recipe** — every one of them keeps taking the
**dish's** recipe, and the variant's recipe is a **separate** read:

| The place | Today | With a choice |
|---|---|---|
| the stock check (add to cart) `order.py:59` | the dish's recipe | the base + the **options' ingredients** are checked too (the egg may be out of stock) |
| the deduction (when ready) `order.py:133` | the dish's recipe | the **frozen snapshot** (§5.2a) |
| the cost `inventory.py:542` | the dish's recipe | the base stays the base; the variant's cost is a **new** read with the same arithmetic |
| the recipe routes `inventory.py:318/366/402` | one recipe per dish | **unchanged** — the variant's recipe has its own routes |
| the menu's stock status `menu.py:319` | the dish's recipe | the base (the variant's status is a detail of the tile, optional) |
| the reports' cost `reports.py:404` | the dish's recipe | the base for the old lines; the frozen cost for the new ones |
| the AI's predictions (3 places) | the dish's recipe | the base — a prediction is per dish |
| the anomaly detector | the dish's recipe | the base |

**The cost of a sold line — the same arithmetic, one layer more:**

```
the cost of a sold line =
      (the variant's own recipe        OR  the dish's recipe × the variant's cost_multiplier)
    + Σ (the chosen options' ingredient_qty × the ingredient's unit_cost)
```

**The rules:**
- the **dish's recipe stays the base** — an item without a variant never changes;
- a **variant** may have its own recipe (the exact grams for the Large) **or** a multiplier (the Large = 1.4 × the base) — the multiplier is the cheap way to start — **its recipe lives in `menu_item_variant_recipes`**, never in `recipes` (§4.1);
- an **option** carries at most one ingredient (the egg, the extra chicken) — a choice that needs several ingredients becomes its own **dish with a recipe** (an "Extra Chicken" add-on item — the mechanism that exists today); the option's ingredient **touches no recipe table**;
- a **negative** ingredient quantity is the way to say "no" ("No egg" = -1 egg) — the stock goes up by one egg, which is right (the stock is clamped at 0 today — `max(0, old - qty)` — a negative delta still adds);
- the **deduction** reads the snapshot (`order_item_options`) — not the live menu — so a menu change mid-service never moves the stock of an order already sold;
- the deduction still happens **when the order is marked ready** (today's rule) — the choice does not change the timing;
- the **cost is frozen into the line** at the moment of the sale (the same way the price is frozen) — and **a line with no frozen cost falls back to the dish's recipe** (that is the 502 old lines).

### 5.2a The frozen cost — what the reports read

The reports read the **line's** cost when there is one, and the **dish's** recipe when
there is not:

```python
# the cost of a sold line, in the reports
cost = line.frozen_cost                     # the new lines - frozen at the sale
if cost is None:                            # the old lines - the dish's recipe, as today
    cost = dish_recipe_cost(line.menu_item_id)
```

**Why the frozen cost and not a live read:** the ingredient's price moves (the flour
costs more this month), and the margin of an order sold in October must not be
rewritten by October's price — the same rule the price follows.

**The rule "an unknown cost is a dash, not a lie"** (the reports' existing rule)
applies to the option's cost too: an option whose ingredient has no `unit_cost` →
the line's cost is **unknown** → a **dash**, never a zero. (All 38 ingredients
have a unit cost today — but a new ingredient may not have one.)

**The recipe editor** (`frontend/src/pages/Inventory/RecipeBuilder.jsx` — today it
edits **one** recipe per dish, `GET/PUT /api/inventory/recipes/{menu_item_id}`):
- the **dish's recipe editor does not change** — the same screen, the same buttons, the same rows;
- a **variant's recipe** is edited by the **same component** with a variant's id (the variant's recipe lives in its own tables);
- the **option's ingredient** is a column on the option's list (the option's ingredient and its quantity) — and the ingredient is picked from the **existing** ingredient list (no new ingredient type);
- the editor shows the **cost of the dish as it is today** and the **cost of each variant** (the same arithmetic) — so the tenant sees the margin before the guest does.

### 5.3 The costing and the margin

- the **dish's** `estimated_cost` stays as the fallback when there is no recipe (today's rule: no recipe → the hand-written estimate);
- the **line's** cost is computed at the moment of the sale and **frozen into the snapshot** (the same way the price is frozen) — the reports read the frozen cost, not today's menu;
- the **reports** (the menu mix, the top items) keep the dish-level rollup and gain a **variant breakdown** (how many Large, how many Regular) — optional, and the cheapest part of the project;
- the rule *"an unknown cost is a dash, not 100%"* (the reports' existing rule) applies to the option's cost too: an option with an ingredient but no `unit_cost` → a dash, never a zero.

### 7.1 The patch for the money hole (phase 0) — **BUILT**

**Status: built, tested and live (Nov 9, 2026, 23:20).** Kens said the word.

**The hole (it was real):** the add-on's price came straight from the request —
`add_ons_price = sum(a.get("price", 0) for a in add_ons)` — so a guest posting
`{"name": "extra egg", "price": -5.0}` brought a 3.00 dish down to **-2.00** and the
order to **0.00** (the probe: **the guest paid nothing for a dish**).

**The patch** — `backend/app/services/order_service.py`, one helper
(`resolve_add_ons`) used by **both** write paths (`create_order` and
`add_items_to_order`) and by the **cart's** price
(`backend/app/routes/promotions.py` → `price_lines`) so the cart and the order
can never disagree:

```python
# BEFORE - the request's number
add_ons_price = sum(a.get("price", 0) for a in add_ons)

# AFTER - the MENU's number
resolved_add_ons, add_ons_price = resolve_add_ons(
    db, add_ons, trust_client_money, outlet_id=order.outlet_id
)
```

**The rules of the helper:**
- an add-on **with** a `menu_item_id` → the **menu's price** and the **menu's name**
  (the request's price is a claim — a guest posting -5.00 gets the menu's price);
- an add-on **without** an id → the **counter's** price for the staff (the extra of
  the day) — and for a **guest** it is **refused** (`400` — *"This add-on is not on
  the menu of this branch."*) — there is no free add-on;
- the counter may still give a price for an add-on that **is** on the menu (the same
  right the counter has over the dish's price) — the name stays the menu's;
- the add-on's dish must be a dish of **this branch** (another tenant's dish is not
  on this menu).

**The probe** (`scripts/addon_price_probe.py` — against a **copy** of the database)
now has **four cases** — **7 checks, all green**:
1. the guest's negative add-on → **refused**;
2. the guest's add-on with the menu's id and a lying price → the **menu's** price and
   name;
3. the counter's price for an extra that is not on the menu → **kept**;
4. the counter's price for an add-on that is on the menu → **kept**, the name is the
   menu's.

**Live on the production path** (the live server, not a copy): the crafted guest's
order answers **400**, the staff's order answers **200** with the counter's price,
and an ordinary guest's order is unchanged (3.00 − the happy hour 0.60 + the tax
0.19 = **2.59** — the same as before the patch).

### 7.1d The patch for phase 4 (the recipe + the stock + the costing) — **BUILT**

**Status: built, probed and live (Nov 10, 2026).**

**What it closes (§5.2):** the size's recipe was not applied to the stock or
to the cost, the choices' ingredients were not in the cost, and the
deduction read the **live menu** — so a recipe that changed mid-service moved
the stock of an order already sold.

**The four pieces:**

**1. The size's own recipe** — its own tables (§4.1:
`menu_item_variant_recipes` + `menu_item_variant_recipe_ingredients`), never
in `recipes`. A size with no recipe of its own uses the **dish's recipe × its
multiplier** (`line_recipe_lines` in `backend/app/services/line_cost.py`).

**2. The API for the size's recipe** (`backend/app/routes/inventory.py`):

| The route | What it does |
|---|---|
| `GET /api/inventory/variants?menu_item_id=` | the sizes of a dish, with the **cost of each one** (the editor shows the margin before the guest does) |
| `GET /api/inventory/variants/{id}/recipe` | the size's own recipe — or the fallback (the base × the multiplier) **in the same shape**, so the editor shows one list |
| `PUT /api/inventory/variants/{id}/recipe` | write the size's own recipe |
| `DELETE /api/inventory/variants/{id}/recipe` | drop it — it falls back to the base × the multiplier again |

**The tenant comes from the RESOURCE** — the size's own outlet — never from
a query parameter. The plan gate (`require_plan_feature("Inventory")`)
and the permission (`inventory:read` / `inventory:write`) are on every
route.

**3. The stock and the cost follow the choices:**

- the **cost of a line** = the size's recipe + the choices' ingredients
  (`compute_line_cost`) — frozen into `order_items.frozen_cost` at the
  moment of the sale (§5.2a);
- the **stock of a line** = the same ingredients (`compute_stock_lines`)
  — frozen into **`order_items.stock_lines`** (a JSON list of
  `{ingredient_id, quantity}`) at the moment of the sale;
- the **deduction** reads the **frozen** list — never the live menu — so
  a recipe that changes mid-service **does not** move the stock of an order
  already sold. The **502 old lines** (no frozen list) keep the old
  behaviour — the live recipe — the compatibility rule of §4.4;
- a **negative** quantity is the way to say "no" ("No egg" = -1) — the
  stock goes **up**;
- the **stock check** (`check_stock_blocking`) reads the live menu — it
  runs **before** the sale, so it must see the menu as it is now.

**4. The reports say where the number comes from ** (`backend/app/routes/reports.py`):
the cost of a line is its **frozen** cost, or the dish's recipe for the old
lines. And the **label is honest**: a dish whose lines came from different
rules is **`mixed`** — the screen says so
(`reports:items.costNote.mixed` in en / km / zh) instead of picking one
rule and pretending.

**The editor** (`frontend/src/pages/Inventory/RecipeBuilder.jsx`): the
**same component** edits the dish's recipe and the sizes' recipes (§5.2a) —
the size tabs, the **cost of every size** next to its name, and the
badge that tells the tenant when a size still uses the base × the multiplier.

**The probe** (`scripts/pos_menu_options_stock_probe.py` — against a **copy**):
**25 checks, all green** — the old path does not move, the multiplier,
the size's own recipe, the choice's ingredient in the cost and in the
stock, a "no" choice makes the stock go **up**, the deduction reads the
**frozen** deltas and the **frozen** size recipe (the menu changes after
the sale and the stock does not), the cost is frozen, an unknown cost is
a **dash** (never zero), and the stock check blocks what is out of stock
— including a size's own ingredient — and never blocks a "no egg".

**Live**: the sale of a size with a choice froze the cost (18.50) and the
stock (the size's own 3.50 + the choice's 1.00); the size's recipe was
then **changed to 9.00** — and the deduction still moved the stock by the
**frozen 3.50**. The menu mix answered **`mixed`** for the dish whose
lines came from both rules.

**What phase 4 does NOT do:** the **picker** (the counter's — phase 5 —
and the guest's modal — phase 6) was still to come — the sizes and the
choices could not be picked yet (**both are built now** — the counter's
§7.1g and the guest's §7.1h). (The **management screen** that lets the
tenant create them **is** built — phase 4b, §7.1e.)

| | The tenant WITH Inventory | The tenant WITHOUT |
|---|---|---|
| the sizes | work | work |

**The lesson ** — *a screen with two faces is two screens.* The embedded
screen and the kiosk share a component, not a rendering: the kiosk's early
return and the kiosk's own cart rendering each needed their own check.
The browser check must walk **every face** a screen has — not the one the
test happens to open.

### 7.1h The patch for phase 6 (the guest's picker) — **BUILT**

**Status: built, proved by a browser and live (Nov 11, 2026).**

The guest opens a dish that carries choices — the **sizes** and the **groups of
choices** appear, one tap each, the **price moves as they go**, and the
line goes into the cart carrying the size, the choices and the note for the
kitchen. The **server owns the money and the rules** — the price is
**asked for**, never worked out in the browser.

---

#### 1. The pieces

**The picker — `customer-app/js/choices.js` ** (the only picker in the guest's
app). It draws the sizes, the groups, the note and the price, and it
**asks** the server for the price:
`GET /api/menu/items/{id}/options/price?enforce_rules=false` — the **preview
mode** (added in this phase). The preview mode applies the **ownership**
rules (a choice that is not on this dish is refused) but **not** the
group's rules (the guest may still be choosing) — the order's write path
enforces those again (phase 2).

**The rules are the menu's.** The picker only keeps the guest from making a
choice the server would refuse (`min_select`, `max_select`, the groups
that belong to this dish, an unavailable choice) — the same promise the
counter's picker makes (`frontend/src/components/pos/ChoicePicker.jsx`).

**The wiring — `customer-app/js/app.js` ** (no picker logic of its own):
the modal opens the picker and awaits it; the customization section shows
**only** when the dish carries choices (a dish without choices keeps the old
modal — §4.4); the line goes into the cart carrying `variant_id`,
`option_ids`, `notes`, `choice_labels` and the **server's** price; two
lines merge only when their choices are identical; the cart shows
`Big · Chili · Mayo` and the note (HTML-escaped — the guest types it);
and `quickAdd()` sends a dish with choices to the modal instead of straight
into the cart.

**The promotion and the order carry the same choices ** — `/promotions/calculate`
and `/orders/` both take `variant_id` / `option_ids` / `notes` → the
cart's number and the order's number **cannot disagree**.

**The three languages ** — `picker.*` in en, km and zh (the size,
the note, the range — *pick 1 to 2* — and the eight refusal messages).

**The deployment is a BIND MOUNT ** — `/var/www/html/posai-customer` **is**
the repo's `customer-app/` (the same inode) → editing the repo **is** the
deployment → there is no deploy step to run.

#### 2. Three live bugs the work found

**1. The API ran the OLD code.** PM2's `pos-backend` had been up since

| The file | What it does |
|---|---|
| `backend/app/middleware/auth.py` | `is_customer_caller()` — only the **staff** keys (`key_type` in `frontend` / `user`) keep the internal view; the customer key, the external key and an **unknown** caller get the guest's view — the rule **fails closed** |

| `backend/app/routes/menu.py` | `public_menu_item()` applied to `GET /items`, `GET /items/{id}`, `GET /items/{id}/options`, `GET /items/{id}/options/price`, `GET /options-catalog` and `GET /option-groups` |

The nine internal names — `estimated_cost`, `has_recipe`,
`cost_multiplier`, `has_own_recipe`, `sku`, `ingredient_id`,
`ingredient_qty`, `ingredient_name`, `ingredient_delta`.

**What was deliberately NOT touched ** — the **internal order write path**.
The routes strip, but `order_service.py` calls `resolve_choices()`
**directly** → the kitchen and the stock still receive the costing, the
recipe links and `ingredient_delta`. The **staff's** answers stay unwidened
— the till needs the margin, the recipe and the stock.

#### 5. Three lessons the probes carry now

1. **A key that ships in a client bundle makes every field it can read

   the guest's browser has it. The rule: a **public** key may read the
   **public** shape only, and the sanitizer must **fail closed** (an
   unknown caller gets the guest's view, never the staff's).
2. **Two price paths are one bug waiting to happen.** The cart's number
   and the order's number are priced by **different code** — the fix is not

3. **A probe is not a screen, and a read that answers 200 is not a read that is
   allowed.** Both of the bugs above were found by asking the **live** API
   what a guest can see, not by reading the code.

### 7.1i The patch for the absolute-priced variant (the staff picker + the charge path) — **BUILT**

**Status: built, proved by a browser and live (Nov 11, 2026).**

§7.1h left one edge open: a size that carries a price **of its own**
(`variant.price`) is the **absolute** price of the line — not the dish's
price plus a delta. The resolver already knew that
(`variant_unit_price()`), but **two** things did not:

1. the **catalog** did not publish the size's own price → the staff's picker
   could only do the delta form → an absolute-priced size would **show**
   the wrong price;
2. the **charge path** took the **client's** arithmetic as the money on a line
   that carries choices → the counter's own picker (dish + delta) could
   become the price the guest is charged.

Both are closed, and the **rule now lives in one place**.

---

#### 1. The rule, in one place

`backend/app/services/line_pricing.py` — **one module, two paths**
(`POST /promotions/calculate` and `POST /orders/` both ask it), so the
cart's number and the order's number **cannot disagree**:

- a line **without** choices keeps the old path **exactly** (§4.4) — the
  counter's price is the counter's price, a guest's price is ignored, the
  dish's price is the fallback;
- a line **with** choices (a size, a choice, or both) is priced by the
  **menu** — the resolver's rule: the size's own price if it has one,
  otherwise the dish's price plus the size's delta, and then the choices'
  deltas;
- a **deliberate** price is a field of its own — `price_override`. The
  ordinary `price` / `unit_price` of a line is the **client's** arithmetic
  (the picker adding the deltas) and is **never** a deliberate act.

The override is honoured on **every** line (a dish without choices too) —
it is the right the counter has always had over a dish's price, now written
down instead of implied. Only a **trusted** caller may use it (the staff
key): the guest's override is ignored, and a value that is not a usable
price (not a number, negative, NaN, infinite) is not an override —
the menu's price stands.

#### 2. The catalog publishes the truth

`options_catalog()` now sends each size's own price — `effective_price`
(the price of ONE line that carries the size) and `effective_delta` (the
size's **contribution** to the dish's price). The staff's `ChoicePicker.jsx`
**reads** those numbers — it never works the rule out for itself (§7.1g).

#### 3. The counter's deliberate price

The pencil next to the price in the cart (`frontend/src/components/pos/CartPanel.jsx`
→ `LinePrice`) opens a field: a finite, non-negative number becomes the
line's `price_override`, and **clearing** the field removes it — the menu's
price stands again. The cart shows **both** prices (the deliberate one,
the menu's struck through) — the counter must see what the dish really
costs next to what the guest is charged. The three new i18n keys
(`cart.editPrice`, `cart.savePrice`, `cart.cancelPrice`) went into
**en**, **zh** and **km**.

#### 4. The two proofs

- **`scripts/pos_choice_pricing_check.py` ** — the **durable** check
  (**39 checks **, green against the live tree): it owns its fixtures
  (its own dish, its own sizes, its own choices — on a **copy** of the
  database), it fingerprints the rows **the user owns** before and after
  (six tables, every row unchanged), it refuses to run on the live
  database, and it reads the **running** server too (the catalog, the
  guest's view — the price, never the costing). It covers: the picker
  is told the truth, the resolver's two forms, the preview and the write
  path **agree**, the deliberate override, a guest's override **ignored**,
  and the old path **not moving**.
- **`scripts/pos_choice_pricing_control.py` ** — the **negative control**
  (the check must fail without the fix): it copies the source to a scratch
  tree, reverts **only** the fix (each replacement asserted to match
  exactly once) and runs the **same** check against the copy → **10 of the
  fix-covering checks fail** and the **21** that do not cover the fix stay
  green (the revert is surgical). The live tree, the live database
  and the running server are proven **untouched** afterwards.
- **`scripts/pos_staff_price_check.js` ** — **proved by a browser** (the
  real till, the real picker, a **real order**): the pencil opens, the
  deliberate price travels in **its own field** (`price_override = 7.25`,
  the ordinary `unit_price` untouched), the **database** charges the
  deliberate price (7.25) **and** the choices are **still frozen** (the
  size and the option), clearing the field puts the menu's price back,
  and the test order is **gone** afterwards.

**A lesson this patch carried** — the money hole was not in the resolver
(it was already right); it was in the **two** places that **copied** its rule
— the picker and the charge path. The fix is not that each copy is
careful; it is that **neither copies it any more** — the picker **reads**
the server's numbers and the charge path **asks** the one resolver.

### 7.1j The patch for the translated choices (the sizes, the groups, the choices) — **BUILT**

**Status: built, proved and live (Nov 11, 2026).**

§8 Q6 is **answered** — the translations are **in this project** — and the
half that was missing was the half the **guest** sees: the dish's name was
translated (the category's too), and the **sizes**, the **groups** and
the **choices** sat next to it in **English** — `大份` next to `Big`.

This patch closes that. It is a **display** patch — and it is deliberately
the *narrowest* kind: the **names** move, and **nothing else does**.

---

#### 1. No new table, and no migration

`menu_content_translations.content_type` is a free-form `String(50)` — there
is no `CHECK` constraint — and the unique key is already
`(content_type, content_id, outlet_id, locale)`. So three new content types
drop straight into the table that was already there:

- `menu_variant` — the size;
- `menu_option_group` — the group of choices;
- `menu_option` — the choice itself.

**The schema does not change** — and the `outlet_id` on every row is what
keeps the tenant rule: a translation belongs to the **branch** whose menu it
was made for and can never surface in another branch's picker.

#### 2. The names move, and only the names

`backend/app/services/menu_options.py` — `apply_choice_translations()` —
walks a payload and puts the guest's language into the **names** (the size's,
the group's, the choice's — and the group's name **inside** the choice, so
a line is never half in one language and half in another).

It is applied at **three** read points — the picker
(`GET /api/menu/items/{id}/options`), the catalog
(`GET /api/menu/options-catalog`) and the price answer
(`GET /api/menu/items/{id}/options/price`) — and each takes an **optional**
`locale`. The ids, the prices, the rules (`min_select`,
`max_select`) and the stock are **untouched**.

**The staff's picker deliberately does NOT send a locale** — the business
language is the operational record, and the counter reads the same words the
kitchen does.

#### 3. The snapshot keeps the business language

This is the rule the whole patch rests on:

- the **display** layer is localised — the guest's picker;
- the **resolver** never is — `resolve_choices()` answers with the **source**
  names, because the order's write path (`order_service`) freezes **that**
  payload into `order_item_options`.

So the **snapshot** keeps `Big` / `Sauce` / `Chili` — the kitchen reads
the business language — while the guest reads `大份` / `酱汁` / `辣椒酱`.
The write path is **not** changed to use localised display names.

The refusal is the one place where the two meet — the server's own sentence
names the **group** in the guest's language (`Please choose 酱汁.`) while the
**shape** of the sentence stays the English one — the guest app already
recognises `Please choose {name}.` and `You can only choose {n} of {name}.`
and says the whole thing in the guest's language.

#### 4. The labels get their own prompt

A size and a choice are **labels** — `Big`, `Sauce`, `Chili` — and the
prose prompt that translates a dish's **description** would hand back a
**sentence** for them. So the choices get their **own** prompt
(`LABEL_PROMPT_TEMPLATE` in `backend/app/services/ai_translation.py`) and
their **own gate** (`is_valid_label()`): an answer that came back as a
sentence, or with a full stop the source did not have, or too long, is
**refused** — and **two different places** hold the refusal: the
**model's cache** does **not** keep the bad answer (the next run asks again)
and the **row** is stored with the **English source** and the status
**`fallback`** — so the tenant can see what was **not** translated
(§7.1j.8).

**Proved against the live model**: eight real labels (`Big`, `Normal`,
`Sauce`, `Chili`, `Mayo`, `Extra egg`, `No onion`, `Less ice`) in
**zh** and **km** — **all sixteen** passed the gate.

#### 5. The guest app asks in the guest's language

`customer-app/js/choices.js` — the picker sends the guest's locale
(`guestLocale()` / `localeQuery()`) and the **app translates nothing
itself** — the server decides what the name is.

`Choices.reloadLocale()` — when the guest **changes the language** with the
picker **open**, the picker re-reads the names, **keeps** the ids that are
still valid, **drops** the ones that are not, re-renders and re-asks the
price. `app.js` calls it from `onLanguageChanged` — the static markup,
the menu and the **choices** all move together.

#### 6. The two proofs

- **`scripts/pos_choice_translation_check.py` ** — the **durable** check
  (**64 checks **, green against the live tree): it owns its fixtures (its
  own dish, its own sizes, its own groups, its own choices — on a
  **copy** of the database, taken with the **backup API** so the copy is
  never torn), it fingerprints the rows **the user owns** before and after
  (seven tables, every row unchanged), it refuses to run on the live
  database, and it reads the **running** server too. It covers: the three
  content types, the unique key, the **English fallback**, the
  **outlet's isolation**, the **guest vs the staff** payload, the
  **localised price answer**, the **frozen snapshot in the business
  language**, the **localised refusal**, the **label gate**, and the
  **route edge** (the real HTTP requests — a route that forgot to pass the
  locale on would pass every other check and still show the guest English).
- **`scripts/pos_choice_translation_control.py` ** — the **negative control**
  (the check must fail without the fix): it copies the source to a scratch
  tree, reverts **only** the fix (the display layer — each replacement
  asserted to match exactly once) and runs the **same** check against the copy
  → **16 of the fix-covering checks fail** and the **29** that do not
  cover the fix stay green (the storage, the money, the frozen snapshot
  and the sanitising must not move — the revert is surgical). The live
  tree, the live database and the running server are proven **untouched**
  afterwards.

#### 7. Live

Deployed (the backend restarted) and the **real** choices of the live
branch backfilled — `Big` / `Normal` / `Sauce` / `Chili` / `Mayo`
— in **zh** and **km**. The live picker answers:

| The guest's language | The size `Big` | The size `Normal` | The group `Sauce` | The choice `Chili` | The choice `Mayo` |
|---|---|---|---|---|---|
| **zh** | `大份` | `普通份` | `酱汁` | `辣椒酱` | `蛋黄酱` |
| **km** | `ធំ` | `ធម្មតា` | `ស៊ូស` | `ម្ទឹស` | `ម៉ាយ៉ូ` |
| **no locale** (the staff's view) | `Big` | `Normal` | `Sauce` | `Chili` | `Mayo` |

The live price answer is right — `3.00` (the dish) `+ 3.00` (the size)
`+ 0.50` (the choice) `= 6.50` — **and** it carries the localised names.

**A lesson this patch carried** — the **storage** was never the problem
(the table and the unique key were already right); the problem was that
**three** read points never asked for a language. A translation that is
stored but never **read** is the same as no translation at all — and
the fix is that **every** read point asks, and the **proof** is that the
**route edge** is checked (not only the helpers beneath it).

**What this patch deliberately does NOT do**:

- it does **not** translate the **write path** — the snapshot stays in the
  business language (§7.1j.3);
- it does **not** localise the **staff's** picker — the counter reads the
  business language;
- it does **not** change the **prices** — the ids, the money and the rules
  are untouched;
- it does **not** change the **schema**.

#### 8. The tenant's side — the read half is built, the **manage** half is **not**

**The read half is built and live** — that is the half the **guest** sees:
the picker's **three** endpoints answer in the guest's language, and the
live branch's own labels are backfilled — **ten** rows (five labels ×
**two** locales) — **every one** of them reads **`done`**.

**The write half is the machine's only** — and this is the honest gap:

- the **only** route that writes a translation is
  `POST /api/menu/translations/backfill` (`menu:write`) — it asks the
  model, runs the gate and stores the answer;
- there is **no** route that edits **one** translation by hand — no `PUT`,
  no `PATCH`, no delete;
- there is **no** screen that shows a translation — the menu management
  screen (`ItemChoicesModal.jsx`) writes the **sizes**, the **groups**
  and the **choices** in the **business language** and it never shows the
  localised name.

So the tenant can make the guest's menu **translated** — but if the model
picks a **wrong word** (and it will — `Extra egg` is not `Extra eggs`),
the tenant cannot **fix** it without a developer — the only lever today is
to change the **English source** and re-run the backfill.

**And the `fallback` status is stored but unseen** — a refused label is
written with the status `fallback` (and the English source) so the tenant
**can** see what was not translated — but only by reading the **database**,
because **no screen reads it**.

**So the honest answer to "is the tenant-facing management of the translations
in scope?"** — the **read** half is **in** and **live**; the **manage**
half is **not built** and it needs **Kens's** call — because it is a
**screen** decision (a new tab on the menu screen? a panel on the choices
modal?) and not a technical one.

That is the **one** open question this patch leaves — see **§8 Q7**.

### 7.1k The patch for phase 8 (the reports' variant breakdown) — **BUILT**

**Status: built, proved and live (Nov 11, 2026).**

Phase 8 was the **cheapest** part of the project and it is now **done**
— the menu mix answers with a **breakdown by size** beside the dish
table (§5.3), and the screen says **what the breakdown covers**.

It stayed **query-only** — the data was **already frozen** (phase 2):
`order_items.variant_id` + `variant_name`. **No new table**, **no
migration**, **no write path touched**.

---

#### 1. One loop, two tables — they cannot disagree

The rule of the whole patch: the breakdown is **not a second
calculation**. `backend/app/routes/reports.py` reads the lines **once**
— the same loop that builds the dish rollup — and every number in the
breakdown comes from the **line values that loop already read**. The two
tables are two views of **one** set of lines, not two sets of lines.

So the route answers with:

- `items` — the dish rollup (**unchanged** — the old screen's numbers
  do not move);
- `variant_items` — one row per **(dish, size)** pair;
- `variant_totals` — what the breakdown **covers** (§7.1k.3).

#### 2. The size's name is the business language

`variant_name` is the name **frozen at the moment of the sale** — the
same rule as the kitchen's ticket and the receipt (§7.1j.3). The
report never translates it; the **column header** is translated (the
"Size" label in en / km / zh) but the **value** is the business
language — because a size's name is part of the operational record.

#### 3. The honesty rule — the screen says what it covers

A breakdown that quietly leaves rows out is a lie the reader cannot see.
So the route publishes the **coverage**, and the screen prints it:

| The number | What it says |
|---|---|
| `quantity` | how many items the breakdown covers |
| `total_quantity` | every item sold — the denominator |
| `unvaried_quantity` / `unvaried_revenue` | the lines sold **without** a size — in the dish table and **not** in the breakdown |
| `row_count` / `cost_known_count` | how many rows, and how many have a **known** cost |

The screen's note reads: *"This breakdown covers **6** of the **11** items
sold. **5** items were sold without a size and are in the table above only."*
— so the reader can **add the two tables up** and the difference is
**named**, not mysterious.

#### 4. The cost rules do not move — they are the same rules

The breakdown reads the **same** cost rules as the dish table (§5.3):

- the **frozen** cost of the sale (the line's own choices are in it);
- the **recipe** (the 502 old lines);
- the **tenant's estimate** — the fallback;
- a dish sold under **two rules** says `mixed` — never one rule picked
  silently;
- an **unknown** cost stays **unknown** — a dash, never a zero, never a fake
  100% margin (the breakdown's `cost_known` and `cost_known_count`
  carry it).

#### 5. The browser holds **no** report rule

`frontend/src/components/reports/reportsConfig.js` — `buildVariantRows()`
— **renames the fields** and nothing else: the server sends the rows
**already rolled up** and **already sorted**, and the browser lays them
out. The cost the tenant has not valued is passed as **null** (a dash)
— the browser does not decide what "unknown" means.

#### 6. Proved — a durable check **and** a negative control

- the **durable check** (`scripts/pos_report_variant_check.py`) — **43/43
  green** — it **owns its fixtures** (its own tenant, outlet,
  dishes, sizes and orders), it works on a **copy** of the database,
  the user's rows are **fingerprinted before and after**, and the live
  database is proven **untouched**. It proves the rules: the rows are
  per **(dish, size)**, the quantity and the revenue are the lines' own,
  only **paid and non-cancelled** lines are counted, the two tables
  count the **same** items, an **unknown** cost stays unknown, a dish
  sold under **two rules** says `mixed`, and the size's name is the **frozen**
  one;
- the **negative control** (`scripts/pos_report_variant_control.py`) —
  phase 8 is **reverted in a scratch copy** of the backend (six blocks, each

### 7.1l The patch for phase 7 (the legacy `modifications` → the "Remarks" group) — **BUILT**

**Status: built, proved and live (Nov 11, 2026).**

Phase 7 was **optional** by its own wording — the dish keeps working either
way — and Kens authorized it on Nov 11 ("proceed implement phase 7 now").
It is now **done**: the legacy free-text list can become a real **"Remarks"
option group**, per dish, and it can be taken back again.

**Nothing in the live menu moved** — all 16 live dishes already carried an
**empty** legacy list, so the migration had nothing to fold. The code is
live; the data was never in play.

#### 1. Two modes, and the default is the safe one

The settled question was: does the list **move** into the group, or does the
group **mirror** it? The answer is **both**, explicitly:

| The mode | What it does | Who calls it |
|---|---|---|
| **Mirror** (the default) | the legacy list **stays on the dish**; the structured group **follows** it | the **write path** — every dish save |
| **Consume** | the legacy list **moves into** the group and the dish column is emptied | the **operator** only — `scripts/pos_phase7_migrate.py --mode=consume` |

Mirror is the default because the management screen's **chips editor** round
trips the legacy list — a consume-on-save would silently empty the tenant's
own field the first time they edited anything. **Consume** is the explicit
operator move, and only that empties the column.

#### 2. The group is the dish's OWN — never a shared outlet group

The rule that would have leaked the most: **one `Remarks` group per dish**.
A shared per-outlet "Remarks" group would let **dish A's notes appear on
dish B** — the customer would order the soup and get the steak's
instructions.

So the migrated group is:

- **one per dish** — a second dish never shares it;
- attached to **its dish only**;
- `variant_id = NULL` — a remark applies to **every size** of the dish;
- `min_select = 0` — **optional**, the dish is orderable without a remark;
- `max_select = the number of remarks` — the legacy list was
  **multi-select**, so many picks stay legal;
- **one zero-price option per legacy string** — the remark is a remark, it
  never moves the price.

#### 3. The ledger — the rollback can only remove what the migration created

`menu_modification_migrations` (the model `MenuModificationMigration`,
`backend/app/models/menu_modifications.py`) records **exactly** what the
migration made: the `group_id`, the `option_ids`, the `link_ids`, the
**original** legacy strings and the **folded** strings, whether the list was
**consumed**, the `max_select` it set, and the `status`.

The ledger is what makes the rollback **honest**: it deletes **only** the
option ids and the link ids the migration itself created — a choice the
tenant adds into the migrated group afterwards is **not** in `option_ids`, so
it **survives** the rollback, with its link to the dish.

Two rules the work found and fixed:

- **the ledger row stays after a rollback** (`status = 'rolled_back'`,
  `group_id = NULL`). Deleting the row made the **next dish save re-create
  the migration** — the rollback did not stick. `group_id` is nullable so a
  removed group can be recorded without a dangling reference.
- **if a tenant-created option remains in the migrated group, the group and
  the dish link remain** and only the migration-owned options go.

#### 4. The write path folds it — inside a savepoint, best-effort, never breaking the dish

`MenuService.create_menu_item` and `MenuService.update_menu_item` call
`fold_legacy_modifications(db, item)` **after** `db.flush()` and **before**
the caller's commit, so the dish's id exists.

The fold runs inside a **SQLAlchemy savepoint**:

- it **never commits** the caller's session;
- a **failure** rolls the savepoint back and leaves the dish exactly as it
  was — a fold must never break a menu save;
- an **empty** legacy list is **inert** — it never deletes an existing
  migrated group or its options;
- a dish **without** a legacy list is **untouched** — no group, no ledger
  row, and it takes the old path exactly;
- a dish whose tenant **already owns** a group named `Remarks` is a
  **hand-off** — the migration steps aside (no takeover, no duplication).

The **savepoint rule is the load-bearing one**: a best-effort helper that
commits the caller's session silently discards the caller's own write when
it fails. The check proves the caller's uncommitted write is **rolled back
with** the fold and survives a **failing** fold.

#### 5. The operator tool — dry-run by default, copy by default

`backend/scripts/pos_phase7_migrate.py`:

- `--dry-run` — report what would happen, change nothing;
- `--live` — write to the live database (the default is a **copy** in
  `/tmp`);
- `--outlet` / `--item` — target one outlet or one dish;
- `--mode=mirror` (default) / `--mode=consume`;
- `--rollback` — undo the migration, **only** what it created.

### 7.2 The order line's new shape

```jsonc
// the browser and the customer app post:
{
  "menu_item_id": 42,
  "quantity": 1,
  "variant_id": 7,              // "Large"
  "option_ids": [101, 104],     // "Bihun", "Extra egg"
  "notes": "less spicy"         // the remark
}
```

**and the server answers with the resolved line:**

```jsonc
{
  "id": 918,                       // the line's id
  "menu_item_id": 42,
  "menu_item_name": "Chicken Mee Soup",
  "quantity": 1,
  "unit_price": 13.00,             // the MENU's price + the size + the choices
  "modifications": [],
  "add_ons": [],
  "variant": { "id": 7, "name": "Large" },
  "options": [
    { "id": 101, "name": "Bihun", "group_name": "Noodle", "price_delta": 0.00, "kitchen_note": null },
    { "id": 104, "name": "Extra egg", "group_name": "Extra", "price_delta": 2.00, "kitchen_note": "NO CORIANDER" }
  ],
  "notes": "less spicy",
  "item_total": 13.00,
  "is_cancelled": false
}
```

**No price in the request. No price the guest can change.**

**The names come from the SNAPSHOT ** — what was sold, as it was at that moment
— and not from the live menu (a dish renamed tomorrow must not rewrite the
answer for an order sold today).

**The size's delta is not repeated in the answer ** — the money of the line is
`unit_price` (the dish's price + the size + the choices, frozen). The
choice's own delta **is** there (each choice carries its own money, and the
snapshot keeps it).

## 8. The open questions for Kens

1. **The sizes: a variant or a group?** The proposal makes the size a **variant**
   (its own price, its own recipe) and the noodle a **group**. The other way
   round is possible (both as groups) — but then the size's recipe has to live
   in the option's ingredient delta, which is clumsier. **The proposal's
   split is recommended**.
2. **A choice that changes the dish's recipe (the noodle) or just the ingredients
   (the topping)?** The proposal: the noodle swaps one ingredient (100 g mee for
   100 g bihun) — a delta on the same line. A bigger change ("the fish is
   fried instead of grilled") is a **separate dish**, not an option.
3. **How many choices may a guest make in total?** The proposal: per group
   (`max_select`), and no global cap — the tenant's menu is the tenant's
   business.
4. **Should a choice be allowed to be "removed" (no coriander)?** The proposal:
   yes — a negative ingredient delta and a CAPS kitchen note.
5. ~~**The customer app first or the counter first?**~~ — **answered: both**
   — the counter's picker is phase 5 (Nov 10) and the guest's is phase 6
   (Nov 11, §7.1h). The counter is where the money is at risk and the
   guest's picker is the face of the business — both were built.
6. ~~**The translations** (en / zh / km) — the variants and the options would want
   their own translation table. Is it in this project or a later one?~~ —
   **answered: in this project** — **built** **and live** (Nov 11, 2026
   — §7.1j) — and **no new table was needed**:
   `menu_content_translations.content_type` is free-form, so the three new
   content types (`menu_variant`, `menu_option_group`, `menu_option`)
   drop into the table that was already there — the dish's name and the
   category's name had made it already.

   **The live behaviour, stated plainly:** the **sizes**, the **groups**
   and the **choices** **are** translated — the guest's picker, the
   catalog and the price answer all answer in the guest's language, and
   the live branch's own labels are backfilled (ten rows — five labels
   × two locales — every one **`done`**). The **staff's** picker still
   reads the **business language** (by design — §7.1j.3) and the
   **snapshot** still freezes the **English** names (the write path is never
   localised). **Proved** by `scripts/pos_choice_translation_check.py`
   (**64/64**) with a **negative control**
   (`scripts/pos_choice_translation_control.py` — **16** fix-covering checks
   fail on a reverted copy).

   **The half that is NOT built** — the **tenant-facing management** of those
   translations: there is **no** route to edit one translation by hand and
   **no** screen that shows one — only the model's backfill
   (`POST /api/menu/translations/backfill`). That is **Q7** below.
7. **Does the tenant need to manage the translations by hand?** — the **read**
   half is **built and live** (§7.1j — the guest sees the translated
   sizes, groups and choices today), but the **manage** half is **not
   built** (§7.1j.8): there is **no** `PUT`/`PATCH` route for a
   single translation and **no** screen that shows one — the tenant
   cannot hand-correct a **wrong** word (the model's pick) and cannot see
   the **`fallback`** rows (the labels that were refused) without reading
   the database.

   **The proposal**: a **small panel on the choices modal** (the one the
   tenant already opens to edit the sizes and the groups — §7.1e) that
   shows each label's **source** and its **translation per locale**, with a
   **single field** to correct it — plus the **backfill** as the **"translate
   it for me"** button. It reuses the table that is already there and the
   outlet-scoped rule — so the **schema does not change** and the **cost
   is one route and one panel**. **The recommendation**: build it —
   the machine will get it wrong, and a tenant who cannot fix it will blame
   the app. **This one is Kens's call** — the read half already works
   and needs nothing.
