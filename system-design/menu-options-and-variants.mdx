# Menu Options & Variants — the dish, the choices, the ticket, the cost

**Document Version:** 1.1 (the proposal — Nov 9, 2026 · revised the same night after
Kens's two rules: *"make sure the new proposal won't impact the existing menu"* and
*"the proposal also has to be compatible in the current recipes management, because the
ingredients inside will use to calculate the actual cost"* ✓✓ — §4.1, §4.4, §5.2, §5.2a)
**Owner:** Ideazes POS AI
**Status:** **Proposed — nothing built.** The review below is against the live code
and the live database (Nov 9, 2026). Every "what today" statement is a fact about
the code as it stands, not a memory. The phases at the end are the proposal.

> **Why this document exists.** Kens: *"the current menu management is too simple —
> ingredients/toppings, size, modifiers, optional, remarks. If we change the menu
> structure it touches the kitchen printing and the recipe management, which involves
> costing. Example: a chicken mee soup — the customer chooses the noodle (mee,
> bihun, flat rice noodle), the size (big or small)."*
>
> So: the structure of the menu changes, and the three things that depend on it
> change with it — **the kitchen ticket**, **the recipe (the stock)** and **the
> costing (the margin)**. This document says what the menu looks like after, what
> each of those three becomes, and in which order it is safe to build.

---

## 1. The summary — one page

**Today the menu is a flat list of dishes.** A dish has a name, a price, a
category, a picture and a **flat list of free-text modification strings**
(`menu_items.modifications`). There are no sizes, no option groups, no prices on a
choice, no ingredient deltas and no remark on the order line.

**The gap, in the words of the example:**

| The guest wants | Today |
|---|---|
| Chicken mee soup | one menu item, one price |
| Big or small | **not possible** — no size concept anywhere |
| Mee, bihun or kway teow | **not possible** — no choice, no ingredient swap |
| Extra egg / no coriander | **not possible** — and the kitchen would never see it |
| "Less spicy, no celery" | the counter staff types it — **and the note is silently dropped** (see §3.4) |
| The right cost and the right margin | one flat cost per dish, whatever the guest chose |

**The proposal — three layers on top of the dish:**

```
menu_items                      the dish            (today)
  ├── menu_item_variants        the size            (NEW)  "Big", "Small"  → its own price, its own recipe
  └── menu_option_groups        the choice group    (NEW)  "Noodle", "Topping", "Spice"
        └── menu_options        one choice          (NEW)  "Mee", "Bihun", "Extra egg" → a price delta, an ingredient delta, a kitchen note
```

**and the sold line keeps a snapshot of the choice** (`order_item_options`, NEW) so
that the receipt, the kitchen ticket, the stock and the margin all speak about the
same thing.

**The four rules the proposal rests on:**

1. **The guest posts ids, never prices.** The server resolves the price from the
   menu. *(Today it does not — see §3.6, that is a live money hole.)*
2. **The choice changes three things at once, or it is not a choice:** the price,
   the ingredients (stock + cost) and the kitchen ticket. A group that does not
   move all three is a free-text remark, not an option.
3. **The sold line is a snapshot.** The history never changes when the menu does.
4. **The tenant can build it.** The sizes, the groups and the choices are not
   only readable — the tenant **creates** them ✓ (phase 4b ✓, §7.1e ✓), and the
   rules of the menu are enforced by the server ✓, never by the browser ✓.
5. **Nothing breaks.** The tables are additive, the existing items keep working,
   the old `modifications` list stays as the legacy remark group. **A dish with no
   variant and no group takes the old code path exactly** — and the **compatibility
   probe** (§4.4) proves it on every phase, against the live menu: the same price,
   the same cost, the same grams, the same ticket lines.

## 3. What breaks, or is already broken

### 3.1 The kitchen ticket — the browser and the PDF lose the choices

`frontend/src/pages/Kitchen.jsx` has **two** ticket builders and they disagree:

| Builder | Used for | The choices |
|---|---|---|
| `generateKitchenTicketHTML()` (line 360) | the browser print and the PDF | **dropped** — it prints only `menu_item_name` and `x{quantity}` |
| `generateKitchenTicket()` (the ESC/POS, line 425) | the network printer | printed — `> ${mod}` per modification |

So on the browser printer the kitchen sees "Chicken Mee Soup x1" and nothing else —
not the noodle, not the size, not "no coriander". This is the single most
dangerous gap in the menu today, and it is **independent** of the new structure: it
is worth fixing on its own, this week, even if the whole options project is
deferred.

### 3.2 The recipe — one per dish, so a size cannot cost differently

`backend/app/models/inventory.py`:

```python
class Recipe:            menu_item_id, outlet_id          # ONE recipe per dish
class RecipeIngredient:  recipe_id, ingredient_id, quantity, unit_override
```

`backend/app/routes/inventory.py` → `GET /api/inventory/cost/{menu_item_id}`
(line 540) walks the recipe and multiplies `ri.quantity * ing.unit_cost`. One
dish, one cost.

Consequence: "Big chicken mee" and "Small chicken mee" would share **one** cost
and **one** stock deduction — the margin of the big one would be wrong, and the
noodle choice would not change the stock at all.

### 3.3 The stock — the deduction follows the dish, not the choice

`backend/app/routes/order.py` → `auto_decrement_stock()` (line ~92) deducts the
recipe's ingredients when the order is marked **ready**; the add-to-cart stock
check (line ~50) walks the same recipe. With a choice, the deduction has to be
`the variant's recipe + the chosen options' ingredient deltas` — otherwise a bowl
of mee and a bowl of bihun take the same noodles out of the shelf.

### 3.4 The remark is silently dropped

`frontend/src/pages/StaffOrder.jsx:310` sends `notes` **per cart line**.
`OrderItemCreate` (`backend/app/routes/order.py:185`) has **no `notes` field** and
`order_items` has **no `notes` column** — so the remark is accepted by the
browser, sent to the server and dropped by the schema. The only `notes` that
survives is the **order-level** one (`OrderCreate.notes`, line 206) — one note for
the whole order, not per line.

So the "less spicy, no celery" of a hawker is typed by the staff and never
reaches the kitchen nor the receipt.

### 3.5 The margin is a flat number per dish

`backend/app/routes/reports.py` (the menu mix, lines 89–186) joins the cost of the
sold lines to the menu and reports the margin per dish. The cost is chosen **per
tenant**, not per dish (`_menu_item_cost`, line 395): the tenant has the **Inventory**
feature → the **recipe** (the real cost ✓) — otherwise `MenuItem.estimated_cost` (the
hand-written estimate ✓) — otherwise **nothing is known** (`cost_known: false` ✓, *a
dash, not a lie* ✓).

With choices, the cost of a line is `the base + the options` — so the margin has to be
computed **per sold line** ✓, under the same rule (the recipe's cost when the plan is
on ✓, the estimate when it is not ✓, a dash when neither is known ✓) — and the
**frozen** cost of the line when the line has one ✓ (§5.2a ✓).

### 3.6 The add-on's price is trusted from the client — a live money hole

`backend/app/services/order_service.py` (line ~109):

```python
provided_price = item_data.get("unit_price") if trust_client_money else None
item_unit_price = provided_price if provided_price is not None else menu_item.price
add_ons_price = sum(a.get("price", 0) for a in add_ons)      # <- ALWAYS from the client
item_total = (item_unit_price + add_ons_price) * quantity
```

The **unit price** is protected (a guest's price is the menu's price ✓), but the
**add-on's price is not** — the guard `trust_client_money` covers only the unit
price. A guest who posts `add_ons: [{"name": "x", "price": -5.0}]` lowers their
own total.

**Verified** with `scripts/addon_price_probe.py` (against a copy of the database,
Nov 9): an order for a 3.00 dish, posted by a "guest" (`trust_client_money =
False`) with a `-5.00` add-on, came out at

```
the item total     : -2.0
the order subtotal : -2.0
the order total    : -2.16
```

**A guest can make their order negative.** This is a **priority 1** fix and it does
not wait for the options project: the price of an add-on must come from the menu,
never from the request. The patch is in §7.1.

## 4. The proposal — the structure

### 4.1 The seven new tables (all additive)

```python
# ── the size ────────────────────────────────────────────────────────────────
class MenuItemVariant(Base):
    """A size (or another whole variation) of a dish.
    Big / Small / Half / Regular / the lunch set."""
    __tablename__ = "menu_item_variants"
    id, outlet_id, menu_item_id
    name = Column(String(100), nullable=False)        # "Big", "Small"
    price = Column(Float, nullable=True)              # null -> the dish's price
    price_delta = Column(Float, default=0.0)          # or a delta on the dish's price
    cost_multiplier = Column(Float, default=1.0)      # or a multiplier on the dish's recipe
    # Its OWN recipe is NOT a row of the `recipes` table - it lives in
    # `menu_item_variant_recipes` (below), keyed by this variant's id.
    sku = Column(String(50), nullable=True)
    is_default = Column(Boolean, default=False)
    is_available = Column(Boolean, default=True)
    sort_order = Column(Integer, default=0)
    created_at, updated_at

# ── the group of choices ───────────────────────────────────────────────────
class MenuOptionGroup(Base):
    """A named group of choices: Size, Noodle, Topping, Spice, Side, Add-on."""
    __tablename__ = "menu_option_groups"
    id, outlet_id
    name = Column(String(100), nullable=False)        # "Noodle"
    min_select = Column(Integer, default=0)           # 0 = optional, 1 = required
    max_select = Column(Integer, default=1)           # 1 = single choice, >1 = multiple
    sort_order = Column(Integer, default=0)
    is_active = Column(Boolean, default=True)
    print_group_name = Column(Boolean, default=False) # does the kitchen read the group's name?
    station = Column(String(50), nullable=True)        # "Soup", "Grill", "Fry" (the split is deferred)
    created_at, updated_at

# ── the link between the dish and the group ───────────────────────────────
class MenuItemOptionGroup(Base):
    __tablename__ = "menu_item_option_groups"
    id, menu_item_id, group_id
    variant_id = Column(Integer, nullable=True)        # null -> the group applies to every variant
    sort_order = Column(Integer, default=0)
    required = Column(Boolean, default=False)          # overrides the group's min_select
    created_at

# ── one choice ────────────────────────────────────────────────────────────
class MenuOption(Base):
    """One choice inside a group."""
    __tablename__ = "menu_options"
    id, outlet_id, group_id
    name = Column(String(100), nullable=False)        # "Mee", "Bihun", "Extra egg"
    price_delta = Column(Float, default=0.0)          # the money
    ingredient_id = Column(Integer, nullable=True)     # the stock (nullable = no stock effect)
    ingredient_qty = Column(DECIMAL(12, 4), default=0.0)   # may be negative ("No egg" = -1)
    kitchen_note = Column(String(100), nullable=True)  # "NO CORIANDER" - printed in CAPS
    sku = Column(String(50), nullable=True)
    is_default = Column(Boolean, default=False)
    is_available = Column(Boolean, default=True)
    sort_order = Column(Integer, default=0)
    created_at, updated_at

# ── the snapshot of what was sold ──────────────────────────────────────────
class OrderItemOption(Base):
    """What was chosen, frozen at the moment of the sale."""
    __tablename__ = "order_item_options"
    id, order_item_id
    group_name = Column(String(100))                  # the name at the time
    option_name = Column(String(100))                 # the name at the time
    variant_name = Column(String(100), nullable=True) # "Big"
    price_delta = Column(Float, default=0.0)          # the money at the time
    ingredient_delta = Column(JSON, default=list)     # [{name, qty}] - the stock at the time
    kitchen_note = Column(String(100), nullable=True) # what the kitchen reads
    print_group_name = Column(Boolean, default=False) # the flag, frozen at the sale
    option_id = Column(Integer, nullable=True)        # null if the option was deleted since
    variant_id = Column(Integer, nullable=True)
    created_at
```

The **relationships** that were built with them ✓: `MenuItem.variants` ✓ and
`MenuItem.option_group_links` ✓, `MenuItemVariant.links` ✓ and `.recipe` ✓
(`uselist=False` ✓ — a variant has **one** recipe ✓), `MenuOptionGroup.options` ✓
and `.links` ✓, `MenuItemOptionGroup.group` / `.variant` / `.menu_item` ✓,
`MenuOption.group` / `.ingredient` ✓, `OrderItem.order_item` ✓ and
`OrderItem.option_snapshot` ✓.

# ── the variant's recipe — its OWN tables ─────────────────────────────────
class MenuItemVariantRecipe(Base):
    """The recipe of a variant - the exact grams of the Large.

    It is NOT a row of the `recipes` table. That table holds **one recipe per
    dish** and thirteen places take it by `menu_item_id` (the stock check, the
    deduction, the cost, the menu's stock status, the reports' cost, the AI's
    predictions...). A second row for the same dish would be picked up by
    `.first()` in the wrong place - the wrong cost and the wrong stock, with
    no error to show for it.

    So the dish's recipe stays exactly where it is, untouched, and the
    variant's recipe lives here. The lookup is by `variant_id`, so it can
    never be mistaken for the dish's.
    """
    __tablename__ = "menu_item_variant_recipes"
    id, outlet_id
    variant_id = Column(Integer, ForeignKey("menu_item_variants.id"), nullable=False)
    created_at, updated_at

class MenuItemVariantRecipeIngredient(Base):
    __tablename__ = "menu_item_variant_recipe_ingredients"
    id, recipe_id, ingredient_id
    quantity = Column(DECIMAL(12, 4), nullable=False)   # the same shape as the dish's
    unit_override = Column(String(50), nullable=True)    # the same shape as the dish's

Plus **three columns** on the order line (`order_items`) ✓ — all nullable ✓, all
additive ✓:

| The column | What it holds | Why |
|---|---|---|
| `notes` (Text) | the per-line remark ✓ | the field the browser already sends and the server already drops (§3.4 ✓) |
| `variant_id` (Integer) | the size of the line ("Big") ✓ | a line may have a **size and no choice at all** ✓ — the snapshot rows hold the OPTIONS ✓, so the size needs its own place ✓ |
| `variant_name` (String(100)) | the name of the size, frozen ✓ | the menu may be renamed tomorrow ✓ — the ticket of yesterday must still say "Big" ✓ |

> **This is a change to the first draft** ✓: the draft said **one** column ✓. The
> two size columns were added in phase 2 ✓, when the write path showed that a
> line with a size and no choice would lose its size ✓. **Nothing was rewritten**
> ✓ — the three columns are nullable ✓ and the 502 old lines have none of them ✓.

**Seven tables, not five** — and every one of them is additive ✓ (§4.4).

### 4.2 The rules of a group

| Rule | Where it lives | What it means |
|---|---|---|
| `min_select` | the group | 0 = optional, 1 = required (the guest must choose) |
| `max_select` | the group | 1 = one choice, n = up to n choices |
| `price_delta` | the option | the money it adds (may be negative) |
| `ingredient_id` + `ingredient_qty` | the option | the stock it takes (may be negative → "No egg") |
| `kitchen_note` | the option | what the kitchen reads, in CAPS |
| `variant_id` on the link | the link | the group's choices can differ per variant ("Big" offers a bigger topping set) |

### 4.3 The example, end to end — chicken mee soup

**The dish** (one menu item, as today):

| Field | Value |
|---|---|
| name | Chicken Mee Soup |
| price | 9.00 (the base) |
| recipe | 200 g chicken, 100 g mee, 1 piece chicken, soup base |

**The variants** (the size):

| Variant | price_delta | recipe | The cost |
|---|---|---|---|
| Small | -1.00 | the dish's recipe × 0.7 | ~2.10 |
| Regular | 0.00 | the dish's recipe | ~3.00 |
| Large | +2.00 | the dish's recipe × 1.4 | ~4.20 |

**The groups**:

| Group | min | max | Options (price / ingredient / kitchen note) |
|---|---|---|---|
| Noodle | 1 | 1 | Mee (0 / mee 100 g) · Bihun (0 / bihun 100 g) · Kway teow (0 / kway teow 100 g) · Flat rice noodle (+1.00 / flat rice 100 g) |
| Topping | 0 | 3 | Extra egg (+2.00 / egg +1 / EXTRA EGG) · Extra chicken (+4.00 / chicken +80 g / EXTRA CHICKEN) · No coriander (0 / coriander -1 g / NO CORIANDER) · Extra sprouts (+0.50 / sprouts +50 g) |
| Spice | 0 | 1 | Mild (0 / -) · Hot (+0.50 / chilli +2 g / HOT) · Extra hot (+0.50 / chilli +4 g / EXTRA HOT) |

**What the guest orders:** "Large Chicken Mee Soup, bihun, extra egg, no coriander, less spicy".

**What the server computes:**

```
the base            9.00
the size           +2.00
the noodle          0.00   (a swap, not a cost)
the topping        +2.00   (the extra egg)
                     ------
the unit price     13.00
```

**What the kitchen reads (the ticket):**

```
*** KITCHEN ***
      12
--------------------------------
[TAKEAWAY] 21:14
Guest: Ah Seng
--------------------------------

1x CHICKEN MEE SOUP
   > LARGE
   > BIHUN
   > EXTRA EGG
   > NO CORIANDER
   > LESS SPICY
--------------------------------
```

**What the stock takes:** `chicken +140 g (the large recipe), bihun 100 g, egg +1,
coriander -1 g` — the dish's recipe is replaced by the variant's, and the options
add their deltas ✓.

**What the margin is:** `13.00 - (4.20 + 0.60 + 0.40) = 7.80` — a real number per
line, not the dish's flat 3.00 ✓.

## 4.4 The compatibility guarantee — the existing menu does not move

**Kens's rule:** *"make sure the new proposal won't impact the existing menu."*

The rule of the whole proposal: **a dish that has no variant and no group takes the
old code path exactly.** The new tables are additive, every new field of the API is
optional, and **nothing that exists today is rewritten** — not a row of the menu, not
a row of the recipes, not an order of yesterday.

| The thing | Today | After the proposal | Why it cannot move |
|---|---|---|---|
| the dish's price | `menu_items.price` | the same ✓ | the resolver adds nothing when there is no variant and no option ✓ |
| the dish's recipe | `recipes` + `recipe_ingredients` — **one row per dish** ✓ | **the same rows, untouched** ✓ | the variant's recipe lives in its own tables (§4.1) ✓ |
| the cost of the dish | `Σ quantity × unit_cost` ✓ | the same ✓ | a line with no choice costs exactly what the dish costs ✓ |
| the stock | the dish's recipe ✓ | the same ✓ | the snapshot's deltas are added **on top of** the base, never instead of it ✓ |
| the tile's stock status | the dish's recipe ✓ | the same ✓ | the menu route still asks for the dish's recipe ✓ |
| `menu_items.modifications` | a free-text list ✓ | the same, printed as it is ✓ | the write path still accepts it ✓ |
| the order lines (502 today ✓) | `order_items.modifications` ✓ | untouched ✓ | the snapshot rows are written only for the new lines ✓ |
| the order line's API | `menu_item_id, quantity, unit_price, modifications, add_ons` ✓ | the same **plus** the optional `variant_id`, `option_ids`, `notes` ✓ | an old client posts the old body and gets the old answer ✓ |
| the customer app | the modal hides the options ✓ | the same until phase 6 ✓ | the PWA posts the old body ✓ |
| the reports' cost | the dish's recipe, live ✓ | the same for the old lines ✓ | a line with no frozen cost falls back to the dish's recipe ✓ |
| the ticket | the dish's name ✓ | the same ✓ | a line with no choice is the line of today ✓ |
| the promotions and the voucher | the subtotal ✓ | the same ✓ | a dish with no choice has the same subtotal ✓ |
| the tax | the subtotal ✓ | the same ✓ | unchanged ✓ |

**The rule in code — three "if there is nothing, do exactly what you did" branches:**

```python
# the price: no variant, no option -> the dish's price, unchanged
unit_price = menu_item.price
if variant:  unit_price += variant.price_delta
unit_price += sum(option.price_delta for option in chosen_options)

# the cost: no variant -> the dish's recipe, unchanged
cost = dish_recipe_cost()
if variant and variant.has_own_recipe: cost = variant_recipe_cost()
elif variant:                           cost = dish_recipe_cost() * variant.cost_multiplier
cost += sum(option.ingredient_qty * ingredient.unit_cost for option in chosen_options)

# the stock: no choice -> the dish's recipe, unchanged
ingredients = dish_recipe_ingredients()
if variant and variant.has_own_recipe: ingredients = variant_recipe_ingredients()
ingredients += the option's deltas
```

**The proof — the compatibility probe.** It is **the acceptance gate of every phase**,
not a test at the end. For every dish of the live menu (16 today ✓) the **old path**
and the **new path** are run side by side, and the answers must be **identical**:

- the price of the line ✓,
- the cost of the line ✓,
- the grams the stock would take ✓,
- the lines of the kitchen ticket ✓.

**A dish with no variant and no group may not move by one cent, one gram or one
line.** The probe is the answer to "will this impact the existing menu" — it is not a
promise, it is a number that has to stay the same.

**And the tenant's data:** the probe runs against a **copy** of the database (the
pattern the other probes use ✓), so the live menu is never the thing being tested ✓.

## 5. The three dependents — what each one becomes

### 5.1 The kitchen printing

**One formatter, three sinks.** Today there are two builders that disagree (§3.1).
The proposal is a single pure function that takes the order and returns the lines:

```
printLines(order) -> [
  { name: "Chicken Mee Soup", qty: 1, variant: "Large",
    options: ["BIHUN", "EXTRA EGG", "NO CORIANDER"], note: "less spicy" }
]
```

and then:
- the **browser/PDF** ticket renders it as HTML (the same shape it renders today, plus the lines) ✓;
- the **ESC/POS** ticket renders it as `> ` lines ✓ (the shape it already has) ✓;
- the **customer app's** ticket (if it ever prints) renders the same lines ✓.

**The rules:**
- the choices are printed in CAPS, one per line, under the item ✓;
- the group name is **not** printed when the option name says it all ("Bihun" ✓) but **is** printed when it is ambiguous ("Noodle: Bihun") ✓ — a per-group flag `print_group_name` ✓ (**built** ✓ — and **frozen** into the snapshot ✓, so the kitchen reads the ticket as it was written ✓);
- the **remark** prints under the item in italics ✓ ("less spicy") ✓;
- a "no" choice prints in CAPS with a NO ✓ ("NO CORIANDER") ✓ — the kitchen must never read "No coriander" as "add coriander" ✓;
- **the item's name is never rewritten** ("Chicken Mee Soup (Large, Bihun)" ✗✗) — the name stays searchable and the choices stay on their own lines ✓.

> **Two decisions the build made** ✓:
> - **the kitchen note wins over the name** ✓ — when a choice carries a note
>   ("NO CORIANDER" ✓), the note is what the kitchen reads ✓; the name is what
>   the guest picked ✓ and it is printed when there is no note ✓;
> - **the remark is a row of its own** ✓ — marked as a remark ✓ (the HTML prints
>   it in italics ✓, the ESC/POS prints it in italic ✓) so the kitchen never
>   reads a remark as a choice ✓.

**The station split (the deferred "stations" feature).** When the stations arrive,

### 5.2 The recipe and the stock — inside the recipe management that exists

**Kens's second rule:** *"the proposal also has to be compatible in the current
recipes management, because the ingredients inside will use to calculate the actual
cost."*

**The recipe management today (Nov 9, 2026 — the live code):**

| The piece | Where | What it does |
|---|---|---|
| the two tables | `backend/app/models/inventory.py` | `recipes` (one row per dish — `menu_item_id` NOT NULL) and `recipe_ingredients` (`recipe_id, ingredient_id, quantity, unit_override`) |
| the three routes | `backend/app/routes/inventory.py` | `GET` / `PUT` / `DELETE /api/inventory/recipes/{menu_item_id}` — the PUT **replaces** the ingredient rows and sets `menu_item.has_recipe = True` ✓ |
| the cost | `backend/app/routes/inventory.py` → `calculate_item_cost` (line 542) | `Σ ri.quantity × ing.unit_cost` — the same arithmetic the reports use (`reports.py:395` `_menu_item_cost`) ✓ |
| the stock | `backend/app/routes/order.py` → `auto_decrement_stock` (line 133) | the dish's recipe, at the moment the order is marked **ready** ✓, with a `StockMovement` row per ingredient ✓ |
| the stock check | `backend/app/routes/order.py` (line 59) | the dish's recipe, at the moment the item is added to the cart ✓ |
| the editor | `frontend/src/pages/Inventory/RecipeBuilder.jsx` | **one** recipe per dish ✓ — the dish's list on the left, the ingredients on the right ✓ |

**The live shape (Nov 9, 2026):** 16 dishes ✓ · 11 with a recipe ✓ · **never more than
one recipe row for a dish** ✓ · 502 order lines ✓ · 38 ingredients, **all** with a unit
cost ✓.

**The rule: the dish's recipe does not move.** The proposal adds the choices to the
**side** of it — it never rewrites it, never re-keys it and never puts a second row
for the same dish into `recipes`.

**The thirteen places that take the recipe** — every one of them keeps taking the
**dish's** recipe, and the variant's recipe is a **separate** read:

| The place | Today | With a choice |
|---|---|---|
| the stock check (add to cart) `order.py:59` | the dish's recipe | the base + the **options' ingredients** are checked too ✓ (the egg may be out of stock ✓) |
| the deduction (when ready) `order.py:133` | the dish's recipe | the **frozen snapshot** ✓ (§5.2a) |
| the cost `inventory.py:542` | the dish's recipe | the base stays the base ✓; the variant's cost is a **new** read with the same arithmetic ✓ |
| the recipe routes `inventory.py:318/366/402` | one recipe per dish | **unchanged** ✓ — the variant's recipe has its own routes ✓ |
| the menu's stock status `menu.py:319` | the dish's recipe | the base ✓ (the variant's status is a detail of the tile, optional ✓) |
| the reports' cost `reports.py:404` | the dish's recipe | the base for the old lines ✓; the frozen cost for the new ones ✓ |
| the AI's predictions (3 places) | the dish's recipe | the base ✓ — a prediction is per dish ✓ |
| the anomaly detector | the dish's recipe | the base ✓ |

**The cost of a sold line — the same arithmetic, one layer more:**

```
the cost of a sold line =
      (the variant's own recipe        OR  the dish's recipe × the variant's cost_multiplier)
    + Σ (the chosen options' ingredient_qty × the ingredient's unit_cost)
```

**The rules:**
- the **dish's recipe stays the base** ✓ — an item without a variant never changes ✓;
- a **variant** may have its own recipe (the exact grams for the Large ✓) **or** a multiplier (the Large = 1.4 × the base ✓) — the multiplier is the cheap way to start ✓ — **its recipe lives in `menu_item_variant_recipes`**, never in `recipes` ✓ (§4.1 ✓);
- an **option** carries at most one ingredient ✓ (the egg, the extra chicken ✓) — a choice that needs several ingredients becomes its own **dish with a recipe** (an "Extra Chicken" add-on item ✓ — the mechanism that exists today ✓); the option's ingredient **touches no recipe table** ✓;
- a **negative** ingredient quantity is the way to say "no" ✓ ("No egg" = -1 egg ✓) — the stock goes up by one egg ✓, which is right ✓ (the stock is clamped at 0 today ✓ — `max(0, old - qty)` ✓ — a negative delta still adds ✓);
- the **deduction** reads the snapshot (`order_item_options`) ✓ — not the live menu ✓ — so a menu change mid-service never moves the stock of an order already sold ✓;
- the deduction still happens **when the order is marked ready** ✓ (today's rule ✓) — the choice does not change the timing ✓;
- the **cost is frozen into the line** at the moment of the sale ✓ (the same way the price is frozen ✓) — and **a line with no frozen cost falls back to the dish's recipe** ✓ (that is the 502 old lines ✓).

### 5.2a The frozen cost — what the reports read

The reports read the **line's** cost when there is one, and the **dish's** recipe when
there is not:

```python
# the cost of a sold line, in the reports
cost = line.frozen_cost                     # the new lines - frozen at the sale
if cost is None:                            # the old lines - the dish's recipe, as today
    cost = dish_recipe_cost(line.menu_item_id)
```

**Why the frozen cost and not a live read:** the ingredient's price moves (the flour
costs more this month ✓), and the margin of an order sold in October must not be
rewritten by October's price ✓ — the same rule the price follows ✓.

**The rule "an unknown cost is a dash, not a lie"** ✓ (the reports' existing rule ✓)
applies to the option's cost too ✓: an option whose ingredient has no `unit_cost` →
the line's cost is **unknown** → a **dash** ✓, never a zero ✓. (All 38 ingredients
have a unit cost today ✓ — but a new ingredient may not have one ✓.)

**The recipe editor** (`frontend/src/pages/Inventory/RecipeBuilder.jsx` — today it
edits **one** recipe per dish, `GET/PUT /api/inventory/recipes/{menu_item_id}` ✓):
- the **dish's recipe editor does not change** ✓ — the same screen, the same buttons, the same rows ✓;
- a **variant's recipe** is edited by the **same component** with a variant's id ✓ (the variant's recipe lives in its own tables ✓);
- the **option's ingredient** is a column on the option's list ✓ (the option's ingredient and its quantity ✓) — and the ingredient is picked from the **existing** ingredient list ✓ (no new ingredient type ✓);
- the editor shows the **cost of the dish as it is today** ✓ and the **cost of each variant** ✓ (the same arithmetic ✓) — so the tenant sees the margin before the guest does ✓.

### 5.3 The costing and the margin

- the **dish's** `estimated_cost` stays as the fallback when there is no recipe ✓ (today's rule: no recipe → the hand-written estimate ✓);
- the **line's** cost is computed at the moment of the sale and **frozen into the snapshot** ✓ (the same way the price is frozen ✓) — the reports read the frozen cost, not today's menu ✓;
- the **reports** (the menu mix, the top items ✓) keep the dish-level rollup ✓ and gain a **variant breakdown** ✓ (how many Large, how many Regular ✓) — optional, and the cheapest part of the project ✓;
- the rule *"an unknown cost is a dash, not 100%"* ✓ (the reports' existing rule ✓) applies to the option's cost too ✓: an option with an ingredient but no `unit_cost` → a dash ✓, never a zero ✓.

  on this menu ✓).

## 8. The open questions for Kens

1. **The sizes: a variant or a group?** The proposal makes the size a **variant**
   (its own price, its own recipe ✓) and the noodle a **group** ✓. The other way
   round is possible (both as groups ✓) — but then the size's recipe has to live
   in the option's ingredient delta ✓, which is clumsier ✓. **The proposal's
   split is recommended** ✓.
2. **A choice that changes the dish's recipe (the noodle) or just the ingredients
   (the topping)?** The proposal: the noodle swaps one ingredient (100 g mee for
   100 g bihun ✓) — a delta on the same line ✓. A bigger change ("the fish is
   fried instead of grilled") is a **separate dish** ✓, not an option ✓.
3. **How many choices may a guest make in total?** The proposal: per group ✓
   (`max_select`) ✓, and no global cap ✓ — the tenant's menu is the tenant's
   business ✓.
4. **Should a choice be allowed to be "removed" (no coriander)?** The proposal:
   yes ✓ — a negative ingredient delta ✓ and a CAPS kitchen note ✓.
5. **The customer app first or the counter first?** The proposal's order puts the
   counter first ✓ (5 before 6 ✓) — the counter is where the money is at risk
   ✓. But the guest's picker (6) is the face of the business ✓ — Kens's call ✓.
6. **The translations** (en / zh / km ✓) — the variants and the options would want
   their own translation table ✓. Is it in this project or a later one ✓?
