## 1. The short answer ✓

**One codebase ✓✓, one deployment ✓✓, one API ✓✓ — and every tenant gets its own branded
delivery PWA ✓✓ ✓.**

**The principle ✓✓ that decides every scope question ✓:**
> **The tenant owns its delivery operation ✓✓. We own the commerce ✓✓.**
> The tenant sets its own charges ✓✓, allocates its own drivers ✓✓, manages them its own way
> ✓✓ — **we do not care how ✓ ✗ ✓** ✓ ✓.

**The commercial line ✓✓** — Grab charges the customer and the merchant a commission ✓✓ and
carries the courier network ✓✓ → **our pitch is the same job at a fraction of the cost ✓✓:
no commission ✓✓, no driver marketplace ✓✓, no GPS ✓✓** ✓ ✓ — and the tenant's own drivers
✓✓ are a **feature for them ✓✓** (they know their customers ✓✓) ✓ ✓✓✓ ✓ ✓.

**And the plan gating ✓✓ (the question ✓) — mapped onto our REAL plans ✓✓:**

| Plan ✓ | Price ✓ | The delivery features ✓ |
|---|---|---|
| **Starter ✓** ✓ | RM99/mo ✓ ✓ | **Delivery ✓** — the order type ✓, the storefront ✓, the flat fee ✓, the driver assignment ✓ ✓ |
| **Basic ✓** ✓ | RM199/mo ✓ ✓ | **Delivery ✓** (+ the outlets ✓ ✓) ✓ ✓ |
| **Pro ✓** ✓ | RM399/mo ✓ ✓ | **Delivery ✓** + **Delivery Zones ✓** (the postcode pricing ✓ ✓) ✓ ✓ |
| **Enterprise ✓** ✓ | RM799/mo ✓ ✓ | **Delivery ✓** + **Delivery Zones ✓** + **Delivery Scheduling ✓** + **Delivery Analytics ✓** ✓ ✓ |

**The split ✓✓ — what is in the core ✓ ("Delivery" ✓ ✓) ✓ ✓**
- the delivery **order type ✓** ✓ — just another order type ✓ ✓ (the address ✓, the fee ✓,
  the driver ✓ ✓) ✓ ✓;
- the **white-label storefront ✓** ✓ — the branding fields **already exist ✓✓**
  (`restaurant_name` ✓, `restaurant_logo` ✓, `brand_color` ✓ ✓) → it costs us almost nothing
  ✓ ✓ → **charging for it would fight the adoption ✓ ✗ ✓ ✓** ✓ ✓;
- the tenant's **own fee settings ✓** ✓ — the whole value is **"no commission ✓✓"** ✓ ✓ →
  charging for the fee settings would contradict the pitch ✓ ✗ ✓ ✓ ✓;
- the **driver assignment ✓** ✓ — it is two fields ✓ ✓ ✓✓ ✓ ✓.

**What is paid ✓✓ (the ops depth ✓ ✓)**
- **Delivery Zones ✓** — the postcode pricing ✓ ✓ → **Pro ✓✓** ✓ ✓;
- **Delivery Scheduling ✓** — the promised windows ✓ ✓ → **Enterprise ✓✓** ✓ ✓;
- **Delivery Analytics ✓** — the delivery revenue ✓, the fee per order ✓ ✓ → **Enterprise ✓✓** ✓ ✓.

**The adoption argument ✓✓ — the decisive one ✓** — a tenant that switches to us **for the
delivery ✓** but has to pay for it ✓ ✗ loses the switch ✓ ✓ → **the basics must be free ✓✓**
✓ ✓ → **the paid tier is the sophistication ✓✓** (the zones ✓, the scheduling ✓, the
analytics ✓ ✓) ✓ ✓✓✓ ✓ ✓.

**And the Starter argument ✓✓** — the delivery costs us **almost nothing on Starter ✓✓** ✓ ✓
(one JSON column ✓ ✓, the storefront reads the existing menu ✓ ✓) → it is a **customer-acquisition
feature ✓✓** ✓ ✓: the tenant tries the delivery free ✓ ✓, it works ✓ ✓, and the zones ✓, the
scheduling ✓ and the analytics ✓ are the **upgrade path ✓✓** ✓ ✓ — **the delivery is the
Starter's hook ✓✓** ✓ ✓✓✓ ✓ ✓.

## 2. What we build ✓ and what we do NOT ✓

| We build ✓✓ | We do NOT build ✓ ✗ |
|---|---|
| the **white-label storefront PWA ✓** (the tenant's branding ✓, the menu ✓, the cart ✓, the checkout ✓, the order status ✓ ✓) ✓ ✓ | a **marketplace ✓ ✗** — the customers are the tenant's own ✓ ✓ ✓ |
| the **delivery order type ✓** in the core POS ✓ ✓ | a **driver app ✓ ✗** — the tenant's own drivers ✓ ✓ ✓ |
| the **fee settings ✓** (the flat fee ✓, the minimum ✓, the free-delivery threshold ✓, the zones ✓ ✓) ✓ ✓ | **GPS / live tracking ✓ ✗** — that is Grab's cost centre ✓ ✓ ✓ |
| the **driver assignment ✓** (a name + a phone ✓ ✓ on the order ✓ ✓) ✓ ✓ | a **courier matching engine ✓ ✗** ✓ ✓ |
| the **status flow ✓** (out for delivery ✓ → delivered ✓ ✓) ✓ ✓ | **commission handling ✓ ✗** — we take no commission ✓ ✓ ✓ |
| the **prepay path ✓** (the DuitNow QR ✓ ✓ / the online payment ✓ ✓) ✓ ✓ | a **delivery schedule/dispatch optimiser ✓ ✗** ✓ ✓ |
| **cash on delivery ✓** (the driver collects ✓ ✓ — the tenant's choice ✓ ✓) ✓ ✓ | **anything that makes the tenant manage OUR way ✓ ✗ ✓** ✓ ✓ |

**The principle restated ✓** — *the tenant manages its drivers by whatever means it likes ✓✓*
✓ ✓: WhatsApp ✓, a spreadsheet ✓, its own app ✓, a group chat ✓ — **we only need to carry the
driver's name and phone on the order ✓✓** ✓ ✓ → the customer can call them ✓ ✓ ✓✓ ✓ ✓.

**The delivery settings ✓ — new ✓✓** (one JSON column ✓ ✓, the house pattern ✓ ✓):

  "enabled": true,

## 4. The order flow ✓

**The statuses ✓✓** — the shared machine ✓ ✓ **plus ONE delivery-specific step ✓ ✓**:

```
pending → confirmed → preparing → ready → out_for_delivery → delivered
                                └── the shared machine ✓ ──┘  └── the delivery only ✓ ✓
```

- **the last step's wording ✓** — "Delivered ✓" for the delivery ✓ ✓ (the translation trick ✓
  ✓ — the same as "Collected" ✓ ✓) ✓ ✓;
- → **one new status value ✓✓** (`out_for_delivery` ✓ ✓) — and it applies **only to the
  delivery type ✓ ✓** ✓ ✓ — the dine-in ✓ and the takeaway ✓ keep their shared machine ✓ ✓
  untouched ✓ ✓ ✓✓;
- → **the cancellation rule ✓** — pending / confirmed / preparing ✓ ✓ (unchanged ✓ ✓) ✓ ✓.

**The driver's place in the flow ✓✓**
1. the order is placed ✓ ✓ (prepaid ✓ or cash on delivery ✓ ✓);
2. the kitchen prepares ✓ ✓ (the same kitchen ✓ ✓);
3. **the staff assigns the driver ✓ ✓** (a name ✓ + a phone ✓ ✓ — from the tenant's own list
   ✓ ✓) ✓ ✓ → **the assignment is on the order ✓ ✓**;
4. **the staff taps "out for delivery" ✓ ✓** when the driver takes it ✓ ✓;
5. **the customer sees the driver's name and phone ✓✓** in their PWA ✓ ✓ → **a WhatsApp call ✓
   ✓ ✓** — the whole "tracking" for the price of a phone number ✓ ✓✓ ✓ ✓;
6. **"delivered" ✓ ✓** → the cash is collected if needed ✓ ✓ → the payment is recorded ✓ ✓.

**The money ✓✓**
- **prepaid ✓✓** — the DuitNow QR ✓ ✓ or the online payment ✓ ✓ → **the kitchen waits ✓ ✓**
  (the rule from `order-flow-standards.mdx` §2.4 ✓ ✓) ✓ ✓ → **no ghost delivery ✓ ✓** ✓ ✓;
- **cash on delivery ✓✓** — the driver collects ✓ ✓ → the staff records it at the handover ✓ ✓
  → the `Payment` row ✓ ✓ with `payment_method = 'cash'` ✓ ✓ ✓✓ ✓ ✓.

## 6. The architecture ✓ — one API ✓✓, two PWAs ✓

| Surface ✓ | Serves ✓ | Status ✓ |
|---|---|---|
| the **in-venue PWA ✓** (the customer app ✓ ✓) | the dine-in ✓ + the takeaway ✓ ✓ (**unchanged ✓ ✓**) ✓ ✓ | exists ✓ ✓ |
| the **delivery PWA ✓** (new ✓ ✓) | the delivery ✓ ✓ | new ✓ ✓ |
| the **POS staff app ✓** | the counter ✓, the kitchen ✓, the driver assignment ✓ ✓ | exists ✓ ✓ |

**The shared core ✓✓ — never duplicated ✓✗:**
- the menu ✓ ✓, the prices ✓ ✓, the tax ✓ ✓, the currency ✓ ✓;
- the **orders** ✓ ✓ — the same order table ✓ ✓ (the `order_type = 'delivery'` ✓ ✓);
- the **outlets ✓** (the tenant ✓, the slug ✓ ✓) ✓ ✓;
- the **payments ✓** ✓ (the `Payment` table ✓ ✓ — the prepay ✓, the cash ✓ ✓) ✓ ✓;
- the **kitchen ✓** ✓ (the delivery order arrives in the same kitchen ✓ ✓) ✓ ✓;
- the **reports ✓** ✓ (the delivery revenue ✓ — the takings per outlet ✓ ✓ already exist ✓ ✓) ✓ ✓.

→ **the delivery PWA is a second *client* of the same API ✓✓** ✓ — **a fork here would
duplicate the whole system ✓ ✗ ✗** ✓ ✓.

**The four audit gates ✓✓** (the standing rule ✓ ✓) — **the delivery PWA ships the public
customer key ✓✓** ✓ → **every new route it calls ✓✓ needs all four ✓✓**:
1. **who may call it ✓?** → the PWA's key is public ✓ → the staff routes ✓ → **403 ✓ ✓** → the
   delivery PWA needs its **own public routes ✓✓** (the storefront ✓, the cart ✓, the order
   ✓, the payment ✓, the status ✓ ✓) — with the **ownership proof ✓** ✓ (the
   `dining_customer_id` ✓ / the order token ✓ ✓) ✓ ✓;
2. **whose data ✓?** → the tenant comes from the **session/slug ✓ ✓** (never from a client
   parameter ✓ ✗ ✓) ✓ ✓;
3. **did they buy it ✓?** → `require_plan_feature("Delivery")` ✓ ✓ (all plans ✓ ✓ → it always
   passes ✓ ✓ — but the **route still declares it ✓ ✓** ✓ ✓) ✓ ✓;
4. **does the UI agree ✓?** → the tenant's plan ✓, the nav ✓, the PWA's visibility ✓ ✓ ✓✓ ✓ ✓.

**And the PWA's public key is NOT a staff credential ✓✓** ✓ ✓ — the PWA's order routes must
prove ownership ✓ ✓ (the order token ✓ ✓ — **a new field ✓** ✓, or the existing
`dining_customer_id` ✓ ✓) ✓ ✓ ✓.

## 8. The open questions ✓

1. **Cash on delivery ✓ — the default ✓?** — my pick ✓: **allowed ✓✓** (the tenant's driver
   collects ✓ ✓) but **the tenant can require prepay ✓ ✓** (`prepaid_only` ✓ ✓) ✓ ✓ — my
   default ✓: **allowed ✓ ✓** ✓ ✓ (the Malaysian market expects it ✓ ✓) ✓ ✓.
2. **The zones ✓ — by postcode ✓ or by area name ✓?** — my pick ✓: **postcodes ✓✓** (the
   customer types one ✓ → the fee ✓ ✓) — **no map ✓ ✗** ✓ ✓.
3. **Does the delivery order carry a separate fee line ✓?** — my pick ✓: **yes ✓✓** (a
   delivery-fee line item ✓ ✓) → the invoice ✓ and the e-Invoice ✓ stay clean ✓ ✓ ✓.
4. **Do the tenants' customers get an account ✓?** — the `dining_customer_id` ✓ ✓ already
   exists ✓ ✓ → **reuse it ✓✓** ✓ ✓ (the PWA's login ✓ ✓ ✓).
5. **Is the delivery PWA its own domain ✓ or a path ✓?** — my pick ✓: **a path ✓✓**
   (`/d/<slug>` ✓ ✓) → **one deployment, one certificate ✓ ✓** ✓ ✓ — a custom domain ✓ ✓ later
   ✓ ✓.
6. **Does the delivery order need its own kitchen screen ✓?** — my pick ✓: **no ✓✓** — the same
   kitchen ✓ ✓ (a restaurant's delivery food is made in the same kitchen ✓ ✓) ✓ ✓.
