## 1. The short answer

**One codebase, one deployment, one API — and every tenant gets its own branded
delivery PWA.**

**The principle that decides every scope question:**
> **The tenant owns its delivery operation. We own the commerce.**
> The tenant sets its own charges, allocates its own drivers, manages them its own way
> — **we do not care how**.

**The commercial line** — Grab charges the customer and the merchant a commission and
carries the courier network → **our pitch is the same job at a fraction of the cost:
no commission and no driver marketplace** — and the tenant's own drivers are a
**feature for them** (they know their customers).
→ **and the customer's WHOLE delivery app — the menu, the cart, the checkout, the
kitchen status, the delivery status, the map and the live tracking — is ONE
entitlement** (§5) → **so the thing we sell is the tenant's own operational depth**
(the zones, the analytics), **never the customer's experience** (§11.1).
→ **and since v1.9 that module sits on Enterprise** → **so the delivery is sold the
way Inventory is sold** — to the tenant that is already running a real operation.

**And the plan gating (the question) — mapped onto our REAL plans:**

**And the plan gating (the question) — mapped onto our REAL plans — and v1.9 settled
it: the delivery is ONE module on ONE plan.**

**The rule (Kens, Nov 14, 2026):** *the delivery app must have the full features, and
we should assign the delivery feature to the Enterprise plan like the inventory
features. Then only the customers of a tenant that subscribes Enterprise AND allows
delivery at that outlet can access the delivery app.*

## 4. The order flow

**The rule that decides the whole design — the shared order machine does not change.**
The core keeps exactly the five statuses it has today:

```
pending → confirmed → preparing → ready → served
                          └──── the shared machine — UNCHANGED ────┘
```

**The delivery is a SECOND, PARALLEL leg on the order** — it never touches the
shared statuses:

```
unassigned → assigned → picked_up → delivered
└──────── the delivery leg — a table, NOT the core statuses ────────┘
```

→ **the handover IS the shared `served` step** — the core moves `ready → served`
exactly when the leg reaches `delivered` → **and the word on the button becomes
"Delivered"** (the same wording trick the house already uses for "Collected" —
`businessType.js:38`).

> **Why the leg and not two new statuses** — this is the answer to "propose the flow
> that does not go against the current ordering flow":

| If we added `out_for_delivery` and `delivered` to `orders.status` | What would break |
|---|---|
| **the live-order rule** | `isLiveOrder()` (`paymentModes.js:47`) — a **prepay** order is live only in `pending`/`confirmed`/`preparing`/`ready` → **the order would vanish from the OrderQueue while the driver is on the road** |
| **the finished-order rule** | `is_order_finished()` (`payment_modes.py:159`) — finished means `completed` **or** `served` + paid → **a third end state needs a third rule, and the revenue reports would silently miss the delivery orders** |
| **the shared flow array** | `OrderQueue.jsx:135` — the hardcoded `flow` → the button would never appear |
| **the cancellation list** | `cancellable_statuses` (`order.py:1287`, `1359`) and the customer app's own cancel (`pwa.py:618`) → literal lists that stop at `preparing` → a new status would need a third edit |
| **the reports** | `reports.py:145` filters on `payment_status == "paid"` → the money still lands, but the status vocabulary forks |

→ **the leg keeps the shared machine, the money rules and the reports exactly as they
are** → **the delivery reuses `served` as the handover** → **no status vocabulary
forks, no rule is rewritten, and the revenue path is untouched.**

**The leg's statuses and the staff's buttons** — the button depends on the **pair**
(core status, leg status) → so the queue's next-step helper must read the **order**,
not just the status (`getNextStatus(current)` → `getNextStatus(order)`,
`OrderQueue.jsx:134`):

| The core status | The leg | The button | What it does |
|---|---|---|---|
| `pending` | `unassigned` | **Confirm** | the shared step (unchanged) |
| `confirmed` | `unassigned` | **Assign driver** | the leg → `assigned` (a name + a phone from the tenant's roster) |
| `confirmed` / `preparing` | `assigned` | **Change driver** | the leg stays `assigned`; the name/phone change |
| `preparing` | `assigned` | **Start preparing** | the shared step (unchanged) |
| `ready` | `assigned` | **Out for delivery** | the leg → `picked_up` — the driver has the food |
| `ready` | `picked_up` | **Delivered** | the leg → `delivered` **and** the core → `served` — the handover |
| `served` | `delivered` | — | done (the money write may still be pending) |

→ **the three rules of the leg** — the driver may be **assigned** from `confirmed`
onward (a driver can be told in advance) · the leg may only go **`picked_up`** from
`ready` (the food must be bagged) · and the core may only go to **`served`** from
`picked_up` (the food must be on the road).

→ **and the leg must be validated on the SERVER — because the backend has no status
whitelist** — `OrderStatusUpdate.status` is a bare `str` (`order.py:340`) and the
status route has **no whitelist** (`order.py:949`) → **any client can write any
status string** → **so the hidden buttons are NOT the guard**:
- a delivery order may only move to **`served`** when its leg is **`picked_up`** —
  checked **server-side**, in the same write as the leg;
- the leg may only move **forward**, one step at a time
  (`unassigned → assigned → picked_up → delivered`), never backwards;
- the **other order types keep today's behaviour exactly** — the shared status route
  is untouched for them.
→ **so the leg is the one place where a new server-side rule must be written** — the
cost of the leg, paid once, in one route.

**The cancellation rule stays exactly as it is** — pending / confirmed / preparing
(`cancellable_statuses` — `order.py:1287` and `1359`; the customer app's own cancel
— `pwa.py:618`) → **a delivery whose leg is `assigned` but not yet `picked_up` sits
at `ready` → it is not cancellable** → **that is the existing rule, unchanged** → and
it is the right one (the kitchen has already cooked it).

**The kitchen** — a delivery ticket is a kitchen ticket **until the driver takes it**:
- the kitchen's **status filter** (`Kitchen.jsx:121` — the `pending`/`confirmed`/
  `preparing`/`ready` list) would keep the ticket in the ready column for the whole
  drive (and the ready tickets stay until they are dismissed — `Kitchen.jsx:268`)
  → **so the kitchen drops the delivery ticket when the leg reaches `picked_up`** →
  the order payload must carry the leg (a `delivery` object) → the kitchen filters
  on it;
- the kitchen's **type chip** (`Kitchen.jsx:362`, `Kitchen.jsx:459`, `Kitchen.jsx:900`
  — all three are `dine_in ? … : takeaway`) → **a third arm → "Delivery"**;
- → **v1.5 corrected a source line** — v1.4 cited `Kitchen.jsx:266` for the status
  filter; the real filter is **line 121** (line 268 is the "ready stays" rule).

**The queue already knows the delivery** — `OrderQueue.jsx:199` already filters the
delivery orders (`o.order_type === 'delivery' && isLiveOrder(o)`) and the type label
at `OrderQueue.jsx:959` already has a delivery arm → **the queue's job is only the
buttons and the leg chip.**

**The customer's status page** — the PWA shows the **merged** timeline:
- the shared steps (Placed → Confirmed → Preparing → Ready);
- the leg's steps (Driver assigned → Out for delivery → Delivered) — **only when the
  leg is not `unassigned`**;
- the driver's name and phone — **always** (the WhatsApp call);
- the ETA — the estimate, refreshed when the driver is assigned.

**The money** — the rules are the existing ones:
- **prepaid** — the DuitNow QR or the online payment → **the kitchen waits**
  (`order-flow-standards.mdx` §2.4) → the order stays `pending` until the money
  lands (`status_after_payment()` → `confirmed`, `payment_modes.py:142`) → **no ghost
  delivery**;
- **cash on delivery** — the driver collects → the staff records it at the handover →
  the `Payment` row with `payment_method = 'cash'` → the postpay write lands the order
  on `completed` (`payment_modes.py:142`);
- → **and a delivery prepay is `prepay_online`** (the money comes through the
  gateway, not at a counter) → **so it needs a connected payment account**
  (`outlet_settings.py:317` — the `LOCKED_MODES` check, `payment_modes.py:47`) **and a
  Malaysian outlet** (`ONLINE_COUNTRIES` — `payment_modes.py:73`; the check itself is
  `country_supports_online()` — `payment_modes.py:96`) → **otherwise the
  delivery order is `postpay`** (cash on delivery) → **which is the default anyway**.

### 4.1 The COD question — a delivery has TWO endings, and they can happen in either order

**What Kens asked:** *we allow prepay AND COD — do we need a new order status flow?*
**The answer: the shared statuses stay exactly as they are, but the delivery needs ONE
new rule — and the live code proves why.**

**Why the shared rule breaks on a delivery.** The shared machine encodes one rule
(`status_after_payment` — `payment_modes.py:142`): **the money lands last → the order
is `completed`**. That is true at a counter and true at a table. It is **not** true
for a delivery, because **the handover and the settlement are two different events
that can happen in either order**:

- the driver hands the food over and the customer pays the driver **at the door** →
  the handover and the money are the same moment;
- the driver takes the cash and the **cash reaches the shop later** → the handover is
  first, the money second;
- a tenant that takes the money at the counter and delivers later → the money is first.

**The two facts, and who owns each:**

| the fact | where it lives | who decides it |
|---|---|---|
| **the handover happened** | `delivery_orders.status = 'delivered'` | the driver, or the staff |
| **the money settled** | `orders.payment_status = 'paid'` | the staff |

→ **the order is finished when BOTH are true** → **and they may arrive in either
order** → **the two orders converge on the same end state** → **the tenant's process
never has to be taught.**

**The trap the live code has today — this is the finding that makes the rule
necessary.** `status_after_payment` writes `completed` for ANY postpay order
(`payment_modes.py:142`), so:

| the state | the core status | `payment_status` | `is_order_finished` says | what goes wrong |
|---|---|---|---|---|
| **the money first, the food still on the road** | `ready` | `paid` | **finished** (the write set `completed`) | the order **leaves the live queue before the customer has the food** — and the POS then **cannot fix it** |
| the handover first, the cash not counted yet | `served` | `pending` | not finished (correct) | — |
| both done | `completed` | `paid` | finished | — |

→ **the first row is the trap** → **and the front end makes it worse**:
`isLiveOrder` (`paymentModes.js:47`) says a postpay order is live only while the money
is missing → **the order vanishes from the queue** → and `canAdvanceOrder`
(`paymentModes.js:62`) says a postpay order may be advanced only while the money is
missing → **once the cash is in, the status button is gone** → **the shop can no
longer see, or move, an order whose driver is still on the road.**

**The rule — one helper, two writers, order-independent:**

```
the delivery order's core status is decided by TWO facts:
    the leg      (unassigned → assigned → picked_up → delivered)
    the money    (payment_status: pending → paid)

  the payment write (the money lands):
      if the leg is already "delivered"  ->  the core goes to "completed"
      else                               ->  the core does NOT move
                                           (the money is recorded; the handover is pending)

  the leg write (the handover happens):
      the core goes to "served"
      if the money is already in          ->  the core goes to "completed"
```

→ **the two writes are the same two facts read in a different order** → **the order
ends at `completed` either way.**

→ **and the two modes land on the two end states the shared machine already knows:**
a **prepay** delivery ends at **`served`** (the money is already in — the prepay branch
of `is_order_finished` — `payment_modes.py:159`) and a **COD** delivery ends at
**`completed`** (the postpay branch) → **no new core status, no new end state, and the
reports are untouched** (they filter on `payment_status == 'paid'` — `reports.py:145`).

→ **the three code touch points — and only three:**
1. **the backend** — a delivery-aware settlement helper (next to `payment_modes.py`) that
   BOTH the payment write (`order_service.py:791`) and the leg write call;
2. **`isLiveOrder`** (`paymentModes.js:47`) — a delivery order is live while **the leg
   is not delivered OR the money is missing** (today: a postpay order is live only
   while unpaid → the early-cash order disappears);
3. **`canAdvanceOrder`** (`paymentModes.js:62`) — **the leg's buttons are not gated by
   the money** (today: a postpay order advances only while it is unpaid) → the kitchen's
   steps stay gated (a prepay order waits for its money) → **the driver's steps do
   not**.

→ **the other order types never reach it** — the rule reads the order's own
`order_type` → **the dine-in and takeaway orders keep today's behaviour exactly.**

### 4.2 Prepay AND COD together — the mode becomes the customer's choice

**What the tenant can set today.** The timing is a map on the outlet's settings, **one
mode per order type** (`resolve_mode` — `payment_modes.py:182` → the map's `delivery`
entry) → so today an outlet is **either** all-prepay **or** all-COD for delivery.

**What Kens asks for.** The customer picks at the checkout: pay online, or pay the
driver.

→ **the order's mode is already a per-order snapshot** (`orders.payment_mode` —
`models.py:255`; stamped at creation — `order_service.py:551`) → **the choice needs NO
new column** → **what changes is where the mode comes from for a delivery order.**

**The proposal — three pieces:**
1. **the outlet's delivery settings gain the ALLOWED modes** (`payment_modes` in the
   JSON column — §3) → **the tenant still decides what is allowed** → **the customer
   picks among what is allowed**;
2. **the delivery PWA's checkout shows the choice** → the customer picks → the server
   resolves the order's mode → **the client's choice is validated against the outlet's
   allow-list** (the shape of the whole design: the client never decides the money)
   → **and the choice is never a plan thing** — every entitled tenant's customer picks
   among the outlet's allowed modes the same way (§5.2);
3. **the lock on `prepay_online` becomes PER ORDER TYPE** — this is the live finding
   that makes the whole thing possible.

**The lock is the blocker, and it is global today.** `prepay_online` is refused for the
WHOLE map when the outlet has no connected payment account or is outside Malaysia
(`normalize_map` — `payment_modes.py:238`; the connected-account check —
`outlet_settings.py:317`; the country rule — `ONLINE_COUNTRIES` — `payment_modes.py:73`)
→ **and the reason it prints is about the in-venue app**: *"the customer app has no
checkout"* (`LOCKED_MODES` — `payment_modes.py:47`).

→ **that reason is FALSE for the delivery app** — the delivery PWA HAS a checkout →
→ **and it is TRUE for the in-venue app, which still has none** → **one global lock
cannot be right for both** → **the lock becomes per order type**: `delivery` may take
`prepay_online` when the outlet has a connected account and is in Malaysia; `dine_in`
and `takeaway` stay locked → **and the tenant's other outlets keep their own country
rule** (the rule stays per OUTLET — `ONLINE_COUNTRIES`).

→ **the front end already has the same shape waiting**: the POS's own settings screen
offers `prepay_online` behind the connected-account switch (`Settings.jsx:1274`) →
→ **the Delivery tab needs the same treatment, per order type.**

**The delivery fee** — the **server** computes it (the client never sends a price) and
it reaches the order's total → **the reports pick it up unchanged** (they filter on
`payment_status == "paid"` — `reports.py:145`).

#### 4.2.1 The counter's chooser — the same allow-list, two doors

**Kens's question:** *so we allow the customer to order as delivery through the

| | **the counter (the staff screen)** | **the delivery PWA** |

| **the money** | the staff records it → **and the mode is DERIVED today** (`StaffOrder.jsx:769` — `modeFor(settings?.payment_timing, orderType)`) → **and v1.13 gives the counter a CHOOSER** (§4.2.1) — **but it is a contract, not a control**: the server owns the mode (`order_service.py:551`) and resolves the staff's choice against the outlet's allow-list | **the customer chooses**: pay online, or cash on delivery → **from the SAME allow-list** (§4.2, §4.2.1) |
| **who sees the tracking** | the tenant, on the **Delivery Management** screen | the customer, on the **order status + the map** (§5.2) |
| **the customer member** | **optional** — `dining_customer_id` is **nullable** (`models.py:224`) | **mandatory** — registration is required (§5) |

→ **so it is ONE delivery order type with two doors in** → → **the kitchen, the leg,
the driver, the settlement rule and the reports are the same either way** → → **and
that is why the WhatsApp model works**: a tenant whose customers order by WhatsApp
runs the **counter** path; a tenant whose customers scan the QR runs the **PWA** path
→ **the tenant can run one, the other, or both** (§11.2).

→ **and the ONE difference that matters — the customer's side** → **the PWA order
carries a member** (`dining_customer_id`) → **so the customer gets the map, the live
tracking, the ETA and the history** → → **a counter order has no member**
(`models.py:224` — nullable) → → **so the customer gets NOTHING on their phone** — no
map, no tracking, no history → **the tenant tracks it on the Delivery Management
screen** → → **v1.12 CLOSES THIS: the member is REQUIRED on a delivery** →
**the rule is below** → **and it is one field**: the order already accepts
`dining_customer_id` (`order.py:262`) → **the staff link the member** → **and the
customer gets the tracking link too**.

#### 4.3.1 THE RULE — a delivery order must belong to a customer of the tenant

**Kens's decision (v1.12):** *"1 rules for delivery type must be customer belong to
tenant's customer."* → **stated as an invariant the server enforces:**

> **A delivery order MUST carry a `dining_customer_id` whose member belongs to the
> tenant's own restaurant group. A delivery order with no member is REFUSED. A
> delivery order whose member belongs to another tenant is REFUSED.**

**and the live code gives that sentence three enforceable clauses:**

| # | the clause | the live proof |
|---|---|---|
| **1** | **the tenant scope is `customer_id` — NEVER the phone** | the member table is `dining_customers` (`models/loyalty.py:47`) → `customer_id` = "Restaurant group" (`models/loyalty.py:55` — `nullable=False`) → and the unique index is **`(customer_id, phone)`** (`models/loyalty.py:51` — *"Unique constraint: phone must be unique per restaurant (customer_id)"*) → **so the SAME phone number exists in two different tenants** → **so a phone lookup alone could attach ANOTHER tenant's member** → **the member picker at the counter searches scoped by the outlet's `customer_id`** |
| **2** | **the walk-in member is EXCLUDED** | the house excludes it by phone — `AND phone != 'WALKIN'` (`loyalty.py:814-816` — *"the house convention used in vouchers.py and ai/__init__.py"* rather than a hardcoded id) → **and a walk-in has no phone to receive the tracking link and no login** → **so a delivery can never ride the walk-in member** → **the delivery's member search skips it, and the server rejects it** |
| **3** | **the check is the SPLIT-BILL precedent, verbatim** | `order.py:1104-1113` — *"The member has to belong to the same restaurant group as the order — a payer from another tenant would burn another restaurant's points"* → and the refusal is **HTTP 404, "This member does not belong to the restaurant"** → **so the delivery reuses the house's own check and its own wording** |

**What the rule changes:**
- **the delivery becomes the ONE order type where a member is REQUIRED** — dine-in and
  takeaway stay optional (`models.py:224` stays nullable) → **so the POS's own
  validation must branch on `order_type`**: a delivery with no member is refused;
- **the counter's staff screen gains a member step** — the phone lookup, scoped by the
  outlet's `customer_id` (§4.3.1 clause 1), **excluding the walk-in** (clause 2) → **and
  the found member's phone is pre-filled into the address block** → **so the customer
  is identified before the order is submitted**;
- **and now EVERY delivery has a customer side** → **the map, the live tracking, the
  ETA and the history are guaranteed on every delivery order** → → **not a maybe for
  the PWA orders and a maybe for the counter orders — always** → **which is what makes
  the tracking worth building** → **and it gives the PWA order and the counter order
  the SAME customer experience**, which was the whole point of the two doors (§4.3);
- **and the loyalty story closes too**: the delivery's points now land on a real
  member of the tenant — **the same reason the split-bill path guards the payer**
  (`order.py:1104-1113`).

**and the one caveat, stated honestly:** this makes the counter delivery **slower to
enter** — the staff must identify the customer → → **and that is a cost the tenant
accepts**, because the alternative is a delivery the customer can never track.

→ **and the entitlement guards BOTH doors** — the PWA's login gate (§5.1) **and the
counter's Delivery button** (§9.11) → → **one entitlement, two doors, one order**
(§6).

## 5. The customer app — the white-label PWA

**A separate entry point** — **not** a flag inside the existing app (that file is
already large) → **a new `delivery-app/`** sharing the API client and the i18n
— **one codebase, one deployment**.

→ **the customer's nine screens are listed in §3.2 (table B)** — this section is the

### 5.1 The one gate — the delivery app's login

**Kens's rule (Nov 14, 2026):** *we only check, while the customer logs into the
delivery app, whether this tenant has subscribed the delivery features. If the tenant
did not subscribe, the customer login shows the message "sorry this tenant didn't
allow the delivery".*

→ **so the check happens ONCE, at the login, and it is the ONLY plan check in the
whole app** → **everything behind it is the full experience** → **and the plan never
appears again** (§5.3).

**The check is server-side — and it is NOT the existing `require_plan_feature()`.** The
live code says why: `require_plan_feature()` compares the feature name against the
session's stamped list and raises 403 (`auth.py:681`) → **but it returns UNCHECKED for
every caller whose key is not a browser session** (`auth.py:652` — the `key_type !=
"user"` early return) → **and the delivery PWA calls with the public customer key**
(`customer-app/js/app.js:11` — `customer_app_key`) → **so that dependency would wave
the delivery PWA straight through** → **the delivery app needs its own explicit
check** (§6, §9.8).

**What it reads — two facts, both already in the house:**
1. **the entitlement** — the tenant's feature list, read from the website API
   (`plan_features.fetch_plan_features()` → `plan_cache.get_features()`) → **the string
   is the tab name** (`admin.py:1052` hands the reader the `tab_name` under `name`) →
   **the check is `"Delivery" in the list`** → **and the reader is the same one the
   staff app reads** → **one truth, two readers** → **and since v1.9 the row is on
   Enterprise only → so this ONE check IS the Enterprise check** → **a tenant that
   downgrades loses the entitlement, and the login gate refuses it** → **the stale
   `allow_delivery` flags no longer leak delivery** (§3.1, §8 Q17);
2. **the subscription** — the tenant's subscription state
   (`subscription_state.fetch_subscription_state()` →
   `subscription_cache.get_state()`) → **and the house's own decision**
   (`subscription_gate.check_subscription_access()`) → **because the features endpoint
   does NOT check the subscription's status** → it reads the plan's `plan_features`
   rows for the tenant's first subscription row → **so a CANCELLED tenant still shows
   its plan's features as enabled** → **the entitlement alone is not enough** → **the
   gate needs both facts.**

→ **and the per-tenant override counts** — the website API's customer-features
endpoint applies the tenant's own `CustomerFeatureOverride` rows on top of the plan
→ **so a tenant whose admin switched the delivery off is refused even though its plan
carries the row** → **that is the "this tenant didn't allow the delivery" case a plan
can never express.**

**Where the check runs — three places, one helper:**
1. **the login** (`POST /api/delivery/{slug}/auth/login`) → **the customer sees the
   message here**;
2. **the registration** (`POST /api/delivery/{slug}/auth/register`) → **the same
   check** → a customer cannot register against a tenant that does not deliver;
3. **the order create** → **re-checked** → **and this one is not optional**: the guest
   token lives **30 days** (`guest_session.py` — `GUEST_TOKEN_TTL_DAYS = 30`) →
   **so a customer who logged in before the tenant lapsed would otherwise keep
   ordering for a month** → **the login gate is the UX; the order gate is the truth.**
4. **the COUNTER** → **the staff screen's Delivery button asks the SAME feature list**
   (§9.11) → **and the order create re-checks** → → **so the entitlement guards BOTH
   doors** — the PWA and the counter (§4.3).

→ **and the outlet's own switch is the third thing** — the tenant must have allowed
delivery **at that outlet** (`outlet_settings.allow_delivery`) → **so a customer may
log in to a tenant that has the delivery but reach an outlet that does not take
delivery orders** → **that is the `outlet_not_delivering` message** (§3.1) → **the two
levels stay distinct**: the **Enterprise plan** says the tenant HAS the delivery; the
**outlet flag** says THIS branch takes delivery orders.

**The messages** — the server returns a **machine code** and the app renders the
**text** (the PWA is multi-lingual → the sentence belongs in the app's i18n):

| the fact | the code | what the customer sees |
|---|---|---|
| the tenant has no delivery entitlement | `delivery_not_allowed` | **"Sorry, this tenant didn't allow the delivery."** |
| the tenant's subscription is cancelled / expired / overdue | `delivery_not_subscribed` | **"Sorry, this tenant didn't allow the delivery."** (Kens's one message) |
| the outlet's `allow_delivery` is off | `outlet_not_delivering` | **"This branch is not accepting delivery orders right now."** (the outlet's own switch — §3.1) |
| the tenant IS entitled | — | the app opens → the full journey (§5.2) |

**And a technical failure is fail-OPEN, like the rest of the house** — if the website
API cannot be read, the plan cache keeps the **stale** list (the house rule: *a stale
plan is better than locking a paying customer out* — `plan_cache.py`) → and only a cold
cache with an unreachable API gives `None` → **then the storefront opens and logs
loudly** → **the order-create check is the backstop** (above).

  customer's app at all.**

→ **and that is the test: if a tenant's plan can change a customer-facing screen, the

**The white-label rule** — **the tenant's branding comes from the outlet settings**
(the logo, the colour, the name — **already stored**) → **no per-tenant build,
no per-tenant deployment**.

**And the delivery app REQUIRES a registered member of the tenant.** Kens's rule: *the

→ **so the delivery checkout is gated on the member's token** (the guest token —

**no member of another tenant can ever be attached to a delivery order.**

→ **what this changes for the tenant:** the tenant's existing walk-in customers become
**members** (with the tenant's loyalty) → **and that is exactly why the tenant shares

→ **and one setting decides whether the tenant can take delivery orders at all** —

→ **and the tenant's own customers are the tenant's business, not ours** — the

**And the delivery prepay** — the customer can **submit and prepay** → the same

   → **the two readers, and they differ** — the **live plan** (the cache, refreshed on

   `auth.py:320`) → **both carry the tab name** → so the rows must set
   `tab_name` to the string the gate compares with;
   → **and the gate is a browser-session gate ONLY** — a server-to-server caller
   (`key_type != "user"` — `auth.py:652`) **returns unchecked** → so the **PWA's
   public routes are NOT plan-gated by this dependency** → **the delivery PWA must
   check the plan itself** — this was a **real gap in this design**, and **v1.5
   closed it**:
   → **the fix is a server-side check, not a client-side one** → `plan_features.py`
   already reads the tenant's plan features → **add a `plan_has_feature()` helper**
   (the customer id and the tab name) → the delivery routes call it → **the
   comparison is against the plan's own list, read on the server** → **the client is
   never trusted to declare what the tenant bought** → and it is the **same list**
   the staff app reads →
   **one truth, two readers**.
   → **the string it compares is the tab name** (`admin.py:1052` hands the reader the
   `tab_name` under `name`) → so the delivery row's tab name — **"Delivery"** — is
   the gate key.
   → **and v1.8 moved the check to ONE place — the delivery app's LOGIN** (§5.1) →
   **the customer-facing answer is one sentence** → **and the same helper re-checks
   on the order create**, because the guest token lives **30 days**

   → **and v1.11 adds the SECOND door** — the **counter** → **the staff screen's

4. **does the UI agree?** → the tenant's plan, the nav, the PWA's visibility.

   The default is a radius (one number, no geocode on the hot path) and the managed

   this is a choice the tenant makes, not a choice the plan makes** → → **and the

   .
6. **Does the delivery order need its own kitchen screen?** — my pick: **no** — the same

#### 9.16.2 The lesson the house should keep — a build is not a deploy

### 9.22 The v1.26 build review — the two PWAs are TWO tracks, and they were sharing one Cache Storage

**Phase 6a shipped and proved the zones live (v1.25). But the shipping of it exposed a
defect in the PWA layer that has nothing to do with the zones** — and it is the kind of
defect that only shows up when you look at the *whole* client instead of the feature.

#### 9.22.1 What was actually wrong

| the defect | what it did | how it was found |
|---|---|---|
| **`customer-app/VERSION` said `2.6.32` while every in-venue asset was still stamped `2.6.28`** | `python3 scripts/build_pwa.py --check` **FAILED** on `index.html`, `sw.js`, `js/pwa.js` and `manifest.json` — the in-venue PWA was claiming a build that four of its own files did not agree with | the check was run **after** the Phase 6a push, and it failed where it had passed at `64421ac` |
| **`sw-delivery.js` still said `BUILD = 'v=2.6.30'` while `delivery.html` asked for `?v=2.6.32`** | the worker **precached one build** while the shell **requested another** — so a returning customer's **OFFLINE fallback silently served the older `delivery.js`** — the one file that holds the whole customer journey | by reading the live `/d/sw.js` and **diffing it against the live shell** |
| **BOTH workers deleted EVERY Cache Storage key except their own** | Cache Storage is **origin-wide** — so activating the delivery worker (`/d/`) **wiped the in-venue precache** (`/`, `pos-customer-v15`), and activating the in-venue worker **wiped the delivery precache** (`pos-delivery-v3`) — **the two apps were evicting each other** | by reading the `activate` handler of both workers |

→ **and the reason the first two happened is a DESIGN gap, not a typo**: **Phase 6a
changed the DELIVERY track and nobody changed the in-venue track** → → but `VERSION` is
**one file for the whole `customer-app/`** → → so the delivery bump **leaked into the
in-venue series** → → and the delivery's OWN worker stamp was **never bumped with it**.

#### 9.22.2 The two rules that fall out — and they are architectural

**Rule 1 — the two PWAs are TWO version SERIES, and the delivery track is its OWN.**

| track | the file that stamps it | its series | its cache namespace | its scope |
|---|---|---|---|---|
| **the in-venue PWA** | `customer-app/VERSION` → `index.html` · `sw.js` · `js/pwa.js` · `manifest.json` | `2.6.28` (unchanged by Phase 6a) | `pos-customer-v15` | `/` |
| **the delivery PWA** | `customer-app/sw-delivery.js` → `delivery.html` · `css/delivery.css` · `js/delivery.js` · `js/choices.js` | `2.6.32` | `pos-delivery-v4` | `/d/` |

→ **the vendored Leaflet (`1.9.4`) is deliberately OUTSIDE both series** — it is
**vendored**, so it does not move with a build.

→ **and `VERSION` belongs to the in-venue track** → → so Phase 6a's delivery bump must
**not** touch it → → **`VERSION` is back at `2.6.28`**, which is what the four in-venue
files were already saying.

**Rule 2 — a worker may only delete ITS OWN cache namespace.**

→ **Cache Storage is per-ORIGIN, not per-scope** — the two workers share one storage →
→ **so `caches.delete` must be filtered by the worker's OWN prefix** (`pos-customer-*`
for the in-venue worker, `pos-delivery-*` for the delivery worker) → → **otherwise the
two apps evict each other's precache**, which is exactly the failure mode of the
"one origin, two PWAs" architecture (§6).

→ **and the cache version must be bumped whenever the precache CONTENTS change** — the
delivery worker moved `pos-delivery-v3` → **`pos-delivery-v4`** precisely so a returning
browser **re-precaches** the new `delivery.js` and the new locale bundles.

#### 9.22.3 The guard — so this cannot drift again

→ **`customer-app/scripts/build_pwa.py` now ALSO checks the delivery track**
(`check_delivery_track()`) — the script does not **stamp** the delivery track (it has its
own series and its own stamp), but it **verifies** that **every asset the delivery worker
precaches is requested with the SAME version query in `delivery.html`** → → and it
**reports the drift the way the house reports it**: the file, the value it found, and the
value the worker precaches.

→ **and the negative control proves the guard bites**: drifting `delivery.html` to
`delivery.js?v=2.6.29` makes the check **fail** with
*"delivery.html: /js/delivery.js is ?v=2.6.29 (the worker precaches it as ?v=2.6.32)"* —
and the check **passes again** once the drift is reverted.

→ **and the live proof, because the customer-app tree is a BIND MOUNT into the web root**
— the fix was live the moment it was written, with no deploy step:
`/d/sw.js` → `BUILD = 'v=2.6.32'`, `CACHE_VERSION = 'pos-delivery-v4'`,
`pos-delivery-*` scoped cleanup · `/sw.js` → `BUILD = 'v=2.6.28'`,
`CACHE_VERSION = 'pos-customer-v15'`, `pos-customer-*` scoped cleanup · and
`build_pwa.py --check` **passes**.

→ **and the commit is `cd94cfe`** — a fix on top of the Phase 6a commit `878272c`.

→ **and one CDN fact, checked rather than assumed**: the **origin** serves `/d/sw.js`
with `Cache-Control: no-cache, must-revalidate` (and `Service-Worker-Allowed: /d/`) —
**but Cloudflare's edge rewrites the header** to `max-age=14400, must-revalidate` →
→ **that is the CF browser-cache TTL, and it does NOT hold the worker back**: the service
worker's **update algorithm revalidates the script** (`updateViaCache` defaults to
revalidating the top-level script), and CF **honours the revalidation** — the live
edge answered `cf-cache-status: EXPIRED` and served the **NEW** worker (`v=2.6.32`,
`pos-delivery-v4`) **the moment it was written** → → **so a worker fix reaches a
returning customer without a deploy and without a manual cache purge.**

→ **the lesson is the house's own, twice over**: **a version stamp is a CONTRACT between
files** — and a contract that no tool checks is a contract that breaks silently, the way
the *counter* screen broke (§9.21.4): **the wiring is where the defects live**, and
**the check is the only thing that sees them before the browser does.**

### 9.26 The v1.30 defect review — the map had no streets under the route

**The defect.** The customer's live-tracking map (and the driver's route map) drew their
basemap from **CARTO's raster tiles**:

    https://{s}.basemaps.cartocdn.com/light_all/{z}/{x}/{y}{r}.png

**CARTO's raster basemaps are KEYED.** The key was not in the deployment, so every tile
request came back as a **2,049-byte placeholder PNG** that renders the words
**"API KEY REQUIRED"** across the map. The route polyline and the driver marker still
drew — they are vector overlays — so the map looked *alive* with a grey square where the
street should be. That is why this read as "the map is broken" rather than "the tile
provider wants credentials", and why it survived the earlier browser reviews: the
review checked that tiles **loaded** (they did — 6 of 6, HTTP 200), not that they were
**maps**.

**The proof of the cause.** Several CARTO hosts, all four subdomains, the legacy Fastly
hostname, and a request with an invalid key all returned the **identical** 2,049-byte
file (MD5 prefix `502fc5f6793`, 16 distinct colours, the text "API KEY REQUIRED"). A
provider that answers identically for a good key, a bad key and no key is not serving
tiles; it is serving a placeholder.

**The fix — OpenStreetMap, through our own server.** The tiles now come from
`https://tile.openstreetmap.org/{z}/{x}/{y}.png`, fetched by **our** server and served
to the browser from **our own origin** at `/d/tiles/{z}/{x}/{y}.png`.

The reason for the proxy is not indirection — it is the **OSM tile policy**
(`operations.osmfoundation.org/policies/tiles`), which asks for three things a browser
cannot deliver:

| the policy asks for | a browser | our server |
|---|---|---|
| a **clear, unique User-Agent** naming the app and a contact | **cannot** — it sends its own (Chrome, not us), and OSMF reserves the right to block traffic it cannot contact | `IdeazesPOS/1.0 (+https://ideazes.com; contact: support@ideazes.com)` |
| a **valid Referer** | sends one only if asked | forwarded, origin-only |
| a **sufficient local cache** | the browser's HTTP cache, if the response allows it | the upstream's own `max-age`, floored at the policy's **seven days** |

**The policy's prohibitions, and how each is respected:**

| the policy forbids | this implementation |
|---|---|
| **bulk downloading** ("pre-seeding" areas or zoom levels, tile archives, `.mbtiles`) | a tile is fetched because a human is looking at that part of the map **right now** — the cache is a bounded HTTP cache (3,000 tiles), not an archive |
| **prefetch features** | there is no background job and no "load the whole city" — the only trigger is Leaflet asking for the viewport |
| **`Cache-Control: no-cache` / `Pragma: no-cache` by default** | the response is `public, max-age=604800` — and the seven-day floor is enforced in code |
| **a restrictive `Referrer-Policy` that prevents the Referer** | the tile request is **same-origin**, so the browser sends the full Referer; our server forwards the **origin only** — a driver's `/d/driver/<token>` path and a customer's restaurant slug never leave the building |
| **blanking the Referer when proxying through a CDN** | the Referer is forwarded, and the response carries `X-Tile-Referer` so it is **auditable** |
| **impersonating a browser's User-Agent** | the User-Agent names our app and a contact — stable across releases, as the policy asks |

**What was ruled out, and why.** `tile.openstreetmap.de` (FOSSGIS) returns real tiles,
but its terms **limit commercial use** of its tile server → so it is **not** the primary.
Geoapify remains responsible for **geocoding, routing and the traffic-aware ETA** — its
raster endpoints answer **404** on this key, and it was never a tile provider here.
**Mapbox** stays out (no account, no bill, no browser token).

**The attribution stays visible.** OpenStreetMap's data is ODbL, so
`js/map-tiles.js` carries the attribution and Leaflet renders it on **both** maps:
*"© OpenStreetMap contributors"*, with the `openstreetmap.org/copyright` link live.
The service workers were told **not** to persist tiles at all (the `TILE_PATH` skip in
`sw-delivery.js` **and** `sw.js` — the in-venue worker has scope `/` and also sees the
delivery app's requests), so the browser's own HTTP cache is the only cache.

**One module, two maps.** `customer-app/js/map-tiles.js` is the single place that knows
where a tile comes from. `js/delivery.js` and `js/driver.js` both call
`PosMapTiles.createLayer()` — so the customer map and the driver's map cannot drift
apart again, and the provider is swapped in **one** file.

**The proof — 42 automated checks (`customer-app/scripts/proof_tiles.py`) and a live browser:**

| the check | what it found |
|---|---|
| the coordinate bounds | **8/8** — a zoom of 20 (OSMF publishes 0–19), an x or y outside the zoom, and a negative coordinate are all refused **before** the upstream is touched |
| the upstream's own response | a **real 14,501-byte PNG**, `image/png`, and a cache lifetime of **604,800s** (the seven-day floor) |
| the cache | the second request is a **HIT** — a repeat view does not re-download |
| **what the upstream actually receives** (a stub server that records the request) | the **identifying User-Agent**, the **forwarded Referer**, `Accept: image/png`, and **no no-cache headers** |
| the live endpoint | **200**, `image/png`, 14,501 bytes, `max-age=604800`, `X-Tile-Upstream: tile.openstreetmap.org`, `X-Tile-Referer: https://order.ideazes.com/` |
| an impossible tile | **404**, not a request to the upstream |
| the source | **no CARTO tile URL in any file's code**, and the tile URL is the same-origin proxy |
| the attribution | present in the shared module and applied by it, on **both** maps |
| the service workers | **both** skip `/d/tiles/` — no tile is persisted |
| the version tracks | the delivery track agrees with itself at **v=2.6.33** (and the driver script at **2.6.31**) |
| **a live browser, the real page** | `https://order.ideazes.com/d/kens-ss17` → **6 of 6 tiles loaded** (not merely 200 — `naturalWidth > 0`), every one of them from `https://order.ideazes.com/d/tiles/15/…`, **zero** requests to any CARTO host, and the attribution rendered |

**A note on the CDN.** Cloudflare fronts the app and caches by URL, and each edge
location holds its own copy — so a copy fetched **before** the cache floor was raised
still carries the older lifetime (which mirrors OSMF's own upstream value) until it
expires, and it still self-heals. No Cloudflare credentials are on the box, so no purge
was run; the origin's contract — the seven-day floor — is what the proof asserts, and
the public header is only ever **more** generous than the upstream's own.


### 9.27 The v1.31 defect review — the map's camera belonged to the APP

Two defects, one rule, and both on the delivery's own two maps.

**The first defect — the customer's tracking map threw away the customer's own zoom.** The
tracking map called `fitBounds()` at the end of every render, and the render runs on every
**8-second poll** — so the camera was reset to the automatic framing of the whole route
every eight seconds, whether or not anything had moved. A customer who zoomed into their
own street got that zoom taken away eight seconds later. Measured: the zoom the customer
chose went **17 → 15** after ONE poll, and `fitBounds` ran **1 → 2** times.

**The second defect — the driver's map was born 0x0, and with no route it never recovered.**
`drawMap()` called `L.map(element)` while the container was still inside the hidden `#app`,
and `drawMap` runs from `render()` inside `refresh()`, which the boot sequence calls
**before** `#app` is un-hidden. Leaflet therefore believed it had no viewport: it asked for
no tiles, and nothing ever corrected it — there is no `invalidateSize()` anywhere in the
app. And the second fault was the same code with no route to draw: `fitBounds` was the only
thing that ever set a centre, so with no route the map had **no centre at all** and every
Leaflet call was refused (*"Set map center and zoom first."*). Measured: created at
**{w: 0, h: 0}**, **0 tiles**, that error.

**The fix — ONE rule, written once.** `customer-app/js/map-camera.js` (`PosMapCamera`) is the
single place that knows who owns the camera, and **both** maps obey it:

| the rule | why it is that way |
|---|---|
| **the app may frame the map once** | the first view is the app's job — it is how the customer is shown the delivery at all |
| **the moment the person pans or zooms, the view is THEIRS** | a map has one camera, and the camera belongs to the person looking at it |
| **ownership is detected by the VIEW, not by the gestures** | Leaflet's `dragstart`/`zoomstart` only fire for a real pointer gesture, and a view also moves by a trackpad pinch, a keyboard, or the browser restoring a scroll position — so the test is *does the current view still match the one the app last set?* |
| **the drift is measured in PIXELS, not metres** | one pixel is a metre at street level and a centimetre at maximum zoom — a distance in metres would call a small drag at z17 "no move" and a rotation jitter at z12 "a move". The view is compared in the unit the finger moved in (16px; a zoom change on its own is always the person) |
| **the app's own framing is NOT animated** | so the view it sets is FINAL before it is remembered — otherwise the comparison is made against a view the map is still travelling to |
| **a NEW order gets a NEW camera** (`reset()`) | the customer is looking at a different delivery, so the old camera belongs to nobody |

And the driver's map, separately: it is created **only once its box has a real size**, a
**`ResizeObserver`** passes later size changes to `invalidateSize()`, and the map **always
gets a view** — the rider's own position first, then this phone's own GPS fix, and only
then a wide regional view. **A blank grey box is not a map.** The rider also now sees their
own **"you are here"** dot, drawn from their phone's own GPS.

**The proof — a NEGATIVE CONTROL, because a fix that only stops the view moving leaves a
FROZEN delivery, which looks like a fix.** The SAME probe was run against the unfixed code
(sandbox, real Chromium, 430x900 viewport):

| | before (negative control) | after (the fix) |
|---|---|---|
| the zoom the customer chose | 17 | 17 |
| the zoom after ONE poll | 17 → **15** (reset) | 17 → **17** (kept) |
| `fitBounds` calls | 1 → **2** | 1 → **1** |
| the driver's map creation size | **{w: 0, h: 0}** | **{w: 364, h: 190}** |
| the driver's tiles (no route) | **0** | **6** |
| the driver's centre (no route) | **Error: Set map center and zoom first.** | **{lat: 3.139, lng: 101.6869, zoom: 11}** |

**And the half that matters most — the app still MOVES the delivery while the person keeps
the view:**

```
rider_marker_moved  : true      the rider marker followed the rider
view_preserved      : true      the customer's view did not move
no_extra_fit        : true      no extra fitBounds behind the customer's back
```

**What this review does NOT do:** no live-tenant test (the fix touches the customer-facing
map, and driving a real tenant needs a real order in flight), no real-device test (the pan
was driven programmatically, not by a thumb), no rotation test (the *later* size-change path
was not observed changing anything on a device), and no offline test of the new precache
entry.

**The lesson the house should keep:** **a map's camera belongs to the PERSON looking at it**
— and the proof of that fix must assert BOTH halves, because a fix that only stops the app
from moving the view leaves a frozen delivery, which looks like a fix. The second half of the
same lesson: **a map must be BORN with a size** — a Leaflet map created inside a hidden box
is 0x0, asks for no tiles, and never recovers on its own.

### 9.29 The v1.32 build — the ETA MOVES with the rider

Backlog item §9.28-1, built. The ETA the customer watched was a **snapshot**: the
traffic-aware estimate taken at the moment the driver was assigned, served unchanged for the
whole delivery. As the rider drove through traffic, the number on the screen did not move.
`route_computed_at` was stored on the leg and never read — it was clearly meant for exactly
this.

**THE RULE: THE ROAD THAT IS LEFT STARTS WHERE THE FOOD IS.**

| the food is… | the remaining road is… | the ETA is |
|---|---|---|
| **in the kitchen** | the road the OUTLET drew (it is already on the leg, traffic-aware) | `now + the drive that is still to come + the preparation that is still owed` |
| **with the RIDER** | the road from the RIDER's last reported position to the customer's door, redrawn traffic-aware | `now + that road` (the preparation is done — it is in the bag) |

Two consequences fall out of that rule, and both of them are deliberate:

* **while the food is in the kitchen, no routing call is spent.** The rider's position says
  nothing about the road the food will travel yet — it is the kitchen's road. The ETA is
  re-timed from the preparation that is still owed, and the preparation burns down from the
  moment of the assignment, so the ETA is **exactly the promise** while the kitchen is
  working, and slips with the clock once the food is ready and the rider is not there yet.
  Both are honest, and neither spends an API call.
* **once the food is with the rider, the road is the rider's.** The route is redrawn from the
  rider's last reported position to the customer's door, traffic-aware
  (`drive_traffic_approximated`, with the plain `drive` as the fallback), and the ETA is
  `now + that road`.

**THE PROMISE IS NEVER TOUCHED.** `eta_promised_at` keeps the number the outlet gave the
customer, and it is what the customer compares against. The live ETA is a **second** number,
not a rewritten promise — and the customer app now shows **both**: the live arrival time and
the promise, on the tracking card, with the big number in the status card following the live
one.

**THREE GUARDS KEEP THE TRAFFIC API HONEST.** A rider's phone reports every 15 seconds, and
a routing call is not free:

| the guard | the number | why |
|---|---|---|
| **the drift** | `LIVE_ROUTE_MIN_DRIFT_M = 100` | the rider must have **moved** 100 m from the point the last route was computed from. Ten metres of GPS noise must never spend an API call. The baseline is the position report that was current when the route was computed — the trail knows it, so no extra column is needed. |
| **the interval** | `LIVE_ROUTE_MIN_INTERVAL_S = 60` | the shortest gap between two live routes for one leg. |
| **the age** | `LIVE_ROUTE_MAX_AGE_S = 900` | the one case that overrides both: the **traffic moves on its own**, so a route that has gone stale is re-timed even if the rider has not moved a metre. |

And a position report **older than 15 minutes** is not used at all — a phone that stopped
reporting half an hour ago does not say where the food is.

**A FAILURE IS NOT AN ERROR.** If the routing call fails — no route, or an exception — the
previous route and the previous ETA stay exactly as they are. The customer keeps the last
honest number instead of losing the map.

**THE RIDER'S PHONE NEVER WAITS FOR THE TRAFFIC API.** The ping route and the `start` action
schedule the refresh in a FastAPI **background task**, and that task opens **its own
session**: FastAPI 0.109 closes the request's session *before* the background task runs, so
a task that borrowed it would see a closed session. The position report is answered first,
and the refresh happens after the answer.

**THE SHARED ROUTE FIELD, AND THE SHOP.** `leg.route_geometry` is now the **live** route, so
the customer's map draws the road that is left and `GET /driver/{token}/route` serves the
same. That means the **head** of the route is the **rider** — not the shop. So:

* the point the route was drawn **from** is **remembered** when the original route is
  computed (`_remember_outlet_point`);
* the head of the route is still trusted as the shop **while the route is the outlet's** —
  and the trail knows the difference: a head that is one of the rider's own position reports
  is read as the rider, and the remembered point (or the outlet's address) is used instead.

**THE PROOF.** `backend/scripts/test_delivery_live_eta.py` — **33 checks**, the traffic API
replaced by a local stub (the suite never calls Geoapify) and the database an isolated
in-memory SQLite with the real models:

```
the route starts at the RIDER, not at the shop   : true
the promise is NOT touched by the live route     : true
10 s later: NO routing call (the interval holds)  : true
a minute later, but only 10 m: NO routing call    : true
the rider moved 300 m: the route IS recomputed    : true
a route older than 15 min is re-timed             : true
the LIVE route survives the failure               : true
the answer was NOT delayed by the traffic API     : true  (0.05s)
```

**THE NEGATIVE CONTROL.** The same suite, run against a copy in which the live ETA is
**reverted** (both files taken from git HEAD): every check the live ETA owns **fails** there,
every other check still **passes**, and the suite says so — *"THE CONTROL IS SURGICAL — the
live ETA is gone and nothing else broke."* The existing tracking suite still passes **35/35**,
including the check that the rider's map opens on the **shop** and not on a hardcoded city.

**What this build does NOT do:** there is still **no push** (§9.28-3 is untouched — a guest
who closes the app hears nothing); the number moves in **steps** (at most once a minute, by
the guards), not continuously; the trail is still raw GPS (§9.28-4); the radius is still not
enforced (§9.28-2); and this was proven against an isolated database and a stubbed traffic
API, **not against a live tenant with a real order in flight**.

**The lesson the house should keep:** **an ETA is a CLAIM about a moving thing, and a claim
about a moving thing has to be re-made.** The number was honest when it was made and stale
five minutes later — and it stayed on the screen the whole time, looking exactly as
trustworthy as the moment it was computed.

not a map** → **the map is the cheap part.**

**The privacy — this is not a small footnote.** The driver's location and the
customer's address are **personal data** (the Malaysia PDPA; the GDPR for the tenants
that operate in the EU):
1. **the customer's address** → it lives in the leg and the order → it is **not** in
   the customer-facing tracking response **after the handover**;
2. **the driver's location** → the pings are **dropped 24 hours after the delivery**
   (the `delivery_pings` table is pruned by the nightly job) → **the pings are never
   part of the order record** (they are a separate table with their own life);
3. **the access** → the tenant's staff see **their own** orders only (the tenant
   scope on every route) → the customer sees **their own order only** (the order
   token / `dining_customer_id`);
4. **the driver** → the driver is tracked too → **the tenant must tell its own
   drivers** (the driver link says so) → **the driver's consent is the tenant's to
   obtain, not ours**;
5. **the map tiles** → the provider's terms require the attribution → the attribution
   goes on the tracking page.

**And the key — the CODE half is DONE (v1.20), and the ROTATION is DECIDED (v1.23): the key
STAYS.** The two
hardcoded Geoapify literals are **gone** from the source (`outlet_settings.py` and
`competitors.py` now read `settings.GEOAPIFY_API_KEY`) and the key lives in
**`backend/.env`** → **and the code fails loudly when it is missing**: the two routes
answer **503** with the reason, and the new `services/geoapify.py` raises
**`GeoapifyUnavailable`** → **the app still boots without the key** — only the
Geoapify-dependent features fail, and they fail clearly → a silent fallback to a shared
key is how a bill arrives from nowhere, and that path is now closed.

→ **and the decision (Kens, Nov 15, 2026)**: *"It is ok. We still can use back existing
geoapify key since this is private repo."* → → **so the key's VALUE stays unchanged** and
the **rotation is not owed** → **the honest statement of where the secret lives**: the
literal is **gone from the working tree** (the code reads `settings.GEOAPIFY_API_KEY`) and
it lives in **`backend/.env`** → **and it is still in the git history**, which is **now a
KNOWN and ACCEPTED risk, taken deliberately** → → **the standing rule that comes with the

## 12. The driver's write — the POS, the link, and what neither may do

**The question:** *how does the driver mark the delivery successful — through our
frontend POS, or another tool?*

**The answer: both — with one rule about what each of them may write.**

**The split — the leg is the driver's, the money is the staff's:**

| the write | who may make it | why |
|---|---|---|
| the leg (`assigned` → `picked_up` → `delivered`) | **the POS staff** *and* **the driver link** | it is the physical truth of the delivery — only the driver and the shop know it |
| the handover (`leg = 'delivered'` → the core moves) | **the server**, in the same write | the server owns the shared machine — it is the only place the status can be trusted |
| **the money** (`payment_status = 'paid'`) | **the POS staff — and the driver link, but ONLY as the COD claim** | it is the tenant's money → the staff write sits behind `staff:orders:write` (`order.py:1013`) → **and v1.20 widened it by exactly one action**: the driver's **Cash collected** button writes the payment row and the `paid` flag **through the house's own `payment_modes.status_after_payment` rule** — the same rule the counter's cash button uses — because for a COD order the rider physically holds the cash at the door (§9.20.3) → → **RATIFIED by Kens (Nov 15, 2026)**: *"Driver should mark delivered and received money after customer paid."* → **so the rider's own taps are the COD settlement, and the staff may still do it from the POS** |
| the cash **claim** ("I took RM 12.50") | the POS staff **and** the driver link | a claim is a fact about the handover → **in v1.20 it settles the money too** (see the row above) → **and it refuses the two cases where it must**: a **prepaid** order answers **409** (there is no cash to claim) and an **already paid** order answers **409** |

→ **so the driver can say "delivered, I took RM 12.50"** → **and the staff still write
the money** → **the tenant's cash flow is unchanged** → **and a COD delivery's two
endings still land in either order** (§4.1).

**Surface A — the POS (every Enterprise tenant that has the delivery, no new build).** The **Delivery Management** screen
(§10.2) carries the leg's buttons: **Assign driver** → **Out for delivery** →
**Delivered** → the same buttons, the same queue, the same server rules as today →
**a tenant whose driver is also its staff needs nothing else** → **and this is the
surface that still works when the driver will not tap anything** (the WhatsApp model).

**Surface B — the driver link (the second surface).** A **one-page web page**, not an
app: the driver opens a link on their own phone and taps three buttons → **nothing to
install, nothing to publish, no app store** → **and it is the same link that carries
the live pings** (§11.2) → **one link, two jobs.**

→ **the link's token is per order, scoped, signed and expiring** — a new claim set
next to the guest token (`guest_session.py:51` — the pattern: a signed token that
names what it may do) → **never the PWA's public key** → **a leaked link moves ONE
order's leg, and it expires.**

→ **what the link may NOT do** (the boundary, stated once):
- **it may not write money, except for ONE action** — the **cash claim** on a COD order, which goes through the house's own money rule (§9.20.3); it may not write `payment_status` or a payment row **any other way**;
- **it may not write the core status directly** — the server moves the core in the same
  write as the leg (that is where the shared machine's rules live);
- **it may not touch the items, the prices, the fee or the address** — the order's money
  was settled at the checkout;
- **it may not cancel** — a cancellation is a staff decision (and the existing rule
  stops at `preparing` anyway — `order.py:1287`).

**Surface C — what we do NOT build.** A driver **app** (§2's boundary) → the link is
the app.

**The live cost of Surface B.** The link only works if the driver opens it → **the
honest risk is the driver's cooperation, not the provider** (§11.2) → → **so Surface A
must be complete on its own** → **it is not a fallback: it is the primary, and the link
is the convenience.**
