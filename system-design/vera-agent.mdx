## 1. The short answer

**One agent named Vera, three capabilities — test, document, support — because the
public documentation is the agent's product and the live system is the source of truth
for it.**

> **Status (v1.3): the guard, the workspace and the channel are built and proven.**
> Vera exists as an OpenClaw agent with her own workspace, her own service account,
> a read-only pinned clone of the product, a two-command exec allowlist, a Telegram
> bot, three severity labels, and a first filed issue. The regression runner, the
> E2E harness, the nightly jobs and the docs pipeline are not built. **Nothing yet
> runs unattended.** The full status table is §9; the order and what each step
> proved is §11.

**The principle that decides every scope question:**
> **Vera never writes product code. Vera proves the product behaves as documented,
> keeps the documentation true, and escalates to the humans what she cannot resolve.**

**The three jobs are not three agents.** Split them and you get three truths drifting
apart plus a support bot quoting last quarter's docs. Testing proves the system still
behaves as documented; documentation records what the system actually does; support
answers from the documentation and escalates what it cannot.

**Vera is one OpenClaw agent** (`vera`) with:

- **Identity:** Vera — the verifier. Deliberately *not* a builder and *not* a
  decision-maker.
- **Model:** `minimax/MiniMax-M2.7` (primary), with `minimax/MiniMax-M3.1-Flash` and
  `minimax/minimax-M2.5` as fallbacks. Vera's work is running tests and reading code,
  not reasoning about product strategy, so she runs on the fast, cheap model — the same
  primary as Lumi and the heartbeat agent. This was changed from
  `minimax/MiniMax-M3.1-Flash` on Nov 13, 2026; see §5.4 for the reasoning and the
  image-capability consequence.
- **Mandate:** regression testing, documentation maintenance, and first-line tenant
  support with escalation to a Telegram group.
- **Hard boundary:** **no write access to product source and no write access to the
  live databases** — enforced at the OS level, not by prompting.

  document as fact.** An earlier probe ran `getChat` against the group with both
  bot tokens and got `Bad Request: chat not found` from both, which reads
  exactly like "neither bot is a member". It was not. The same probe's `getMe`
  call *also* failed for both tokens — and `getMe` succeeds for **any** valid
  bot token regardless of group membership. A failing `getMe` is therefore the
  signature of an **invalid token**, not of a missing chat. The probe was
  reading the token out of `openclaw.json`, where it exists only as an
  unresolvable `SecretRef`, so it was sending a placeholder. **The lesson:
  never infer membership from a `getChat` failure without first checking that
  `getMe` succeeds on the same token.** The trustworthy signal is a send
  attempted with the runtime's own resolved credentials, and that send now
  succeeds.

## 5. Physical path of the workspace

This is the part that decides whether the whole thing is safe. Three separate
concerns must not share a directory:

1. Vera's own workspace and agent directory (her identity, her memory, her logs)
2. The shared Playwright install and browser cache (Lumi's and Vera's — one copy)
3. The product source (read-only, and preferably not even visible)

### 5.1 The layout that was built

```
/srv/openclaw/                              <- root-owned, 0755
└── vera/                                   <- owned by the `vera` service account
    │
    ├── src/                                <- the pinned clone
    │   └── POS_AI/                         <- bind-mounted READ-ONLY (ro bind mount)
    ├── e2e/
    │   └── venv/                           <- isolated python env: pytest 9.2.0, playwright 1.65.1
    ├── browsers/                           <- chromium-1254 + chromium_headless_shell-1254
    ├── artifacts/                          <- screenshots, traces, issue bodies she writes
    ├── db/sandbox/                         <- sandbox database COPIES (never the originals)
    ├── logs/                               <- her run logs
    ├── queue/                              <- work items awaiting her
    ├── state/                              <- her git config + runtime state
    ├── bin/                                <- ROOT-OWNED wrappers, 0755 root:root
    │   ├── vera-exec                      <- drops privileges to `vera`; refuses the live tree
    │   └── vera-issue                     <- files an issue with the operator's credential
    │
    ├── AGENTS.md                           <- her persona - the workspace root IS her workspace
    ├── SOUL.md
    ├── IDENTITY.md
    └── USER.md
```

Her **agentDir** is `/root/.openclaw/agents/vera/agent` (root-owned, `0700`) — it is
**not** under `/srv`. That is the one part of the v1.2 layout that changed, and it
changed because v1.2 conflated two different things: an agent's *workspace* (where
her persona and her working area live) and its *agentDir* (where OpenClaw keeps
that agent's auth store and session state). They are separate by design, and the
auth store must not be shared with another agent.

### 5.2 Why each path, and what was verified

**The `vera` service account, not `kens`.** v1.2 proposed running Vera as the
existing `kens` user. That was wrong for two reasons, both now fixed:

- `kens` is a **human login account** with a password and `sudo` in group 27. A
  testing agent that runs as a human account inherits that human's authority — and
  Vera's whole job is to run unattended against a live system.
- `kens` is **not** an identity the OpenClaw process belongs to. The Gateway runs
  as `root`, so the only way Vera can run as anything else is for the privilege drop
  to happen **inside the command**.

So there is now a dedicated system account:

```
vera:x:995:986:Vera QA agent (OpenClaw):/home/vera:/usr/sbin/nologin
```

created with `useradd --system --no-create-home --shell /usr/sbin/nologin` and
locked (`passwd -S vera` reports `L`). It has **no login shell, no password and no
home directory** — it exists only to be a filesystem identity, and it is not a
person.

**OpenClaw has no per-agent OS-user switch.** That was verified against the
documentation and the runtime, and it is precisely why the enforcement is a wrapper
rather than a config key. The Gateway's `exec` always runs as the Gateway's own
user; the drop to `vera` happens inside `/srv/openclaw/vera/bin/vera-exec`, and
that wrapper is one of only **two** commands in Vera's exec allowlist.

**`/srv` as the root, because `/root` is a wall.** `/root` is
`drwx------ root:root`, so no non-root identity can traverse it. The live product
tree lives at `/root/.openclaw/workspace/mydoc/Projects/POS_AI` — therefore
**invisible to `vera`**, verified by running `sudo -u vera cat` against it and
getting *Permission denied*. That single fact is the boundary, and it is enforced
by the kernel rather than by a sentence in a prompt.

**The browser cache is Vera's own, not shared.** v1.2 proposed one shared
`/srv/openclaw/.cache/ms-playwright`. In the event Vera's runtime is **Python**
Playwright, because the project's test suites are Python:

- `e2e/venv` — a dedicated venv holding **pytest 9.2.0** and **playwright 1.65.1**.
  Creating it required `apt install python3.12-venv` first: the venv module was
  present but `ensurepip` was not, so the first attempt failed outright.
- `browsers/` — `chromium-1254` and `chromium_headless_shell-1254`, installed by
  `playwright install chromium` **as the `vera` user** into Vera's own directory.

Note the revision: the Node Playwright in the workspace is `1.64.1` and wants
chromium `1248`, while the Python Playwright is `1.65.1` and wants `1254`. Copying
the `1248` build across would have produced a browser/runtime mismatch, so the
matching build was installed for the version actually in use. A browser launch was
then verified **as `vera`** — it rendered a page and returned its text.

**Why `/srv/openclaw/vera` and not a folder inside the product tree.** A workspace
under the product tree would have put Vera's writable directory next to the live
source, in the same permission neighbourhood, and would have made the "her tree vs
the live tree" distinction a matter of discipline rather than of ownership. Under
`/srv`, her tree is owned by `vera`, the live tree is owned by `root` and hidden
behind `/root`, and the two cannot be confused even by accident.


### 5.3 The read-only projection of the product source

Vera needs to read the product source. She must never write it.

**The mechanism (v1.3): a dedicated `vera` identity, a pinned clone, a read-only
bind mount, and a root-owned privilege-dropping wrapper.** Three layers, each of
which fails independently.

**1 — The identity.** Vera's shell commands run as `vera` (uid 995), not `root` and
not `kens`. `vera` cannot traverse `/root` (mode `0700`), so the live product tree
is not merely unwritable for her — it is **invisible**.

**2 — The read-only projection.** The product source reaches Vera as a **clone of
the committed tree at a pinned SHA**, never as the live working tree:

```
git clone --no-checkout https://github.com/Kiens8/POS_AI /srv/openclaw/vera/src/POS_AI
git -C /srv/openclaw/vera/src/POS_AI checkout --detach db381ac93c71220a008b3d98c72eeaca280c26d1
mount --bind        /srv/openclaw/vera/src /srv/openclaw/vera/src
mount -o remount,bind,ro /srv/openclaw/vera/src
```

The `ro` bind mount is what makes the projection read-only **at the kernel level** —
not "owned by someone else so we hope", but `EROFS` from the filesystem itself.
`findmnt` confirms `ro,relatime`.

A clone of the committed tree is not the live tree: it contains none of the ignored
live files — no `backend/.env`, no `website_api/.env.test`, no `frontend/.env`, no
SQLite database, no built `dist/`. **Vera never sees a secret and never has a path
to a live database.**

**3 — The wrapper.** `/srv/openclaw/vera/bin/vera-exec` is `0755 root:root`, refuses
to run as anyone but root, refuses to run inside the live product tree, and then
drops to `vera`:

```bash
exec /usr/bin/setpriv --reuid=vera --regid=vera --init-groups --inh-caps=-all \
  env HOME=/srv/openclaw/vera \
      PLAYWRIGHT_BROWSERS_PATH=/srv/openclaw/vera/browsers \
      PATH=/srv/openclaw/vera/e2e/venv/bin:/usr/local/bin:/usr/bin:/bin \
      VIRTUAL_ENV=/srv/openclaw/vera/e2e/venv \
      GIT_CONFIG_GLOBAL=/srv/openclaw/vera/state/gitconfig \
      "$@"
```

**What was proven, and how.**

| Check | Command | Result |
|---|---|---|
| `vera` cannot read the live tree | `sudo -u vera cat .../POS_AI/backend/app/routes/order.py` | *Permission denied* — the tree is invisible to her |
| `vera` can read her own clone | `sudo -u vera head -c 120 /srv/openclaw/vera/src/POS_AI/backend/app/routes/order.py` | the source came back |
| `vera` cannot write the clone | `sudo -u vera touch .../POS_AI/WRITE_TEST` | *Permission denied* |
| the clone is read-only for **everyone** | `touch /srv/openclaw/vera/src/.writetest` (as root) | *Read-only file system* |

**The destructive-git commands, tested one by one against the real clone:**

| Command | Exit | Message |
|---|---|---|
| `git clean -xfd` | 0 | no-op — the tree was already clean and the mount is `ro` |
| `git checkout -- .` | 128 | *fatal: Unable to create '.../.git/index.lock': Read-only file system* |
| `git reset --hard` | 128 | same |
| `git stash` | 1 | refused |
| `git restore .` | 128 | same |
| `git rm -rf .` | 128 | same |

After all six, the clone was still at `db381ac…`, still **597** tracked files, still
**zero** dirty files. `git clean` exiting 0 is not a hole: it had nothing to remove
and the read-only mount would have refused it anyway.

> **Why the destructive commands stay banned in the live tree.** In the live tree,
> `git clean -xfd` would remove **70** paths: every live `.env`, every live `*.db`
> including the WAL and SHM files, the built `admin/dist/` and `site/.next/` trees,
> and every `node_modules/`. That is a production outage in one command. Vera
> cannot reach that tree at all, so the hazard is **closed by construction** rather
> than by a rule.

**One practical wrinkle, and how it was handled.** Git refuses to operate on a
repository whose ownership differs from the invoking user (*"dubious ownership"*"),
and the clone is root-owned. Vera therefore gets her own git config at
`/srv/openclaw/vera/state/gitconfig`, with `safe.directory` set for the clone. It
contains no credential and grants no write access — `git log` works, `git clean`
still cannot write.

**Honest limitation, unchanged from v1.2.** A **session permission policy takes
precedence over the config** when one is present. So the OpenClaw config is
**defence in depth, never the primary boundary**. The primary boundary is the
**non-root execution identity plus the read-only bind mount**. If the OS-level
boundary is ever wrong, the prompt-level boundary is what is left — which is why
the OS boundary comes first.

```json

```

- **No restart was needed.** The change applies to the next turn of an existing
  session and to every session created afterwards; `openclaw agents list` reports
  the new model immediately.
- **It was verified live, not just written.** A spawned Vera subagent resolved and
  ran on `minimax/MiniMax-M2.7` (`modelApplied: true`), and a second probe returned
  `MODELPROOF minimax/MiniMax-M2.7` from inside the child session.
- **The image-capability trade-off is real, and the mechanism is documented rather
  than assumed.** `minimax/MiniMax-M2.7` is **text-only** (`input: ["text"]`); the
  former `minimax/MiniMax-M3.1-Flash` was `["text", "image"]`. Two separate things
  were checked, and they are easy to conflate:
  1. **Does the tool survive the switch?** Yes — `view_image` is still callable on
     the text-only primary, and it was **proved live**: on a `minimax/MiniMax-M2.7`
     session, `view_image` on a real PNG returned a correct description of the
     image. The tool is not gated off by the primary model's lack of vision.
     On Vera's own depth-0 surface `view_image` is a **deferred** tool — reached
     through `dispatch_action`/`tool_search` rather than called directly — so a
     screenshot read is always a second, separate model call (§5.5).
  2. **Which model actually reads the pixels?** Not the primary. The runtime's
     native-vision path is explicitly refused for a MiniMax primary that is not an
     `MiniMax-M3*` model, so `view_image` takes its **fallback route**: it resolves
     a separate image-capable model and calls *that*. The MiniMax extension
     registers exactly such a provider — a media-understanding provider with
     `capabilities: ["image"]`, `defaultModels: { image: "MiniMax-VL-01" }` and
     `autoPriority: { image: 40 }` — which is what makes the fallback resolvable
     here. The provider picks up the provider's own API key, which Vera already
     has, because she runs MiniMax models.
  **What this means for Vera:** reading a screenshot still costs an **extra model
  call to a different model**, and that call is a MiniMax VLM call — not something
  the primary `MiniMax-M2.7` does. Her QA flow still works; it is just no longer
  free. Note also that `MiniMax-VL-01` is **not** one of her configured fallbacks
  — the fallback chain (`M3.1-Flash` → `minimax-M2.5`) governs *agent turns*, not
  the image path, and the two must not be conflated. No explicit
  `agents.defaults.imageModel` and no `tools.media` config exists, so this is
  automatic provider resolution, not a pinned image model. If image-based QA ever
  becomes a hard requirement, an explicit image model should be configured and
  verified rather than left to auto-resolution.

**Three deviations from v1.2's proposed command, each for a concrete reason.**

- **`--role reviewer` was not used.** The bundled role templates would have seeded
  an `AGENTS.md`, a `SOUL.md` body and an `IDENTITY.md` — but `--role`, like
  `--agent-dir`, `--bind` and the interactive wizard, **holds exclusive state
  ownership and requires the Gateway to be stopped**. Vera was added with
  `--non-interactive --workspace` instead, which works against the running Gateway,
  and Lumi then **authored her four persona files directly** (`AGENTS.md`,
  `SOUL.md`, `IDENTITY.md`, `USER.md`) and removed the scaffolded `BOOTSTRAP.md`.
  The result is better anyway: v1.2's proposal was to *correct* a reviewer
  template into Vera, and writing her charter directly is clearer than correcting
  someone else's.
- **`--agent-dir` was not passed**, because the default OpenClaw chose is already
  the right one: `/root/.openclaw/agents/vera/agent`, root-owned and `0700`. A
  shared `agentDir` would mix two agents' credentials — the auth store is
  per-agent by design.
- **`--bind` was not used**, for the same Gateway-stopped reason. The binding was
  written afterwards with `openclaw config set bindings …` (see §5.5).

The fleet today is `main` (Lumi, workspace `/root/.openclaw/workspace`, model
`minimax/MiniMax-M2.7`, tool profile `full`), `heartbeat` (workspace
`/root/.openclaw/agents/heartbeat/workspace`, model `minimax/MiniMax-M2.7`) and
**`vera`** (workspace `/srv/openclaw/vera`, model `minimax/MiniMax-M2.7`).
Vera is the third agent, and the first with a **source-isolated, non-root-owned
workspace** and a **pinned tool policy**.

**One addition the design did not anticipate:** `main` cannot spawn `vera` unless
it is named. `sessions_spawn` refused with *"agentId is not allowed for
sessions_spawn (allowed: main)"*, because `agents.entries.main.subagents.allowAgents`
defaults to `main` alone. It is now `["main","vera"]`, so Lumi can delegate a QA
task to Vera and get her findings back — the intended division of labour, with the
delegation flowing *down* the permission gradient.


### 5.5 The tool policy — the part that decides whether this is safe

**This section is the reason the design changed after v1.0.** The mechanism is
real and per-agent, and the obvious choice is wrong.

**What was verified.** `agents.entries.<id>.tools` accepts `profile`, `allow`,
`alsoAllow`, `deny`, `fs`, `exec`, `sandbox` and more — all confirmed against the
live config schema. The fleet already uses the per-agent override: `main` carries
`tools.profile: "full"` while the global default is `coding`.

**The four built-in profiles, measured against the runtime:**

| Profile | Tools | `exec` | `read`/`write` | **`message`** | `gateway`/`plugins` |
|---|---|---|---|---|---|
| `minimal` | 3 | no | no | **no** | `gateway` only |
| `coding` | 55 | **yes** | **yes** | **NO** | yes |
| `messaging` | 21 | no | no | yes | `gateway` only |
| `full` | all | yes | yes | yes | yes |

**The trap.** The `coding` profile **does not contain the `message` tool** — the
`message` tool lives in the `messaging` profile. A Vera built on `coding` alone
would have been **silently unable to send the escalation message** that the entire
group-escalation design depends on. The failure would not have been an error; it
would have been a quiet agent that never posts, and the team would have read that
as "no failures tonight" rather than "the escalations never went out".

**The fix.** `coding` plus a narrow additive grant:

```json
"vera": {
  "workspace": "/srv/openclaw/vera",
  "agentDir": "/root/.openclaw/agents/vera/agent",
  "model": { "primary": "minimax/MiniMax-M2.7",
             "fallbacks": ["minimax/MiniMax-M3.1-Flash", "minimax/minimax-M2.5"] },
  "identity": { "name": "Vera" },
  "tools": {
    "profile": "coding",
    "alsoAllow": ["message"],
    "deny": ["apply_patch", "write", "edit"],
    "fs": { "workspaceOnly": true },
    "exec": { "host": "gateway", "mode": "allowlist" }
  }
}
```

**The `exec` line is new in v1.3, and it is the piece that turns "she should not
write product code" into "she cannot run a command that would".** See §5.6.

**Line by line:**

- **`profile: "coding"`** — gives `exec`, `read`, the web tools, memory, sessions
  and the automation tool. It is the narrowest profile that can actually run a
  test suite.
- **`alsoAllow: ["message"]`** — adds the one tool the escalation flow needs.
  `alsoAllow` is the correct mechanism: it is *merged on top of* the profile, and
  the runtime warns that configured tool sections *"no longer implicitly widen the
  profile"* and must be granted explicitly. Two different numbers matter here, and
  conflating them is how this kind of claim goes stale:
  - **Profile-level grants: 56.** The `coding` profile contributes 55 tool ids
    (counted from the runtime's own catalog) and `alsoAllow` adds `message` for
    56. This is the *resolved grant list* — a policy-resolution count, not a
    live-session count, and not comparable with the 48 below.
  - **Live depth-0 surface: 48 tools — 9 native and 39 deferred.** What Vera's
    running session actually exposes is smaller than the grant list, because
    `deny` and runtime availability gating remove tools from the surface after
    the grant list is resolved. Measured **directly on Vera's own depth-0
    session** (`agent:vera:main`, running `minimax/MiniMax-M2.7`) by asking the
    session to report its own tool schema:
    - **native, directly callable (9):** `dispatch_action`, `exec`, `ls`,
      `message`, `process`, `read`, `sessions_yield`, `tool_describe`,
      `tool_search`
    - **deferred, reached through `dispatch_action`/`tool_search` (39):**
      `agents_wait`, `ask_user`, `automations`, `conversations_list`,
      `conversations_send`, `conversations_turn`, `create_goal`, `dashboard`,
      `gateway`, `get_goal`, `github_identity_status`, `image_generate`,
      `intent`, `memory_get`, `memory_search`, `music_generate`, `plugins`,
      `portal`, `presence`, `progress_card`, `secrets`, `session_status`,
      `sessions`, `sessions_history`, `sessions_list`, `sessions_search`,
      `sessions_send`, `sessions_spawn`, `skill_workshop`, `skills_read`,
      `skills_search`, `subagents`, `terminal`, `theme`, `update_goal`,
      `video_generate`, `view_image`, `web_fetch`, `web_search`
    `message` is in the **native** list, so it is directly callable, not merely
    reachable through `exec` — the escalation path is unaffected.
  - The **48 is the authoritative number** for *"what can Vera actually call"*,
    and it was read off the live session rather than inferred. It still contains
    `message`, and it still contains no `openclaw`, no `nodes`, no `computer`, no
    `mobile_ui`. It also contains no `write`, no `edit` and no `apply_patch` —
    so the `deny` list is confirmed on the **live surface**, not merely present
    in the config.
  - ⚠️ **A number that was wrong, and exactly why it was wrong.** An earlier
    revision of this section claimed *"43 tools"*, with a native list of `exec`,
    `message`, `sessions_yield`, `view_image`, `wait`. That figure came from a
    `catalog.all()` call made inside an `exec` code-mode program, and that call
    enumerates the **code-mode bridge catalog** — the tools the bridge can
    reach — not the calling session's exposed surface. The telemetry proves the
    conflation: the bridge reported `visibleTools: ["exec","wait"]` and
    `codeModeEngaged: true`. So `exec` and `wait` in that old "native list" were
    bridge tools, and `wait` is not a session tool at all.
    A repeat of the identical `catalog.all()` program, run on M2.7 against a
    scratch state directory with a stub-only provider, returned
    `toolCount=40` with `has_view_image=false`, and its list contained `write`,
    `edit` and `apply_patch` — the three tools her `deny` list forbids — while
    omitting `message`. A list that includes the tools she is forbidden and
    withholds the one she needs is not her surface. The method also has no
    stable value to report: the same `catalog.all()` call returned **43**, then
    **40**, and the two depth-1 probes in §5.7 returned **28** and **32** — the
    number tracks the *run configuration*, not her policy, so it was never a
    sound proxy for her surface in the first place. **The session's own schema is
    the correct oracle, and it says 48.**
- **`deny: ["apply_patch", "write", "edit"]`** — **Vera cannot write product code
  through the file tools at all.** This is not a prompt; it is the tool policy
  refusing to offer the tool. Note the ordering: `deny` is applied *after* the
  profile and `alsoAllow` are merged, so it wins over the profile's grant of
  `write`/`edit`/`apply_patch`. Vera still gets `read` and `ls` — she must be able
  to inspect the code she is testing.
  - **Caveat, stated honestly:** `deny` removes the *tool*, not the *filesystem*.
    A determined command through `exec` can still write files, because `exec`
    runs a shell. This deny list is a strong second layer, not the boundary —
    the boundary remains the non-root identity and the read-only projection (§5.3).
    **Probed and sharpened (§5.6):** such a write is bounded by **uid 995**, not
    by root and not by this deny list. A top-level redirect is refused before
    dispatch; a nested one runs as `vera` and the kernel refuses it. A
    determined command can write inside the space the `vera` identity may write,
    and nowhere else.
- **`fs: { workspaceOnly: true }`** — per agent, so Lumi's posture is untouched.
- **`terminal` is present, and it is a write surface the advisory does not
  model.** Vera's live depth-0 surface (48 tools) contains `terminal`, which
  types into a shared operator terminal via its `input` action. It is bounded
  three ways: it only manages terminals an operator opened from the Control UI
  panel (none exist in a Telegram session), its `input` action requires
  **one-time operator approval** whenever the resolved exec policy mode is not
  `full`, and `allow-always` is an explicitly unavailable decision — so it can
  never be pre-authorised for unattended use. Worth stating because
  `openclaw doctor` does not count it: the `doctor.exec_filesystem_policy` check
  compares only `write`/`edit`/`apply_patch` against `exec`/`process` (§5.6).
- **Genuinely absent:** `openclaw`, `nodes`, `computer` and `mobile_ui` are not in
  the `coding` profile, so they are not in Vera's profile. She cannot delegate
  OpenClaw setup and repair, and she cannot drive a desktop or a paired node.
  An agent that can restart its own Gateway can defeat any boundary you put
  around it.

- **`gateway` and `plugins` are a correction, not a grant.** An earlier draft of
  this document claimed they were *"deliberately absent"* from `coding`. That was
  **false**, and it is corrected here because it is a security-relevant claim.
  Measured from the runtime catalog: the `coding` profile **does** contain both
  `gateway` and `plugins`. What actually protects Vera is not their absence but
  their *operational gates*, both confirmed by live read-only probes:
  - `gateway` exposes exactly one action, `update.run`, and the runtime
    describes it as requiring *"an explicit owner request or operator-scheduled
    update"*. It is not a general-purpose status or config reader.
  - `plugins` with `action="list"` returned `{"gated": true}` — the tool is
    present but gated, and the plugin-management path is a human-approved
    operation.
  - The genuinely load-bearing controls remain `deny` on the file tools and the
    non-root identity; `gateway` and `plugins` are a second layer, not the
    boundary (§5.6).

**Why not `full`?** `full` is `allow: ["*"]` — a wildcard, not a list, so the
difference from `coding` is everything `coding` leaves out. Concretely it adds
`openclaw` (*"Delegate OpenClaw setup and repair"*), `nodes`, `computer` and
`mobile_ui`, and it removes any reliance on the profile boundary for
`gateway`/`plugins` at all. An unattended agent that can delegate its own
reconfiguration is a self-modifying agent. The main agent has `full` because Lumi
is interactive and trusted; Vera is neither. Note that `gateway` and `plugins`
were *not* part of this argument even before the correction — they are present
in `coding` too.

**Why not `messaging`?** It has `message` but no `exec` and no `read` — she could
post to the group and nothing else. A tester who cannot run the tests is not a
tester.

### 5.6 The exec policy — why the tool policy alone was not enough

v1.2 already said, honestly, that `deny` removes the *tool* and not the
*filesystem*: *"a determined command through `exec` can still write files, because
`exec` runs a shell."* v1.3 closes that gap, and it turned out to need **two**
levers rather than one.

**Lever 1 — the exec mode is `allowlist`, not `full`.** The runtime distinguishes
these sharply: `security: "allowlist"` means *"run only allowlisted commands
without asking"*, while `security: "full"` means *"do not require an allowlist
match"*. With `askFallback: deny` (the default), a command that is not on the
allowlist is **refused**, not merely un-approved.

Vera's two allowlist entries are the two wrappers:

```
/srv/openclaw/vera/bin/vera-exec
/srv/openclaw/vera/bin/vera-issue
```

**The pattern form is not free choice — it was got wrong once and cost a full
verification cycle.** The allowlist matcher globs each pattern against the
**resolved executable path** of the command segment, not against the command
line. The intuitive entry `/srv/openclaw/vera/bin/vera-exec *` therefore matches
*nothing*: the resolved path is `/srv/openclaw/vera/bin/vera-exec`, and the
trailing ` *` can never be satisfied by it. An entry that matches no path is
silently inert — it does not error, it just never fires. The first attempt at
this verification therefore showed the two wrappers being refused with
`exec denied: allowlist miss` while unrelated built-in safe bins (`head`,
`tail`, `wc`, `test`, `pwd`) sailed through, which reads exactly like a
misconfigured allowlist rather than a wrong glob. The working form is the bare
resolved path, with no argument suffix:

```bash
openclaw approvals allowlist add --agent vera "/srv/openclaw/vera/bin/vera-exec"
openclaw approvals allowlist add --agent vera "/srv/openclaw/vera/bin/vera-issue"
```

Both entries now report `Last Used` in `openclaw approvals get`, which is the
cheap confirmation that a pattern actually fires — a never-matching pattern
never shows a use.

So Vera's shell is not "a shell that should not do bad things" — it is a shell
with exactly **two** commands in it, both of which are root-owned files that
cannot be edited by the identity running them. A plain `cat /etc/hostname` typed
by Vera is refused by the runtime before it reaches a shell.

**Lever 2 — the wrapper drops privileges.** `allowlist` restricts *which command
is run*; it does not change *who runs it*. The Gateway's `exec` runs as `root`.
So `vera-exec` is what makes the command run as `vera` (§5.3), and the two levers
compose: the allowlist decides *what* may run, the wrapper decides *as whom*.

**Verified end to end, with Vera herself as the actor** — not by reading the
config. Run as a real `vera` subagent against the live allowlist:

| Attempt | Expected | Observed |
|---|---|---|
| `vera-exec git -C …/src/POS_AI log --oneline -1` | allowed, prints the pinned SHA | **exit 0** — `db381ac Initial commit: POS AI platform (backend, website API, POS, customer app, sites)` |
| `vera-exec git -C …/mydoc/Projects/POS_AI log --oneline -1` (live tree) | denied by the OS | **exit 128** — `fatal: cannot change to '/root/.openclaw/workspace/mydoc/Projects/POS_AI': Permission denied` |
| `cat /etc/hostname` (no wrapper) | refused by the allowlist | **never executed** — `Error: exec denied: allowlist miss` |
| `cat …/POS_AI/backend/app/routes/order.py` (no wrapper) | refused by the allowlist | **never executed** — `Error: exec denied: allowlist miss` |

**The two denials are enforced by two different layers, and that distinction is
the point.** Steps 3 and 4 were refused by the **OpenClaw exec policy**, before
any process was spawned — no shell ever saw the command. Step 2 was *allowed by
the policy* (the wrapper is on the allowlist) and then refused by the **OS**,
because the wrapper had already dropped to the unprivileged `vera` identity and
`/root` is not traversable by it. Policy denied the command; the filesystem
denied the path. Both are needed, and neither alone would be sufficient: the
policy keeps an unwrapped command from being typed at all, while the privilege
drop is what keeps the wrapper's own arguments from reaching the live tree.

The live product tree was independently confirmed untouched after the run: still
at pinned `db381ac…`, zero dirty files.

**A third case was probed, because it is the one that could have broken the whole
model.** Everything above tests a *path*. It does not test a *shell construct*.
The Gateway's `exec` spawns as `[shell, …, command]`, so the command string is
evaluated by an outer shell running as **root** — and a redirection (`> file`) is
a shell construct that the outer shell would apply itself, before the wrapper
ever dropped privileges. If that were reachable, the entire two-layer argument
above would have been decoration.

It is not reachable, and it took two probes to establish that, because the two
shapes fail for two different reasons.

| Attempt | Expected | Observed |
|---|---|---|
| `vera-exec echo REDIR_PROBE > /root/vera-redirect-probe.txt` | the outer root shell would apply the redirect | **never executed** — `Error: exec denied: allowlist miss` |
| `vera-exec echo REDIR_OK > /srv/openclaw/vera/state/redirect-probe.txt` | same | **never executed** — `Error: exec denied: allowlist miss` |
| `vera-exec sh -c 'echo NESTED_PROBE > /root/vera-nested-probe.txt'` | the inner shell inherits uid 995; the kernel refuses | **exit 2** — `sh: 1: cannot create /root/vera-nested-probe.txt: Permission denied` |
| `vera-exec sh -c 'echo NESTED_OK > /srv/openclaw/vera/state/nested-probe.txt'` | writes inside her own workspace | **exit 0** — file created, owned `vera:vera` |

**Why the first two never ran at all.** The runtime's allowlist analysis
classifies a shell file-redirect as a construct it refuses to analyze (the
`redirect` risk kind), so the command cannot be matched against the bare-path
allowlist pattern and is refused before dispatch — the refusal is reported
verbatim as `exec denied: allowlist miss`. The outer root shell therefore never
gets to interpret the redirection.

**Why the third ran and still could not write.** Here the redirect is *inside* a
quoted argument, so the top-level command is still the allowlisted wrapper and
it is dispatched. But the nested shell inherits the identity the wrapper dropped
to — uid 995 — and the kernel refuses the write. The same construct aimed at
her own workspace succeeds, and the file is owned by `vera:vera`.

**So the honest version of the §5.5 caveat is sharper than the caveat itself.**
§5.5 says a determined command through `exec` can still write files, because
`exec` runs a shell. That is true, and the probe adds the missing half: such a
write is bounded by **uid 995**, not by root and not by the tool policy. A
determined command can write files — inside the space the `vera` identity may
write, and nowhere else. Two layers, two different mechanisms, same outcome.

Verified independently from `root` after the probes: zero `*probe*` files
anywhere on the host except the one inside `/srv/openclaw/vera/state`, which was
removed; the live product tree still at pinned `db381ac…` with zero dirty
files.

**The `doctor.exec_filesystem_policy` advisory, and why its generic fix is wrong
here.** `openclaw doctor --lint` reports one advisory against Vera's scope, and
it is worth documenting precisely because it is *correct as stated* and *wrong
as a remedy*. Its live values:

```
checkId: doctor.exec_filesystem_policy     severity: warn
scope:   agents.entries.vera.tools
Runtime tools: exec, process; disabled filesystem tools: write, edit, apply_patch.
Effective exec host is "gateway" with sandbox.mode="off" and workspaceAccess="none".
```

The check is a generic invariant: *if the three mutating file tools are all
denied but a runtime tool is available, that runtime tool can still write.* It
keys on **tool grants only** — `MUTATING_FS_TOOLS` (`write`, `edit`,
`apply_patch`) against `RUNTIME_TOOLS` (`exec`, `process`) — and it never looks
at the exec allowlist, the privilege drop, or the filesystem permissions. So for
Vera it is true and harmless: her entire `exec` surface is two root-owned
wrappers that drop to uid 995.

**It is advisory only.** `collectExecFilesystemPolicyWarnings` produces the
warning and nothing consumes it — there is no fixer path for this check id, so
`openclaw doctor --fix` will not change it. It will reappear on every lint run
until the design changes. That is the intended state, not an oversight.

**Neither half of the generic remediation may be applied:**

1. *"For read-only agents, also deny `exec`/`process`."* Vera is not a read-only
   agent; `exec` is her function. Denying it deletes the test harness and leaves
   a QA agent that cannot run tests.
2. *"otherwise use sandbox mode `all` with workspaceAccess `ro` or `none`."*
   This cannot work for Vera even if we wanted it. The check's own skip
   condition is `sandbox.mode === "all" && execHost !== "gateway" && execHost !==
   "node" && sandbox.workspaceAccess !== "rw"`. Vera's `exec.host` is
   `"gateway"`, so that skip can never fire for her and the warning would
   persist even under `sandbox.mode: "all"`. Independently, this host has no
   sandbox backend to honour it — `bwrap`, `firejail`, Docker and Podman are
   all absent (§9).

So the advisory is **accepted and left open**, and the residual risk is
recorded rather than silenced.

**What the advisory under-counts: `terminal`.** The check models exactly two
runtime tools, `exec` and `process`. Vera's live depth-0 surface also contains
**`terminal`**, which is a write-capable surface — its `input` action types
into a shared operator terminal — and the advisory never sees it. Three things
bound it, and they are worth stating because the advisory does not:

- `terminal` manages only terminals an operator opened from the Control UI
  panel, discovered via `list`. In a Telegram session there are none.
- Its `input` action is gated: when the resolved exec policy mode is not
  `full`, it requires **one-time operator approval**, and `allow-always` is
  explicitly listed as an unavailable decision — so it can never be
  pre-authorised for unattended use.
- `process` is scope-bound: its session filter is
  `!scopeKey || session?.scopeKey === scopeKey`, so Vera can only drive
  sessions started inside her own scope. It cannot widen what `exec` was
  allowed to start.

The accurate summary of Vera's write surface is therefore: `exec` is bounded by
an allowlist of two wrappers; those wrappers drop to uid 995; `process` cannot
widen the set of sessions `exec` may start; and `terminal` requires a human to
approve each input. The advisory is directionally right — `exec` *can* write —
and its remedy is wrong for this design, and it misses one tool.

### 5.7 The binding, the Telegram account, and the severity labels

`accountId: "vera"`. The runtime resolves in a fixed order — peer → guild/team →

match wins for her account and `main` keeps everything else. The exact-account
binding is listed **first** in the array as well, so the ordering is correct under

## 6. The live-database guard

**This section exists because it is the highest-consequence risk in the whole
proposal, and it is already latent in the current test scripts.**

### 6.1 What was found

- `backend/app/core/config.py` hard-codes
  `sqlite:////root/.openclaw/workspace/mydoc/Projects/POS_AI/database/pos_ai.db`
- `website_api/app/core/config.py` hard-codes
  `sqlite:////root/.openclaw/workspace/mydoc/Projects/POS_AI/website_api/website_api.db`
- **`website_api/scripts/test_promotion.py`** opens `website_api.db` with a plain
  `sqlite3.connect(ROOT / "website_api.db")` — **read-write** — and then runs
  `UPDATE plan_prices ...` and `UPDATE subscription_plans ...` and commits. It also
  promotes and demotes plans through the live admin flow
- **`website_api/scripts/test_newuser.py`** opens the POS database with a normal
  `sqlite3.connect` (not `mode=ro`) and contains **tenant deletion** logic, including
  cascade cleanup across roughly twenty tables
- Test inventory: **8** backend test files, **18** website API test files, and
  approximately **121** test/check/probe scripts under
  `/root/.openclaw/workspace/scripts`. `pytest` is **not installed**; `pip 24.0` is

**A testing agent pointed at these scripts would corrupt live tenant data.** This is
not hypothetical — `test_promotion.py` mutates live subscription pricing on every run.

### 6.2 The guard, in layers

**Layer 1 — OS identity (the real one).** Vera runs as `kens`. The live databases
live under `/root/...`, which `kens` cannot traverse. The write is **impossible at
the filesystem level**, not merely discouraged.

**Layer 2 — a sandbox copy, and only ever the copy.** Every test run gets fresh
copies:

```
cp pos_ai.db      /srv/openclaw/vera/sandbox/db/pos_ai.db
cp website_api.db /srv/openclaw/vera/sandbox/db/website_api.db
```

and the services under test are pointed at the copies.

**Layer 3 — the env override that makes it possible.** Both `config.py` files use
`pydantic_settings.BaseSettings`, so **`DATABASE_URL` is overridable by environment
variable** without editing a line of product code. The test harness sets:

```
DATABASE_URL=sqlite:////srv/openclaw/vera/sandbox/db/pos_ai.db
DATABASE_URL=sqlite:////srv/openclaw/vera/sandbox/db/website_api.db
```

This is the single most valuable finding for this design: **the live-DB risk can be
removed without touching product code**, which keeps the "no changes to product
code" promise intact.

**Layer 4 — the hard-coded scripts.** Some scripts bypass the config entirely and
hard-code the path. For those, the fix is a **wrapper that rewrites the path at
invocation time** (a copy of the script in the sandbox with the path substituted),
**never an edit to the original in the production tree**.

**Layer 5 — the nightly guard.** A root cron runs a checksum of the live database
files before and after every Vera run. Any change in mtime or hash raises a **P1
escalation** immediately.

### 6.3 The rule

> **Vera never opens the live databases. Not read-write, not to "just check
> something", not with a `mode=ro` URI as a shortcut — because `mode=ro` in one
> script is often the *first* half of a script whose second half writes.**

Read-only inspection of the live state is a **human** action, or a **separate,
explicitly authorised** read-only job with its own tool policy — never Vera's
default behaviour.

### 7.2 Change detection — how Vera knows something changed

**Changed in v1.2 — the source is now a Git repository.** The product source at
`/root/.openclaw/workspace/mydoc/Projects/POS_AI` is the root of its own repository:
remote `https://github.com/Kiens8/POS_AI`, branch `main`, **private**, first commit
`db381ac`, **597 tracked files** (verified live). The `mydoc/` tree is still excluded
from the *workspace* repository's `.gitignore`, so the two histories are separate and
the workspace index no longer carries a gitlink to it.

**This removes the reason the fingerprint manifest existed.** A commit diff is a
strictly better change signal than a path + mtime + size manifest: it is exact, it
is attributed, and it carries a message. The manifest survives only as a fallback
for the uncommitted edits that live in the working tree.

**Three detection signals, in order of reliability:**

1. **The git commit diff.** A new commit on `main` names exactly which files
   changed, and the changed files map to surfaces by directory: `backend/` → API,
   `website_api/` → Website API, `admin/` → Admin app, `frontend/` → POS frontend,
   `customer-app/` → Customer order app, `site/` → Site, `delivery/` → Delivery app
   (when it ships), `database/` → schema and seed. This is now the **primary** signal
   for *what* changed
2. **The `program-changes/` records.** The docs repo already carries per-surface
   change records. Each change to a surface is expected to add a record naming the
   surface, the nature of the change and the surfaces affected. Vera reads the
   newest record and derives the affected surface set. This remains **the
   authoritative signal for *intent*** — the git diff says what moved, the record
   says why and what it was supposed to do. The two are complementary, not
   competing
3. **A nightly full sweep regardless**, so a change that slipped past 1 and 2 is
   still caught the next day

**On `inotify`:** neither `inotifywait` nor `pyinotify` is installed, and the
product tree has roughly **2,938 files** (excluding `node_modules`, `.git` and
`*.db`) across about **432 MB** without `node_modules`; the committed source is
**597 files**. So a filesystem watcher is not proposed here — the git diff is
simpler, survives reboots, needs no new daemon, and needs no manifest file. If
inotify is wanted later, `pip install pyinotify` is the only dependency.

### 7.3 The regression run

**On demand (a change was detected) and nightly (a full sweep).**

Per run:

1. **Prepare the sandbox** — fresh copies of both databases into
   `/srv/openclaw/vera/sandbox/db/`, run as `kens`
2. **Point the services at the copies** — via the `DATABASE_URL` environment
   override (§6.2 Layer 3), on a **separate port set** so the running production
   services on `8000 / 9000 / 3001 / 5000 / 8080` are never disturbed
3. **Run the API suites** — the 8 backend test files and the 18 website API test
   files, via `pytest` (**not installed — `pip install pytest` is a prerequisite**)
   or via the existing standalone-script style
4. **Run the E2E harness** — Playwright against the sandbox ports:
   - admin app: login → outlet → menu → pricing → plan gate
   - POS frontend: order → discount → tax → payment → receipt
   - customer order app: browse → cart → checkout → online payment (Malaysia only)
   - delivery app: **skipped until it ships**
5. **Collect artefacts** — JUnit XML, screenshots, Playwright traces, and a
   `summary.md` verdict per surface
6. **Verify the live databases are untouched** — compare the live DB checksums
   against the pre-run baseline (§6.2 Layer 5)

### 7.6 The trigger mechanics

OpenClaw's automation support (cron, stream, condition-watcher, webhook, hook) and
`openclaw automations add` were both verified. Relevant flags:
`--name`, `--cron`, `--tz`, `--message`, `--script`, `--script-timeout-seconds`,
`--session`, `--tools`, `--model`, `--to`, `--keep-after-run`, `--trigger-once`.

**The proposed jobs:**

| Job | Schedule | Type | Tools | Delivers to |
|---|---|---|---|---|
| **Nightly full regression** | `30 23 * * *` Asia/Kuala_Lumpur | cron, agent `vera` | `--tools "exec read"` | Vera's own log + group only on failure |
| **Change-triggered regression** | on a change record lands | condition-watcher, agent `vera` | `--tools "exec read"` | same |
| **Sandbox refresh + live-DB integrity check** | `0 0 * * *` Asia/Kuala_Lumpur | **command payload**, no agent | — (runs `sh -lc`) | P1 to the group on any change |
| **Doc drift check** | `0 4 * * *` Asia/Kuala_Lumpur | cron, agent `vera` | `--tools "read exec"` | Drift report, no ping |
| **Weekly full sweep** | Sunday `0 3 * * 0` | cron, agent `vera` | `--tools "exec read"` | Summary to the group |
| **Issue intake → Lumi** | every 10m | cron, agent `main` | `--tools "exec read"` | The issue link in the group; the fix itself is an attended session on `main` (§7.7) |

**Two constraints on unattended runs, both from the verified facts:**

1. **Automation jobs inherit the owning agent's tool policy.** An unattended agent
   with `exec` and a loose policy is exactly the shape of accident we are trying to
   prevent. There are now **two real, verified levers**, and the proposal uses
   both:
   - **Per-job tool allow-list.** `openclaw automations add --tools <list>` takes
     an explicit list (e.g. `--tools "exec read"`, and `""` disables all tools).
     This is the tighter of the two, because it is scoped to the job rather than
     to the agent. Vera's nightly regression gets `--tools "exec read"` — enough
     to run the harness and read the results, and nothing else.
   - **Per-agent exec allowlist.** `openclaw approvals allowlist add --agent vera
     "<glob>"` pins the *commands* that may run unattended — the test runners,
     the Playwright invocation, the copy script — and nothing else. The glob
     syntax is supported (`~/Projects/**/bin/rg` is the documented example), and
     `--agent "*"` applies one rule fleet-wide.
   - **A blanket `exec` allowance is not acceptable for an unattended agent.** The
     exec allowlist is the belt to the `--tools` braces.
   - **The allowlist must also cover issue filing.** Vera files issues against the
     GitHub REST API, but **not** by calling `curl` through `exec` — `curl` is not
     on the allowlist and must not be. The allowlist pins the **root-owned
     `vera-issue` wrapper** (`/srv/openclaw/vera/bin/vera-issue`) as the second
     and last entry, and that wrapper is what performs the REST call with the
     operator's credential (§7.7). The `gh` CLI is not installed on this host.
     The two allowlist entries are therefore exactly the two wrappers, and
     nothing else (§5.6).
2. **The root-privileged jobs must not run as the agent at all.** The live-DB
   integrity check, the sandbox database copy and the source refresh are **command
   payloads**, not agent jobs: `--command "<shell>"` runs `sh -lc <shell>` on the
   Gateway, with `--command-cwd` and repeatable `--command-env` for the
   environment. That keeps them **root-owned and out of the agent's tool policy
   entirely** — there is no model in the loop to widen their permissions, because
   there is no model in the loop at all. This is strictly better than asking an
   agent to run them.

The runtime constraint from §5.3 applies here with full force: because `kens`'s own
`sudo` requires a password while root can run `sudo -u kens` non-interactively,
**the root-owned command payloads run as root, and they drop to `kens` explicitly
where the sandbox work needs it** — `sudo -u kens -H <harness command>`. That
keeps the file copies owned by the identity that will actually read them.

The existing automations are `heartbeat:heartbeat` (every 30m, agent `heartbeat`),
`memory-core:memory-dr...` (cron `0 3 * * *`, agent `main`) and `Daily OpenClaw DB
Backup` (cron `30 4 * * * @ Asia/Kuala_Lumpur`, agent `main`). Vera's jobs are
proposed to run in the gaps — the nightly window of 02:00–04:30 is currently taken
by the memory and backup jobs, so **02:00 is a poor choice** and Vera's nightly
regression is proposed for **23:30** instead, with the integrity check immediately
after it.

### 7.7 The issue → fix → verify loop

**This is the change v1.2 makes to the trigger.** Previously the only way out of a
failed regression was an escalation *message* to a Telegram group: a human read it
and decided what to do. A repository turns that message into a **tracked work item**
with an owner, a state and a diff, and it gives the fixer — `main`, the agent that
is allowed to write product code — something concrete to work from that is not a
chat message.

**The contract:**

1. **Vera files the issue.** On a P1–P3 failure she creates an issue in
   `Kiens8/POS_AI`, labelled by severity (`vera:p1`, `vera:p2`, `vera:p3`), with the
   §4.3 escalation format as the body — so the issue and the Telegram message carry
   identical content and no information exists in only one of them. The issue title
   names the surface and the symptom. Vera never edits product code; the issue *is*
   the fix request
2. **The group is still told.** P1 and P2 are posted to the group immediately, now
   with the issue link; P3 is batched hourly, as before. The issue is the record; the
   group is the alarm
3. **Lumi picks it up.** `main` polls the repository's open issues for the `vera:*`
   labels and takes the oldest unclaimed P1/P2 first. It reproduces the failure
   against the same sandbox the regression used (§6.2 Layer 3), fixes the source,
   and **verifies the fix with the same suite that failed**
4. **The fix is a reviewable artefact.** The change lands on a **branch with a pull
   request** against `main`, not as a bare commit to `main`, so the diff that fixed
   a tenant outage is reviewable after the fact
5. **The deploy is a separate step.** Merging to `main` and restarting the affected
   pm2 service is the deploy, because **the live tree is the repository checkout**
   (§5.3). That step is deliberately **not** part of the unattended loop
6. **Vera re-verifies.** After the deploy she re-runs the failing suite. Only a
   green re-run closes the issue, and she comments the result on it. A fix that
   does not turn the suite green does not close the issue

**How `main` learns about the issue.** Two mechanisms are possible and they are not
equivalent:

- **Polling (proposed).** A cron job reads the repository's open issues through the
  GitHub REST API and acts on the ones carrying a `vera:*` label. Everything stays
  on the host, no endpoint is exposed, and the cost is the polling interval. This
  is the mechanism the v1.2 job table assumes
- **A GitHub webhook into the Gateway (not available today).** OpenClaw supports
  inbound webhook hooks — a `hooks` block with `enabled`, a dedicated `token`, a
  dedicated `path` and an `allowedAgentIds` allow-list, authenticated with
  `Authorization: Bearer <token>` — and they are the right shape for a push
  trigger. **But the Gateway currently binds to loopback** (`127.0.0.1:18789`,
  verified live), so GitHub cannot reach it, and `hooks` today holds only the
  `internal` entries. A webhook trigger therefore needs a deliberate exposure
  decision from Kens, and it is not proposed

**The credential: v1.2 was wrong about this, and v1.3 corrects it.** v1.2 said the
stored PAT "returns 403 *Resource not accessible by personal access token* on the
issues API for that repository, even though it holds `triage` and `admin` on the
repository itself", and concluded that a **separate, Issues-scoped token** was
required.

**That conclusion was wrong, and so was the reasoning behind it.** `triage` and
`admin` are *repository roles*, not *token scopes* — mixing them up is what
produced the wrong answer. The real cause of the 403 was a single missing grant:
**Issues: read and write on `Kiens8/POS_AI`**. Once Kens added that grant to the
**existing** PAT, the same credential works for everything, verified live:

```
GET /repos/Kiens8/POS_AI/issues  -> 200
GET /repos/Kiens8/POS_AI/pulls   -> 200
GET /repos/Kiens8/POS_AI/labels  -> 200
```

**There is no second token, and none is needed.** The stored credential stays in
`/root/.git-credentials` (mode `0600`, root-only, outside both repositories), and
the root-owned `vera-issue` wrapper reads it at run time, uses it, and never
persists or prints it.

> **One detail that cost a debugging cycle, recorded because it will bite again.**
> The credential store holds the token as the **password** field of
> `https://<user>:<PAT>@github.com` — **not** as the username. An extraction that
> takes the username returns a valid-looking string that authenticates as **401
> Bad credentials**. The wrapper now takes the password field, with a fallback for
> a single-token store entry.

**How Vera files an issue without ever seeing the credential.** She cannot read
`/root/.git-credentials` (mode `0600`, owned by `root`, and `/root` itself is
`0700`), and she must not be able to. The credential never leaves the root-owned
wrapper: `/srv/openclaw/vera/bin/vera-issue` is `0755 root:root`, refuses to run as
anyone but root, reads the PAT at run time, POSTs to the GitHub API, prints only
the issue URL and number, and discards the token. Vera calls it as one of her two
allowlisted commands.

**Proven live.** The wrapper filed issue **#1** against `Kiens8/POS_AI` with the
`vera:p3` label — a real defect found by reading the pinned clone (the
`allow_delivery` default disagrees across five layers of the stack, §12) — and
returned:

```
https://github.com/Kiens8/POS_AI/issues/1
1
```

## 8. Failure modes and the honest risks

| Risk | Severity | Mitigation |
|---|---|---|
| **A test script writes to a live database** | Critical | Non-root identity + copy databases + `DATABASE_URL` override + checksum guard (§6) |
| **A regression run disturbs production** | Critical | Dedicated sandbox ports; production ports (`8000/9000/3001/5000/8080`) are never touched |
| **An unattended agent misuses `exec`** | High | Per-job `--tools` allow-list + per-agent exec allowlist limited to the harness commands; no blanket `exec`. **Probed live**: a top-level shell redirect is refused before dispatch (`exec denied: allowlist miss`), and a redirect nested inside the wrapper runs as uid 995 and is refused by the kernel (`Permission denied`) — so a determined command can write only where the `vera` identity may write (§5.6) |
| **`doctor.exec_filesystem_policy` fires on Vera's scope** | Low | Accepted by design and left open — advisory only, no fixer, so it reappears on every lint. Its generic remedy is wrong here: denying `exec`/`process` would delete the test harness, and `sandbox.mode: "all"` cannot silence it for a `gateway`-hosted exec and has no backend on this host (§5.6) |
| **Vera cannot send the escalation** | High | `message` is **not** in the `coding` profile — it must be added via `alsoAllow` (§5.5). **Live-proven**: Vera's depth-0 session sent to group `-5583541067` and returned `{"ok": true, "messageId": "10", "chatId": "-5583541067"}`. Note the limit — a **depth-1 subagent cannot send it** (§5.7); escalation must originate from the depth-0 session |
| **Vera reconfigures the Gateway or reloads plugins** | High | `openclaw` is genuinely absent from `coding` (§5.5). `gateway` and `plugins` **are** present in the profile — the protection is their operational gates, confirmed by live probe: `gateway` exposes only `update.run` (owner-request or operator-scheduled), and `plugins` returns `{"gated": true}` |
| **Doc drift goes unnoticed** | Medium | Nightly drift check against the fingerprint manifest |
| **Vera publishes unreviewed public text** | High | Publishing is a separate human-approved step (§7.4) |
| **Escalation spam** | Medium | Group is escalation-only; severity gates the ping; P4/P5 never ping |
| **The `/srv` layout is adopted but the identity is not** | Critical | The identity change is the boundary; without it the layout is decoration |
| **Browser cache drift** | Low | One shared cache path, pinned Playwright version `1.64.1` |
| **Escalation to a wrong or unknown group id** | Medium | Group id is a required input before any job is created |
| **An unattended fix edits production source** | High | The intake job is read-only; the fix is an attended session on `main`, and the deploy (merge + restart) is a separate human-approved step (§7.7) |
| **A destructive git command runs in the live tree** | Critical | `git clean -xfd` there removes 70 paths including every live `.env` and `*.db`; the destructive commands stay banned (§5.3) and Vera works on a clone |
| **Vera's issue credential leaks** | Low | The PAT never leaves the root-owned `vera-issue` wrapper: it is read at run time, used, and discarded, and Vera cannot read `/root/.git-credentials`. There is **no second token** to leak — the same credential the workspace already uses, with its Issues grant (§7.7) |
| **Vera runs a command she was not meant to** | Low | `exec.mode: allowlist` with exactly two entries — the two wrappers — and `askFallback: deny`, so anything else is refused by the runtime before a shell sees it (§5.6) |
| **The `vera` identity is given shell access elsewhere** | Low | `vera` has `/usr/sbin/nologin`, a locked password, no home directory, and no membership of any privileged group. It exists only to be a filesystem identity (§5.2) |
