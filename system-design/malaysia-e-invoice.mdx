## Overview

Malaysia's e-Invoice mandate is live. **No industry is exempt** — restaurants included ✓.
This document is the plan for making the POS an e-Invoice-compliant ERP for our Malaysian
customers: the tax invoice the guest asks for at the counter, and the monthly consolidated
e-Invoice that covers the walk-in sales nobody asked a receipt for.

Two things make this a POS problem and not an accounting problem:

1. **The volume is per transaction.** A restaurant serving 200 covers a day would need 200
   validated e-Invoices a day ✓. LHDN's answer is the **consolidated e-Invoice**: one
   document for all the B2C sales of a **month** ✓.
2. **The clock starts at the table.** The guest asks for a tax invoice *while the coffee is
   still hot* ✓. If the POS cannot produce one at the counter, the restaurant sends someone
   to LHDN's portal by hand — and then does not buy a POS that cannot do it ✓.

### The shape of the solution

```
the order is paid
   ├── the guest did NOT ask for a tax invoice → a normal receipt
   │      └── the sale joins the MONTHLY CONSOLIDATED e-INVOICE (locked on the 1st,
   │             submitted by the 7th of the next month)
   ├── the guest DID ask for a tax invoice → an INDIVIDUAL e-INVOICE
   │      ├── the guest gave a TIN → validate it (once, then cache it) → the document
   │      │      carries the buyer's details
   │      ├── the guest gave a name or an id but no TIN → Search Taxpayer's TIN
   │      ├── the guest gave only a MyKad / MyPR / MyKAS → the General TIN + the id number
   │      ├── the guest gave only a passport (a foreigner) → EI00000000020 + the passport
   │      └── the guest gave nothing → they get a receipt, and the sale is consolidated
   └── the guest asks LATER (within the month, before the batch lock) → the order leaves
          the batch and is invoiced individually (the retro-request)
```

| Annual turnover / revenue | Mandatory from |
|---|---|
| Above RM100M | **1 Aug 2024** ✓ |
| RM25M – RM100M | **1 Jan 2025** ✓ |
| RM5M – RM25M | **1 Jul 2025** ✓ |
| Up to RM5M (operating in FY2022) | **1 Jan 2026** ✓ |
| RM3M+ and started 2023–2025 | **1 Jul 2026** ✓ |
| Started 2026 onwards | 1 Jul 2026 or the commencement date ✓ — the **second-year rule** applies if the first-year revenue is expected below RM3M ✓ |
| **Below RM3M** | **exempt** ✓ — unless a shareholder, holding company, related company or joint-venture partner with a turnover of at least RM3M pulls them in ✓ |

**Phase 4 (up to RM5M) has a relaxation period until 31 December 2027; full enforcement
from 1 January 2028** ✓. And the **SVDP** (Special Voluntary Disclosure Programme) lets
missed or erroneous e-Invoices be **back-filed without penalty** from 7 July 2026 to
31 December 2027 ✓ — using the **"SVDP 1.2"** (unsigned) or **"SVDP 1.3"** (signed)
document versions ✓.

> **Read this before selling it.** Most of our restaurant customers are **under RM3M and
> therefore exempt** ✓. The e-Invoice is not a compliance deadline for them — it is a
> **differentiator** for the chains that cross RM3M ✓, for the ones growing towards it ✓,
> and for the ones whose *customers* (corporate accounts, hotels, canteens) demand an
> e-Invoice from them ✓. Sell it as readiness, not as a threat ✓.

**No sector is exempt** ✓ — the tourism, hospitality and F&B industries are in scope like
everything else ✓. The F&B-specific guidance is about *how* (the consolidated mechanism ✓),
not *whether* ✓.

## How MyInvois works

The POS becomes an **ERP client** ✓. LHDN does not push invoices at us — we push documents
at LHDN and they validate them ✓.

1. **Authenticate.** OAuth 2.0 client credentials against the identity service → a bearer
   token valid for **60 minutes** ✓.
2. **Submit.** One or more documents, each a **base64-encoded UBL 2.1 JSON** plus its
   **SHA-256 hash** and a **code number** (our reference) ✓. The API answers **202** with a
   `submissionUID` and the accepted/rejected document IDs ✓ — *accepted*, not *valid* ✓.
3. **Wait.** Validation is asynchronous ✓. We poll **Get Submission** until the submission
   is `valid` or `invalid` ✓ — and the **notifications** tell us the same thing without
   the polling ✓ ✓. In practice the validated document comes back in **under two
   seconds** ✓ (the guideline's own POS flow ✓).
4. **Show.** A valid document gets a UUID ✓; the receipt carries the **validation QR we
   draw from that UUID** ✓ so the guest can check it themselves ✓.

> **The rate limit is per Client ID** ✓ — and **in the intermediary model that is one
> bucket for every tenant** ✓ (we hold one credential ✓). So the claim "a busy tenant
> cannot starve another one" is **false** in the model we recommend ✓ → the worker needs
> a **fair queue** ✓: one in-flight submission per tenant, round-robin between the
> tenants, and a per-tenant daily cap ✓. *In the **direct** model each tenant has its
> own Client ID ✓ and the isolation is free ✓ — that is a real argument for the direct
> model for the big chains ✓.*

> **The receipt's validation QR is ours to draw ✓** — there is **no API** that returns
> it ✓. The General Guideline v4.8 §2.4.4 ✓ says the *supplier* *"embeds a QR code which
> contains a **validation link** to the visual representation of the validated e-Invoice"*
> ✓ — so we build the QR from the document's **UUID** ✓ (a MyInvois validation URL ✓)
> and print it on the receipt ✓. The SDK's "Taxpayer's QR Code" API ✓ is a different
> thing entirely ✓ (it reads a business's own QR ✓).

### Two ways to be connected — and which one we pick

| | **Direct** (the tenant's own ERP credentials) | **Intermediary** (our platform) |
|---|---|---|
| The credentials | each tenant holds their own `client_id` / `client_secret` ✓ | **we** hold one set ✓ |
| The onboarding | every tenant registers with LHDN and authorises their ERP ✓ | every tenant authorises **us** as their representative ✓ |
| Our effort per tenant | high — registration, credentials, testing ✓ | low — one authorisation per tenant ✓ |
| The risk | the tenant's key sits in our database ✓ | we are on the hook for every tenant's document ✓ |
| Fits | the big chains with their own ERP ✓ | **the long tail — our customers** ✓ |

> **We are a "non-Peppol technology provider"** ✓ (General Guideline v4.8 ✓, Table 2.1 ✓) — the model
> the market's integrators use ✓. **Recommendation: the intermediary model** ✓ — one LHDN
> credential for the platform ✓, one authorisation per tenant ✓, and the tenant's own
> credentials stay theirs ✓. The **direct model** is the fallback for a chain that insists
> on holding its own key ✓ (or for a tenant that runs its own ERP next to our POS ✓).

## The document we build

**UBL 2.1 JSON** ✓, `Invoice` version **1.0** (no digital signature) or **1.1** (signed) ✓.
**Start with 1.0** ✓ — the only difference between them is the signature, and a signature
is a whole project on its own ✓. 1.1 is the target once the pipeline is proven ✓.
**But v1.0 is on borrowed time** ✓ — the SDK says *"v1.0 … will be deprecated and replaced
by version 1.1 at a later date that will be announced later"* ✓ → the signing work is
**not** a Phase 5 luxury ✓, it is a **migration with a deadline we do not know yet** ✓ →
the certificate / PKI lead time has to start early ✓ ✓. The SVDP versions are **v1.2
(unsigned)** ✓ and **v1.3 (signed)** ✓ ✓ — note the SDK's numbering ✓, and the guideline's
"**SVDP 1.2**" ✓ / "**SVDP 1.3**" ✓ ✓ — they are the same documents ✓.

#### The tax model — one tax category is not enough ✓

A restaurant's bill is not one tax ✓. The food is **sales tax 6%** ✓ (`01` ✓) and the
**service charge** is **service tax 5%** ✓ (`02` ✓) ✓ — and in some states a **tourism
tax** ✓ (`03` ✓) applies ✓. So the invoice carries **one `TaxSubtotal` per tax category**
✓ — UBL allows several ✓ — and the mapping above's single `TaxSubtotal` row is the
**simple case** ✓ (a food-only order ✓).

**The money rules (decided once, applied everywhere ✓)**
- **Prices are tax-inclusive** ✓ (that is how a Malaysian menu is written ✓) → the line
  amount is the **gross** ✓ and the taxable base is `amount / 1.06` ✓ (or `/ 1.05` ✓ for
  a service-charge line ✓).
- **Round per line to 2 decimals** ✓, then **the invoice's tax is the sum of the lines'
  tax** ✓ — the remainder never floats between the line and the total ✓.
- **`LegalMonetaryTotal` must tie** ✓: `TaxableAmount + TaxAmount = PayableAmount` ✓ per
  tax category ✓ and the categories sum to the invoice total ✓.
- **The VAT regime replaces SST** ✓ — the tax type codes change with it ✓ → the tax type
  is read from the **seeded table** ✓, never hardcoded ✓ (open question 4 ✓).

> **The two codes I had wrong** (checked against the SDK's own samples ✓): the country is
> **`MYS`** with `listID: "ISO3166-1"` ✓ — not `MY` ✓; and the tax scheme is **`OTH`** with
> `schemeID: "UN/ECE 5153"` ✓ — not `SST` ✓.

| e-Invoice types | `01` invoice, `02` credit note, `03` debit note, `04` refund note, `11`–`14` self-billed ✓ |
| Currency | `MYR` ✓ — and the **exchange rate** when it is not ✓ |
| Unit of measurement | UN/ECE Rec 20 ✓ — `C62` (one) ✓, `EA` (each) ✓, `H87` (piece) ✓, `KGM` (kilogram) ✓ |
| Country | `MYS` ✓ |
| State | the 14 states + 3 federal territories ✓ (`CountrySubentityCode`, e.g. `10` ✓) |
| Payment modes | `01` cash … `08` others ✓ |
| Classification / MSIC | the item's classification code ✓ and the restaurant's MSIC code ✓ |

Every one of these is validated by the **Code Validator** ✓ — a wrong code is a rejected
document, not a warning ✓. The tables are **seeded into the backend from the SDK's JSON
files** ✓ — never typed by hand ✓.

### The validators we will meet

| Validator | What it rejects | How we stay out of trouble |
|---|---|---|
| Structure | the document does not match the version's schema ✓ | build the JSON from the **Get Document Type** schema ✓, and validate it locally before sending ✓ |
| Core fields | the mandatory fields are missing ✓ | the buyer always has a name, an address and a contact number ✓ |
| Taxpayer | the seller/buyer TIN is invalid at the issue date ✓ | validate the buyer's TIN **when it is saved** ✓, not at the counter ✓ |
| Referenced documents | a credit note points at an invalid invoice ✓ | the credit note carries the original's UUID ✓ (`BillingReference` ✓) |
| Code | a code is not in the table ✓ | the code tables are **seeded** ✓ — **the DuitNow payment mode (`03` vs `06` ✓) is still open** ✓, so it must be **seeded, not guessed** ✓ |
| **Duplicate document** | the same `codeNumber` submitted twice ✓ | the code number is immutable and unique per taxpayer ✓ — a retry **never** changes it ✓ — **and a rejected document is never "fixed and resubmitted"** ✓: the payload is immutable too ✓ → the correction path is the **credit / debit / refund note** ✓, or a **new document with a new code number** ✓ (see the correction strategy ✓) |
| **Currency** | the wrong currency / a missing exchange rate ✓ | **only MYR outlets may submit** ✓ — see below ✓ |

> **The currency validator is a real constraint on us.** Demo Cafe 1 bills in **USD** ✓ and
> Kens SS17 in **RM/MYR** ✓ — and they are the **same tenant** ✓. MyInvois is a Malaysian
> system ✓: a USD invoice either fails the currency validator or needs an exchange rate and
> a foreign currency code ✓. **The rule: an outlet submits e-Invoices only when its
> `currency_code == "MYR"`** ✓. The USD outlet keeps its receipts ✓; the MYR outlet gets the
> e-Invoices ✓. The tenant-scoped design makes this a per-outlet flag, not a per-tenant one ✓.

## The three flows

### A. The individual tax invoice (on request)

```
the guest asks for a tax invoice at the payment
   → the payment panel shows a "Tax invoice" toggle + the buyer's fields (Table 3.1)
   → the guest's TIN is resolved: a TIN they know → Validate Taxpayer's TIN
     a name or an IC they know → Search Taxpayer's TIN (by name, or idType + idValue)
     both are cached per tenant (with a TTL — see below)
   → the order is marked e_invoice_requested = true
   → the order is queued for submission
   → the worker builds the UBL JSON, submits it, polls the submission
   → the validated document comes back (in practice, under 2 seconds ✓)
   → the receipt carries the validation QR we drew from the document's UUID ✓
```

**The counter interaction may take up to 60 seconds** ✓ (the guideline's own POS flow ✓) —
so asking the guest for their details at the table is the intended design ✓, not an
excuse ✓.

**The TIN cache ✓** — the SDK says validate **once**, at the moment the buyer is recorded ✓
(*"it is advised to perform validation of buyer's TINs when the buyer entity is being
defined" ✓*), and *"not … before every document submission"* ✓ (the calls would be
throttled ✓). So ✓
- the cache is keyed by **(tenant, TIN or idType+idValue)** ✓,
- it has a **TTL** (30 days ✓) — because the Taxpayer Validator checks the taxpayer's
  validity **at the date of issuance** ✓ ✓,
- and a **rejected** document that failed the Taxpayer Validator triggers a
  **re-validation** ✓ (never a blind retry ✓).

**A guest usually does not know their TIN ✓** — they know their **name** and their **MyKad
/ MyPR / passport number** ✓. `Validate Taxpayer's TIN` needs a **TIN in the path** ✓, so
the counter needs **Search Taxpayer's TIN** ✓ (by taxpayer name ✓, or by
idType + idValue ✓) ✓ — otherwise the flow dies at step two ✓.

**The guest must never be told it is done when it is not** ✓. If the validation is slow or
LHDN is down ✓, the receipt prints with the reference and the status ✓ and the document
arrives later ✓ (the reprint ✓). The POS shows the validated document **to the cashier** ✓
— that is the guideline's flow ✓.

### B. The retro-request (the guest asks later)

**§3.6.8** ✓ — the buyer may ask for an e-Invoice **any time within the month of the
transaction** ✓. That is exactly the window the monthly batch needs ✓.

So the POS needs a **"request an e-Invoice for a past order"** path ✓:
- from the **order history** ✓ (the manager searches the order ✓ and issues the invoice ✓)
- or from the **customer portal** ✓ (the loyalty guest finds their order ✓ and requests it ✓) ✓ — this is a nice fit for the customer portal we already have ✓ — **but the portal must prove the guest owns the order** ✓ (the PWA pattern ✓): `table_uuid` ✓ or `dining_customer_id` ✓ — otherwise anybody can request an invoice for somebody else's order ✓
- the order **leaves the monthly batch** ✓ and is invoiced individually ✓
- the request after the month-end is too late ✓ — the POS says so plainly ✓ (the guideline
  says the supplier **may** deny a late request ✓ — Example 5 ✓)

#### The race the doc must answer: the batch lock ✓

The buyer's right ends with the month ✓ (§3.6.8 ✓ — *"within the month of the
transaction"* ✓, Example 5 ✓: a request on 1 October for a 30 September purchase is
**late** ✓) — but our **batch** runs on ✓. So the two clocks must be lined up ✓:
**the buyer's window ends at the month-end ✓, our batch locks on the 1st ✓** — the very
same moment ✓ ✓.

**The rule ✓**
- The batch is **built and locked on the 1st** ✓ (the period's last day + 1 ✓) — which is
  exactly when the buyer's retro-request right expires ✓ ✓.
- The **locked** batch is submitted by the **7th** ✓ (§3.6.2 ✓) ✓ — the **submission**
  and the **request window** are two different clocks ✓, and only the first one is
  seven days long ✓ ✓.
- A request that arrives **after the lock** → the POS says plainly: *"this sale is already
  in the monthly consolidated e-Invoice"* ✓ and offers the **consolidated document's
  reference** ✓ — not a second invoice ✓ (and a second e-Invoice for the same sale would
  be a **duplicate** ✓ — the Duplicate Document Validator ✓ — and simply wrong ✓) ✓.

### C. The monthly consolidated e-Invoice

- Every order that was **not** individually invoiced joins the month's batch ✓.
- The batch is **built and locked on the 1st** ✓ and **submitted within 7 calendar days
  after the month-end** ✓ (§3.6.2 ✓) — by the **7th** ✓.
- **The consolidation method is ours to choose** (§3.6.3 ✓):
  - **(a) each receipt's summary as a separate line item** ✓ — the clearest for a reviewer ✓
  - **(b) the receipts as line items in a continuous receipt-number chain** ✓ — the
    smallest document ✓ (a break in the chain starts a new line ✓)
  - **(c) per branch or location** ✓ — **each outlet submits its own consolidated
    e-Invoice** ✓ ✓ — which is the natural fit for our multi-outlet tenant ✓
- **The receipt reference number must be on every line** ✓ (Table 3.5 ✓) — **in the
  *"Description"* field** ✓ — our order number is the audit trail ✓.
- **The buyer is `General Public` / `EI00000000010`** ✓ and the rest is `NA` ✓
  (**Table 3.5** ✓ — not Appendix 2 ✓).
- **The limits**: 5MB per submission ✓, 100 e-Invoices per submission ✓, 300KB per
  e-Invoice ✓ — so a busy month is **split into several documents** ✓ (§3.6.4 ✓).
- **Never consolidated**: a transaction above **RM10,000** ✓ (its own e-Invoice ✓ — **unless
  the outlet is inside the relaxation period** ✓, see below ✓), a **buyer we know is a
  business** ✓ (a B2B sale ✓ — see below ✓), and the industries in Table 3.6 ✓.

#### The relaxation switch ✓ (§16.2 ✓)

The RM10,000 rule and the Table 3.6 industries **do not apply** during the **interim
relaxation period** ✓ — and for **Phase 4 (up to RM5M) that period runs until
31 December 2027** ✓ (Table 16.1 ✓) ✓ — i.e. **for the customers we are actually selling
to** ✓.

**So the outlet setting ✓**
- `relaxation_until` ✓ — the tenant's own phase and its relaxation end date ✓ (the tenant
  declares its turnover ✓ — **we never compute an exemption for it** ✓).
- While the tenant is inside the window ✓ → the RM10,000 guard is **off** ✓ and the
  Section 3.7 industries are **not** blocked ✓ (§16.2(a) ✓).
- After the window ✓ → the guard is **on** ✓ (1 Jan 2028 for Phase 4 ✓) ✓.

**And §16.2(d) ✓** — during the relaxation period a supplier **may decline** an
individual request ✓. **We do not** ✓ — we issue the individual e-Invoice anyway ✓ (the
buyer gets a better outcome ✓ and the receipt is honest ✓). But the POS must be able to
**record** the request and answer *"your sale is in the monthly consolidated
e-Invoice"* ✓ if we ever do decline ✓ — the request is **never silently dropped** ✓.

#### A B2B sale is only B2B if we know it ✓

"Never consolidated: B2B" ✓ is only actionable if we **know** the buyer is a business ✓
— and we know it **only** when the buyer gave a TIN ✓ (or is a known corporate account ✓).
So the operative rule is ✓:

- The buyer **asks for an e-Invoice** → an individual document ✓ (always ✓).
- The buyer **gives a TIN** but does **not** ask → it is still a **business sale** ✓ →
  **never consolidated** ✓ → the POS offers the e-Invoice ✓.
- The buyer gives **nothing** → the sale is B2C ✓ → consolidated ✓.

#### The correction strategy — a rejected consolidated document ✓

The payload is immutable ✓ and the code number is immutable ✓ → **a rejected consolidated
document cannot be edited and resubmitted** ✓. The path is ✓:

1. The rejection reason is stored **verbatim** ✓ on the document ✓.
2. If the document was **validated** and the mistake is ours → **cancel it** ✓ (inside the
   72-hour window ✓) and **rebuild** the batch ✓ — the rebuilt batch carries **new code
   numbers** ✓ and the same receipt references ✓ (the audit trail survives ✓).
3. If the window has passed → the receipts are re-issued as **individual** e-Invoices ✓
   (each with its own code number ✓) and the consolidated document is **cancelled** ✓.
4. Every rebuilt document keeps the **same `receipt_ref`** ✓ → the reconciliation
   between the receipt and the e-Invoice never breaks ✓.

### D. The credit note (the voided order)

An order that was already invoiced and must be reversed:
- **Within 72 hours** of the validation → `Cancel Document` ✓ (free, no document) ✓ —
  with a **`reason`** ✓ (≤ 300 characters ✓) — and the error states are ours to handle ✓:
  `OperationPeriodOver` ✓ (the window has closed ✓), `IncorrectState` ✓ (the document is
  already rejected or invalid ✓), `ActiveReferencingDocuments` ✓ (a credit note already
  points at it ✓ → the credit note is the answer ✓).
- **After 72 hours** → a **credit note** (`InvoiceTypeCode 02`) that references the
  original's UUID ✓ (the Referenced Documents Validator checks it ✓ — the reference goes
  in `BillingReference` ✓).

**The buyer can reject our e-Invoice ✓** — within 72 hours ✓ — and the rejection arrives
as a **notification** ✓ (General Guideline v4.8 §2.3.4 ✓) ✓. So the POS needs ✓:
- a **notification reader** ✓ (the worker polls Get Notifications ✓) ✓,
- an **orders-screen alert** ✓ (*"the buyer rejected e-Invoice INV-1234 — cancel or credit
  it"*) ✓,
- and the **same 72-hour clock** ✓ as our own cancel ✓.

> **A consolidated e-Invoice cannot be rejected ✓** — IRBM notifies the **supplier only**
> ✓ (§3.6.10 ✓) ✓, so the rejection path is an **individual-document** problem only ✓.

The POS's "cancel order" action must therefore know whether an e-Invoice exists for that
order ✓ — the cancel path cannot simply mark the order cancelled and walk away ✓.

### The worker

- A **background task** ✓ (the backend already runs scheduled jobs ✓) that picks the
  `queued` documents ✓, builds them ✓, submits them ✓ and polls them ✓.
- **The monthly batch job runs on the 1st–7th of the month** ✓ — and the operator sees
  the deadline and how many sales are still unbatched ✓.
- The **token is cached** ✓ — **per credential** ✓ (one set in the intermediary model ✓,
  one per tenant in the direct model ✓) — and refreshed at 55 minutes ✓ — **never** a
  token per call ✓ (the SDK names this as the #1 anti-pattern ✓).
- The **429** answers carry a `Retry-After` ✓ — we honour it ✓.
- The **backoff** on a failure is exponential ✓.
- A submission is **never re-sent** because we did not hear back ✓ — the
  duplicate-document validator would reject the second copy ✓ and the API would start
  throttling us ✓.
- **The poll cadence** ✓ — poll `Get Submission` every **2 seconds** ✓ (the guideline's
  own flow validates in under two seconds ✓) up to **30 attempts** ✓ (a minute ✓) — then
  fall back to **Get Notifications** ✓ (the push channel ✓) and **Get Document Details**
  ✓ (the validation result ✓) ✓. Polling is the *fallback*, not the primary ✓ ✓.
- **The fair queue** ✓ — the rate limit is per Client ID ✓ and in the intermediary model
  that is **one bucket for every tenant** ✓ → the worker keeps **one in-flight submission
  per tenant** ✓ and serves the tenants **round-robin** ✓, with a **per-tenant daily cap**
  ✓ ✓ (a big chain's month-end batch must not eat the API's 100 RPM ✓).
- **The reconciliation** ✓ — after a crash we may hold a document with no `submissionUID`
  ✓ (the POST succeeded, the write did not ✓) → we **search** for our own `codeNumber` ✓
  (Search Documents ✓ — **not** Get Recent Documents ✓, which only sees 31 days ✓)
  ✓ and recover the UUID ✓ — we never re-send ✓ ✓.

## The rails

The **audit recipe** applies to every route this feature adds ✓:

1. **Who may call it?** → `require_permission("einvoice:read")` /
   `require_permission("einvoice:write")` ✓ (the admin role ✓) and
   `require_staff_permission("staff:einvoice:read")` ✓ for the counter's read-only view ✓.
   The **role table** is `ROLE_PERMISSIONS` in `backend/app/middleware/auth.py` ✓.
   **And a write for the counter** ✓ — the cashier must set `e_invoice_requested` ✓ and
   store the buyer's details ✓ on the order ✓, so the counter's write goes through the
   **order** route ✓ (`orders:write` ✓ — the role already has it ✓) and the e-Invoice
   routes themselves stay admin-only ✓ ✓. A read-only staff permission alone cannot
   express "the guest asked for an invoice" ✓.
2. **Whose data may it touch?** → the tenant helpers in `backend/app/core/tenant.py` ✓ —
   `require_outlet_tenant` for the settings and the documents ✓. The **tenant comes from
   the session** ✓, never from a query parameter ✓.
3. **Did the tenant buy it?** → `require_plan_feature("E-Invoice")` ✓ — the plan cache reads
   it live ✓. **And the outlet must be MYR** ✓ — a USD outlet never sees the tab ✓ ✓
   (the currency validator ✓).
4. **Does the UI agree?** → the nav item's `minRole` + `feature` in
   `frontend/src/config/navItems.js` ✓ and the settings tab's gate ✓.

The same discipline for the frontend ✓: check `res.ok` **and** `Array.isArray(...)` before
`.filter` / `.map` ✓; skip the call entirely when the feature is off ✓.

### The credentials ✓

- The **client secret** lives **in the backend only** ✓ — never in the browser ✓, never in
  the receipt ✓, never in a log line ✓.
- Encrypted at rest ✓ (the same treatment as the other secrets ✓).
- The **token cache is per credential and in memory** ✓ — one set in the intermediary
  model ✓, one per tenant in the direct model ✓ — a restart just means one extra login ✓.
- The **sandbox and production credentials are separate** ✓ so a test can never touch
  production ✓.
- In the **intermediary model** ✓ the credentials are **ours** ✓ — the tenant's

## The open questions

1. ~~**The QR code endpoint**~~ ✓ — **answered** ✓: the "Taxpayer's QR Code" API reads a
   *business's* QR ✓ (TIN, BRN, SST, MSIC ✓) and is **not** the receipt's QR ✓; the
   receipt's validation QR is **ours to draw** ✓ from the document's UUID ✓ (General
   Guideline v4.8 §2.4.4 ✓) ✓. *What remains: the exact MyInvois validation URL format*
   ✓ — to be read from the SDK's sample ✓ ✓.
2. **The structure of v1.0 in practice** — the field paths must be taken from
   `Get Document Type` ✓ (the SDK serves the structure definition ✓) rather than guessed
   from the UBL spec ✓.
3. **The intermediary onboarding** — how a tenant authorises our ERP client in the MyInvois
   portal ✓, and whether the authorisation is per tenant or per document type ✓.
4. **The VAT** — the VAT regime replaces SST ✓; the tax type codes will change with it ✓ —
   the code tables are seeded ✓, so this is a deploy ✓, not a code change ✓.
5. **The payment mode for DuitNow by QR** — `03` (bank transfer ✓) or `06` (e-wallet ✓) —
   the code validator rejects the wrong one ✓, so it must be **seeded, not guessed** ✓.
6. **The service charge's tax treatment** ✓ — service tax `02` ✓ at 5% ✓ on the service
   charge, while the food is sales tax `01` ✓ at 6% ✓ — to be confirmed against the
   seeded code table ✓ and the tenant's own SST registration ✓ ✓.
7. **The RM1M–5M deferral** ✓ — a secondary source said the RM1M–5M band moves to
   **1 January 2027** ✓, but **Table 1.1 of the General Guideline v4.8 says 1 January
   2026** ✓ → the doc follows the guideline ✓, and the deferral must be confirmed ✓ ✓.
