# API Authentication Strategy

## Overview

This document outlines a **layered authentication strategy** for both Website API and Backend POS API. The approach is designed to:

1. **Block unauthorized external access** (Postman, curl, API testing tools)
2. **Maintain simple security for internal trusted apps**
3. **Enable future external developer access** with proper authentication
4. **Protect internal API keys** from being exposed to external developers

---

## Key Security Concern

### The Problem: API Key Exposure Risk

If Customer Order Apps (built by external developers) directly call Website API:

```
❌ PROBLEM - API Key Exposed:
┌─────────────────────┐     API Key in source code     ┌─────────────────┐
│ Customer Order App    │ ─────────────────────────────▶ │  Website API    │
│ (External Dev)        │     Same internal key!        │  /admin/*       │
└─────────────────────┘                                └─────────────────┘
```

External developers would have access to the same internal API key as Frontend POS, which is a **security risk**.

---

## Solution: Backend-for-Frontend (BFF) Pattern

### The Architecture

```
✅ SECURE - Internal Key Hidden:
┌─────────────────────┐     User Token (JWT)     ┌─────────────────┐
│ Customer Order App    │ ──────────────────────▶ │  Backend POS API │
│ (External Dev)        │   No API key needed!    │                 │
└─────────────────────┘                          │  Internal call   │
                                                │  to Website API  │
                                                └────────┬────────┘
                                                         │
                                                         │ Internal Key (hidden)
                                                         ▼
                                                ┌─────────────────┐
                                                │  Website API    │
                                                │  /admin/*      │
                                                └─────────────────┘
```

### Benefits

| Aspect | Direct Call (Problem) | BFF Pattern (Solution) |
|--------|----------------------|------------------------|
| API Key in Client App | ❌ Exposed to external devs | ✅ Hidden, never in client |
| Internal Endpoints | ❌ Directly accessible | ✅ Only via Backend |
| Customer Data | URL contains customer ID | Token contains customer ID |
| External Dev Access | Full admin key | User token only |

## Two-Tier Security Model

### Tier 1: Website API (Simple & Locked Down)

**Goal: Block all unauthorized external tool access**

```
┌─────────────────────────────────────────────────────────┐
│              Website API (apisite.ideazes.com)            │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  ✅ Allow: Frontend POS (API Key + Origin)              │
│  ✅ Allow: Backend POS API (Internal service calls)      │
│  ❌ Block: Postman / curl / external tools             │
│  ❌ Block: Unknown origins                             │
│  ❌ Block: External IP addresses (admin endpoints)     │
│                                                          │
│  Auth: API Key + Origin/IP Restriction                  │
└─────────────────────────────────────────────────────────┘
```

### Tier 2: Backend POS API (Full Hybrid for External Devs)

**Goal: Allow external developers with proper auth, protect internal keys**

```
┌─────────────────────────────────────────────────────────┐
│              Backend POS API (api.ideazes.com)            │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  ✅ Allow: Frontend POS (API Key)                       │
│  ✅ Allow: Customer Apps (User Token ONLY)              │
│  ✅ Allow: External devs (API Key + User Token)         │
│  ✅ Internal: Calls Website API with hidden key         │
│  ❌ Block: Requests without proper authentication       │
│                                                          │
│  Auth: Hybrid (API Key + User Token)                    │
│  Special: BFF proxy for Website API calls               │
└─────────────────────────────────────────────────────────┘
```

## API Access Patterns

### Pattern 1: Frontend POS → Website API (Direct)

Used for internal operations where Frontend POS needs direct access.

```
Frontend POS (app.ideazes.com)
         │
         │ API Key + Origin Check
         ▼
   Website API
   /api/admin/*
```

| Caller | Auth | Access |
|--------|------|--------|
| Frontend POS | API Key + Origin | All admin endpoints |

### Pattern 2: Customer App → Backend POS API → Website API (BFF)

Used for external developer apps. Backend POS acts as a proxy, hiding the internal API key.

```
Customer Order App (order.ideazes.com or 3rd party)
         │
         │ User Token (JWT)
         ▼
   Backend POS API
   /customer/*
         │
         │ Internal call (no key exposed to client)
         ▼
   Website API
   /admin/*
```

| Caller | Auth | Access |
|--------|------|--------|
| Customer App | User Token | Customer-specific data only |
| Backend POS | Internal key | Website API (hidden from client) |

### Pattern 3: External Developer → Backend POS API

Used for future external developer integration.

```
External Developer App
         │
         │ API Key + User Token
         ▼
   Backend POS API
   /api/*
```

| Caller | Auth | Access |
|--------|------|--------|
| External Dev | API Key + User Token | Approved endpoints only |

## Tier 1: Website API Security

### Security Model

Website API uses a **simple but strict security model**:

1. **API Key Validation** - Only requests with valid API key can proceed
2. **Origin/Referer Check** - Only requests from trusted domains (Frontend POS)
3. **IP Restriction** - Admin endpoints restricted to internal IPs
4. **Tool Blocking** - Explicitly blocks Postman, curl, and similar tools

### Implementation

```python
# Website API middleware - Locked down security
from fastapi import Request, HTTPException

ALLOWED_ORIGINS = [
    # Internal apps (trusted)
    "https://admin.ideazes.com",    # Admin App
    "https://app.ideazes.com",      # Frontend POS
    "https://order.ideazes.com",     # Customer Order App
    "https://site.ideazes.com",     # Site App (marketing + auth)
    "https://www.ideazes.com",      # Public website
    # Internal IPs
    "127.0.0.1",
    "localhost",
]

BLOCKED_USER_AGENTS = [
    "Postman",
    "Thunder Client",
    "HTTPie",
    "curl",
    "insomnia",
]

def verify_request(request: Request):
    """Verify request is from trusted source"""
    
    # 1. Check User-Agent for blocked tools
    user_agent = request.headers.get("User-Agent", "")
    for blocked in BLOCKED_USER_AGENTS:
        if blocked.lower() in user_agent.lower():
            raise HTTPException(
                status_code=403,
                detail="API testing tools are not allowed"
            )
    
    # 2. Check API Key
    api_key = request.headers.get("X-API-Key")
    if not api_key or not validate_api_key(api_key):
        raise HTTPException(status_code=401, detail="Invalid API key")
    
    # 3. Check Origin/Referer (skip for internal service calls)
    origin = request.headers.get("Origin") or request.headers.get("Referer", "")
    if origin and not is_internal_service(request):
        allowed = any(o in origin for o in ALLOWED_ORIGINS)
        if not allowed:
            raise HTTPException(
                status_code=403,
                detail="Requests from this origin are not allowed"
            )
    
    # 4. For admin endpoints - restrict to internal IPs
    if request.url.path.startswith("/api/admin/"):
        client_ip = request.client.host
        if not is_internal_ip(client_ip) and not is_internal_service(request):
            raise HTTPException(
                status_code=403,
                detail="Admin access restricted to internal network"
            )
    
    return True

def is_internal_service(request: Request) -> bool:
    """Check if request is from internal service (Backend POS API)"""
    # Check for internal service header or IP
    internal_header = request.headers.get("X-Internal-Service")
    if internal_header == "backend-pos":
        return True
    return False
```

## Tier 2: Backend POS API Security

### Security Model

Backend POS API uses **full hybrid authentication** with BFF proxy capability:

1. **API Key** - Identifies the application/developer (external devs)
2. **User Token** - Authenticates the end user (all clients)
3. **BFF Proxy** - Internal calls to Website API with hidden key
4. **Rate Limiting** - Prevents abuse
5. **Permission System** - Granular access control

### Components

#### 1. API Keys (Developer/App Identification)

| Field | Description |
|-------|-------------|
| `key_id` | Unique identifier for the API key |
| `key_hash` | Hashed version of the API key |
| `app_name` | Name of the application |
| `developer_id` | Reference to registered developer |
| `service` | Which service the key is for |
| `status` | active, suspended, revoked |
| `rate_limit` | Requests per minute limit |
| `created_at` | Key creation timestamp |

#### 2. User Tokens (User Authentication)

| Field | Description |
|-------|-------------|
| `token_id` | Unique token identifier |
| `user_id` | Reference to authenticated user |
| `token_hash` | Hashed version of the token |
| `expires_at` | Token expiration timestamp |
| `status` | active, expired, revoked |
| `created_at` | Token creation timestamp |

### BFF Implementation Example

```python
# Backend POS API - Customer endpoints (BFF pattern)
@router.get("/customer/features")
async def get_customer_features(
    current_user: dict = Depends(get_current_customer)
):
    """
    Get customer features via BFF pattern.
    User token validated here, internal API key never exposed to client.
    """
    customer_id = current_user["customer_id"]
    
    # Internal call to Website API - key is hidden from client
    website_api_response = await call_website_api(
        endpoint=f"/api/admin/customer/{customer_id}/features",
        internal=True  # Uses internal API key, not exposed
    )
    
    return website_api_response.json()

async def call_website_api(endpoint: str, internal: bool = False):
    """Internal call to Website API with hidden key"""
    headers = {}
    if internal:
        headers["X-Internal-Service"] = "backend-pos"
        headers["X-API-Key"] = settings.WEBSITE_API_INTERNAL_KEY  # Hidden key
    else:
        headers["X-API-Key"] = get_api_key_from_request()
    
    response = await http_client.get(
        f"{WEBSITE_API_BASE}{endpoint}",
        headers=headers
    )
    return response
```

from app.core.tier1_security import ALLOWED_ORIGINS, is_internal_service, is_internal_ip

def check_origin_for_api_key(request: Request) -> bool:
    """
    Check if origin is allowed for API key requests.
    Returns True if origin check should be skipped (internal service).
    """
    # Skip if internal service
    if is_internal_service(request):
        return True
    
    # Check origin
    origin = request.headers.get("origin") or request.headers.get("referer", "")
    if not origin:
        client_ip = request.client.host if request.client else ""
        if is_internal_ip(client_ip):
            return True
        return False
    
    for allowed in ALLOWED_ORIGINS:
        if allowed in origin:
            return True
    
    return False

async def get_admin_or_api_key_auth(
    request: Request,  # Added for origin checking
    x_api_key: Optional[str] = Header(None, alias="X-API-Key"),
    ...
):
    # ... existing admin token check ...
    
    # Check for API key (external apps like Frontend POS)
    if x_api_key:
        # Tier 1: Check origin for API key requests
        if not check_origin_for_api_key(request):
            raise HTTPException(
                status_code=403,
                detail="Request origin not allowed. API key requests must come from trusted domains."
            )
        return {"type": "api_key", "key": x_api_key}

## Migration Strategy

### For Website API

1. Add origin checking for Frontend POS
2. Add internal service header support for Backend POS
3. Only allow Frontend POS and Backend POS (internal) access
4. Customer Apps no longer directly access Website API

### For Customer Order App (BFF Migration)

**Before:**
```javascript
// ❌ OLD - API key exposed
const API_KEY = 'pk_7efDBsHoS...';
fetch(`${WEBSITE_API}/api/admin/customer/${customerId}/features`, {
    headers: { 'X-API-Key': API_KEY }
})
```

**After:**
```javascript
// ✅ NEW - User token only, no API key
fetch(`${BACKEND_API}/customer/features`, {
    headers: { 'Authorization': `Bearer ${userToken}` }
})
```

### For Backend POS API

1. Add `/customer/*` BFF endpoints
2. Store internal Website API key securely (env var, not in code)
3. Proxy requests to Website API with internal key
4. Validate user token before proxying

---

## Summary

| API | Auth Strategy | External Tools | Target Users | Access Pattern |
|-----|--------------|----------------|--------------|----------------|
| **Website API** | API Key + Origin + IP | BLOCKED | Frontend POS, Backend POS (internal) | Direct or Internal |
| **Backend POS API** | Full Hybrid + BFF | Allowed | All apps (Customer, External) | User Token / API Key |

**Key Principles:**
1. Website API stays simple but locked down - no external tool access
2. Backend POS API acts as BFF - hides internal keys from external devs
3. Customer Apps use User Tokens - no API keys exposed to clients
4. External developers get their own keys with proper authentication
