## The shape of it

- The web agent screen (embedded - the one in the app shell, today) gets a
  **"Full screen"** button - in its header, on the right, next to the read-only badge -
  **exactly where the Staff Order's is** (`frontend/src/pages/StaffOrder.jsx:1410`).
- The button opens **`/ai-agent/full`** - a **kiosk route** - edge to edge, no sidebar, no
  app bar, no mobile bottom bar, **no page scroll** - the same trick as `/staff-order/full`
  and `/kitchen/full` (`frontend/src/App.jsx:423-425`).
- The full-screen agent **keeps**: the conversation, the proposals inline under the answer
  that asked for them, the capability panel, the greeting, the error banner.
- The full-screen agent **drops**: the sidebar, the app bar, the mobile bottom bar, and
  the **always-open capability panel** (it becomes a chip in the header).

**It is the same screen, in the same code, in a second mode** - the house pattern:
`StaffOrder` already does exactly this (`mode="embedded" | "kiosk"`), and so does `Kitchen`.
The web agent becomes `AgentChat({ mode = 'embedded' })`.

## Why there is a full screen at all - the defect, measured

**This is not a styling wish. There is a real layout defect in the embedded screen, and
it is arithmetic.**

The container (`frontend/src/pages/AI/agent/index.jsx:221`):

```
h-[calc(100vh-4rem)] flex flex-col
```

It sits inside the shell's main (`frontend/src/App.jsx:500`):

```
<main className="print-page lg:ml-64 px-4 pt-4 pb-20 lg:pb-4">
```

And the shell has a **sticky top bar of `h-16`** (`frontend/src/App.jsx:472` - 4rem) and a
**fixed mobile bottom nav** (the `pb-20` - 5rem - is the space reserved for it).

So the page is:

```
4rem (header) + 1rem (pt-4) + (100vh - 4rem) (the container) + 5rem (pb-20) = 100vh + 6rem
```

**The page is about 6rem taller than the viewport.** Which means **the PAGE scrolls, not
the message pane** - and the composer, which is the last thing inside the container, is
**below the fold**. That is the complaint, and it is exactly what the arithmetic predicts.

Two further facts about the same line:

- it is **`100vh`**, not `100dvh` - so on a phone the **mobile URL bar** eats into the
  composer area as well, and the composer moves when the URL bar hides;
- the `overflow-y-auto` scroller (`index.jsx:247`) is inside a container that is already
  too tall, so **it never gets to be the scroller** - the document is.

**And the composer itself** (`index.jsx:320`) is a single-line `<input type="text">`:
no multiline, no Enter-to-send, and **no IME guard anywhere in the frontend** (no
`isComposing` and no `compositionend` in the whole of `frontend/src/`) - so a tenant
typing **Chinese or Khmer** would have the candidate character sent out from under the
cursor.

## The design - the full-screen shell

```
+---------------------------------------------------------------------------+
|  [Back]  [agent tile] Agent name       [Capabilities chip] [Read-only]    |  <- header
+---------------------------------------------------------------------------+
|                                                                           |
|    the conversation - bubbles, and the proposal cards inline under the     |
|    answer that asked for them. THIS is the only thing that scrolls.       |
|                                                                           |
+---------------------------------------------------------------------------+
|  [ Ask your agent...                            ]                  [Send] |  <- pinned
+---------------------------------------------------------------------------+
```

**The shell - copied from the kiosk branch** (`frontend/src/App.jsx:427-449`):

| Where | The classes |
|---|---|
| the kiosk wrapper | `h-[100dvh] overflow-hidden` |
| the full-screen root | `h-[100dvh] flex flex-col overflow-hidden` |
| the header | `h-14 shrink-0 flex items-center gap-3 px-3 sm:px-4 border-b border-gray-200 bg-white` |
| the agent tile | `w-9 h-9 shrink-0 bg-gradient-to-br from-purple-500 to-indigo-600 rounded-lg` (the **Sparkles**, unchanged) |
| the message pane | `flex-1 min-h-0 overflow-y-auto p-4 space-y-4` |
| the composer row | `shrink-0 border-t border-gray-200 bg-white` |

**The composer is the LAST FLEX CHILD, not `position: fixed`.** That is the whole
technique: a flex column whose last child is `shrink-0` is **pinned** (the column is
exactly the viewport height, so the child has nowhere to go but the bottom) and it
**cannot overlap the content**, because the content above it is `flex-1 min-h-0` and
therefore ends where the composer begins. The classic fixed-composer bug - the composer
floating over the last message - is impossible in this structure.

**The desktop** keeps the conversation in a **centred column** (max-width ~880px) so a
long answer on a wide monitor stays readable, with the bubbles inside it.

**The phone**:

- the root is `100dvh`, so the URL bar collapsing cannot clip the composer;
- the composer carries `padding-bottom: env(safe-area-inset-bottom)` so it clears the iOS
  home indicator;
- **the on-screen keyboard** is the one thing `100dvh` does NOT solve on iOS Safari - the
  keyboard does not shrink the viewport. A `visualViewport` listener writes the keyboard
  height into a CSS variable (`--kb-inset`) and the composer is padded by it. There is
  **no `visualViewport` usage anywhere in `frontend/src/` today**, so this is new ground
  and it is a deliberate, small piece of new code.

## The design - the composer (in BOTH modes)

This is the part Kens asked for, and it lands in **both** the embedded screen and the
full screen - one shared component, so the two cannot drift.

| Behaviour | The rule |
|---|---|
| the text box | a **`<textarea>`**, auto-growing from **1 to 6 rows** (~120px), then scrolling internally |
| send | **Enter** sends, **Shift+Enter** inserts a newline |
| the IME guard | `event.nativeEvent.isComposing` is checked before sending - **a candidate character being chosen must never be sent** |
| the send button | disabled when the input is empty **or** a request is in flight |
| loading | the existing three-dot bubble stays in the stream; the composer shows a spinner and refuses a second send |
| autofocus | **desktop only** - never on mobile, or the keyboard opens over the screen the moment it loads |
| the error banner | sits **above** the composer as a strip, not between the stream and the composer (today it is between them, and it pushes the composer down) |

**Why the guard matters here specifically.** The tenants of this product type in **Chinese
and Khmer** (`en` / `zh` / `km`, `frontend/src/i18n/locales/`). In an IME, pressing Enter
**confirms the candidate** - it does not send. Without the guard, the first half of a
sentence disappears into the backend on the first Enter. The whole frontend has **zero**
such guards today, so this is a fix, not a port.

## The design - who scrolls, and when

- **One scroller.** The message pane. The root is `overflow-hidden`, so the document has
  no scrollbar at all.
- **Auto-scroll to the bottom on a new message - but only when the reader is already
  near the bottom** (an ~80px threshold). The screen already scrolls to the bottom on
  every change (`index.jsx:92-95`); without the threshold, a tenant reading a
  **proposal card** gets yanked to the bottom by the next reply. That is the one
  behaviour change in this design that touches something a tenant already relies on.

---

## The design - the capability panel and the proposal cards

- **The proposal cards stay exactly where they are**: **inline, under the answer that
  asked for them** (`index.jsx:286-300`). The card is a frozen plan waiting for a
  person, and its meaning comes from the pairing. Nothing moves.
- **The capability panel becomes a chip in the header.** Today it is a permanent block
  above the conversation (`index.jsx:241-244`, `mb-3 shrink-0`) - it is a good panel, but
  in a full screen it is permanent vertical space taken from the conversation, which is
  the opposite of the point. In the full screen it collapses to a chip showing the same
  **read** and **propose** counts, and one tap opens the full list. The information is
  one tap away and the counts stay visible; in the **embedded** screen the panel stays
  exactly as it is today.

## The rails - the rules it must not break

1. **The route is a kiosk route** - `App.jsx` already has the `isKioskRoute` branch for
   `/staff-order/full` and `/kitchen/full` -> `/ai-agent/full` joins it (one condition,
   one branch) - and it is wrapped in **`ProtectedRoute`** exactly like the other two ->
   **the login is the gate** -> the Exit needs no second secret.
2. **The role and the plan gates are the web agent's own** - `navItems.js:53`:
   `{ path: '/ai-agent', minRole: 'manager', feature: FEATURES.AI_AGENT, requiresAgentAccess: true }`
   -> the **"Full screen" button shows only when the web agent itself shows**. **No new
   feature flag** - it is the same feature, the same way the Staff Order's button reuses
   its own nav entry.
3. **The third gate is the server's, and it stays the server's** -
   `GET /api/ai/agent/access` (`backend/app/routes/ai_agent.py:316`) answers whether the
   tenant holds the `AI Agent` row **and** has a configured, active profile. The
   full-screen screen calls **the same hook** (`frontend/src/hooks/useAgentAccess.js`) and
   renders **the same blocked screen with the same named reason** - `no_profile`,
   `profile_inactive`, `agent_disabled`, `plan` - plus the same **Retry** button. A
   full-screen URL is **not** a way around the gates.
4. **The tenant rules are unchanged** - the outlet comes from the **session**
   (`resolveOutletId(session)`), never from the query string.
5. **Nothing new is fetched** - the full screen calls the **same**
   `POST /api/ai/agent/chat` (`backend/app/routes/ai_agent.py:398`) with the **same**
   body `{ message, outlet_id }` -> **no backend change at all**.
6. **This is NOT the chatbot** - the ordinary chatbot lives at `/chatbot`
   (`frontend/src/pages/Chatbot.jsx`) and stays exactly where it is. The web agent is the
   **tenant's own agent** and keeps its own screen. The two are separate doors.
7. **The i18n namespace is `agentChat`** - the new keys land in **en / zh / km** in
   lockstep (the house rule - every key in all three; the namespace today holds 9
   top-level keys in each of the three locales, and they match).

## The exit

- The **Back** button in the header returns to **`/ai-agent`** - the same one-tap exit
  the Staff Order and Kitchen kiosks have (`frontend/src/pages/Kitchen.jsx:781`).
- **No PIN on the exit** (consistent with the Kitchen kiosk, decided 4 Nov 2026) - the
  POS logs in per user, so the route is already behind a login, and a PIN would be a
  second secret for nothing.
- **No auto-return** (consistent with the Staff Order kiosk) - the screen stays until the
  tenant leaves it.
- **We do not use the browser's Fullscreen API** - the button is a **route**, not
  `requestFullscreen()` -> no permission prompt, no confusion with F11, and it
  **survives a refresh** (the URL *is* the mode).
- The **Escape key does not exit** - consistent with the other two kiosks; an accidental
  keypress must not drop a tenant out of the conversation.

## The test plan

**Layout**
- at 1440x900, 1024x768 and 390x844, the composer is **fully visible without scrolling**,
  and the document has **no** scrollbar (`document.scrollHeight` = the window height);
- the message pane scrolls on its own, and scrolling it **never moves the composer**;
- on a phone, the composer clears the home indicator and the on-screen keyboard;
- a refresh on `/ai-agent/full` keeps the full screen (the route decides).

**The composer**
- Enter sends; Shift+Enter adds a newline;
- typing Chinese or Khmer and pressing Enter **does not** send mid-composition;
- the textarea grows to 6 rows, then scrolls internally, and the message pane is never
  fully covered;
- the send button is disabled when empty and while loading, and a second Enter during a
  request does nothing;
- the composer behaves **identically** in the embedded screen and the full screen (the
  shared component, so this is one behaviour, not two).

**The gates**
- a tenant without the `AI Agent` row, or without a configured active profile, sees the
  **existing blocked screen with its named reason** in the full screen - the full-screen
  URL is not a way around the gates;
- the **"Full screen" button** appears for a manager with the `AI Agent` feature and the
  agent available, and disappears without them.

**The untouched**
- `/chatbot` is unaffected;
- `/ai-agent` works as before, apart from the new button and the upgraded composer;
- the **proposal cards** still appear inline under their answer, and **Approve / Edit /
  Reject** still work in both modes.

**The house checks**
- `npm run i18n:check` passes (every new key in en, zh and km);
- the build goes to a **temp** directory, and the live bundle is re-proved after deploy.

## The phased plan

**Phase 1 - the shared composer (half a day).**
`AgentComposer.jsx` - the textarea, the auto-grow, Enter-to-send, the IME guard, the
send button, the spinner, the error strip. The **embedded** screen switches to it, so the
upgrade lands on the screen Kens uses today before the full screen even exists.

**What Phase 1 does NOT do:** it does not add the route, and it does not change the
embedded layout. It is the composer, alone.

**Phase 2 - the route and the button (half a day).**
The `/ai-agent/full` route in the `isKioskRoute` branch, the `mode` prop, the full-screen
shell, the header, the pinned composer, the **"Full screen"** button on the embedded
screen, the Back button, the capability chip, the i18n keys.

**What Phase 2 does NOT do:** it does not stream, and it does not give the agent a memory
(below).

**Phase 3 - the phone and the polish (half a day).**
The `visualViewport` keyboard inset, the safe-area padding, the scroll threshold, the
desktop column, the autofocus rule.

**What Phase 3 does NOT do:** it does not change the embedded screen's layout - the
embedded screen keeps its own height behaviour, and only its composer is new.

## What this design does NOT claim

Two things a full-screen chat usually implies, and that this screen **does not** have
today. Both are recorded here so nobody reads them into the design:

1. **There is no streaming.** `POST /api/ai/agent/chat` returns **one-shot JSON**
   (`response_model=AgentChatResponse`, `backend/app/routes/ai_agent.py:398`). The
   full-screen screen shows the **three-dot loader** until the whole reply arrives. Real
   streaming is a separate backend scope.
2. **There is no conversation memory.** The request body carries **only**
   `{ message, outlet_id }` (`backend/app/routes/ai_agent.py:130-139`) and the model call
   is made with that one message - so the bubble list **looks** like a conversation, but
   the agent **sees one message at a time**. Real memory needs a thread id, server-side
   persistence, and a messages-list model call.

**Neither is implied by this design, and neither is pretended.** The full screen makes
the *typing* easy and the *reading* comfortable; the intelligence on the other side of
the pipe is a separate piece of work.

## The open questions

1. **Should the embedded screen also lose its permanent capability panel?** - it stays as
   it is in Phase 1-3 (there is vertical room there). Answered by default: **no**.
2. **Should the full screen remember the last outlet?** - the outlet comes from the
   session, so it is whatever the tenant last selected. **No new state.**
3. **Should the composer show the Enter / Shift+Enter hint?** - proposed as a subtle
   placeholder hint on desktop only. On a phone there is no Enter key, so the hint would
   be noise.
4. **Does the full screen need a print or export of the conversation?** - not asked for;
   the proposal has no route for it.
