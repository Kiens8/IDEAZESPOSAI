# The AI Manager — a vertical agent per tenant

**Document Version:** 1.1 (the proposal — Nov 19, 2026 · revised the same day: the MCP server
becomes the backbone, n8n is demoted to one client among many, and the tool catalogue is added)
**Owner:** Ideazes POS AI
**Status:** **Proposal.** Nothing in it is built. It is the design Kens asked for after the
current chatbot was reviewed: *"is it enough for the current state, or do we move forward —
integrate the SaaS POS with something like n8n, let each tenant have their own vertical AI
agent, an AI Manager that manages the store and matches our site app."* Then: *"I am not
recommend create an OpenClaw agent per tenant. My purpose is to serve an AI agent per tenant —
this AI agent can be triggered somewhere, either our frontend POS, or another channel; this
agent can create or answer something related to their one outlet. How about the approach of an
MCP server?"*

> built today) · `program-changes/ai-feature-gating/ai-feature-gating.mdx` (how a feature row

## 1. The short answer

**The chatbot we have is good enough to sell. It is not an AI Manager, and no integration
tooling turns it into one.**

What exists today is a **pull** model: a human asks, the bot answers from POS data. What Kens
described is a **push** model with agency: a per-tenant agent that watches the store, knows the
tenant's own rules, and *does* things — always inside the POS's own rules.

The distance between the two is **not the model**. MiniMax already answers. The distance is
three missing layers:

1. **An action layer** — the agent can only read. Every write it performs is a new tool with
   its own permission, its own approval step and its own audit row.
2. **A trigger layer** — nothing in the product emits an event the agent could react to.
   The only webhooks that exist today are **inbound** payment ones.
3. **A tenant-profile layer** — the bot's behaviour lives in Python code paths. For the agent
   to be *the tenant's* agent, its persona, SOPs, permissions and working hours have to be
   **tenant data**, not code.

**The architectural answer (v1.1): the POS backend becomes an MCP server.** It is the
**tool layer** and the **identity layer** — every tool is tenant-scoped by the credential that
calls it, and every tool is a route underneath, so the existing gates apply for free. On top of
that server, the **agent runtime is the tenant's choice**: our own POS frontend chatbot, n8n, a
Telegram bridge, a WhatsApp bot, a future OpenClaw agent. We build the server once; the
runtime is pluggable.

**n8n is one client among many, not the architecture.** It has an MCP Client Tool node that
plugs straight into its AI Agent node, so it can consume our server as-is — but nothing in the
product depends on it, and the tenant never has to touch it.

## 2. What is actually built today (the audit this proposal starts from)

Every line below was read from the running code, not from the docs.

### 2.1 The chatbot

| Artifact | What it is |
|---|---|
| `backend/app/ai/chatbot.py` (1,295 lines) | The engine. Regex intent tables (`INTENT_PATTERNS`), a role map (`ROLE_INTENTS`), one handler per intent, and an AI fallback. |
| `backend/app/ai/chatbot_tools.py` (537 lines) | The tool registry the fallback calls — **10 tools, every one of them a read** (the catalogue is §4). |
| `backend/app/ai/minimax.py` | The shared MiniMax helper. Strips the `<think>` block so reasoning never leaks into a user-visible answer. |
| `backend/app/routes/chatbot.py` | `POST /api/chatbot/`, plus `/test`, `/greeting`, `/quick-replies`. Gated by `require_permission("ai:read")` **and** `require_plan_feature("AI Chatbot")`. |
| `backend/app/routes/ai_chatbot.py` | `POST /api/ai/chat/order` — the customer-facing conversational order. Same two gates. |

Two facts that shape the whole proposal:

- **The tool-calling loop only runs for `chatbot_type == "admin"`** (`chatbot.py`, the
  `tools = tool_schemas()` branch). A manager gets the AI fallback with the *snapshot* in the
  prompt; a staff member gets neither the tools nor a model. The tool machinery exists — it is
  simply gated to one role.
- **`MAX_TOOL_ROUNDS = 3`** (`chatbot.py:20`). The loop is bounded and the answer is written
  from the tool results. The pattern — *ask the model, let it call bounded read tools, write
  the answer from the numbers* — is the right one and Phase A extends it rather than replacing
  it.

### 2.2 The AI surfaces that already exist

- `backend/app/routes/ai/__init__.py` — `POST /api/ai/insights`, `GET /api/ai/menu-analytics`,
  and the **campaign** CRUD (`/campaigns`, `/campaigns/{id}/toggle`, `/campaigns/{id}/execute`,
  `/campaigns/suggest`, `/campaigns/{id}/simulate`). Reads need `ai:read`; the campaign writes
  need `ai:write` — and only the **admin** role carries `ai:*`.
- `backend/app/routes/ai_forecast.py`, `ai_inventory.py`, `ai_orders.py`, `ai_search.py`,
  `ai_security.py` — the forecast, inventory-prediction, order-analytics, smart-search and
  fraud-alert surfaces.
- `frontend/src/pages/AI/index.jsx` — the AI Tools page. Five tabs, each gated by a feature
  row **and** a plan, with a locked tab that offers an upgrade.
- `frontend/src/pages/Chatbot.jsx` — the chatbot panel in the staff app.
- `frontend/src/pages/Settings.jsx` — the **AI Chatbot** tab, gated by the feature row
  `AI Chatbot Settings`. It writes `bot_name`, `bot_language`, `bot_greeting`, `ai_enabled` on
  the outlet (`backend/app/models/models.py:496-499`).

So the tenant already has a **name and a greeting** for its bot. That is the thin end of the
tenant-profile idea, and it lives in the outlet row.

### 2.3 The machinery the agent would reuse

| Need | What already exists |
|---|---|
| Plan entitlement | `backend/app/services/plan_features.py` reads the website API over the house's loopback path; `require_plan_feature("<display name>")` gates a route. The feature list is stamped into the session at login. |

The admin route `POST /api/admin/customer-features` already writes it and pushes the change to the POS cache. **This is the hook for selling the AI Manager to one tenant without inventing a billing mechanism.** |
| Server-to-server calls | `backend/app/routes/internal.py` — `/plan-changed`, `/subscription-changed`, `/order-paid`, all behind `require_internal_key`. The pattern for "the POS tells somebody something" exists. |
| An inbox for things that need attention | `backend/app/routes/notifications.py` — list, unread count, mark read, plus the stock check. The bell in the staff app already exists. |
| Push to a phone | `backend/app/services/delivery_push.py` — VAPID web push, with subscribe/unsubscribe and a payload builder. It ships to the **customer** app today; the same service can carry the manager's briefing. |
| An audit trail | `order_reprints` (`models.py:548`) — who, when, how many copies, why, and whether the token was on the paper. The house already has a pattern for "this was done by a human and here is the record". |
| AI findings with an acknowledgement | `AIAlert` (`ai_alerts`) — severity, the related order/user/item, `is_acknowledged`, `acknowledged_at`, `acknowledged_by`. |

### 2.4 What is missing, itemised

| Missing | Evidence it is missing |
|---|---|
| A write tool | All 10 tools in `chatbot_tools.py` are reads. `TOOLS` maps names to read functions only. |
| An approval step | No table, route or enum anywhere holds a *pending approval*. |
| An audit row for AI actions | `order_reprints` is human-only; there is no AI-action log. |
| A domain event bus | `grep` for `n8n`, `webhook` and `scheduler` in `backend/app` returns only inbound payment webhooks and `subscription_cache` comments. There is no APScheduler and no event table. The only scheduling in the box is four crontab lines (notifications at 09:00, the HitPay reconcile every 10 minutes, the delivery entitlement sweep at 03:23, a log rotation). |
| A tenant agent profile | The bot's knowledge is code. The only tenant-owned knobs are `bot_name`, `bot_language`, `bot_greeting`, `ai_enabled`. |
| An agent "role" in the POS | `ROLE_INTENTS` has `staff`, `manager`, `customer`, `admin` — all of them *human* roles. There is no `agent` role, so no permission namespace an agent could hold. |
| An MCP server | `grep -rn "mcp" backend/app` returns **nothing**; `backend/requirements.txt` has no MCP library. The server would be built on FastAPI, so the transport can be added without a new framework. |

## 3. The design

### 3.1 The shape

```
        ┌────────────────────────────────────────────────────────────┐
  MCP   │  POS BACKEND = the MCP server                              │
 clients│  • the tool registry (one registry, exposed twice)         │
        │  • tenant identity from the credential, never from args    │
        │  • every tool = a gated route underneath                    │
        │  • the tenant profile, the approvals, the audit log        │
        └───┬──────────────┬──────────────┬──────────────┬─────────┘
            │              │              │              │
    ┌───────▼──────┐ ┌─────▼─────┐ ┌──────▼──────┐ ┌─────▼──────┐
    │ our POS      │ │ n8n       │ │ Telegram /  │ │ the tenant │
    │ frontend     │ │ (MCP      │ │ WhatsApp    │ │'s own      │
    │ chatbot      │ │  Client)  │ │ bridge      │ │ agent      │
    │ (in-process) │ │           │ │             │ │            │
    └──────────────┘ └───────────┘ └─────────────┘ └────────────┘
            ▲                                            │
            │  the trigger layer (the one thing MCP        │
            │  does NOT give us): order.placed,            │
            │  stock.low, shift.ended, payment.failed      │
            └──────────────────────────────────────────────┘
```

**The POS backend owns the tools and the identity. The runtime is pluggable.**

Why this shape and not "n8n creates the agent per tenant":

- **Tenant isolation comes from the credential, not from code.** An MCP client presents a
  token; the server resolves it to `customer_id` + `outlet_id` and binds the session to it.
  Every tool call inside that session is scoped by construction. That is exactly the rule
  already held in `chatbot_tools.py` — `ToolContext(db, tenant_id, default_outlet_id)` and the
  `scope(outlet_arg)` helper, which **refuses** an outlet that is not the tenant's.
- **One tool surface, many channels.** Kens's requirement — *"triggered from our frontend POS,
  or another channel"* — is exactly the MCP contract. The POS frontend calls the tools
  in-process (it already does, 10 tools behind `MAX_TOOL_ROUNDS = 3`); an external channel
  connects over MCP. Same tools, same rules, same audit.
- **No licence problem.** MCP is a spec, not a product. n8n's Sustainable Use License never
  enters the picture, because n8n is a *client* of ours, not something we host and resell.
- **The tenant's agent runtime becomes the tenant's choice.** That is the most honest reading
  of "each tenant has its own vertical AI agent".

### 3.2 The MCP server (Phase 0)

**The transport.** FastAPI already serves the API; MCP is a second surface on the same
application, not a new service. Two decisions the design must make early:

- **Transport:** stdio is for local processes; a tenant's agent is remote, so the server must
  speak **Streamable HTTP** (the current MCP remote transport). n8n's MCP Client Tool node
  speaks it.
- **Authentication:** the server reuses the house's key model. A tenant's agent presents an
  API key; the server resolves it to `(customer_id, outlet_id, scope)` and refuses anything
  else. **The tenant comes from the credential, never from the model's arguments** — the rule
  `chatbot_tools.py` already states in its own docstring.

**The token.** The website API's `api_keys` table already carries a `permissions` JSON
column. The proposal extends it (or adds a sibling table) with `customer_id`, `outlet_id`,
`scope` (`read` / `draft` / `action`) and the plan row it rides on. A tenant holds one token
for their agent, revocable like any key. It is the same token that carries `require_permission`
and `require_plan_feature` on the routes underneath, so a lapsed plan refuses the tool call
rather than the UI.

**One registry, two exposures.** The tool definitions live in **one** place and are rendered
twice: as the OpenAI-style function schemas MiniMax already consumes (`tool_schemas()`) and
as the MCP tool catalogue. If the two were written separately they would drift, and we would
have two truths about what the agent can do.

**What the MCP server does NOT do:**

- It does **not** call the model. The *client* holds the LLM. (Consequence: per-tenant token
  cost is invisible to us unless the client uses our model proxy — §4.4.)
- It does **not** trigger itself. MCP is pull-based; the proactive side is §3.5.
- It does **not** weaken a gate. Every tool is the same gated route the staff app uses.

### 3.3 The action layer (Phase A)

The tool registry grows a third kind of tool. The three kinds behave differently:

| Kind | Example | Approval | Audit |
|---|---|---|---|
| **Read** | `get_sales`, `get_alerts` | none | none |
| **Draft** | `draft_purchase_order`, `draft_campaign`, `draft_shift_swap` | none — it produces a *proposal*, nothing changes | the proposal is stored |
| **Action** | `send_purchase_order`, `publish_campaign`, `apply_price_change` | **required** — a human with the right permission approves | an `ai_actions` row |

The rules that make this safe, each one drawn from a rule the house already enforces:

- **The agent holds a role, not a god-mode key.** A new `agent` role in `ROLE_PERMISSIONS`,
  with `ai:act` and a scoped list of the action tools it may call. It never inherits `admin:*`.
- **The server owns the money and the price.** The agent may propose a price change; the
  write goes through the same pricing path the staff screen uses, so the promotion precedence,
  the tax and the order's locked price are unchanged (`pricing-engine-and-promotions.mdx`).
- **Every action is written down before it runs**, in an `ai_actions` row: the agent, the
  tenant, the outlet, the tool, the arguments, the JSON of what changed, who approved it, when.
  The `order_reprints` row is the precedent; the fields are the same idea.
- **An action that is refused is recorded as refused.** Silence is not success — the same rule
  the delivery sweep and the unattended watcher already live by.
- **The approval is a human's, in the POS.** The approval lands in the existing notification
  inbox. Nothing is auto-approved because a model was confident.
- **The MCP server refuses an action tool outright** when the credential's scope is `read`
  only. The refusal happens at the transport, before the tool body runs.

### 3.4 The tenant profile (Phase B)

A per-tenant record that turns one engine into fifty managers:

| Field | Example | Why |
|---|---|---|
| `name` | "Aunty Mei" | The name the tenant already gives the bot today. |
| `persona` / `system_prompt` | "You are the outlet manager of a kopitiam. Be brief. Speak in the outlet's timezone." | The tenant's voice, not ours. |
| `language` | `en` / `zh` / `ms` / `kh` | Already exists per outlet (`bot_language`). |
| `sop` (list) | "Every morning at 09:30, check yesterday's waste vs sales and message the kitchen." | The tenant's own procedure. |
| `allowed_actions` | `["draft_purchase_order", "draft_campaign"]` | What this agent may ever do. Empty set = read-only, which is today's behaviour. |
| `quiet_hours` | `23:00–07:00` | When the agent may not push anything. |
| `escalation` | "money > RM 500 → notify the admin" | The tenant's own thresholds. |
| `outlet_scope` | `["all"]` or a list | Which outlets this agent watches. |
| `runtime` | `pos_frontend` / `n8n` / `telegram` / … | Which client runs this agent. The profile is runtime-agnostic. |

This is the layer that makes the product *vertical*: the same engine, a different manager for
every tenant, and **no code change** to onboard a new one.

### 3.5 The trigger layer (Phase C)

The POS starts emitting **domain events**. MCP is pull-based, so the proactive side needs its
own path. The minimum set for a restaurant manager:

| Event | Emitted when | A manager agent would… |
|---|---|---|
| `order.placed` | an order is created | flag a table that has been open too long |
| `order.paid` | the money settles | close the shift count |
| `order.stalled` | an order sits past the kitchen's reminder | tell the kitchen |
| `stock.low` | an ingredient falls to its threshold | draft a purchase order |
| `staff.clocked_in` / `shift.ended` | the shift starts and ends | compare the actual to the roster |
| `table.turned` | a table is settled | suggest the next seating |
| `payment.failed` | a gateway webhook says no | alert the counter |
| `refund.issued` | a refund is written | flag it for the security review |

Three implementation notes:

- **Emit from the write path, not from a poller.** The delivery module already showed the
  house rule: the server owns the decision, and the enforcement lives where the data is
  written. An event emitted next to the order insert is truthful; an event inferred by a cron
  that scans for rows is a guess.
- **Deliver through the existing internal-key pattern.** `backend/app/routes/internal.py`
  already carries `/plan-changed` and `/order-paid` behind `require_internal_key`. A tenant's
  client subscribes with its own key, scoped to its own tenant, and the POS signs the payload.
- **A queue, not a synchronous call.** An event that blocks an order insert because a tenant's
  webhook is slow is a self-inflicted outage. The insert commits; the event is queued; the
  delivery is retried with a backoff and a dead-letter log.

### 3.6 The surface (Phase D)

The **AI Manager** page in the staff app — the "matches our site app" surface Kens asked for:

- **Today** — the briefing: sales against the same hour yesterday, orders waiting, tables
  occupied, anything the agent thinks the manager should know, in the outlet's timezone.
- **Needs you** — the approvals. A draft purchase order, a proposed campaign, a price change.
  Approve, edit, or reject — each one an audit row.
- **Alerts** — the agent's findings, next to the existing AI alerts, with the same
  acknowledge path (`AIAlert` already has one).
- **Agent** — the profile from §3.4, the working hours, the allowed actions, the escalation
  thresholds, the channel the briefing arrives on, and the **agent token** the tenant hands to
  their own runtime.

## 4. The tool catalogue

### 4.1 The ten tools that exist today

All ten live in `backend/app/ai/chatbot_tools.py` and are **read-only**. The rules they
already obey, in the module's own words: the tenant comes from the session, never from the
model's arguments; the money is grouped per currency and never added up; a tool allow-list,
not a SQL generator; every answer is returned in the API's `data` field; `MAX_ROWS = 15`.

| Tool | Parameters | What it answers | Notable behaviour |
|---|---|---|---|
| `get_sales` | `period`, `outlet` | The revenue, the order count and the average order value for a period | One bucket **per currency** — two currencies are never summed |
| `get_orders` | `period`, `outlet` | The order counts by status, by type and by hour | The busiest hours come from this |
| `list_outlets` | — | The group's outlets: name, currency, address, phone, tables, staff | The only tool with no parameters |
| `compare_outlets` | `period`, `metric` | The same metric for every outlet, so they can be compared | `metric` is sales, orders or average_order_value |
| `get_tables` | `outlet` | The table occupancy right now, per outlet | Occupied / available, up to 15 tables |
| `get_menu_performance` | `period`, `outlet` | The best and the worst selling menu items | Cancelled lines are excluded |
| `get_staff` | `outlet` | The headcount per outlet and per role | **Counts only, never names** |
| `get_customers` | `period`, `outlet` | How many guests were served, and how many came back | **Counts only, never names** |
| `get_payments` | `period`, `outlet` | The payment mix — how much came in per method | Per currency, per method |
| `get_alerts` | `outlet`, `limit` | The recent AI alerts — what the system flagged and why | The newest first, capped at `MAX_ROWS` |

The periods are a closed set: `today`, `yesterday`, `last_7_days`, `this_week`,
`last_30_days`, `this_month`, `year`. A tool that cannot resolve a period **says so rather
than guessing**.

| Tool | Backed by | What it answers |

| `get_stock_movements` | `inventory.py` | The purchase and waste history — what is being thrown away |
| `get_purchase_orders` | `purchase_orders.py` | The open purchase orders and their status |
| `get_suppliers` | `suppliers.py` | The suppliers, their lead times and their prices |
| `get_recipes` | `inventory.py` (recipes) | What is in a dish — the cost behind the price |
| `get_promotions` | `promotions.py` | The running promotions, and how often each is used |
| `get_vouchers` | `vouchers.py` | The issued, redeemed and expired vouchers |
| `get_loyalty_members` | `loyalty.py` | The members, their points and their last visit — **counts and tiers, not names** |
| `get_forecast` | `ai_forecast.py` | The demand forecast for the coming days, and the staffing it implies |
| `get_shift` | `users.py` (clock), `staff` routes | Who is clocked in, who is not, the overtime |
| `get_order` | `order.py` | One order — its lines, its status, its payments |

### 4.3 The tools we plan to add — draft and action

**Draft** (produces a proposal; changes nothing) and **action** (changes something; needs a
human's approval and writes an `ai_actions` row). The route in the middle column is the
existing endpoint the tool must go through — the agent never writes to the database.

| Tool | Kind | Goes through | Approval |
|---|---|---|---|
| `draft_purchase_order` | draft | `purchase_orders.py` `POST /` | — |
| `draft_promotion` | draft | `promotions.py` `POST /` | — |
| `draft_campaign` | draft | `ai/__init__.py` `POST /api/ai/campaigns` | — |
| `draft_price_change` | draft | `menu.py` / `order_pricing.py` | — |
| `draft_stock_transfer` | draft | `transfers.py` `POST /` | — |
| `draft_voucher_issue` | draft | `vouchers.py` `POST /issue` | — |
| `draft_shift_swap` | draft | `users.py` (clock / roster) | — |
| `send_purchase_order` | action | `purchase_orders.py` `PUT /{id}/status` | required |
| `create_promotion` | action | `promotions.py` `POST /` | required |
| `execute_campaign` | action | `ai/__init__.py` `POST /campaigns/{id}/execute` | required |
| `apply_price_change` | action | `menu.py` | required (money) |
| `record_stock_waste` | action | `inventory.py` `POST /stock-movements/waste` | required |
| `issue_voucher` | action | `vouchers.py` `POST /issue` | required |
| `acknowledge_alert` | action | `ai_security.py` `POST /alerts/{id}/acknowledge` | required |
| `notify_staff` | action | `notifications.py` | required |

**Two things deliberately absent** from the action list: anything that **refunds or voids a
paid order**, and anything that **changes a price the customer has already been quoted**.
Both are money, both are irreversible from the tenant's point of view, and both are the
manager's call in person. If they are ever added, they get the strictest approval rule in the
product — and they go to the manager, never to the agent.

### 4.4 The model proxy

In an MCP setup the *client* holds the LLM, so per-tenant token cost is invisible to us
unless the client uses **our** proxy. The proposal: the backend exposes a tenant-scoped,
OpenAI-compatible model endpoint; the client's model node points at it; the server logs tokens
per tenant, enforces the model, caps spend, and refuses a tenant whose plan lapsed. The same
trick the house already uses for the plan read (`plan_features.py` over the house's loopback
path).

Without this, the cost of a proactive agent is unknown and unbounded — and a proactive agent
that talks every morning for every outlet is exactly the case that turns a margin into a loss.

## 5. Data and configuration

### 5.1 New tables (proposal)

| Table | Holds |
|---|---|
| `tenant_agent_profiles` | One row per tenant: the profile of §3.4. |
| `agent_tokens` | The MCP credentials: `customer_id`, `outlet_id`, `scope`, `plan row`, `revoked`. |
| `ai_actions` | The audit row: agent, tenant, outlet, tool, arguments, result, approval, timestamps. |
| `ai_action_proposals` | A pending draft awaiting a human — the approval queue's payload. |
| `domain_events` | The outbox: the event, the tenant, the payload, the delivery state. |

All five are tenant-scoped by `customer_id`, and the outlet scope is a column — the same
"tenant = the restaurant group" rule the delivery leg and the AI tools already use.

### 5.2 Reused configuration

- `outlet_settings.bot_name` / `bot_language` / `bot_greeting` / `ai_enabled` — the profile
  **seeds** from these, so a tenant that has already named its bot sees its name carried over.
- The feature row and the plan gate — unchanged; the AI Manager rides the existing
  `require_plan_feature` machinery (§6).

### 5.3 The model

MiniMax, as today (`settings.MINIMAX_MODEL`, the `ai/minimax.py` helper). One change worth
making: the agent's calls should go through **one** client with a **cost log** — the number of
calls, the tokens and the tenant they belong to. Without that, a proactive agent that runs
every morning for every outlet is an unbounded bill and nobody knows whose it is.

## 6. Plan and role gating

The house has two independent gates, and the agent needs both:

- **The role** says what a *person* may do with a kind of data.
- **The plan** says what the restaurant *bought*. `require_plan_feature` compares the feature's
  **display name** against the tenant's list, which is read from the website API over the
  house's loopback path.

**Plan rows.** The live feature table holds 44 rows, of which the AI category is:

| Row | Display name | Pro | Enterprise |
|---|---|---|---|
| `ai_chatbot` | AI Chatbot | yes | yes |
| `ai_tools` | AI Tools | yes | yes |
| `ai_customer_insights` | AI Insights | yes | yes |
| `ai_menu_analytics` | Menu Analytics | yes | yes |
| `ai_campaigns` | AI Campaigns | yes | yes |
| `ai_competitor_analysis` | Competitor Analysis | no | yes |
| `Competitor Discover` | Competitor Discover | no | yes |

Plus the settings row `ai_chatbot_setting` → **AI Chatbot Settings** (Pro and Enterprise).
Starter and Basic carry **no** AI row at all.

**The proposal:** two new rows.

| Row | Display name | Plan |
|---|---|---|
| `ai_agent` | AI Agent | Pro — read-only agent (MCP read tools, profile, briefing, inbox) |
| `ai_agent_actions` | AI Agent Actions | Enterprise — the agent may also *act* (draft + action tools) |

The two-row split is deliberate: **the agent that reports is a different purchase from the
agent that writes**, and the write one is the one that needs the audit, the approval queue and
the review. Splitting them also means a tenant can buy the briefing on Pro and not be
refused at runtime for a missing entitlement — the plan gate refuses a *route*, and an action
is a route.

**The per-tenant exception already exists.** `customer_feature_overrides` lets the admin grant
or refuse a feature for one customer with a reason and a `created_by`. So the "AI Manager" can
be sold to a single tenant on a plan that does not include it, without a new billing path —
the row is written, the POS cache is notified (`notify_pos_plan_changed`), and the tenant's
agent switches on.

**The role.** The agent is not a person, so it gets its own entry in `ROLE_PERMISSIONS`:

- `ai:read` — everything today's tools already need.
- `ai:act` — the draft and action tools, and nothing else.
- `ai:approve` — **not** given to the agent. Ever. The approval is a human's.

A human who approves an action is recorded as the approver, with their own permissions checked
at that moment — so the manager's `ai:*` and the admin's `ai:*` still differ, and a staff
member cannot approve a price change.

**The MCP token's scope is a third, separate axis.** A token's scope (`read` / `draft` /
`action`) is checked **at the transport**, before the tool body runs — so an agent that
somehow tries an action tool with a read token is refused without the tool ever seeing the
request.

## 7. Where n8n fits — and where it does not

*(v1.1: this section was rewritten. In v1.0 n8n was the proposed agent runtime; Kens pushed
back on that and proposed MCP instead. The verdict is now the opposite: n8n is one client
among many.)*

### 7.1 What n8n is good at

- Letting a **tenant** wire their own automations without us building each one: WhatsApp
  broadcasts, a delivery aggregator, an accounting export, a Google Sheet, a Telegram channel.
- Surviving the long tail of integrations we would never ship.
- Being **visible** to the tenant — the flow is in a UI they can open and read.

### 7.2 What n8n is bad at, for this job

| Problem | Why n8n does not solve it |
|---|---|
| **Tenant isolation** | A flow runs with the credentials it was given. Getting "this flow may only ever read this tenant's data" right means re-implementing the isolation the POS already has in `require_outlet_access` and the tenant scope on every tool. |
| **The money rules** | The agent must never be able to write a price the pricing engine would not have written. A workflow that calls the POS API is subject to the POS's rules; a workflow that writes to the database directly is not. |
| **Plan gating** | `require_plan_feature` refuses a route for a tenant that did not buy it. A tenant's n8n flow is outside that gate unless we make it call our gated routes — at which point n8n is a caller, not the brain. |
| **The agent's own identity** | The agent needs a tenant profile, a working-hours rule, an escalation threshold and an audit trail. That is data the POS must own; it cannot live in a workflow JSON. |
| **Cost** | A proactive agent that runs every morning for every outlet is a per-tenant bill (model calls + n8n executions). That has to be priced deliberately, not discovered later. |
| **The licence, if the tenant ever logs in** | n8n is under the **Sustainable Use License**, which restricts hosting n8n as a service to clients and embedding it in a product without a commercial agreement. Running n8n internally, one instance, one workflow per tenant, is ordinary internal use and is fine. Giving the tenant a login into our n8n is selling access to n8n — that needs a commercial licence, and the per-project RBAC that isolates one tenant's workflows from another's is an Enterprise feature (Community Edition has no project isolation at all). |

### 7.3 The shape that works

**The POS owns the agent's tools and identity; n8n is a client.**

n8n has an **MCP Client Tool** node — an MCP client that attaches to an AI Agent node's
tools — so n8n consumes our MCP server as-is, with no bespoke integration code. A tenant's
n8n workflow becomes: *a trigger (schedule or our webhook) → the AI Agent node → the MCP
Client Tool pointing at our server → our tools → the answer.* The tenant's own runtime, the
tenant's own connectors, and **not one line of our code in the loop**.

But the same shape serves a Telegram bridge, a WhatsApp bot, or a future OpenClaw agent with
no change to the server. That is the whole point of the MCP decision.

**If n8n is not installed, nothing above changes.** The product does not depend on it.

## 8. The phases

Each phase names what it **does not** do. Nothing in Phase A depends on Phase C, and Phase C
does not depend on Phase D.

### Phase 0 — the MCP server (read-only)

**Does:** the MCP transport on the existing FastAPI app; the tenant-scoped token; the 10 read
tools of §4.1 exposed through one registry; the plan and permission gates applied at the
transport; the model proxy sketch.

**Does not:** write anything; emit events; change the chatbot's behaviour; involve n8n.

**Proves:** one tenant, one outlet, one token — a client outside the POS calls
`get_sales` and gets that outlet's numbers, and a second tenant's token gets a different
tenant's numbers. The identity model is proven before anything risky is built on it.

### Phase A — the action layer

**Does:** extend the tool registry with the draft and action tools of §4.3; add the `agent`
role with `ai:act`; add the `ai_actions` audit table and the `ai_action_proposals` queue;
deliver the proposals into the existing notification inbox; a human approves.

**Does not:** emit events; run on a schedule; introduce n8n.

**Proves:** the agent can propose a purchase order from the inventory suggestion the AI
already makes, a manager sees it in the inbox, the manager approves, a purchase order exists,
and `ai_actions` holds the whole story.

### Phase B — the tenant profile

**Does:** `tenant_agent_profiles`; the profile screen; the profile seeds from the outlet's
existing bot settings; the profile's `allowed_actions` narrows what the agent may call; the
`runtime` field names the client.

**Does not:** introduce new capabilities — it configures the ones Phase A built.

**Proves:** two tenants with different personas, hours and allowed actions get visibly
different behaviour from the same engine, and no code changed between them.

### Phase C — the trigger layer

**Does:** the `domain_events` outbox; emit the §3.5 events from the write paths; the signed,
tenant-scoped outbound webhook; the queue, the retry and the dead-letter log.

**Does not:** require n8n — the events are consumed by the native agent in Phase D; n8n is one
possible consumer.

**Proves:** an order placed in one tenant produces an event that reaches that tenant's
endpoint, signed and scoped — and that a second tenant's endpoint never sees it.

### Phase D — the AI Manager surface

**Does:** the briefing, the approvals queue, the alerts, the profile screen, the channel
settings, the agent-token screen; the native agent consumes the Phase C events and produces
the §3.6 briefing.

**Does not:** invent a new notification system — the inbox, the push service and the alerts
table are reused.

### Phase E — the money

**Does:** the `ai_agent` and `ai_agent_actions` feature rows; the plan assignment; the
per-tenant override path used for the first design partners; the cost log per tenant.

**Does not:** change how any other plan row is priced.

### Phase F — the connectors (optional, and last)

**Does:** the documented setup for a tenant's own runtime — n8n with the MCP Client Tool, a
Telegram bridge, the signed webhook, the token.

**Does not:** make any runtime a dependency of the agent. If n8n is not installed, nothing
above changes.

## 9. Open questions for Kens

1. **Does the agent act, or only propose?** The safest first ship is *propose only* — the
   agent drafts, a human approves, forever. The stronger version acts on low-risk actions
   (a draft purchase order, a report) and escalates the rest. Which do we want to sell?
2. **Which runtime ships first?** The MCP server is the constant; the *client* is a choice.
   Our own POS chatbot is the cheapest first client (it is already there). n8n is the most
   impressive demo. A Telegram bridge is the fastest to prove "another channel". My
   recommendation: our chatbot first, n8n second.
3. **Do we expose the MCP server publicly, or only to a tenant's own runtime?** Public means
   any MCP client can connect with a token — powerful, and a new public surface on the same
   app that holds the payment API. Tenant-private (a token bound to one tenant, one outlet)
   is the safe middle.
4. **Which channel first?** The staff-app inbox is free. Web push exists today for the
   customer app (`delivery_push.py`). WhatsApp is a third party, a cost and a policy
   question. Which is first?
5. **What does it cost?** Model calls scale with tenants and with how often the agent speaks.
   Per outlet? Per agent run? A message cap? This has to be decided before Phase C, not after.
6. **Do we need a human's approval for *every* action, or only for money?** A proposed price
   change and a proposed staff shift are not the same risk.
7. **Does the AI Manager replace the AI Tools page, or sit beside it?** The Tools page is
   five read-only tabs; the Manager would be the same insights with a trigger and a
   personality. Merging them is a cleaner product, but it is a change to a page tenants
   already use.
