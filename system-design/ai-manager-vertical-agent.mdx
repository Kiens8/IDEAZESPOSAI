## 1. The short answer

**The chatbot we have is good enough to sell. It is not an AI Manager, and no integration
tooling turns it into one.**

What exists today is a **pull** model: a human asks, the bot answers from POS data. What Kens
described is a **push** model with agency: a per-tenant agent that watches the store, knows the
tenant's own rules, and *does* things — always inside the POS's own rules.

The distance between the two is **not the model**. MiniMax already answers. The distance is
three missing layers:

1. **An action layer** — the agent can only read. Every write it performs is a new tool with
   its own permission, its own approval step and its own audit row.
2. **A trigger layer** — nothing in the product emits an event the agent could react to.
   The only webhooks that exist today are **inbound** payment ones.
3. **A tenant-profile layer** — the bot's behaviour lives in Python code paths. For the agent
   to be *the tenant's* agent, its persona, SOPs, permissions and working hours have to be
   **tenant data**, not code.

**The architectural answer (v1.1): the POS backend becomes an MCP server.** It is the
**tool layer** and the **identity layer** — every tool is tenant-scoped by the credential that
calls it, and every tool is a route underneath, so the existing gates apply for free. On top of
that server, the **agent runtime is the tenant's choice**: our own POS frontend chatbot, n8n, a
Telegram bridge, a WhatsApp bot, a future OpenClaw agent. We build the server once; the
runtime is pluggable.

**n8n is one client among many, not the architecture.** It has an MCP Client Tool node that
plugs straight into its AI Agent node, so it can consume our server as-is — but nothing in the
product depends on it, and the tenant never has to touch it.

## 2. What is actually built today (the audit this proposal starts from)

Every line below was read from the running code, not from the docs.

### 2.1 The chatbot

| Artifact | What it is |
|---|---|
| `backend/app/ai/chatbot.py` (1,295 lines) | The engine. Regex intent tables (`INTENT_PATTERNS`), a role map (`ROLE_INTENTS`), one handler per intent, and an AI fallback. |
| `backend/app/ai/chatbot_tools.py` (537 lines) | The tool registry the fallback calls — **10 tools, every one of them a read** (the catalogue is §4). |
| `backend/app/ai/minimax.py` | The shared MiniMax helper. Strips the `<think>` block so reasoning never leaks into a user-visible answer. |
| `backend/app/routes/chatbot.py` | `POST /api/chatbot/`, plus `/test`, `/greeting`, `/quick-replies`. Gated by `require_permission("ai:read")` **and** `require_plan_feature("AI Chatbot")`. |
| `backend/app/routes/ai_chatbot.py` | `POST /api/ai/chat/order` — the customer-facing conversational order. Same two gates. |

Two facts that shape the whole proposal:

- **The tool-calling loop only runs for `chatbot_type == "admin"`** (`chatbot.py`, the
  `tools = tool_schemas()` branch). A manager gets the AI fallback with the *snapshot* in the
  prompt; a staff member gets neither the tools nor a model. The tool machinery exists — it is
  simply gated to one role.
- **`MAX_TOOL_ROUNDS = 3`** (`chatbot.py:20`). The loop is bounded and the answer is written
  from the tool results. The pattern — *ask the model, let it call bounded read tools, write
  the answer from the numbers* — is the right one and Phase A extends it rather than replacing
  it.

## 3. The design

### 3.1 The shape

```
        ┌────────────────────────────────────────────────────────────┐
  MCP   │  POS BACKEND = the MCP server                              │
 clients│  • the tool registry (one registry, exposed twice)         │
        │  • tenant identity from the credential, never from args    │
        │  • every tool = a gated route underneath                    │
        │  • the tenant profile, the approvals, the audit log        │
        └───┬──────────────┬──────────────┬──────────────┬─────────┘
            │              │              │              │
    ┌───────▼──────┐ ┌─────▼─────┐ ┌──────▼──────┐ ┌─────▼──────┐
    │ our POS      │ │ n8n       │ │ Telegram /  │ │ the tenant │
    │ frontend     │ │ (MCP      │ │ WhatsApp    │ │'s own      │
    │ chatbot      │ │  Client)  │ │ bridge      │ │ agent      │
    │ (in-process) │ │           │ │             │ │            │
    └──────────────┘ └───────────┘ └─────────────┘ └────────────┘
            ▲                                            │
            │  the trigger layer (the one thing MCP        │
            │  does NOT give us): order.placed,            │
            │  stock.low, shift.ended, payment.failed      │
            └──────────────────────────────────────────────┘
```

**The POS backend owns the tools and the identity. The runtime is pluggable.**

Why this shape and not "n8n creates the agent per tenant":

- **Tenant isolation comes from the credential, not from code.** An MCP client presents a
  token; the server resolves it to `customer_id` + `outlet_id` and binds the session to it.
  Every tool call inside that session is scoped by construction. That is exactly the rule
  already held in `chatbot_tools.py` — `ToolContext(db, tenant_id, default_outlet_id)` and the
  `scope(outlet_arg)` helper, which **refuses** an outlet that is not the tenant's.
- **One tool surface, many channels.** Kens's requirement — *"triggered from our frontend POS,
  or another channel"* — is exactly the MCP contract. The POS frontend calls the tools
  in-process (it already does, 10 tools behind `MAX_TOOL_ROUNDS = 3`); an external channel
  connects over MCP. Same tools, same rules, same audit.
- **No licence problem.** MCP is a spec, not a product. n8n's Sustainable Use License never
  enters the picture, because n8n is a *client* of ours, not something we host and resell.
- **The tenant's agent runtime becomes the tenant's choice.** That is the most honest reading
  of "each tenant has its own vertical AI agent".

### 3.2 The MCP server (Phase 0)

**The transport.** FastAPI already serves the API; MCP is a second surface on the same
application, not a new service. Two decisions the design must make early:

- **Transport:** stdio is for local processes; a tenant's agent is remote, so the server must
  speak **Streamable HTTP** (the current MCP remote transport). n8n's MCP Client Tool node
  speaks it.
- **Authentication:** the server reuses the house's key model. A tenant's agent presents an
  API key; the server resolves it to `(customer_id, outlet_id, scope)` and refuses anything
  else. **The tenant comes from the credential, never from the model's arguments** — the rule
  `chatbot_tools.py` already states in its own docstring.

**The token.** The token lives in the **POS's own** database, in a new `agent_tokens` table
(`customer_id`, `outlet_id`, `scope` of `read` / `draft` / `action`, the plan row it rides on,
`revoked`), and a **new lookup function** resolves it into the same `key_info` dict shape the
rest of the app already understands — the fourth credential path beside the three hardcoded
keys in `PERMISSIONS` (§10.1). It is deliberately *not* the website API's `api_keys` table:
that table carries a `permissions` JSON column, but **the POS auth path never reads it** —
`get_key_info()` matches a literal string against the hardcoded `PERMISSIONS` dict — so a row
written there would not authenticate anything. A tenant holds one token for their agent,
revocable like any key.

**The plan is checked by the MCP layer, not by the route.** A lapsed plan must refuse the
tool call rather than the UI, but the house's plan gate cannot do that on this path:
`require_plan_feature` returns the credential untouched unless `key_type == "user"`, because
a session is what carries a plan (§8, Phase 0). The MCP transport therefore reads the plan
itself — the same `plan_cache` read and the same three states as §4.5 — at the transport and
again inside each tool body.

**One registry, two exposures.** The tool definitions live in **one** place and are rendered
twice: as the OpenAI-style function schemas MiniMax already consumes (`tool_schemas()`) and
as the MCP tool catalogue. If the two were written separately they would drift, and we would
have two truths about what the agent can do.

**The catalogue is filtered by the tenant's plan.** A tool declares the feature row that
gates it, and a tenant's agent is only offered the tools whose rows are in that tenant's live
feature list — read from the same source the API reads it from (`plan_cache` /
`fetch_plan_features`). The gate is re-checked on every call as well, because the plan can
change mid-session. The full rule, and why it is data rather than code, is §4.5.

**What the MCP server does NOT do:**

- It does **not** call the model. The *client* holds the LLM. (Consequence: the cost of a
  **foreign** client's model calls is invisible to us unless the client uses our model proxy
  — §4.4. **Our own runtime is the exception**: our chatbot calls MiniMax from our own
  backend on our own key, so that cost is already ours — though today we throw the number
  away instead of recording it. §4.6.)
- It does **not** trigger itself. MCP is pull-based; the proactive side is §3.5.
- It does **not** weaken a gate. Every tool is the same gated route the staff app uses.

### 3.3 The action layer (Phase A)

The tool registry grows a third kind of tool. The three kinds behave differently:

| Kind | Example | Approval | Audit |
|---|---|---|---|
| **Read** | `get_sales`, `get_alerts` | none | none |
| **Draft** | `draft_purchase_order`, `draft_campaign`, `draft_shift_swap` | **required** — it produces a *proposal*, and the approval is what creates the thing | the proposal is stored, and an `ai_actions` row is written when it is decided |
| **Action** | `send_purchase_order`, `execute_campaign`, `apply_price_change` | **required** — a human with the right permission approves | an `ai_actions` row |

The rules that make this safe, each one drawn from a rule the house already enforces:

- **The agent holds a token, not a god-mode key.** `ROLE_PERMISSIONS` maps *session* roles
  to permissions, and the agent has no session — so its authority is the token row: a scope
  (`read` / `draft` / `action`) checked at the transport, and a permissions list
  (`ai:read`, `ai:act`) the tool bodies check. It never inherits `admin:*`, and it never
  holds `ai:approve`.
- **The server owns the money and the price.** The agent may propose a price change; the
  write goes through the same pricing path the staff screen uses, so the promotion precedence,
  the tax and the order's locked price are unchanged (`pricing-engine-and-promotions.mdx`).
- **Every action is written down before it runs**, in an `ai_actions` row: the agent, the
  tenant, the outlet, the tool, the arguments, the JSON of what changed, who approved it, when.
  The `order_reprints` row is the precedent; the fields are the same idea.
- **An action that is refused is recorded as refused.** Silence is not success — the same rule
  the delivery sweep and the unattended watcher already live by.
- **The approval is a human's, in the POS.** The approval lands in the agent's own
  notification feed — the new generic `agent_notifications` table (§5.1), because the
  existing notification route is the *inventory* feed and cannot carry a decision. Nothing
  is auto-approved because a model was confident.
- **The MCP server refuses an action tool outright** when the credential's scope is `read`
  only. The refusal happens at the transport, before the tool body runs.

#### 3.3.1 The approval happens in the chat — with explicit controls

**Kens's decision: the agent drafts, a human approves — and yes, the human approves using
the chat.**

That last part is the one that needs writing down, because "the chat approves it" is the
phrase that hides a hole. **A chat transcript is not an approval channel.** If "yes" typed
into the chatbot can approve a purchase order, then the model — which writes the assistant's
side of that transcript — can approve its own draft by asking a question a human is likely
to say yes to. Approval cannot be a *phrase*.

**What exists today — nothing that approves anything.**

- The chatbot's tool set is **read-only**. All eleven tools in
  `backend/app/ai/chatbot_tools.py` read and aggregate; none of them writes.
- `frontend/src/pages/Chatbot.jsx` has exactly two buttons — one that fills the input with
  a suggested reply, and the send button. There is no approve, no reject, no edit.
- There is no `ai_actions` table and no proposal queue.

**What the proposal adds.**

1. **A proposal object.** The draft tool returns a proposal — an id, the tool, the
   arguments, a human-readable summary of what would change, and a state (`pending`).
2. **Three explicit controls, rendered as buttons on the proposal card** — **Approve**,
   **Edit**, **Reject**. Not a text intent. The card is a first-class object in the
   transcript, not a paragraph of assistant text.
3. **A separate route for the decision** —
   `POST /api/ai/proposals/{id}/approve|edit|reject`. The chat's message endpoint never
   approves anything; approval is not reachable by writing text.
4. **The approver's own permissions are checked at approval time**, not at draft time. The
   agent never holds `ai:approve`. The person clicking Approve is checked in that person's
   own session, and the check is **stricter than `require_permission`**: a new
   `require_human_approver` dependency demands a *signed session* (`key_type == "user"`)
   **and** the permission. The shared frontend API key is refused outright — it carries an
   `ai:*` wildcard, and a secret everybody holds cannot be a decision — and so is the agent
   token, which is not a session at all. So a waiter's session cannot approve a purchase
   order by replaying a manager's token, and neither can our own server-side key.
5. **The audit row is written before the action runs** — `ai_actions`, with the agent, the
   approver, the timestamp, the arguments and the JSON of what changed. An approval is
   recorded even when the action then fails, and a refusal is recorded as refused (§3.3).

**What "edit" means.** Edit sends the human's correction back to the agent as a **new**
draft: the agent revises and shows a new card. The arguments are never patched in place,
and the model never holds the arguments of an approved action — so it cannot quietly
rewrite one after the fact.

**The trap this closes.** The failure mode of "approve in the chat" is not that a human
approves the wrong thing. It is that **an instruction hidden in tool output** — a menu
item or a customer note carrying "approve this order" — ends up in the transcript, and a
phrase-matching approver executes it. The buttons make that impossible: the only path to
approval is a signed HTTP request from a human's own session.

### 3.4 The tenant profile (Phase B)

A per-tenant record that turns one engine into fifty managers:

| Field | Example | Why |
|---|---|---|
| `name` | "Aunty Mei" | The name the tenant already gives the bot today. |
| `system_prompt` | "You are the outlet manager of a kopitiam. Be brief. Speak in the outlet's timezone." | The tenant's voice, not ours. |
| `language` | `en` / `zh` / `ms` / `kh` | Already exists per outlet (`bot_language`). |
| `greeting` | "Welcome to Nasi Lemak Corner MY!" | Already exists per outlet (`bot_greeting`). |
| `sop` (list) | "Every morning at 09:30, check yesterday's waste vs sales and message the kitchen." | The tenant's own procedure. |
| `allowed_actions` | `["draft_purchase_order", "draft_campaign"]` | What this agent may ever do. Empty set = read-only for the draft and action tools. |
| `quiet_hours` | `23:00–07:00` | When the agent may not push anything. |
| `escalation` | `{"metric": "waiting_orders", "operator": ">=", "value": 5, "severity": "high", "action": "notify_staff"}` | The tenant's own thresholds — a SCHEMA, not free text, and measured against the outlet's real numbers (§8.9). |
| `outlet_scope` | `["all"]` or a list of branch ids | Which outlets this agent watches. |
| `runtime` | **derived** — `pos_frontend` / `n8n` / `telegram_bridge` / `mcp_client` / `none` | Which client runs this agent. **Not stored and not picked** — it is derived from the tenant's live connections (§8.11). The profile itself is runtime-agnostic. |
| `ai_enabled` | `true` | Whether the tenant's agent is switched on at all. |
| `is_active` | `true` | Whether this profile narrows the agent. A profile the tenant has switched off narrows nothing. |

**The `escalation` field is a schema, and it is evaluated.** The design first sketched it as
free text — *"money > RM 500 → notify the admin"* — and that was the honest shape of a
*threshold the code cannot check*. A note to oneself that the house never once looks at is
not a threshold, and a screen that shows it next to a working rule makes it look like one.
The built shape is a rule with a **metric the house can measure** (`waiting_orders`,
`sales_drop_pct`, `occupied_tables`, `open_alerts`), a **comparison**, a **number**, a
**severity** and an **action**; a metric that does not exist, a value that is not a number,
a comparison that is not one of `>=` `>` `<=` `<`, and an action that is not ours are all
**refused** — the same rule the allow-list follows, for the same reason: a typo must not
leave the agent quietly unable to do what the screen promised. The threshold decides **WHEN**;
the profile's `allowed_actions` decide **WHETHER MAY** — and a refusal is reported rather
than swallowed, because silence must never mean "healthy".

The tenant's **older free-text rules are kept**, under `legacy_rules`, and are **never
evaluated** — there was no evaluator before the real schema, so they were never thresholds.
They survive a save of the Agent tab, and the screen says plainly that they are inert,
because the tenant's own words are the tenant's business even when the house cannot act
on them.

This is the layer that makes the product *vertical*: the same engine, a different manager for
every tenant, and **no code change** to onboard a new one.

**The table above is the built schema, not the sketch.** The `persona` / `system_prompt` pair
of the first draft became one column, `system_prompt` — a persona and a prompt are the same
thing to a model, and two columns would have had to be reconciled at every read. The row's
owner is **one row per tenant**, addressed by `customer_id`.

**What the profile may do, and what it may not (§8.4).** The profile is the third gate and the
lowest: it sits below the plan gate and below the token's own scope, so it can only take a
tool AWAY. It never narrows the read tools, because the plan says what the tenant may
**see** and the profile says what this agent may **do** — two questions, two owners. And the
profile's three states are kept apart on purpose: no profile at all means the plan decides
(Phase A's behaviour), an active profile narrows, and an active profile with an EMPTY
`allowed_actions` is read-only.

### 3.5 The trigger layer — the event bus (Phase C)

MCP is **pull**: the client asks, the server answers. That covers "the manager typed a
question". It does not cover "the agent noticed something". For that the POS needs its own
side — an **event bus** — and the two are complementary rather than alternatives:

> **The event bus tells the agent THAT something happened. The MCP server tells the agent
> WHAT it may do about it.**

An event carries **no power and almost no data** — a name, a tenant, an outlet, an object id, a
timestamp. The agent reacts by calling the tools over MCP, with its own token, and the server
answers under the tenant's plan and the tenant's outlet scope. So the bus cannot leak what
the tools would refuse, and the tools cannot be reached without a credential.

#### 3.5.1 The four parts

**1. The emitters — in the write path, never a poller.**

| Event | Emitted when | A manager agent would… |
|---|---|---|
| `order.placed` | an order is created | flag a table that has been open too long |
| `order.paid` | the money settles | close the shift count |
| `order.stalled` | an order sits past the kitchen's reminder | tell the kitchen |
| `stock.low` | an ingredient falls to its threshold | draft a purchase order |
| `staff.clocked_in` / `shift.ended` | the shift starts and ends | compare the actual to the roster |
| `table.turned` | a table is settled | suggest the next seating |
| `payment.failed` | a gateway webhook says no | alert the counter |
| `refund.issued` | a refund is written | flag it for the security review |

The delivery module already settled the house rule: **the server owns the decision, and the
enforcement lives where the data is written.** An event emitted next to the order insert is
*truthful*; an event inferred by a cron that scans for rows is a *guess* — it double-fires,
and it cannot see a transaction that has not committed.

**2. The outbox — `domain_events`, written in the same transaction.**

The event row is written **in the same DB transaction as the business change**. That is what
makes it true: either the order exists and the event exists, or neither does. There is no
window where an agent saw an order that was rolled back. The row carries
`event_id`, `event_type`, `customer_id`, `outlet_id`, `payload` (ids only),
`created_at`, `delivered_at`, `attempts`, `state`.

**3. The dispatcher — one worker, the same pattern as the delivery sweep.**

The box already runs a cron worker (`scripts/sweep_delivery_entitlement.py`, 03:23 daily).
The dispatcher is the same shape: a script that reads the undelivered `domain_events`, asks
the **subscribers** which ones they want, and delivers. It is **not** a synchronous call from
the order insert — an event that blocks an order because a tenant's webhook is slow is a
self-inflicted outage on the live payment path. The order commits; the event is queued; the
dispatcher retries with a backoff and drops into a dead-letter log after N attempts.

**4. The subscriptions — per tenant, per outlet, per event type.**

A row saying *this tenant, this outlet, wants these events, delivered this way*:

| Subscription field | Example | Why |
|---|---|---|
| `customer_id` / `outlet_id` | 22 / 3 | The tenant — **never** from the payload |
| `event_types` | `["stock.low", "order.stalled"]` | What this agent cares about |
| `channel` | `in_app` / `telegram` / `webhook` | Where the answer goes |
| `endpoint` / `chat_id` / `bot_token_ref` | a chat id, a SecretRef | Where exactly |
| `runtime` | `pos_frontend` / `n8n` / `telegram_bridge` | Which client runs the agent |
| `quiet_hours` | `23:00–07:00` | From the tenant profile (§3.4) |
| `enabled` | true | The off switch a tenant can pull |

#### 3.5.2 The two shapes of a trigger

**Push (proactive).** The POS notices something.

```
order insert ──▶ domain_events row (same transaction)
                      │
                 dispatcher (cron / worker)
                      │  asks the subscribers
                      ▼
              tenant's agent runtime  ──▶ MCP tool calls (with the tenant's token)
                      │
                      ▼
              the answer lands on the channel
```

**Pull (reactive).** A human says something.

```
manager types in Telegram ──▶ the channel's bridge ──▶ the agent runtime
                                                              │
                                                              ▼
                                                  MCP tool calls (same token)
                                                              │
                                                              ▼
                                                   the answer goes back
```

Both shapes end at the **same MCP server, with the same token, under the same plan and outlet
scope**. That is the point of the split: the bus is a *notification mechanism*, the MCP server
is the *authority*. A tenant's Telegram agent and our own POS chatbot have exactly the same
powers.

#### 3.5.3 The channels, concretely

**Channel A — the frontend POS app (we already have it).**

The staff app's **notification bell** already polls `GET /api/inventory/notifications/`
every **30 seconds** (`frontend/src/components/NotificationBell.jsx`) and shows a badge — but
it is an **inventory** bell. The router is mounted at `/api/inventory/notifications`, the
table is `inventory_notifications`, and every row carries an `ingredient_id` with a
`notification_type` of low stock / out of stock / critical low. The bell is also hidden
entirely for a tenant whose plan has no Inventory feature (`INVENTORY_FEATURES` in the
component). It is an alert feed about ingredients, not a queue about decisions.

So the native channel needs **one new, generic, tenant-scoped table** — `agent_notifications`
(§5.1) — carrying the agent's briefings, its alerts and its pending approvals, each row
addressed to an outlet with a read state. One table, three kinds, one unread count. The
existing inventory notifications are untouched; the bell grows a second source rather than
being bent into a shape it was never built for.

For a phone, `delivery_push.py` already speaks **VAPID web push** — the transport is
reusable. The **subscription is not**: `push_subscriptions.dining_customer_id` is `NOT NULL`
and `subscribe()` takes a dining member's id, so every row in the table is a customer's phone
for delivery news. A manager's phone is a new subscription (a staff-keyed row, or a sibling
table) — new work in Phase C, not a re-use of an existing one.

**Channel B — Telegram (the tenant's own channel).**

This is the case Kens named, and it is the one that makes the runtime swappable:

- **The tenant connects Telegram** — a bot token stored as a **SecretRef** (never a plain
  value, never in the workflow JSON), the chat id bound to `customer_id` + `outlet_id` in the
  subscription row. One subscription = one tenant + one outlet + one chat.
- **Inbound** — Telegram posts the message to a webhook; the bridge resolves the chat id to
  the tenant, then the agent runtime calls our MCP server with that tenant's token. The
  bridge never touches the database — it is a client, exactly like n8n.
- **Outbound** — the dispatcher delivers the event to the runtime; the runtime calls the
  tools and sends the answer to the chat.
- **The channel is not the identity.** The chat id is a *routing* fact. Every tool call still
  arrives with a token that resolves to the tenant, so a misrouted or spoofed message cannot
  reach another restaurant's data — the token's scope is what decides.
- **The POS backend has no Telegram code today.** `grep -rn telegram backend/app` returns
  nothing; the only Telegram in the house is the OpenClaw gateway's own channel. So this
  channel is new code, and it lives in the *bridge*, not in the POS.

**Channel C — a signed webhook (the tenant's own runtime).**

The dispatcher POSTs the event to the tenant's endpoint with a signature over the body, a
timestamp and the tenant id, scoped to that tenant's key — the pattern
`backend/app/routes/internal.py` already uses for `/plan-changed` and `/order-paid`. This is
the channel n8n consumes, and the channel any other runtime consumes.

#### 3.5.4 The rules that keep the bus honest

- **The event carries no money and no personal data.** An event says *which* order, not what
  it cost and who it belonged to. The agent fetches the detail through a tool, under the
  gate. A webhook payload that carried the order total would leak it to whatever endpoint the
  tenant pointed at.
- **At-least-once, and the receiver must be idempotent.** The dispatcher may deliver twice
  (it crashed after the push and before the mark). Every event carries a stable `event_id`, and
  a consumer that acts on it must record what it has already acted on.
- **A failed delivery is a recorded failure, not silence.** Dead-lettered events are visible
  in the admin app. The house already lives by this — the unattended watcher rule: *silence
  must never mean "healthy."*
- **The plan gate applies to the events too.** A tenant on Pro must not receive a
  `stock.low` event, because `Inventory` is an Enterprise row. The dispatcher asks the same
  feature list the tools ask, and drops an event whose module the tenant does not hold.
- **Quiet hours are the tenant's, and they are enforced here.** An event that arrives at 02:00
  is held, not dropped — it is delivered when the tenant's day starts.
- **One event, one tenant.** The dispatcher never fans an event out across tenants, and the
  tenant id on the row is the tenant the event belongs to.

### 3.6 The surface (Phase D)

**Where this lives: the FRONTEND POS STAFF APP.** Not the website admin app, not the
customer app, not a separate agent console. Concretely, it is the staff app's **existing
`/ai-tools` route** — `frontend/src/App.jsx:496` → `frontend/src/pages/AI/index.jsx` —
which Kens has decided the AI Manager **replaces** rather than sits beside.

That is the answer to "where is the §3.6 surface implemented?": the same React app, under the
same `/api` base, with the same session cookie, behind the same nav gating. **One page
changes. The app does not gain a second front door.** The chatbot at **`/chatbot`** stays
where it is — it remains the conversational surface, and the approval cards of §3.3.1 appear
inside it.

The page carries four sections:

- **Today** — the briefing: sales against the same hour yesterday, orders waiting, tables
  occupied, anything the agent thinks the manager should know, in the outlet's timezone.
- **Needs you** — the approvals. A draft purchase order, a proposed campaign, a price change.
  Approve, edit, or reject — each one an audit row, and the same three controls the chat
  offers (§3.3.1). The chat card and the page card are two views of **one** proposal, not
  two queues.
- **Alerts** — the agent's findings, next to the existing AI alerts, with the same
  acknowledge path (`AIAlert` already has one).
- **Agent** — the profile from §3.4, the working hours, the allowed actions, the escalation
  thresholds, the channel the briefing arrives on, and the **agent token** the tenant hands to
  their own runtime.

**What happens to the five tabs the page carries today.** The current AI Tools page is five
read-only tabs — Insights, Menu Analytics, Campaigns, Competitor Discover, Competitor
Analysis — each behind its own feature row and plan. The Manager keeps that material; what
it adds is the trigger and the personality. **Proposal, for Kens to confirm in the design
review:** Insights and Menu Analytics are what the agent reads to build *Today* and *Alerts*,
so they become sections rather than tabs; Campaigns becomes the surface the agent drafts
into; and the two competitor tabs stay as they are, under their own feature rows, because
competitor data is not the tenant's own store and does not belong inside an agent that
manages an outlet.

**The nav and the plan do not move.** `navItems.js` keeps one AI entry — the `/ai-tools`
entry, still behind the `AI Tools` feature row — instead of two. A tenant on a plan without
`AI Tools` does not see the page today and does not get the Manager page later. The
`AI Tools` row is what the page is called and what it is gated by; the content underneath it
is what Phase D replaces.

### 4.4 The model proxy — a Phase F question, not a Phase 0 one

In an MCP setup the *client* holds the LLM. For a **foreign** runtime — n8n, a Telegram
bridge, a tenant's own agent — that means per-tenant token cost is invisible to us, because
their model key, their bill. The proxy closes that: the backend exposes a tenant-scoped,
OpenAI-compatible model endpoint, the client's model node points at it, and the server logs
tokens per tenant, enforces the model, caps spend, and refuses a tenant whose plan lapsed.
The same trick the house already uses for the plan read (`plan_features.py` over the
house's loopback path).

**But our own runtime does not need it, and that changes the priority.** Our chatbot calls
MiniMax from our own backend, on our own key — `ai/chatbot.py` posts to
`settings.MINIMAX_BASE_URL` with `settings.MINIMAX_API_KEY`. The browser never holds a model
key; it posts to `/api/chatbot/` and the backend does the rest. So for the runtime Kens
picked first, the cost is **already ours, already attributed to a tenant by the request, and
already gated** by `require_plan_feature("AI Chatbot")`. There is nothing for a proxy to
discover.

That is why the proxy is **Phase F**, where it belongs: it exists for the tenant who brings
their own runtime, and it is only worth building once that tenant actually exists. For the
proactive agent, the cheaper and more direct instrument is **§4.6** — record the `usage`
block the response already carries, at the call site we already own.

*(v1.14: **the proxy is BUILT** — `backend/app/services/agent_proxy.py` and
`backend/app/routes/agent_proxy.py`, mounted at `/api/agent-proxy/v1`. The recorded answers
are in §8.10. The short version: it is OpenAI-shaped, it takes the agent token and nothing
else, the tenant comes from the credential, the gates run before the model, and it refuses
to stream rather than pretending to.)*

### 4.5 The gate every tool carries

Every tool above declares **one feature row** — the row of the module it touches. That row
is the tool's plan gate. Three rules follow from it.

**Rule 1 — the gate is data, never a tier name.** The tool does not know what "Pro" or
"Enterprise" is. It knows it touches `Inventory`. The plan row for `Inventory` is read live
from the website API's `features` / `plan_features` tables, through the machinery the house
already has:

- `backend/app/services/plan_features.py` — `get_plan_features(tenant_id, fetch)` reads the
  plan's feature **names** and caches them. The name it collects is the row's `tab_name`
  (the website API's customer-features route returns `tab_name` under the key `name`), so
  that string — not `display_name` — is what the gate compares. Today all 44 live rows have
  the two identical, which is why the source comment calls it "the display name"; a new row
  must set both to the same string, or the gate compares a string that was never put in the
  plan.
- `backend/app/core/plan_cache.py` — the cache distinguishes three states, and the third one
  is the one that matters:
  - a **fresh or stale known list** — the tenant bought these features;
  - an **empty known list** — the tenant bought no paid feature (a Starter tenant);
  - **`None`** — the plan could not be read and was never known.

`None` is not "no features". It is "we could not ask". The delivery entitlement pattern
already draws this line: it checks the plan includes delivery, then that the subscription is
active, then that the outlet's own delivery switch is on. **We could not ask is not the same
as not allowed** — a lookup failure must never be reported to a tenant as a refusal, because
the tenant *has* the feature and we simply could not confirm it.

**Rule 2 — no tier names in code.** The catalogue never says "Pro-only" or "Enterprise-only".
It says "`Inventory`". If the admin later moves the `Inventory` row from Enterprise to Pro —
which is exactly what Kens said could happen — the tools that touch inventory become
available to Pro tenants **with no code change and no redeploy of the catalogue**. The tier
names in the tables in §4.1–4.3 are annotations of *today's* plan assignment, not the rule.
They are marked as such.

**Rule 3 — the gate is checked on every call, not only when listing.** Two checks, both
required:

1. **At catalogue time** — `list_tools` (MCP) / the tool-schema registry returns only the
   tools whose feature rows are in this tenant's live feature list. A Pro tenant's agent is
   never even *offered* `get_inventory_levels`.
3. **At call time** — every tool body re-checks the gate before it runs. The plan can change
   mid-session: the tenant upgrades, downgrades, lapses, or an admin moves a feature row
   between plans while the agent is holding a session. The listing was true when it was made;
   the call-time check is what makes it true *now*. The read is served from
   `plan_cache`, so it is cheap — and a cache miss costs one live read, not a refusal.

**And the check has to be ours on the agent's path.** `require_plan_feature` is a **no-op for
a key caller**: it returns the credential untouched unless `key_type == "user"`, because a
session is what carries a plan (the route dependency's own docstring says server-to-server
callers "are not governed by a browser session and are not checked here"). The chatbot is a
session, so its route gate works. The MCP transport is **not** — it presents a key — so a
tool reached only through the route dependency would be **ungated**. The MCP layer checks the
plan itself, from the same `plan_cache`, with the same three states (§8, Phase 0).

**What a refusal looks like.** When a tool is called and the gate fails, the tool returns a
**module-level refusal**, in the same shape as every other answer (the `data` field):

> `This restaurant's plan does not include the Inventory module.`

It does **not** return an empty result, and it does **not** invent plausible data. An empty
result would be read by the model as "there is no stock" — a refusal is the only answer that
cannot be misread.

**Why this matters more than it looks.** Today the chatbot's read tools are gated **once, at
the route**, by `require_plan_feature("AI Chatbot")` — no tool carries its own module gate.
Two consequences follow:

- A tenant with `AI Chatbot` can ask the agent about AI alerts, the demand forecast and the
  order insights, whose own routes (`ai_security.py`, `ai_forecast.py`, `ai_orders.py`) carry
  **no plan gate at all** — only `ai:read`. The features are paid for elsewhere; the agent
  reaches them anyway.
- Several modules are gated in the **frontend only**. `frontend/src/config/navItems.js` hides
  Promotions, Loyalty, Vouchers and every Inventory page by feature row, but
  `promotions.py`, `vouchers.py` and `loyalty.py` carry **no `require_plan_feature`**. The
  screen hides what the API does not refuse — hiding a menu item is a usability decision, not
  an authorisation boundary.

Per-tool gating closes both, and it is the difference between an agent that is *about the
business* and an agent that is *about the plan*.

### 4.6 The metering we do not have

The MiniMax API returns a `usage` object with every response — prompt tokens, completion
tokens, and for a reasoning model like `MiniMax-M3`, the thinking tokens as well. **Today the
chatbot discards it.** The parser keeps `choices[0].message` and nothing else
(`ai/chatbot.py`), so there is no token count anywhere in the product — `grep` for
`prompt_tokens` across the backend returns nothing.

That is acceptable while the model is only ever called because a human asked something, and
the `AI Chatbot` plan row is the price. It stops being acceptable the moment the agent
speaks **on its own**, because then two questions become unanswerable: which tenant spent
the tokens, and when to stop.

The fix is deliberately small, and it belongs at the call site rather than behind a proxy:

- Read `usage` off the response and log it with the tenant, the outlet and the model.
- One row per call is enough to start.
- **Size the cap with the amplification in mind.** `MAX_TOOL_ROUNDS = 3` means one question
  can cost up to three round-trips, each up to `max_tokens: 800`, and `MiniMax-M3` is a
  *reasoning* model — it spends part of the budget thinking before it answers. One question
  is not one token count. (The translator already learned this the hard way:
  `TRANSLATION_MAX_TOKENS = 16000`, with the comment *"With a small ceiling the response
  comes back empty and nothing gets translated."*)

## 6. Plan and role gating

The house has two independent gates, and the agent needs both:

- **The role** says what a *person* may do with a kind of data.
- **The plan** says what the restaurant *bought*. `require_plan_feature` compares a
  **feature name** against the tenant's list, which is read from the website API over the
  house's loopback path. That name is the row's `tab_name` (§4.5) — so a new feature row has
  to carry the right `tab_name`, or the gate compares a string the plan does not hold.

**Plan rows.** The live feature table holds 44 rows, of which the AI category is:

| Row | Display name | Pro | Enterprise |
|---|---|---|---|
| `ai_chatbot` | AI Chatbot | yes | yes |
| `ai_tools` | AI Tools | yes | yes |
| `ai_customer_insights` | AI Insights | yes | yes |
| `ai_menu_analytics` | Menu Analytics | yes | yes |
| `ai_campaigns` | AI Campaigns | yes | yes |
| `ai_competitor_analysis` | Competitor Analysis | no | yes |
| `Competitor Discover` | Competitor Discover | no | yes |

Plus the settings row `ai_chatbot_setting` → **AI Chatbot Settings** (Pro and Enterprise).
Starter and Basic carry **no** AI row at all.

**The proposal:** two new rows.

| Row | Display name | Plan |
|---|---|---|
| `ai_agent` | AI Agent | Pro — read-only agent (MCP read tools, profile, briefing, inbox) |
| `ai_agent_actions` | AI Agent Actions | Enterprise — the agent may also *act* (draft + action tools) |

The two-row split is deliberate: **the agent that reports is a different purchase from the
agent that writes**, and the write one is the one that needs the audit, the approval queue and
the review. Splitting them also means a tenant can buy the briefing on Pro and not be
refused at runtime for a missing entitlement — the plan gate refuses a *route*, and an action
is a route.

**The per-tenant exception already exists.** `customer_feature_overrides` lets the admin grant
or refuse a feature for one customer with a reason and a `created_by`. So the "AI Manager" can
be sold to a single tenant on a plan that does not include it, without a new billing path —
the row is written, the POS cache is notified (`notify_pos_plan_changed`), and the tenant's
agent switches on.

**The agent's authority is its token, not a role.** `ROLE_PERMISSIONS` maps **session roles**
to permissions — the browser's signed-in user is looked up there by role
(`get_auth_context`), and an API key carries its own permission list instead. The agent holds
a token, not a session, so giving it an entry in `ROLE_PERMISSIONS` would describe nothing
that exists. Its authority is the token's **scope**:

- `read` — everything today's tools already need.
- `draft` — the draft tools, and nothing else.
- `action` — the action tools, and nothing else.

**The human's authority is a new permission.** `ai:approve` is added to `manager`; the
`admin` already covers it through its existing `ai:*` wildcard, and `staff` has neither — so
a waiter cannot approve a price change. The agent's token **never** carries `ai:approve`:
the scope has no such value, and the approval is a human's. A human who approves an action is
recorded as the approver, with their own permissions checked **at that moment**, in their own
session — the manager's approval and the admin's approval are separate records with separate
permissions behind them.

**The MCP token's scope is a third, separate axis.** A token's scope (`read` / `draft` /
`action`) is checked **at the transport**, before the tool body runs — so an agent that
somehow tries an action tool with a read token is refused without the tool ever seeing the
request.

**Where the gate sits today, and where it moves.** The route-level gate is what the house
uses today, and it works — but it is one gate for a whole route. The chatbot's route carries
`require_plan_feature("AI Chatbot")` and that is the **only** gate on it: the read tools
inside have no gate of their own, so a tenant with `AI Chatbot` can ask the agent about
alerts, forecasts and order insights whose own routes carry no plan gate at all, and about
Promotions, Loyalty and Vouchers, whose routes carry none either — those are hidden in the
frontend only (`navItems.js`). Hiding a menu item is a usability decision; refusing a call is
an authorisation boundary.

The proposal moves the gate **down to the tool** (§4.5):

| | Today | Proposal |
|---|---|---|
| The gate | one per route, `require_plan_feature` | one per tool, carrying the feature row of the module it touches |
| Where it is checked | at the route, once, at request entry | at catalogue time **and** at call time, per tool |
| What a refusal says | the route returns 403 | `This restaurant's plan does not include the Inventory module.` |
| A tier change | a code change per route | a row move in `plan_features` — no code change |
| A lookup failure | the route refuses | **never** reported as a refusal — "we could not ask" is not "not allowed" |

The route gate stays — it is still the coarse boundary for the page. The tool gate is the
fine one, and the two are not redundant: the route gate answers *"may this tenant open the
AI Manager at all?"*, the tool gate answers *"may this agent read stock?"*.

## 7. Where n8n fits — and where it does not

*(v1.1: this section was rewritten. In v1.0 n8n was the proposed agent runtime; Kens pushed
back on that and proposed MCP instead. The verdict is now the opposite: n8n is one client
among many.)*

### 7.1 What n8n is good at

- Letting a **tenant** wire their own automations without us building each one: WhatsApp
  broadcasts, a delivery aggregator, an accounting export, a Google Sheet, a Telegram channel.
- Surviving the long tail of integrations we would never ship.
- Being **visible** to the tenant — the flow is in a UI they can open and read.

### 7.2 What n8n is bad at, for this job

| Problem | Why n8n does not solve it |
|---|---|
| **Tenant isolation** | A flow runs with the credentials it was given. Getting "this flow may only ever read this tenant's data" right means re-implementing the isolation the POS already has in `require_outlet_access` and the tenant scope on every tool. |
| **The money rules** | The agent must never be able to write a price the pricing engine would not have written. A workflow that calls the POS API is subject to the POS's rules; a workflow that writes to the database directly is not. |
| **Plan gating** | `require_plan_feature` refuses a route for a tenant that did not buy it. A tenant's n8n flow is outside that gate unless we make it call our gated routes — at which point n8n is a caller, not the brain. |
| **The agent's own identity** | The agent needs a tenant profile, a working-hours rule, an escalation threshold and an audit trail. That is data the POS must own; it cannot live in a workflow JSON. |
| **Cost** | A proactive agent that runs every morning for every outlet is a per-tenant bill (model calls + n8n executions). That has to be priced deliberately, not discovered later. |
| **The licence, if the tenant ever logs in** | n8n is under the **Sustainable Use License**, which restricts hosting n8n as a service to clients and embedding it in a product without a commercial agreement. Running n8n internally, one instance, one workflow per tenant, is ordinary internal use and is fine. Giving the tenant a login into our n8n is selling access to n8n — that needs a commercial licence, and the per-project RBAC that isolates one tenant's workflows from another's is an Enterprise feature (Community Edition has no project isolation at all). |

### 7.3 The shape that works

**The POS owns the agent's tools and identity; n8n is a client.**

n8n has an **MCP Client Tool** node — an MCP client that attaches to an AI Agent node's
tools — so n8n consumes our MCP server as-is, with no bespoke integration code. A tenant's
n8n workflow becomes: *a trigger (schedule or our webhook) → the AI Agent node → the MCP
Client Tool pointing at our server → our tools → the answer.* The tenant's own runtime, the
tenant's own connectors, and **not one line of our code in the loop**.

But the same shape serves a Telegram bridge, a WhatsApp bot, or a future OpenClaw agent with
no change to the server. That is the whole point of the MCP decision.

**If n8n is not installed, nothing above changes.** The product does not depend on it.

## 8. The phases

*(v1.6: this section was re-audited against the live code and re-ordered. The phase letters
are unchanged — §3.2 is still Phase 0, §3.3 Phase A, and so on — but four things moved, and
they are listed first because they are the reason the order is what it is.)*

### 8.1 What the re-audit changed

**1. The two feature rows move to Phase 0.** The plan gate compares a **string** — the row's
`tab_name` — against the tenant's live feature list, and that list is read from the website
API's `features` and `plan_features` tables. A gate can only be satisfied by a row that
exists. So if `AI Agent` and `AI Agent Actions` are created in Phase E, then through Phases 0
to D the gate reads "not in your plan" for every tenant including us, every gated tool
refuses, and none of the phases can be proven at all. The rows are **data, not code**: they
go in Phase 0, with their plan assignment, and Phase E keeps only the commercial packaging —
the price, the tiering decision, the per-tenant override for the design partners, and the
cost report over the usage log.

The row has **three** places to be written, and all three are needed:

- `website_api/app/core/seed_features.py` — for a fresh install. This file is **not** the
  source of truth for the live database: it holds 20 rows and the live `features` table holds
  44, so 30 live rows exist only in the database. A new row goes into the seed **and** into
  the live table.
- the live `features` table — `name` (`ai_agent`, `ai_agent_actions`), `display_name` (`AI
  Agent`, `AI Agent Actions`), `tab_name` (the same string), `category` (`ai`), `is_active`.
- the live `plan_features` table — `AI Agent` to Pro and Enterprise, `AI Agent Actions` to
  Enterprise, per §6.

**The gate string is `tab_name`, not `display_name`.** The POS reads the list from
`/api/admin/customer/{id}/features`, and that route returns the row's `tab_name` under the
key `name` — which is the key `fetch_plan_features` collects. Today the two are identical for
all 44 live rows, so the distinction is invisible; a new row must set both to the same
string, or the gate compares a string that was never put in the plan.

**2. The metering and the cap move forward, into Phase D.** The push side is the unbounded
side (§9.2): the pull path is bounded by a human asking, the proactive path is bounded by
nothing. So the `usage` log and the daily briefing cap ship **with** the briefing that first
spends a token without being asked — not after. A cost log added the morning after the first
unmetered briefing is a bill you can attribute but not prevent.

**3. Phase A's delivery target is a new table.** The "existing notification inbox" is the
**inventory** feed: `inventory_notifications`, every row carrying an `ingredient_id`, the
router mounted at `/api/inventory/notifications`, and the bell hidden entirely for a tenant
without an Inventory feature. It is an alert feed about ingredients, not a queue about
decisions. The proposals get the new generic `agent_notifications` table (§5.1).

**4. The agent's authority is its token, not a role.** `ROLE_PERMISSIONS` is a map of
**session** roles to permissions — the browser's signed-in user is looked up there by role.
The agent holds a token, so an entry in `ROLE_PERMISSIONS` would describe nothing that
exists. Its authority is the token row: a **scope** (`read` / `draft` / `action`) checked at
the transport, and a **permissions list** the tool bodies check (`ai:read`, `ai:act`).
`ai:approve` is only ever on a human session, and the human roles gain it explicitly
(`manager`; `admin` already covers it through its `ai:*` wildcard).

### 8.2 The dependency graph

```
Phase 0 ──> Phase A ──> Phase B ──> Phase C ──> Phase D ──> Phase E ──> Phase F
(MCP +    (the action  (the tenant  (the      (the       (the     (the
feature   layer)        profile)    trigger)  surface)  money)   connectors)
rows)
```

The edges that are not obvious from the list:

- **C depends on A** — the native channel writes into the `agent_notifications` table Phase A
  creates.
- **D depends on A, B and C** — the page shows A's proposals, B's profile and C's events.
- **E depends on nothing new in code** — it is pricing and packaging, and it can ship any
  time after Phase 0's rows exist.
- **F depends on A's registry and Phase 0's transport** — a foreign runtime is a client of
  what Phase 0 already built.

Nothing in Phase A depends on Phase C or Phase D. The **metering and the cap land in
Phase D**, with the briefing that first spends a token unasked.

### 8.3 What Phase A's implementation settled

The design left four questions open. The code answered them, and this is the record of how —
so the next reader does not have to re-derive them from the diff.

**1. A draft tool also waits for a human.** §4.3's table had the draft rows at "—" for
approval, while §3.3 had the draft producing "a *proposal*, nothing changes" and Phase A's
own proof section had a manager approving a *drafted* purchase order into a real one. The
implementation reads those together as: the *tool call* needs no approval — it changes
nothing — and the **approval is what creates the thing**. So both kinds produce a stored
proposal, both wait for a human, and both write an `ai_actions` row when they are decided.
The table's "Approval" column now reads `required` on every row.

**2. Draft against action is *what it asks for*, not *whether it needs approval*.**

| | The draft asks for | The action asks for |
|---|---|---|
| `purchase_order` | the order, in `pending` | the order, **sent** to the supplier |
| `promotion` | the promotion, **not running** | the promotion, **running** |
| `campaign` | the campaign, **not active** | the campaign, **executed** — vouchers sent |
| `price` | a price **derived from the live cost** at the margin asked for | a price **somebody chose** — the money action |
| `voucher` | the house **template's** terms — the draft may not invent the money | **bespoke** terms |
| `shift_swap` | the handover, drafted | — (the clock *is* the roster) |

The two that share a route — a promotion, a voucher — differ in exactly that way: the draft
takes the house's standard form and the action takes the bespoke one. That is what stops a
`draft` token from being a quieter `action` token.

**3. The approval runs the house's own routes, with the approver's session.** The approved
operation is executed by calling the POS backend's own endpoints over the loopback, with the
**approver's signed session cookie** forwarded. So the route's own permission, its own plan
gate, its own outlet tenancy and the pricing path all run *with that person's authority* —
and the agent never writes business data. It also means the permission the tool needs is
the route's own: `record_stock_waste` needs `inventory:write`, which the `manager` role does
not hold, so a manager is refused that one and the refusal is recorded.

**4. The approver must present a signed session, not merely hold the permission.** The
shared frontend API key carries an `ai:*` wildcard, so a plain `require_permission` check
would have let that shared secret approve a purchase order. `require_human_approver` demands
`key_type == "user"` **and** the permission, so the shared key, the agent token and the
`staff` role are all refused — and only a person in their own session decides.

**What was proven.** `backend/scripts/test_mcp_actions.py` — 53 checks against the live
server — covers the scope ladder at the transport, that a proposal changes nothing, that
only a person approves (agent token, shared key and staff session each refused), that the
approval runs the house's own route, that the `ai_actions` row was written **before** the
operation ran, that an edit creates a new proposal and never patches the old one's
arguments, that a refusal is recorded as a refusal, that the tenant is the session's
tenant, and that a failed operation is still on the record. Phase 0's three proofs still
pass unchanged (18 / 35 / 10).

### 8.4 What Phase B's implementation settled

Phase B was a configuration layer, so the questions it raised were mostly about **where the
authority comes from** and **what a profile is allowed to change**. The code answered them, and
this is the record of how — so the next reader does not have to re-derive them from the diff.

**1. The profile is a THIRD GATE, and the lowest one.** The engine of Phase A had two locks:
the credential's own scope (`read` / `draft` / `action`) and the tenant's live plan. The
profile is the third, and it sits **below** both, because it may only take a tool AWAY. A
profile can never add a tool the plan does not hold or the token's scope does not cover, so
configuring one can only ever make the agent more careful. The gate is applied in **two**
places, because a hidden tool and a refused tool are different things: the catalogue omits it
(`mcp_tool_catalogue`), and the call itself is refused (`check_profile_gate`). An agent that
is never offered a tool cannot try to call it, and an agent that tries anyway is told why.

**2. The profile does NOT narrow the read tools.** The plan says what the tenant may **see**;
the profile says what this agent may **do**. Two questions, two owners — so the ten read
tools are governed by the plan and the credential, exactly as in Phase A, and `allowed_actions`
holds only the draft and action tools. A tenant that wants a read-only agent writes
`allowed_actions: []`, which is explicit, visible and reversible.

**3. "No profile" means the plan decides — not read-only.** The alternative — "no profile means
read-only" — reads safer in the abstract, but it would silently demote every tenant that
bought `AI Agent Actions` to a read-only agent the moment this table shipped. The profile is
therefore an **opt-in narrowing**, and the three states are kept apart: no row (the plan
decides), an active row (it narrows), an inactive row (the plan decides again). An active row
with an empty allow-list is read-only, and that is a state a tenant reaches on purpose.

**4. The profile is addressed by the credential, never by a parameter.** Every profile route
reads the signed-in session's `customer_id`. There is no `customer_id` query parameter to
pass, so one tenant's manager cannot ask for another tenant's profile by typing their number.
The routes also **refuse a session that carries no tenant** rather than falling back to
something.

**5. The permissions are the house's own, and the profile is a MANAGEMENT surface.** Reads
need `ai:read`, writes and seeding need `ai:write` — so a **manager** may read and may not
write, an **admin** may do both, and **staff** may do neither. The design's §6 gate table
already said the campaign writes need `ai:write` and only the admin role carries `ai:*`; the
profile simply obeys the same table rather than inventing a rule of its own. The floor does
not configure the manager.

**6. The seed copies, and it falls back the way the house chatbot falls back.** The four
knobs come from the tenant's **first active branch**. When that branch has no settings row,
the profile takes the house chatbot's own fallback — **"Lumi"** — rather than coming out
nameless; and an existing settings row with an empty `bot_name` falls back the same way. The
seed **never overwrites** a profile that already exists: the tenant may have changed things
since, and a re-seed must not throw their work away.

**7. The two strict fields are strict for a reason.** An `allowed_actions` entry that is not a
real tool is **refused, not ignored** — a typo would otherwise leave the agent quietly unable
to do anything and nobody would know why. A branch in `outlet_scope` that is not the
tenant's is refused too, because the profile may narrow the tenant's own branches and may not
name another group's. A scope outside the tenant's branches is a refusal the agent explains
in its own words: *"the tenant profile's outlet scope does not include it."*

**8. The seed's two paths are proven separately, because they are different things.** Every
live branch of the house calls its bot "Lumi" in "en" with the bot switched on — which are
also the house DEFAULTS. A live tenant therefore **cannot** tell "the seed copied the branch's
settings" apart from "the seed fell back to the default". So the proof creates a **scratch
tenant** whose settings say something distinctive — a different name, a different language, a
greeting, and the bot switched off — and proves the COPY path there, and proves the FALLBACK
path on a branch that has no settings row at all.

**What was proven.** `backend/scripts/test_mcp_profile.py` — 59 checks against the live
server — covers that a profile with an allow-list narrows the catalogue and that a tool
outside it is refused **at call time**; that an empty allow-list is read-only; that the seed
copies the settings and falls back to "Lumi"; that a second seed does not overwrite; that two
tenants with different profiles get **visibly different behaviour from the same engine**,
which is the design's own proof; that the routes' permissions are manager-read, admin-write,
floor-neither; that one tenant cannot see another's profile; that the outlet scope narrows the
branches; and that a typo'd tool name, a foreign branch and an impossible quiet hour are all
refused rather than silently dropped. Phase 0's and Phase A's proofs still pass unchanged
(18 / 35 / 10 / 53 — **116 checks**).

### 8.5 What Phase C's implementation settled

Phase C was the trigger layer, so the questions it raised were about **where the event is
written, what happens when that write fails, and what an event may carry**. The code answered
them, and this is the record of how — so the next reader does not have to re-derive them from
the diff.

**1. THE EVENT IS WRITTEN IN THE CALLER'S TRANSACTION, AND THE CALLER COMMITS.** `emit()`
never commits and never rolls back. It writes one row and hands it back. The write path — the
order insert, the payment, the stock decrement, the clock-in — calls it and then commits as
it always did, and that one commit carries both the business change and the event. So there
is no window where an agent saw an order that was rolled back, and no window where the order
landed without its event. The proof pins this from both sides: a rolled-back write takes the
event with it, and a committed write carries it along.

**2. AN EMITTER FAILURE NEVER ROLLS BACK A SUCCESSFUL WRITE.** This was the one that could
have gone badly. A live payment must not fall over because an event row could not be written,
so `emit_event(...)` catches the failure, logs it loudly, and returns nothing — the business
write stands on its own. The proof forces the bus to fail (`emit` raises) and shows the order
still lands, with no half-written event row beside it. The trade is deliberate and is the
house's own rule: **the business write is the truth; the event is a notice about it.**

**3. THE TENANT COMES FROM THE ROW, NEVER FROM THE PAYLOAD.** An event's `customer_id` is
resolved from the business row that was just written — the order's own tenant, or the
outlet's tenant when the order carries none. A caller cannot name a tenant in a payload,
because a payload naming one is refused outright. The payload carries **ids and small facts
only**: the order id and number, the table id, the payment method, the reminder cycle. The
money and the personal data are deliberately absent, and a payload carrying either is
**refused** rather than written — the catalogue's own list of forbidden keys. An agent that
wants to know what the order cost fetches it through a tool, under the tenant's plan.

**4. THE CLAIM IS A COMPARE-AND-SET, NOT A LUCKY SEQUENCE.** `claim_events(...)` updates
only the rows that are still `pending` and reads back how many the worker actually won. Two
workers racing for the same row therefore produce ONE winner. The design's §10.1 said the
backend runs one uvicorn worker — that is a convenience, not a guarantee, and the claim does
not lean on it. The proof claims the same row twice and shows the second worker wins nothing.

**5. THE PLAN GATE APPLIES TO THE EVENTS TOO, AND THE REFUSAL IS VISIBLE.** A tenant that
did not buy `Inventory` receives no `stock.low` event — and the delivery row is written as
**skipped**, naming the module the tenant does not hold. A refusal a tenant cannot see is
indistinguishable from a bug, so it is recorded. The plan is read **live** from the website
API through the house's own `tenant_features`, with a cache, so the gate is proven against a
real tenant's real plan.

**6. QUIET HOURS HOLD; THEY NEVER DROP.** An eligible event inside the window is written as
**held**, with an `available_at` when the tenant's day starts, and the event goes back to
`pending`. Nothing is lost and nothing arrives at 3am. The proof shows the held event is
neither delivered nor dropped.

**7. A FAILED DELIVERY IS A RECORDED FAILURE, NOT SILENCE.** A webhook that cannot succeed
lands in the dead-letter log with the reason attached, and the tenant can read that log and
requeue it. Retries back off. The dead letter is a place a human looks — the opposite of a
silent drop.

**8. THE WEBHOOK IS SIGNED OVER THE BODY THAT ARRIVED.** The signature covers the body, the
timestamp and the tenant, in Stripe's shape (`t=<timestamp>,v1=<hex>`), and it is scoped to
the subscription's own secret — so one tenant's runtime cannot forge another's deliveries.
The proof verifies the signature over the body the endpoint actually received, and shows that
a **tampered body** and a **foreign secret** both fail to verify.

**9. ONE EVENT IS THE HONEST EXCEPTION: `order.stalled`.** Every other event is written next
to a business write. `order.stalled` has no write behind it — an order does not stall
because somebody wrote something, it stalls because the **CLOCK** moved — so it is swept.
Two things keep the sweep honest: the decision is the **server's** (the outlet's own
`order_reminder_minutes`, the same number the kitchen screen reads), and the event id is
**derived** from the order and the cycle, and the column is UNIQUE — so the second attempt in
the same cycle is a collision the database refuses, not a second reminder. Without that key,
a sweep running every minute would remind the manager sixty times an hour. The proof shows
one reminder per cycle, no second reminder for the same cycle, and a new reminder for a later
one.

**10. AND THE TENANT OF A SWEPT ORDER IS READ THE SAME WAY.** The sweep originally read the
tenant from the order row alone, while every emitter resolved it from the order **or** the
outlet. An order written without an explicit tenant therefore reached no subscriber at all —
silently, with nothing to show for it. The code now resolves the tenant by the same rule the
emitters use, so the sweep and the emitters cannot drift apart.

**What was proven.** `backend/scripts/test_phase_c_events.py` — **60 checks**, each in its own
in-memory world with its own tenant, outlet and session, so one poisoned check cannot take
an unrelated check down with it — covers: that the event rides the business transaction in
both directions; that a broken emitter leaves the order standing and writes no event; that
the tenant is the row's own and never the payload's; that a money-carrying or
personal-data-carrying payload and an unknown event type are both refused; that the event
reaches its own tenant's subscriber and **never** a second tenant's, and that a subscription
narrowed to one branch does not see another branch's event; that a tenant holding `Inventory`
receives `stock.low` and one that does not receives nothing — with the refusal recorded and
named; that quiet hours hold the event instead of dropping it; that a delivery which cannot
succeed lands in the dead-letter log with its reason; that the webhook's signature verifies
over the body that arrived and that a tampered body and a foreign secret do not; that the
claim is atomic; that the settlement fires `order.paid` **once**, that a second write of an
already-paid order fires nothing, that `stock.low` fires only on a genuine **crossing** and
not on every write below the line, that a table turns only when its order reaches its end
state and only on the transition, and that the clock-in and clock-out fire their own events;
and that the ageing sweep reminds once per cycle, not twice for the same cycle, and leaves
no trail at all when nobody has subscribed.

Phase 0's, Phase A's and Phase B's proofs still pass unchanged (18 / 35 / 10 / 53 / 59 —
**175 checks**).

### 8.6 What Phase D's implementation settled

Phase D was the surface and the meter, so its questions were about **what a refusal looks
like, what a briefing counts, and where the day starts**. The code answered them, and this
is the record.

**1. THE ORDER OF THE CHECKS IS FIXED, AND IT IS NOT THE OBVIOUS ONE.** The plan gate, then
the quiet hours, then the daily allowance, and only then the model. The quiet hours sit
**above** the allowance because a tenant's own hours are a rule about the moment, while the
allowance is a rule about the count — and the cap is counted per outlet per **tenant-local
day**, so the day's boundary is the branch's, not the server's.

**2. AN UNREADABLE PLAN IS NOT A REFUSAL.** A plan that cannot be read raises; it never
masquerades as a tenant who was refused. The two answers mean opposite things — one is a
platform fault, the other is a decision the tenant's plan made — and collapsing them would
have recorded the platform's failure as the tenant's fault.

**3. THE QUIET IS A RECORDED DECISION, NEVER A SILENCE.** Four distinct kinds —
`call`, `cap_reached`, `quiet_hours`, `plan_blocked`, `failed` — and every one of them
leaves a row the tenant can read. A dropped briefing that left no trace is indistinguishable
from a briefing that was never due.

**4. A BRIEFING IS EXACTLY ONE MODEL CALL.** It records the tenant, the outlet, the model,
the purpose and the token usage. The reasoning tokens are a **breakdown** of the completion
tokens, never an extra charge on top of them — and when MiniMax omits `total_tokens`, the
fallback is prompt + completion, not prompt + completion + thinking.

**5. THE PULL PATH IS METERED BUT NOT CHARGED AGAINST THE ALLOWANCE.** The cap counts
`briefing` calls only. The chatbot is the price of the pull path (§9.2), and the meter never
changes what a tenant pays.

**What was proven.** `backend/scripts/test_phase_d_manager.py` — **41 checks**, each in its
own in-memory world, covering the routes and their mounting; the tenant being the session's
tenant and never a body's or a query parameter's; the order of the four checks; the four
decision kinds staying distinct; an unreadable plan raising rather than refusing; the
allowance being per outlet per tenant-local day; the reasoning tokens being a breakdown; and
the channel settings being real.

### 8.7 What Phase E's implementation settled

Phase E was the money, so its questions were about **what the two rows cost, what an
add-on price is, and when the POS is told**. The code answered them, and this is the record.

**1. THE ADD-ON PRICE IS A TABLE OF ITS OWN.** `feature_prices` prices a **FEATURE**; it is
not `plan_prices`, which prices a subscription. The two are billed on different schedules,
and nothing about an add-on changes how any plan is priced. One price per feature per
currency, enforced by a unique constraint — a second row for the same pair would be a
second price for the same thing.

**2. THE ADD-ON IS PRICED AT THE LEVEL OF THE PLAN THAT ALREADY CARRIES THE ROW.** The model
is not what is being priced: at the published card ($0.30/M in, $1.20/M out on MiniMax-M3) a
briefing of ~2k prompt and ~1k completion tokens costs about $0.0018. What is being priced
is the **push path** — the agent speaks first, whether or not a person reads it. So
`ai_agent` is priced at Pro's $20/month and `ai_agent_actions` at Enterprise's $50/month
(USD and MYR, per currency), and a design partner granted the add-on pays no more than they
would on the plan. `ai_chatbot` is **not** priced as an add-on: §9.2 settles that the row
*is* the price of the pull path, and pricing it twice would charge twice for one thing.

**3. THE MONEY IS GROUPED BY CURRENCY, AND THERE IS NO TOTAL ACROSS CURRENCIES.** The
add-on payload is a map of currency to amount. The cost report's money is a map too. Adding
USD to MYR would produce a number nobody can pay.

**4. THE OVERRIDE RECORDS WHY, AND WHO.** `customer_feature_overrides` had `reason` and
`created_by` columns and the design asked for both — but the route dropped the reason and
never wrote the author, so every override in the table had neither. Both are recorded now,
and the admin UI asks for the reason when an override is granted on top of a plan that does
not carry the row, because that is the case where the plan and the override disagree and the
disagreement needs a why.

**5. THE POS IS NOTIFIED AFTER THE COMMIT, NEVER BEFORE.** Both paths had the same race:
the customer override and `PUT /plan-features` notified the POS backend **before** the
database commit. The POS reads the features from that database, so a notification that
arrives early lets it read the **old** set and cache it as fresh — and nothing would tell it
again. The change would sit in the database and not in the product. The notification now
follows the commit, and the proof watches the moment the notification fires and checks that
the committed row was already visible and already carried its reason.

the bill and make the report lie. The reasoning tokens are a breakdown and are never billed
twice. The route is scoped to the session's tenant, and an outlet filter is checked against
that session.

### 8.9 What the AI Manager fixes settled

Five problems Kens named, five commits, and the answers are worth writing down because three
of them are the same mistake wearing different clothes.

**1. A PROFILE THAT DOES NOT REACH THE SCREEN IS NOT A PROFILE.** The tenant profile was
the agent's identity, and the agent was reachable only through the MCP transport — while the
chatbot the staff and the admin actually talk to every day knew nothing about it. The
profile's name, greeting and system prompt are now the chatbot's, and its outlet scope
narrows the branches: a branch outside the scope is **refused**, not answered, and the scope
reaches the chatbot's **tools** as well, so the model cannot reach past it with a tool call.
It only narrows — the **guest's** assistant is not the tenant's agent and keeps the branch's
own voice, the profile's prompt cannot widen what the plan allows, and with **no** profile
the Phase A behaviour is untouched. The rule: *a configuration the tenant cannot see taking
effect is not a configuration.*

**2. A FIELD THAT IS STORED LOOKS EXACTLY LIKE A FIELD THAT WORKS.** The profile has twelve
fields, and the honest answer differs per field: some are read by a running part of the
system, some are stored and displayed. A tenant who sets a stored field reasonably expects
it to work. So the catalogue is in the **backend** — because the backend is the code that
reads these fields — and each field says whether it is **IN USE** or **STORED ONLY**, and
**where** it is read. `sop` is stored and nothing reads it yet, and the screen says so. (`runtime` was stored and nothing read it too — until it was derived from the live connections instead, §8.11.) The rule: *a stored field must be labelled as stored.*

**3. A THRESHOLD NOBODY EVALUATES IS A NOTE TO ONESELF.** The Agent tab showed the
escalation settings as raw JSON and nothing ever looked at them. They are now a **schema**
(§3.4) and they are **evaluated**, with the **measured value** shown beside the threshold —
because a screen that showed only the rules would be showing a note to oneself. The rule:
*the threshold decides WHEN, the profile decides WHETHER MAY, and a refusal is reported
rather than swallowed.*

**4. TWO SURFACES, TWO GATES.** The AI Manager and the AI Tools were one page, so the
tenant's agent and the analytics it reads shared a navigation entry, a route and a gate.
They are now separate screens with separate gates — and `AI Agent Actions` is **not** the
AI Manager's gate, because it is the gate for the *actions the agent may take*. Using it as
the gate for the screen meant a tenant could see the tools and not the agent.

**5. A STALE WRITE IS A LOST UPDATE.** The Profile screen round-tripped the stored
escalation value on every save, so saving a profile could quietly **revert** a threshold
the tenant had just set in the Agent tab. The Profile screen no longer carries the
thresholds at all — they belong to the Agent tab, and the field is left out of the body so
the server keeps what is stored. The same shape of bug is why the older free-text rules
are **kept but never evaluated**, and shown as inert.

### 8.10 What Phase F's implementation settled

Phase F had two halves, and they turned out to have different shapes. The **setup** is a
read; the **proxy** is a spend. Writing them down matters because the design said what
should exist and not who may hold the key.

**1. THE PROXY IS OPENAI-SHAPED, BECAUSE THE CLIENT IS NOT OURS.** The design said "a
tenant-scoped, OpenAI-compatible model endpoint". The reason it matters is not elegance:
n8n, LangChain and most agent frameworks already speak OpenAI, and a bespoke endpoint would
put a bespoke client in front of every one of them. So the proxy answers OpenAI's shapes —
`/api/agent-proxy/v1/chat/completions`, `/api/agent-proxy/v1/models`, `object:
chat.completion`, the `usage` block — and the credential travels the way an OpenAI client
sends it: `Authorization: Bearer <token>`. The house's own `X-Agent-Token` is accepted on
the same path, because the MCP transport and the proxy are ONE credential and a runtime
should not have to know which door it is at.

**2. THE PROXY TAKES THE AGENT TOKEN AND NOTHING ELSE.** An ordinary API key is refused, and
a signed-in member of staff is refused — in both directions, exactly as the MCP transport
holds it. The proxy is a *narrower* door, not a wider one: it is the same agent credential,
pointed at a different surface.

**3. A SECOND DOOR IS NOT A WIDER KEY.** The agent credential was confined to `/api/mcp`.
It is now confined to `/api/mcp` **and** `/api/agent-proxy`, and nowhere else — an agent
token presented to an ordinary route is refused by the house's own middleware with a loud
answer. The rule: *every surface an agent credential reaches must be named, and the
credential's blast radius is the list.*

**4. THE TENANT IS THE CREDENTIAL, NEVER THE BODY.** The proxy reads the tenant from the
resolved token. There is no parameter, no body field and no header that can name another
restaurant — and the proof proves it by sending a `customer_id` of `999999` in the body and
checking that the recorded row still carries the credential's tenant.

**5. THE GATES RUN BEFORE THE MODEL, AND AN UNREADABLE PLAN IS NOT A REFUSAL.** The order
is the plan, then the subscription, then the model, then the cap, and only then the call. A
plan that could not be read answers **503** and a plan that does not hold the row answers
**403** — the same distinction §8.6 settled for the briefing, kept because the remedy is
different: one is our fault and the other is the tenant's own decision.

**6. THE MODEL IS ENFORCED BY NAME.** A model outside the allowlist is refused, and the
refusal **names the models that are served**. A runtime is never left guessing which name
it should have used, and the comparison is case-insensitive because a model name is a label.

**7. IT DOES NOT STREAM — IT REFUSES.** A request that asks for `stream: true` is answered
with a clear `400` rather than a silently non-streaming body. A client that thinks it is
streaming and is not would hang or mis-parse, and a refusal is the honest answer.

**8. THE SPEND IS COUNTED ON THE TENANT-LOCAL DAY, AND A REFUSAL LEAVES A ROW.** The cap
is counted per tenant (per outlet, when the token is bound to one) over the **tenant-local**
day, so the day's boundary is the branch's. And the rule from §8.6 holds here too: a call
that was **not** made still leaves a **VISIBLE ROW** — `cap_reached` and `failed` are
recorded with their reason and with zero tokens, because a decision row must never drain the
allowance it is about.

**9. THE SETUP IS A READ, AND IT HANDS OUT NO SECRET.** `GET /api/ai/connectors/setup`
answers from the **live configuration** — the MCP path, the proxy base path, the models the
proxy serves, the token's **PREFIX** and scope, and the tenant's own subscriptions — so the
answer cannot drift from the code. It never shows the token, and it never shows a signing
secret: the secret is shown once, when the subscription is created, and the prefix is how a
human tells two tokens apart without the secret ever being stored.

**10. THE ONE WRITE IS THE TOKEN, AND IT BELONGS TO THE ADMIN.** `POST
/api/ai/connectors/token` mints a token for the **session's** tenant and shows it **ONCE**;
only the SHA-256 is stored, so it can never be read back. Creating one needs `ai:write`, so
the **admin** holds it and the **manager** does not — a token speaks for the whole tenant
and belongs to the person who owns the tenant's connections. And the only thing a body may
name is an `outlet_id`, which is checked against the session's tenant before anything is
written.

**11. HUMAN APPROVAL STILL STANDS.** The scope ladder reaches `action`, and that is safe
because an action **proposes**: it files a proposal, and a person approves it through the
house's own routes with the approver's own signed session. The agent credential's scope
never bypasses the human.

### 8.11 What the derived runtime settled

The tenant profile carried a `runtime` field, and the Profile screen offered it as a
dropdown: *"This POS app" / "n8n" / "Telegram" / "MCP client"*. Kens asked what that
dropdown actually did, and the honest answer was: **nothing**. No gate read it, no tool
read it, no delivery path read it. It was a field a human picked that changed no
behaviour — so it looked like a switch, and it was a note to oneself.

**1. A FIELD THAT ONLY CLAIMS A STATE MUST NOT BE PRESENTED AS THE STATE.** The runtime
was a **claim**, not a fact: a tenant whose agent genuinely ran inside n8n could leave the
field on "This POS app" and be told the screen was showing their runtime. The field is now
**derived from the tenant's live records** — the enabled event subscriptions and the
active agent tokens — so the screen cannot lie about what is connected.

The precedence is fixed and documented, so the answer is the same every time and the
tenant can be told *why*:

| # | Runtime | The live record that proves it |
|---|---|---|
| 1 | `telegram_bridge` | the agent answers in Telegram — an enabled subscription on the `telegram` channel |
| 2 | `n8n` | the tenant's own runtime, on the signed webhook — an enabled subscription on the `webhook` channel |
| 3 | `mcp_client` | a runtime authenticating with an agent token — an active, unrevoked, unexpired token |
| 4 | `pos_frontend` | only the house's own POS app — an enabled `in_app` / `staff_push` subscription |
| 5 | `none` | no live connection at all |

**EVERY** live connection is reported, not only the winner — a tenant with a Telegram
bridge and an n8n workflow is told about both. A **switched-off subscription, an inactive
token and a revoked token are not connections**: a connection that is off is not a runtime.

**2. THE DERIVED RUNTIME GRANTS NOTHING.** This is the part that had to be true, because
"runtime" is a word that sounds like a permission. It is not one. The plan gate, the
token's scope, the profile's allow-list and the human approval are exactly as they were —
and the proof asserts it directly, by checking that an empty allow-list is still empty
with a webhook connected, and that deriving the runtime changes no capability at all.

**3. THE STORED COLUMN IS LEGACY AND INERT.** `tenant_agent_profiles.runtime` survives,
because dropping a column is a migration and the history is worth keeping — but it is
never read by a gate, a tool or a delivery path, and **a save that carries a runtime no
longer stores it**. That is deliberate: a stale client that still sends the field must not
be able to make the value authoritative again. (It is *ignored* rather than *refused*,
because refusing the whole save would break that client over a field that grants
nothing.) The row exposes the history as **`runtime_stored`**, so a hand-picked label can
never be mistaken for the truth, and the Profile screen shows the derived value with the
reason it was derived.

**4. THE VOCABULARY IS ONE LIST.** The codes live in the backend — `pos_frontend`, `n8n`,
`telegram_bridge`, `mcp_client`, `none` — and the backend hands that list to the frontend
on every read. The frontend mirrors it in one module, and the frontend proof reads the
**backend's own source** and fails if the two drift. A runtime added on one side and
forgotten on the other breaks the build rather than showing a tenant an empty label.

**Proved** by `backend/scripts/test_agent_runtime.py` (34 checks: no connection, the POS
frontend, an MCP client, an n8n webhook, a Telegram bridge, several connections at once,
the switched-off cases, the stale stored label, the "grants nothing" case, the vocabulary
and the routes) and by the frontend proof (43 checks, including that the dropdown is gone
and that the save no longer sends a runtime).

### 8.12 What the web agent screen settled

Kens asked for a **new web agent screen** in the frontend POS, for a tenant whose plan holds the
AI Manager feature **and** who has already configured the profile — and he asked for the access
link either at the AI Manager's profile tab **or** on a new screen. The ordinary chatbot screen
stays exactly where it is; this is a **second** surface beside it, not a replacement.

**1. THE CHATBOT IS NOT THE AGENT, AND THE AGENT NOW HAS A SCREEN.** The POS already had a
chatbot at `/chatbot`. It is the **house's** assistant — it speaks for the restaurant, in the
branch's voice. The web agent at `/ai-agent` is the **tenant's own** agent — the one §3.4's
profile describes — speaking to the tenant's own staff, in the tenant's own voice, watching
only the branches the profile watches. Two different speakers, two different screens, one app.

**2. THE SCREEN HAS TWO GATES, AND THE SERVER OWNS BOTH.** A tenant may see the screen only
when **both** of these hold:

| # | Gate | Why it is a gate at all |
|---|---|---|
| 1 | the plan holds the **`AI Agent`** row | the screen is the agent's, and the agent is what the row buys |
| 2 | a **CONFIGURED, ACTIVE** profile exists | without a profile there is no agent — an empty screen that says "hello" would be pretending something exists |

The three profile states are told apart honestly: **no profile**, **a profile that is switched
off**, and **a profile that is on**. Each gets its own answer, and each says what to do about
it. The frontend hides the navigation entry as well, but the frontend is a **convenience** — the
server re-checks both gates on **every** call, so a stale screen or a forged request changes
nothing.

**3. `AI Agent Actions` IS NOT REQUIRED — AND THAT IS THE POINT.** The row that grants
**writes** is not demanded by a screen that grants none. Requiring it would refuse a read-only
tenant a read-only screen, which is the wrong way round. A tenant holding `AI Agent` and
nothing else gets the screen; a tenant holding `AI Agent Actions` and **not** `AI Agent` does
**not** — because the row that buys the agent is the row the screen rides on.

**4. NOTHING ON THE SCREEN WRITES.** The route performs **no write at all**: not a proposal,
not an action, not the escalation notice — the ordinary chatbot's one write belongs to the
ordinary chatbot and is **not** fired from here. The tools the chatbot may call here are the
read-only ones. The profile's `allowed_actions` is **REPORTED**, so the tenant can see its own
agent's remit, and it is **never used** to act: a profile that names `notify_staff` still only
reads. The write paths keep their own gates — the plan row, the token's scope, the profile's
allow-list and **a human's approval**.

**5. THE TENANT IS THE SESSION'S TENANT.** Never a body field and never a query parameter. The
outlet — which the caller **may** name — is checked against that tenant with
`require_outlet_access`, which derives the outlet's real owner **from the outlet row itself**.
So a manager of one restaurant group cannot reach another group's branch by naming its id, and a
sibling branch **outside the profile's scope** is refused rather than answered.

**6. THE PROFILE GOVERNS THE VOICE AND THE SCOPE.** The profile's name, greeting, language and
system prompt are the agent's, and its **standing instructions (the SOP)** ride in the same
system prompt — so the agent actually follows the procedure the tenant wrote. The profile's
`outlet_scope` narrows the branches, and the scope is handed to the **tools** as well, so the
model cannot walk around it through a tool call either.

### 8.13 What the live run settled

The screen of §8.12 was built, proved against the source, and pushed. Then it was opened in
a **real browser** against the **live deployment**, and the run settled something neither
proof could have: a route that exists **on disk** is not a route that exists **in the
process**.

**1. THE FAILURE WAS NOT IN THE CODE, AND THAT IS EXACTLY WHY IT WAS WORTH FINDING.** Kens
signed in with the demo cafe credential and the screen said the web agent could not be
reached. Both suites were green. The cause was **deployment, not implementation**: the
backend process had been started on **Nov 20, 13:10** — *before* the commit that added the
routes — and uvicorn was running **without `--reload`**, so `/api/ai/agent/access` and
`/api/ai/agent/chat` were never mounted in the running process. The FRONTEND bundle was
already live and served the new page. So the page **rendered correctly** and its API call
went to a server that had never heard of the route. The fix was **one restart**
(`pm2 restart pos-backend --update-env`) and **no code change at all**.

The rule this settles: **a proof that runs against the source is not a proof that runs
against the deployment.** The suites answer "is the route correct?"; only a browser against
the running service answers "is the route **mounted**?".

**2. THE SCREEN DISTINGUISHED "REFUSED" FROM "UNREACHABLE", AND THAT WAS WORTH HAVING
SAID SO.** The error Kens saw was **not** the plan refusing him — nothing had refused
anything. The frontend already separates the two failures, and the separation is the
difference between a tenant who thinks they need to **buy** something and a tenant who
needs to tell their operator the **server is stale**:

| What the server did | What the tenant is told | What it actually means |
|---|---|---|
| `403` from the plan gate | the **named** reason — `plan` | the plan does not hold the row |
| `200` with `available: false` | the **named** reason — `no_profile`, `profile_inactive`, `agent_disabled` | there is no agent to talk to yet |
| the route is **not mounted** | the agent **could not be reached** | the server is running older code |

Two of these are *the tenant's own situation* and one is *the platform's*. A screen that
collapsed them into one message would have sent a paying tenant off to buy a feature they
already had.

**3. THE PLAN GATE WAS CHECKED, NOT ASSUMED.** The session for this tenant carries
`website_customer_id`, so `require_plan_feature` resolves the tenant's **LIVE** feature list
through the plan cache and falls back to the login-time snapshot **only** when the plan
cannot be read. The plan cache is filled on demand and refreshed when the website API
pushes a plan change — so a tenant whose plan moved is seen in its **new** state, not the
state it was in when it signed in. The screen's own gate therefore reflects what the
tenant **bought today**, which is the only thing a gate is allowed to mean. The session's
feature list was confirmed to carry `AI Agent` (and, separately, `AI Agent Actions` — which
§8.12's rule says the screen must not *require*, and does not).

**4. THE WHOLE PATH WAS WALKED AS A TENANT, NOT AS A CALL.** Signed in through the real
login form on the live origin as the tenant's own admin, with the outlet set to the demo
cafe: the sidebar's **Web Agent** entry is present and opens `/ai-agent`; the screen opens
on **Aunty Mei**, **Read-only**; a real question ("What is on the menu today?") is answered
from the tenant's own menu, grouped by category; the **AI Manager → Profile** tab's **Open
web agent** button lands on the same screen; and the **ordinary `/chatbot` screen is
untouched** — still the house's Lumi, still answering. The proof of §8.12 was that the
chatbot is *not* disturbed; the live run is what showed that it is *not disturbed in
production*.

**Proved** by the live run itself — the restart, the mounted routes on the live OpenAPI
schema, and the browser walk of all four surfaces above — on top of the two suites of §8.12
(`backend/scripts/test_ai_agent_screen.py`, 39 checks; `frontend/scripts/test-ai-agent-screen.mjs`,
37 checks), which remain green and now describe a feature that is **running**.

### 8.14 What the agent's own tools settled

Kens looked at the screen of §8.12 and said the thing that had to be said: **as built, it
duplicates the chatbot.** The route called `get_chatbot_response()`, which hands the model
only the **ten read tools**. The **fifteen** draft/action tools never entered the call. So
`/ai-agent` was "the ordinary chatbot, wearing the tenant's profile" — a different voice and
a different branch scope over the same read-only toolset. And `allowed_actions` was stored,
editable in the profile screen, reported on the agent screen, and **read by no gate on any
surface the tenant actually uses**. The classic "field that is stored looks exactly like a
field that works."

This section records what the fix settled. The answer is not "the chatbot, plus buttons."

**1. ONE REGISTRY, TWO EXPOSURES.** The MCP registry (`app/ai/mcp_registry.py`) was already
the single authority on what a tenant's agent may do. The web agent now renders **that same
catalogue** into the OpenAI-style schemas the model consumes, through the same gate stack.
There is no second list to drift, and a tool the tenant may not use is never **offered** — so
the model cannot even try it, and the refusal is never the agent's problem to solve.

**2. THE EFFECTIVE CATALOGUE IS AN INTERSECTION OF FIVE THINGS.**

| # | Gate | What it decides |
|---|---|---|
| 1 | the **`AI Agent`** row | may this tenant use its agent at all |
| 2 | the **module's own row** | may it touch this module |
| 3 | the **`AI Agent Actions`** row | may it **propose** (the draft/action tools) |
| 4 | the **credential's scope** | read < draft < action |
| 5 | the **profile's allow-list** | may only **narrow** the draft/action tools |

The READ tools are governed by the plan's **visibility** — a tenant that has not bought
`Staff` is never shown the staff tool — and are **never** narrowed by the profile. The
ordinary `/chatbot` surface keeps its own, wider behaviour; this does not touch it.

**3. THE SCOPE OF A BROWSER SESSION IS DERIVED, AND IT CAN ONLY LOWER.** An MCP credential
carries its own scope. A browser session carries a person's **permissions**, so the scope is
derived from them: a session that may **approve** proposals may also **propose** them, and a
session that may only **read** is never offered a draft or an action tool. The derivation can
only ever lower what the plan and the profile allow — `ai:read` alone never reaches a draft
tool. The proposal is still inert: it is a frozen plan waiting for a person with the tool's
own permission.

**4. `AI Agent Actions` GATES THE ACTION TOOLS INDIVIDUALLY — NOT THE SCREEN ENTRY.** This
settles the tension in §8.12, which said the row that grants writes must not be demanded by a
screen that grants none. The screen no longer grants **none**: it grants *proposals*. So the
row is required **for the action tools** and not for the screen, and a tenant without it gets
the screen, the read tools, and a panel that says the agent may only read. A tenant with it
gets the profile's assigned proposal tools — and a panel that says so, in the words that
matter: *it can ask to change*, never *it can change*.

**5. A PROPOSAL IS A PROPOSAL, AND THE CARD SAYS SO.** The draft and action tools store a
**proposal** — immutable arguments, a frozen plan — and change nothing. The card appears
**inline in the chat**, under the answer that asked for it, with the three explicit controls
Kens named: **Approve**, **Edit**, **Reject**. It calls the **same** decision routes the AI
Manager's "Needs you" list calls — **one queue, two views** — and an edit creates a **new
version** and supersedes the old one rather than patching the frozen arguments. The card
states in words that nothing has changed yet, because a card that looked like a receipt would
be a lie. The model cannot approve its own proposal, and neither can an agent token.

**6. THE PANEL SHOWS THE EFFECTIVE CATALOGUE, NOT THE PROFILE'S LIST.** The "what this agent
can do" panel is built from the intersection **on the server**, so it shows what works rather
than what was typed into a form. The read tools and the proposal tools are listed separately,
because they are different promises.

**7. THE MODEL LEADS.** The screen is an **agent**, and the canned intent handlers would
answer "order a 50-egg purchase order" with the QR-code instructions. In agent mode the model
leads, with the gated catalogue; only the two social turns stay local. The ordinary
chatbot's engine was **extended additively** — the catalogue, the runner and the mode are
optional parameters that default to the old behaviour — so `/chatbot` is byte-for-byte the
same surface it was.

**8. THE MONEY BELONGS TO THE BRANCH.** Every changed summary in the action tools now carries
the **selected branch's own currency**, and the tool descriptions say "the branch's own
currency" rather than "ringgit". Two branches of one group can be in two currencies, and their
money is never added up.

**9. THE TRANSPORT'S WALLS.** `/api/mcp` and `/api/agent-proxy` are **machine** doors. The
app's CORS policy is deliberately permissive — the staff app and the API are cross-origin by
design — so a **guard** now sits **outside** the CORS middleware on the agent paths only: a
browser `Origin` is refused, every agent-path response carries `Cache-Control: no-store`, and
the permissive CORS headers are stripped on the way out. The transport also caps the **body**
(256 KB, checked on the declared length **and** on the real one), the **batch** (20 messages)
and the **rate** (120 calls a minute per token, so one tenant cannot spend another's quota).
The **replay window is sixty seconds**: the same draft call inside the window returns the
**same proposal** instead of creating a second one — a manager who approves two identical
cards must not send two purchase orders. It is **not** six seconds; six is too short for the
retry it exists to catch.

**10. THE PROOF FOUND A REAL BUG, AND IT WAS A BAD ONE.** The guard called the inner app as
`app(scope, receive, send, guarded_send)` — **four** arguments. ASGI's contract is three, and
Starlette's own `BaseHTTPMiddleware` is strict about it, so **every request to the machine
door returned 500**. The suites were green because none of them made a request that went
*through* the guard on the success path. The rule this settles: **a guard that touches every
request must be proved by a request that actually goes through it** — and a middleware is
where a signature error hides, because the failure is a `TypeError` in a wrapper rather than
a wrong answer in a handler.

**11. THE FIELD CATALOGUE IS TRUE AGAIN.** §8.9 built the catalogue so a tenant can tell a
field that works from a field that is only stored. Two entries had drifted from the code: the
**SOP** was marked "stored, nothing reads it" while the web agent's system prompt read it on
every turn — it is **operational**, and it says where; and the **`runtime`** column was marked
operational while §8.11 made it explicitly **legacy and inert** — it is stored only, read by
nothing. A catalogue that lies is worse than no catalogue, because it is the one place the
tenant is told the truth.

**Proved** by `backend/scripts/test_ai_agent_screen.py` (72 checks — the effective catalogue:
the plan's module rows narrowing the read tools, `AI Agent Actions` gating the action tools
without gating the screen, the profile narrowing only the action tools, the scope derived
from the signed session, another tenant's branch refused, and the whole proposal path: the
model is offered the gated tools, a draft stores a **proposal** with a frozen plan, **no
promotion is created**, and the answer carries the proposal), by
`backend/scripts/test_mcp_hardening.py` (19 checks — the browser door, the cache headers, the
body cap including a body that hides its size, the batch cap, the rate cap with its
`Retry-After`, and the replay guard returning the same proposal), and by
`frontend/scripts/test-ai-agent-screen.mjs` (66 checks — the capability panel, the inline
proposal card with its three controls, and every new label in English, Chinese and Khmer).

### 8.15 What shipping the tools exposed

§8.14 settled what the agent may do. Shipping it exposed three things that the design did
not have an opinion about yet, and the code is where each of them was decided.

**1. THE MODEL MUST BE TOLD WHAT A PROPOSAL IS.** The tools were gated, the proposals were
stored, and the screen drew the cards — and the model was still told to "use the tools when
needed" and nothing else. So the model called a draft tool and then wrote *"I've ordered the
supplier."* Nothing had been ordered; a card was waiting for a person. The rule this settles:
**a proposal is a thing the agent made, and the model has to be able to NAME it** — so the
system prompt tells it, in as many words, that a proposal tool changes nothing by itself,
that it must say plainly that this is a proposal waiting for approval, that it must never
say the change has been made, and that it must never call a proposal tool to see what it
would do. The paragraph is built FROM the catalogue the caller supplied, so it cannot
describe a tool this tenant does not have.

**2. AN EMPTY ANSWER IS AN ANSWER, AND IT HAS THREE FORMS.** The model loop could finish
with nothing to say — the model asked for tools on every one of the `MAX_TOOL_ROUNDS` rounds
and the loop ran out before it wrote a sentence, or the model answered with an empty body
after its tools had run. Both used to fall into the canned `out_of_scope` help menu: an
answer to a question nobody asked. And both **discarded the `tools_used`** accumulated on the
way, which is the expensive half — a draft tool stores a **proposal**, the proposal is
waiting for a human, and the screen draws its card from `data.tools_used`. Throwing the list
away silently dropped a proposal the tenant still had to approve.

So the tools are preserved and the answer says what actually happened, in three distinct
shapes:

| the situation | the answer |
|---|---|
| the model said nothing and nothing ran | `ai_empty_answer` |
| the tools ran and the words did not | `ai_empty_answer_tools` |
| a proposal is waiting | `ai_empty_answer_proposal` — and it says **nothing has changed yet** |

The third is the one that matters. A tenant who has just approved a price change and then
reads a generic error will reasonably believe the change was lost.

**3. THE METER MUST SURVIVE THE REQUEST.** The token count was written into the request's
session and never committed, and `get_db` only **closes** the session — so the row rolled
back with it and the tenant's token count was simply gone. The commit is on the **meter row
alone**; the proposal rows are committed by their own writer, so this can never half-commit a
proposal. And the meter is **never** the reason a question fails to be answered: a failure to
write the row is logged and swallowed.

**4. THE MONEY BELONGS TO THE BRANCH — AND THE PROOF FOUND A REAL GAP.** The action tools
wrote `RM` into their summary sentences as a literal. The house is Malaysian, so the bug was
invisible here — and it would have been wrong the moment a tenant's second branch traded in
another currency. A summary is a **sentence a human reads and approves**: *"Draft the price
of 'Chicken Wings' at RM 18.90"* is a wrong sentence when the branch's own settings say the
branch trades in dollars. The number is right and the sentence is wrong, which is worse than
no sentence, because the approver sees a figure that looks careful and is about the wrong
money. The currency now comes from the branch's **own** `OutletSettings` row, and the figure
itself is unchanged — the currency belongs to the sentence, not to the number, so the plan's
body still carries a plain number and never a symbol.

The proof that says so asserted that a branch of **another** restaurant group is refused, and
it **failed**: `currency_of` looked the branch up by id with no tenant check — the one lookup
in `ActionContext` that was not tenant-scoped. The **code was fixed rather than the test
weakened**. The rule this settles: *a lookup that names a branch is a lookup of somebody's
business, and "somebody" has to be checked.*

**5. THE LIVE SCRIPTS DO NOT CARRY THE PASSWORD.** The live scripts logged in with the test
password as a literal in the source. These accounts exist on the **live** database, so the
value is a real credential — and a password written in a tracked file is a password every
clone of the repository knows. The password now comes from the environment or from
`frontend/.env.test` (gitignored, never committed, with `frontend/.env.test.example`
committed so a fresh clone knows what to create), exactly as `website_api/scripts/_test_creds.py`
already did for the website API's scripts. A script that runs with an empty password fails
later with a message that says nothing about the real problem, so a **missing** credential
exits immediately with setup guidance instead.

**Proved** by `backend/scripts/test_ai_fallback_recovery.py` (26 checks — the loop running
out, the proposal surviving the empty answer, **no** promotion created, and the meter
**committed** and visible to a fresh session on a second connection to a real file), by
`backend/scripts/test_action_tool_currency.py` (26 checks — two branches of one group in two
currencies, each summary carrying its own symbol, the plan body carrying a plain number, the
unknown staying unknown, the cache never letting one branch answer for another, and another
group's branch refused), and live in the browser by
`frontend/scripts/live-agent-screen-check.mjs` (43 checks against the running deployment, with
its own **negative control**: the first turn is a read question and must produce no proposal
card, so the detector cannot be a detector of nothing). The fallback proof is
**negative-controlled**: against a reverted copy, 16 of its 26 checks fail.

The rule all three settle: *a proposal that the model made is still a proposal; a summary is
a sentence a human approves; and a proof that cannot fail is not a proof.*

### 8.16 What proving the proofs settled

§8.15 said the fallback proof was negative-controlled. It was time to check whether that
sentence was **true**, and the check found something worth a section of its own.

**THE CONTROL THAT PASSED.** A control was built by copying the tree at an old commit and
running the suite that shipped with it. It came back **GREEN** — every check passing, on
code that was supposed to be broken. A green control is not a passing test; it is a
**mistake that looks like success**, and it is the most dangerous shape a mistake can take
because it reports exactly what you hoped for.

The reason is worth stating plainly, because it is easy to get wrong: a control is not
**"an old tree"**. A control is **TODAY'S suite against the OLD code**. The old tree
carries the old suite, so the proof was handed its own homework and graded itself. The two
things have to be mismatched on purpose — the new assertions, the old behaviour — because
the only question a control answers is *"would these assertions have caught the bug?"*

**THE FALLBACK PROOF, CONTROLLED PROPERLY.** Today's suite, today's tree, with only
`chatbot.py` and `translations.py` reverted to their pre-fix state: **16 of its 26 checks
fail** — the intent is `out_of_scope` instead of `ai_fallback`, the tools are not preserved,
the proposal does not ride back, the screen gets no card, the card is not pending, and the
meter rows are not persisted. The claim in §8.15 was **true** — and it had been true
without ever having been demonstrated, which is a different kind of true from the kind that
earns the right to be written down.

**THE CURRENCY PROOF, AND WHY ITS FIRST CONTROL WAS WORTHLESS.** Built the same wrong
way, the currency control did not fail a check — it **crashed**, with
`AttributeError: 'ActionContext' object has no attribute 'currency_of'`, because the whole
file had been rolled back and the suite could not even start. A suite that cannot run
against the old code proves nothing about whether its assertions are load-bearing; it only
proves that the code changed shape. So the currency proof was controlled **surgically**
instead: today's tree, with **only the tenant guard removed** and everything else — the
per-branch cache, the settings lookup, the house-default fallback, the plain number in the
plan body — left exactly as shipped.

That control fails **exactly one** of its 26 checks:

> `another group's branch is REFUSED` — *currency_of answered for another group's branch*

**One check, for one line of code.** That is what a good control looks like: it does not
fail broadly to prove the suite is strict, it fails **precisely**, on the assertion that
belongs to the defect and on no other. A control that fails everything proves the suite is
strict; a control that fails one thing proves the suite is **aimed**.

**THE BROWSER PROOF.** The live check carries its own negative control in the shape of its
own first turn: it is a **read** question, so it must produce **no** proposal card — and a
detector that could pass on a card that never came would be a detector of nothing. The live
proof was run repeatedly against the running deployment, and it stands at **43 of 43**.

The rule this settles: **a control that passes is not yet a control.** It is a proof grading
its own homework, and the only way to tell the difference is that a real control fails —
mismatched on purpose, in the new assertions and the old behaviour, and failing on the
check that belongs to the defect rather than on everything at once.

### 8.17 What the resolver hardening settled

§8.14 gave the web agent the agent's own tools. Having them, the next question was the one
every tool catalogue eventually asks: **when the model names a record, how do we know it
named the RIGHT one?** The answer was: we did not, and in four different ways.

**THE FOUR DEFECTS.** The resolver took the model's words at face value.

1. **AN ID AND A NAME THAT DISAGREE.** A call that said *"menu item 18, called 'Latte'"*
   when 18 is called *'Espresso'* named two different records. The plan froze one and the
   summary said the other, so the human approved a card that said one thing and did
   another. Now an id and a name must agree, for every kind of record, and a disagreement
   is a refusal with a reason.
2. **A NAME SEARCHED ACROSS EVERY TENANT.** The first row with that name in the database
   may belong to another restaurant group — so a group without a 'Latte' was told it had
   one, or was told about somebody else's. Names are now searched inside the agent's own
   branches, and a record of another tenant is not found by id OR by name.
3. **A DEFAULT BRANCH READ AS A NAMED BRANCH.** A call that named no branch had NOT named
   the default one — it had said nothing about the branch at all. Two branches of one group
   may both sell a 'Latte'; that is an ambiguity, and an ambiguity is **refused, never
   guessed**. A branch the CALL named disambiguates; a branch the CREDENTIAL is bound to is
   just as hard; and when there is neither, the record decides — and the money in the
   summary is then *that* branch's currency.
4. **A SNAPSHOT THAT NAMED A DIFFERENT RECORD FROM THE PLAN.** The arguments were stored
   as they came, the summary named what the planner resolved, and the plan acted on the
   resolved id — so the immutable record the human approves could point at a different item
   from the one the approval would change. The snapshot is now written from **what the
   planner resolved**: the same id, the same name and the same branch that the summary
   names and the route targets. An edited proposal keeps that identity, and the edit is
   held to the same branch scope as the original.

**AND TWO MORE FOUND ALONG THE WAY.** The chatbot's `AIChatbot.__init__` turned an absent
branch into **outlet 1** — which is another restaurant group's branch. A session with no
branch of its own read somebody else's numbers. An absent branch is now absent: the chat
gets one of **this tenant's** branches, or none at all. And `get_menu_performance`
aggregated **every** order item as revenue, so an evening of unpaid dine-in bills looked
like takings; revenue is now **paid** revenue, and unpaid orders are reported separately
with their amount.

**THE CANONICAL LOOKUP.** The agent could not price an item by name safely, because a
name is not an identity. There is now a read tool — `get_menu_items` — that hands back the
house's **own id** for each item, per branch, so the model names an item by the id the
house gave it. It is the eleventh read tool, and the catalogue is still **one** registry
with **two** exposures.

**THE EXACT PRICE.** A request that named a price could be routed to `draft_price_change`,
which *derives* a price from cost and a margin. The two tools end in different numbers, so
the guidance now says which is which — in the tool descriptions the model reads at call
time, and in the agent's own instructions: **a named price goes to `apply_price_change`;**
`draft_price_change` is for a price *derived* from a cost and a margin.

**THE PROOF.** `backend/scripts/test_action_tool_resolution.py` — **53 checks** — builds two
restaurant groups on a throwaway database and proves each of the four defects and the two
found alongside them, through the REAL `ActionContext`, the REAL planners and the REAL
proposal service. The rule this settles: **the record the call means and the record the
plan acts on are the same record, and a snapshot that cannot say so is not a snapshot.**

### 8.18 What the chatbot's privilege settled

§8.17 hardened the resolver. The next question was the one the **chat** asks, and the
chatbot had been answering it from the wrong place: **who is this, and what may they
see?** The answer came out of the request body — and four defects fell out of that.

**THE DEFECTS.**

1. **A MANAGER WHO CLAIMED TO BE THE ADMIN** (issue 22). `chatbot_type` was read from the
   body and passed straight into the chatbot, so a body that said `"admin"` opened the
   admin-only **tool surface** for a manager. The body is a CLAIM; the signed session's
   role is the PROOF.
2. **THE PUBLIC CUSTOMER KEY, READING ANOTHER TENANT'S NUMBERS** (issue 27). That key
   ships inside the guest app's own JavaScript, so anybody can read it — and it carries
   `ai:read`. It could claim the admin chat, and with it the tools that read a group's
   revenue, its orders and its staff. This is the one that mattered most: the key is
   public by construction.
3. **A TOOL ANSWER CUT MID-STRING** (issue 26). A tool answer longer than 6000 characters
   was sliced in its **serialised** form, which lands in the middle of a string. The model
   was then handed a broken JSON document and told that this *was* the tool's answer — so
   it answered from half a document, or invented the rest.
4. **THE ORDER HOURS IN UTC** (issue 25). `get_orders` bucketed the hours by the stored
   (UTC) clock, so a lunch rush at 12:00 in Kuala Lumpur was filed under `04` and the
   peak-hour question got a wrong answer.

**THE RULE THAT SETTLES ALL FOUR.** The chat type is a **privilege**, so it is a property
of the **CREDENTIAL**, and the body may only **LOWER** it — never raise it. A signed
session gets the chat its ROLE earns (`admin`, `manager`, `staff`); every other caller —
the public customer key, the external developer key, anything unknown — is a **guest**,
because the house's own rule is that a payload is only widened on PROOF. The admin
**tools** are a separate grant again (`allow_admin_tools`), earned only by a signed-in
admin session; the string `"admin"` in a body is never enough.

**THE ANSWER THAT STAYS WHOLE.** A cut of the serialised form is not a smaller document,
it is a broken one. `_fit_tool_answer()` now **shrinks** the answer until it fits and
keeps it a valid JSON document the whole way; when it was shortened it says so
(`_truncated`, `_notice`) and tells the model to narrow the question. A shortened answer
that says it is shortened is useful; one that pretends to be whole is not.

**THE BRANCH THAT OWNS THE HOUR.** The hours are the **branch's** hours. The conversion
is done once, with the branch's own timezone, where the orders are stored as naive UTC.

**AND TWO MORE FOUND WHILE PROVING IT.** The guest's own handlers — the menu, the
recommendations and the order status — queried without a branch filter, so a guest could
read **another branch's dishes** and **another branch's order**. They are now scoped to the
branch the chat is about. Reading a branch's *public menu* is what the guest app does on
purpose; reading another group's *books* is not, and that was the line the old code did not
draw.

**THE PROOF.** `backend/scripts/test_chatbot_privilege.py` — **35 checks** — proves the
credential deciding, the body lowering, the tools staying shut for the public key, the long
answer staying valid JSON (including a 200 KB answer), and the hour being the branch's.
It runs **over HTTP against the running backend**, because the claim being refused has to be
refused by the route, not by a helper. The rule this settles: **a privilege is a property of
the CREDENTIAL, and a string in a body is a claim.**

### Phase 0 — the MCP server (read-only), and the two feature rows

**Does:** the MCP transport on the existing FastAPI app, mounted at `/api/mcp` so the
deny-by-default middleware covers it (§10.1); the tenant-scoped token — the new
`agent_tokens` table and the new lookup that resolves it into the same `key_info` shape the
house already understands, beside the three hardcoded keys in `PERMISSIONS`; the ten read

itself**, because `require_plan_feature` is a no-op for a key caller (§4.5); the two feature
rows and their plan assignment, written into the seed **and** the live tables (§8.1).

**Does not:** write anything; call a model; change the chatbot's behaviour; involve n8n;
**carry the model proxy** — that is Phase F, and §4.4 says why.

**Proves:** one tenant, one outlet, one token — a client outside the POS calls `get_sales`
and gets that outlet's numbers, and a second tenant's token gets a different tenant's
numbers. The identity model is proven before anything risky is built on it. And the gate is
proven in the same phase: a tenant whose plan does not hold the row is refused **by name** —
*"This restaurant's plan does not include the Inventory module."* — and not by an empty
result, because an empty result is read by the model as "there is no stock".

**The two traps this phase must not walk into.** Both are live-code facts, and both are
silent when they are wrong:

- **`require_plan_feature` does not gate a key caller.** It returns the credential untouched
  unless `key_type == "user"`, because a session is what carries a plan. The chatbot is a
  session, so its route gate works; an MCP token is not, so the route dependency would let
  it through untouched. The MCP layer checks the plan itself, from the same `plan_cache`,
  with the same three states (§4.5). The token's `key_info` must also carry
  `website_customer_id`, or the shared routes' own plan gate cannot read this tenant's plan
  either.
- **A key type the shared routes do not know is treated as a customer.**
  `is_customer_caller` treats any credential whose `key_type` is not `frontend` or `user` as
  a customer caller, and `require_shared_permission` accepts only `frontend`, `customer`
  and `user`. An agent token typed `agent` would therefore be **refused by the shared
  routes** and **served the public menu payload** by `menu.py` — the public half, without the
  costing or the recipe links. The token's type is chosen with both functions in mind, and
  that choice is part of this phase, not an afterthought.

**Proves:** an order placed in one tenant produces an event that reaches that tenant's
subscriber, and a second tenant's subscriber never sees it. A second proof: a Pro tenant
receives no `stock.low` event at all, because `Inventory` is not in that tenant's feature
list (§4.5).

*(Both proofs hold, and the code settled three questions the section used to carry — the
transaction, the failure and the exception. §8.5.)*

### Phase D — the AI Manager surface, the metering and the cap

**Does:** the briefing, the approvals queue, the alerts, the profile screen, the channel

**Proves:** the manager opens `/ai-tools` and sees today's briefing, the proposals waiting

### 9.2 The cost question — re-scoped

**What the answer already settles.** For our frontend POS channel there is no new decision
here. The model call is the one we already make:

- The call is **server-side, on our key, in our own backend** — `ai/chatbot.py` posts to
  `settings.MINIMAX_BASE_URL` with `settings.MINIMAX_API_KEY`. The browser never holds a
  model key; it posts to `/api/chatbot/` and the backend does the rest.
- The route is **already gated** — `require_permission("ai:read")` and
  `require_plan_feature("AI Chatbot")`, and `ai_chatbot` is a Pro+ row. A tenant without
  the feature cannot spend a token.
- Only the roles that need it reach the model at all — `admin` and `manager`. `staff` and
  `customer` are answered from the intent handlers and never call MiniMax.

account, and the tenant has already bought the row that lets them spend it.** The model
proxy (§4.4) therefore drops to Phase F — it only matters when a runtime we do not control
is holding the LLM.

**What genuinely remains — the push side, and it is a different question.** The pull path is
bounded by human behaviour: the cost scales with how often the staff ask. The proactive
agent is not. A morning briefing for every outlet, every tenant, whether or not anyone
reads it, is O(tenants × outlets × briefings × tool-rounds × tokens), and nothing in the
current design bounds it. Two decisions, both small:

1. **Attribution — which tenant spent the tokens?** This is **not** answered today, and it
   is not a proxy problem: the `usage` block comes back in every MiniMax response and the
   chatbot throws it away. Recording it is a few lines at the call site (§4.6).
2. **The cap — how many proactive briefings per outlet per day, and what happens at the
   cap?** The agent goes quiet, or the tenant is told it has reached its allowance? Quiet
   hours (§3.5.4) is the first throttle; a daily briefing cap is the second.

**And the thing that is *not* a question.** Nobody has to decide whether a tenant is
charged per token. We do not meter tokens for the pull path today and we should not start:
the `AI Chatbot` row *is* the price. If a tenant wants the proactive agent, that is a **new
feature row** (`AI Agent` — created in Phase 0, priced in Phase E) that says what they get —
not a meter on every call.

## 10. Impact on the existing apps

*(v1.3: Kens asked the blunt question — if we build the MCP server, does the POS frontend or
the backend API app break? This section is the answer, verified against the running code.)*

The short answer: **the backend barely moves, and the frontend does not move at all until
Phase D** — when the AI Manager replaces the AI Tools page in the staff app (§3.6) — but two
traps will bite if the MCP server is mounted carelessly, and one of them is a plan-gate
regression that would change what a paying tenant's chatbot says to them today.

### 10.1 The backend API app — four things, and one of them is a trap

**The existing tools are reusable as-is. Zero edits to `chatbot_tools.py`.**

`backend/app/chatbot_tools.py` (really `backend/app/ai/chatbot_tools.py`) already exposes
everything an MCP server needs:

| It already has | Why it matters for MCP |
|---|---|
| `TOOLS` — a dict of ten name → function | The registry the MCP `list_tools` enumerates |
| `tool_schemas()` — the OpenAI-style function schemas | The MCP tool schemas, same source |
| `run_tool(ctx, name, arguments)` | The MCP tool dispatcher, unchanged |
| `ToolContext(db, tenant_id, default_outlet_id)` | The credential → tenant binding |
| `ToolError` | The refusal shape the MCP layer returns |
| `MAX_ROWS = 15`, `PERIODS` | The existing rails, inherited for free |

The decisive detail: **`ToolContext` takes the tenant as a constructor argument.** The tenant
is not read from the session *inside* the tool — the caller supplies it. So an MCP server
builds the same `ToolContext` from a token's tenant and calls the same functions. The rule
"the tenant comes from the credential, never from the model's arguments" is not something
MCP has to re-implement; it is already the shape of the code.

**Trap 1 — the mount path decides whether MCP is authenticated at all.**

`backend/app/main.py` denies by default, but only for one prefix:

```python
if path.startswith("/api/") and not _is_public_api_path(path):
    ...  # 401 without a credential
```

MCP's conventional path is `/mcp`. **Mount it there and the authentication middleware never
runs.** The `SubscriptionAccessMiddleware` has the same `/api` prefix test, so it would skip
as well. The endpoint would be open.

The fix is a prefix, not a rewrite: **mount at `/api/mcp`**, so the existing deny-by-default
covers it — and still verify the token explicitly inside the MCP layer, because the
middleware proves *a credential exists*, not *the credential is an agent token*. Two checks,
two different jobs.

**Trap 2 — per-tool plan gating changes the live chatbot's behaviour.**

Today the chatbot's read tools are gated **once, at the route**, by
`require_plan_feature("AI Chatbot")` — no tool carries its own module gate. The moment the
gate moves down into the tool bodies (§4.5), a tenant whose plan holds `AI Chatbot` but not
`AI Insights` starts getting `get_alerts` refused — **inside the chatbot they use every
day**. That is a plan-gate regression shipped alongside a new transport, and it is invisible
until a tenant notices.

The rule this section proposes:

> **Phase 0 ships the tool-level gate on the MCP path only.** The chatbot's behaviour changes
> in a later, deliberate step — with its own note, its own test, and its own release.

Note also that `get_alerts` reads the AI alerts, and `ai_security.py`, `ai_forecast.py` and
`ai_orders.py` carry **no plan gate at all** today — only `ai:read`. So the chatbot is
already reaching past the tenant's paid features. That is the bug §4.5 fixes, but the fix
must not be a surprise.

**The key system needs one new lookup, not a change.**

`middleware/auth.py` holds a **hardcoded three-tier key table** (`PERMISSIONS`: the frontend
key, the customer key, the external key) and `get_key_info()` matches a literal string
against it. A tenant-scoped, revocable, per-outlet MCP token cannot live there — that table
is static config, not data. So the `agent_tokens` table (§5.1) is read by a **new function**
that returns the same `key_info` dict shape the rest of the app already understands. The
three existing keys are untouched.

**New tables need no migration.** `main.py` runs `Base.metadata.create_all(bind=engine)` at
boot, plus the idempotent `_ensure_added_columns()` and `_ensure_push_schema()` belt-and-braces.
New models are created automatically — the house pattern. `ai_actions`, `agent_tokens`,
`agent_notifications`, `domain_events` and `event_subscriptions` all follow it.

**One worker.** The backend runs **one uvicorn worker** — the prepay expiry sweep depends on
it (`main.py`: *"the backend runs ONE uvicorn worker, so there is exactly one sweep"*). MCP
over HTTP is stateless, so a second worker is not required and not harmful. But the **event
dispatcher must claim rows atomically** (`SELECT … FOR UPDATE SKIP LOCKED`, or a
compare-and-set on the row's `state`) rather than relying on being the only worker. The
one-worker assumption is a convenience we may lose, not a guarantee we may build on.

### 10.2 The frontend POS — nothing until Phase D, then one page

- **Nothing in Phases 0–C.** The frontend is a REST client against `/api/*`; MCP is
  server-to-server. The nav gating (`frontend/src/config/navItems.js`), the feature hook
  (`frontend/src/hooks/useFeatures.jsx`) and the notification bell
  (`frontend/src/components/NotificationBell.jsx`) are untouched. **Phase B included the
  profile screen in its scope, and that was the one place the phases disagreed with this
  section — the screen moves to Phase D.** What Phase B built is the API behind it
  (`/api/ai/profile`), so Phase D's screen is React work against routes that already exist.
- **In Phase D, one page changes** — the `/ai-tools` page is replaced by the AI Manager
  page (§3.6), and the chat gains the proposal card and its three controls (§3.3.1). Both
  are ordinary React work against our own REST routes. The frontend still never speaks
  MCP.
- **The browser should not become an MCP client.** MCP over streamable HTTP with SSE and
  custom auth headers is awkward in a browser, and it would put a credential where the
  session cookie already works. The **AI Manager** page (Phase D) keeps calling our own
  REST routes; the backend is what speaks MCP. The browser stays inside the cookie model it
  already understands.
- **The one behavioural change reaches the frontend indirectly** — through the chatbot's
  answers. That is Trap 2 above, and it is why the gate change is staged.

### 10.3 The do-not-touch list

Things that look like they should change, and must not:

| Do not | Why |
|---|---|
| Move or rename `app/ai/chatbot_tools.py` | `ai/chatbot.py` imports `ToolContext`, `run_tool` and `tool_schemas` from it (line 1157). Add `app/ai/mcp_server.py` **beside** it and import from it — one registry, two consumers, no move. |
| Change the three hardcoded keys in `PERMISSIONS` | They serve the frontend, the customer app and the external developer. The agent token is a **fourth, separate** path. |
| Change `require_authentication`'s behaviour | It is deny-by-default and correct. The MCP mount simply has to live under the prefix it already guards. |
| Re-gate the chatbot's existing read tools in Phase 0 | A plan-gate regression in the product a paying tenant uses today (§10.1, Trap 2). |
| Add an Alembic migration | There is no Alembic. `create_all` at boot is the pattern. |
| Add an MCP client to the browser bundle | The session cookie is the browser's credential. |

### 10.4 A security note found while reading

`main.py` imports `TrustedHostMiddleware` (line 13) but **never adds it** — `add_middleware`
is called only twice, for CORS and for `SubscriptionAccessMiddleware`. The app therefore
accepts any `Host` header today.

That is pre-existing and unrelated to MCP. But it becomes relevant the moment the MCP
server is reachable from outside the box: the `Host` header is the cheapest way to bind a
virtual host to an app that does not check it. **When the MCP server is exposed, add the
middleware** — it is a two-line change and it should not wait for the exposure.
