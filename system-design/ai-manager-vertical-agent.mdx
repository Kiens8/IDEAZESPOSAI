## 1. The short answer

**The chatbot we have is good enough to sell. It is not an AI Manager, and no integration
tooling turns it into one.**

What exists today is a **pull** model: a human asks, the bot answers from POS data. What Kens
described is a **push** model with agency: a per-tenant agent that watches the store, knows the
tenant's own rules, and *does* things — always inside the POS's own rules.

The distance between the two is **not the model**. MiniMax already answers. The distance is
three missing layers:

1. **An action layer** — the agent can only read. Every write it performs is a new tool with
   its own permission, its own approval step and its own audit row.
2. **A trigger layer** — nothing in the product emits an event the agent could react to.
   The only webhooks that exist today are **inbound** payment ones.
3. **A tenant-profile layer** — the bot's behaviour lives in Python code paths. For the agent
   to be *the tenant's* agent, its persona, SOPs, permissions and working hours have to be
   **tenant data**, not code.

**The architectural answer (v1.1): the POS backend becomes an MCP server.** It is the
**tool layer** and the **identity layer** — every tool is tenant-scoped by the credential that
calls it, and every tool is a route underneath, so the existing gates apply for free. On top of
that server, the **agent runtime is the tenant's choice**: our own POS frontend chatbot, n8n, a
Telegram bridge, a WhatsApp bot, a future OpenClaw agent. We build the server once; the
runtime is pluggable.

**n8n is one client among many, not the architecture.** It has an MCP Client Tool node that
plugs straight into its AI Agent node, so it can consume our server as-is — but nothing in the
product depends on it, and the tenant never has to touch it.

## 2. What is actually built today (the audit this proposal starts from)

Every line below was read from the running code, not from the docs.

### 2.1 The chatbot

| Artifact | What it is |
|---|---|
| `backend/app/ai/chatbot.py` (1,295 lines) | The engine. Regex intent tables (`INTENT_PATTERNS`), a role map (`ROLE_INTENTS`), one handler per intent, and an AI fallback. |
| `backend/app/ai/chatbot_tools.py` (537 lines) | The tool registry the fallback calls — **10 tools, every one of them a read** (the catalogue is §4). |
| `backend/app/ai/minimax.py` | The shared MiniMax helper. Strips the `<think>` block so reasoning never leaks into a user-visible answer. |
| `backend/app/routes/chatbot.py` | `POST /api/chatbot/`, plus `/test`, `/greeting`, `/quick-replies`. Gated by `require_permission("ai:read")` **and** `require_plan_feature("AI Chatbot")`. |
| `backend/app/routes/ai_chatbot.py` | `POST /api/ai/chat/order` — the customer-facing conversational order. Same two gates. |

Two facts that shape the whole proposal:

- **The tool-calling loop only runs for `chatbot_type == "admin"`** (`chatbot.py`, the
  `tools = tool_schemas()` branch). A manager gets the AI fallback with the *snapshot* in the
  prompt; a staff member gets neither the tools nor a model. The tool machinery exists — it is
  simply gated to one role.
- **`MAX_TOOL_ROUNDS = 3`** (`chatbot.py:20`). The loop is bounded and the answer is written
  from the tool results. The pattern — *ask the model, let it call bounded read tools, write
  the answer from the numbers* — is the right one and Phase A extends it rather than replacing
  it.

  `/campaigns/suggest`, `/campaigns/{id}/simulate`). Reads need `ai:read`; the campaign writes

- `frontend/src/pages/Settings.jsx` — the **AI Chatbot** tab, gated by the feature row

So the tenant already has a **name and a greeting** for its bot. That is the thin end of the

## 3. The design

### 3.1 The shape

```
        ┌────────────────────────────────────────────────────────────┐
  MCP   │  POS BACKEND = the MCP server                              │
 clients│  • the tool registry (one registry, exposed twice)         │
        │  • tenant identity from the credential, never from args    │
        │  • every tool = a gated route underneath                    │
        │  • the tenant profile, the approvals, the audit log        │
        └───┬──────────────┬──────────────┬──────────────┬─────────┘
            │              │              │              │
    ┌───────▼──────┐ ┌─────▼─────┐ ┌──────▼──────┐ ┌─────▼──────┐
    │ our POS      │ │ n8n       │ │ Telegram /  │ │ the tenant │
    │ frontend     │ │ (MCP      │ │ WhatsApp    │ │'s own      │
    │ chatbot      │ │  Client)  │ │ bridge      │ │ agent      │
    │ (in-process) │ │           │ │             │ │            │
    └──────────────┘ └───────────┘ └─────────────┘ └────────────┘
            ▲                                            │
            │  the trigger layer (the one thing MCP        │
            │  does NOT give us): order.placed,            │
            │  stock.low, shift.ended, payment.failed      │
            └──────────────────────────────────────────────┘
```

**The POS backend owns the tools and the identity. The runtime is pluggable.**

Why this shape and not "n8n creates the agent per tenant":

- **Tenant isolation comes from the credential, not from code.** An MCP client presents a
  token; the server resolves it to `customer_id` + `outlet_id` and binds the session to it.
  Every tool call inside that session is scoped by construction. That is exactly the rule
  already held in `chatbot_tools.py` — `ToolContext(db, tenant_id, default_outlet_id)` and the
  `scope(outlet_arg)` helper, which **refuses** an outlet that is not the tenant's.
- **One tool surface, many channels.** Kens's requirement — *"triggered from our frontend POS,
  or another channel"* — is exactly the MCP contract. The POS frontend calls the tools
  in-process (it already does, 10 tools behind `MAX_TOOL_ROUNDS = 3`); an external channel
  connects over MCP. Same tools, same rules, same audit.
- **No licence problem.** MCP is a spec, not a product. n8n's Sustainable Use License never
  enters the picture, because n8n is a *client* of ours, not something we host and resell.
- **The tenant's agent runtime becomes the tenant's choice.** That is the most honest reading
  of "each tenant has its own vertical AI agent".

### 3.2 The MCP server (Phase 0)

**The transport.** FastAPI already serves the API; MCP is a second surface on the same
application, not a new service. Two decisions the design must make early:

- **Transport:** stdio is for local processes; a tenant's agent is remote, so the server must
  speak **Streamable HTTP** (the current MCP remote transport). n8n's MCP Client Tool node
  speaks it.
- **Authentication:** the server reuses the house's key model. A tenant's agent presents an
  API key; the server resolves it to `(customer_id, outlet_id, scope)` and refuses anything
  else. **The tenant comes from the credential, never from the model's arguments** — the rule
  `chatbot_tools.py` already states in its own docstring.

**The token.** The token lives in the **POS's own** database, in a new `agent_tokens` table
(`customer_id`, `outlet_id`, `scope` of `read` / `draft` / `action`, the plan row it rides on,
`revoked`), and a **new lookup function** resolves it into the same `key_info` dict shape the
rest of the app already understands — the fourth credential path beside the three hardcoded
keys in `PERMISSIONS` (§10.1). It is deliberately *not* the website API's `api_keys` table:
that table carries a `permissions` JSON column, but **the POS auth path never reads it** —
`get_key_info()` matches a literal string against the hardcoded `PERMISSIONS` dict — so a row
written there would not authenticate anything. A tenant holds one token for their agent,
revocable like any key.

**The plan is checked by the MCP layer, not by the route.** A lapsed plan must refuse the
tool call rather than the UI, but the house's plan gate cannot do that on this path:
`require_plan_feature` returns the credential untouched unless `key_type == "user"`, because
a session is what carries a plan (§8, Phase 0). The MCP transport therefore reads the plan
itself — the same `plan_cache` read and the same three states as §4.5 — at the transport and
again inside each tool body.

**One registry, two exposures.** The tool definitions live in **one** place and are rendered
twice: as the OpenAI-style function schemas MiniMax already consumes (`tool_schemas()`) and
as the MCP tool catalogue. If the two were written separately they would drift, and we would
have two truths about what the agent can do.

**The catalogue is filtered by the tenant's plan.** A tool declares the feature row that
gates it, and a tenant's agent is only offered the tools whose rows are in that tenant's live
feature list — read from the same source the API reads it from (`plan_cache` /
`fetch_plan_features`). The gate is re-checked on every call as well, because the plan can
change mid-session. The full rule, and why it is data rather than code, is §4.5.

**What the MCP server does NOT do:**

- It does **not** call the model. The *client* holds the LLM. (Consequence: the cost of a
  **foreign** client's model calls is invisible to us unless the client uses our model proxy
  — §4.4. **Our own runtime is the exception**: our chatbot calls MiniMax from our own
  backend on our own key, so that cost is already ours — though today we throw the number
  away instead of recording it. §4.6.)
- It does **not** trigger itself. MCP is pull-based; the proactive side is §3.5.
- It does **not** weaken a gate. Every tool is the same gated route the staff app uses.

### 3.3 The action layer (Phase A)

The tool registry grows a third kind of tool. The three kinds behave differently:

| Kind | Example | Approval | Audit |
|---|---|---|---|
| **Read** | `get_sales`, `get_alerts` | none | none |
| **Draft** | `draft_purchase_order`, `draft_campaign`, `draft_shift_swap` | **required** — it produces a *proposal*, and the approval is what creates the thing | the proposal is stored, and an `ai_actions` row is written when it is decided |
| **Action** | `send_purchase_order`, `execute_campaign`, `apply_price_change` | **required** — a human with the right permission approves | an `ai_actions` row |

The rules that make this safe, each one drawn from a rule the house already enforces:

- **The agent holds a token, not a god-mode key.** `ROLE_PERMISSIONS` maps *session* roles
  to permissions, and the agent has no session — so its authority is the token row: a scope
  (`read` / `draft` / `action`) checked at the transport, and a permissions list
  (`ai:read`, `ai:act`) the tool bodies check. It never inherits `admin:*`, and it never
  holds `ai:approve`.
- **The server owns the money and the price.** The agent may propose a price change; the
  write goes through the same pricing path the staff screen uses, so the promotion precedence,
  the tax and the order's locked price are unchanged (`pricing-engine-and-promotions.mdx`).
- **Every action is written down before it runs**, in an `ai_actions` row: the agent, the
  tenant, the outlet, the tool, the arguments, the JSON of what changed, who approved it, when.
  The `order_reprints` row is the precedent; the fields are the same idea.
- **An action that is refused is recorded as refused.** Silence is not success — the same rule
  the delivery sweep and the unattended watcher already live by.
- **The approval is a human's, in the POS.** The approval lands in the agent's own
  notification feed — the new generic `agent_notifications` table (§5.1), because the
  existing notification route is the *inventory* feed and cannot carry a decision. Nothing
  is auto-approved because a model was confident.
- **The MCP server refuses an action tool outright** when the credential's scope is `read`
  only. The refusal happens at the transport, before the tool body runs.

#### 3.3.1 The approval happens in the chat — with explicit controls

**Kens's decision: the agent drafts, a human approves — and yes, the human approves using
the chat.**

That last part is the one that needs writing down, because "the chat approves it" is the
phrase that hides a hole. **A chat transcript is not an approval channel.** If "yes" typed
into the chatbot can approve a purchase order, then the model — which writes the assistant's
side of that transcript — can approve its own draft by asking a question a human is likely
to say yes to. Approval cannot be a *phrase*.

**What exists today — nothing that approves anything.**

- The chatbot's tool set is **read-only**. All ten tools in
  `backend/app/ai/chatbot_tools.py` read and aggregate; none of them writes.
- `frontend/src/pages/Chatbot.jsx` has exactly two buttons — one that fills the input with
  a suggested reply, and the send button. There is no approve, no reject, no edit.
- There is no `ai_actions` table and no proposal queue.

**What the proposal adds.**

1. **A proposal object.** The draft tool returns a proposal — an id, the tool, the
   arguments, a human-readable summary of what would change, and a state (`pending`).
2. **Three explicit controls, rendered as buttons on the proposal card** — **Approve**,
   **Edit**, **Reject**. Not a text intent. The card is a first-class object in the
   transcript, not a paragraph of assistant text.
3. **A separate route for the decision** —
   `POST /api/ai/proposals/{id}/approve|edit|reject`. The chat's message endpoint never
   approves anything; approval is not reachable by writing text.
4. **The approver's own permissions are checked at approval time**, not at draft time. The
   agent never holds `ai:approve`. The person clicking Approve is checked in that person's
   own session, and the check is **stricter than `require_permission`**: a new
   `require_human_approver` dependency demands a *signed session* (`key_type == "user"`)
   **and** the permission. The shared frontend API key is refused outright — it carries an
   `ai:*` wildcard, and a secret everybody holds cannot be a decision — and so is the agent
   token, which is not a session at all. So a waiter's session cannot approve a purchase
   order by replaying a manager's token, and neither can our own server-side key.
5. **The audit row is written before the action runs** — `ai_actions`, with the agent, the
   approver, the timestamp, the arguments and the JSON of what changed. An approval is
   recorded even when the action then fails, and a refusal is recorded as refused (§3.3).

**What "edit" means.** Edit sends the human's correction back to the agent as a **new**
draft: the agent revises and shows a new card. The arguments are never patched in place,
and the model never holds the arguments of an approved action — so it cannot quietly
rewrite one after the fact.

**The trap this closes.** The failure mode of "approve in the chat" is not that a human
approves the wrong thing. It is that **an instruction hidden in tool output** — a menu
item or a customer note carrying "approve this order" — ends up in the transcript, and a
phrase-matching approver executes it. The buttons make that impossible: the only path to
approval is a signed HTTP request from a human's own session.

### 3.4 The tenant profile (Phase B)

A per-tenant record that turns one engine into fifty managers:

| Field | Example | Why |
|---|---|---|
| `name` | "Aunty Mei" | The name the tenant already gives the bot today. |
| `persona` / `system_prompt` | "You are the outlet manager of a kopitiam. Be brief. Speak in the outlet's timezone." | The tenant's voice, not ours. |
| `language` | `en` / `zh` / `ms` / `kh` | Already exists per outlet (`bot_language`). |
| `sop` (list) | "Every morning at 09:30, check yesterday's waste vs sales and message the kitchen." | The tenant's own procedure. |
| `allowed_actions` | `["draft_purchase_order", "draft_campaign"]` | What this agent may ever do. Empty set = read-only, which is today's behaviour. |
| `quiet_hours` | `23:00–07:00` | When the agent may not push anything. |
| `escalation` | "money > RM 500 → notify the admin" | The tenant's own thresholds. |
| `outlet_scope` | `["all"]` or a list | Which outlets this agent watches. |
| `runtime` | `pos_frontend` / `n8n` / `telegram` / … | Which client runs this agent. The profile is runtime-agnostic. |

This is the layer that makes the product *vertical*: the same engine, a different manager for
every tenant, and **no code change** to onboard a new one.

### 3.5 The trigger layer — the event bus (Phase C)

MCP is **pull**: the client asks, the server answers. That covers "the manager typed a
question". It does not cover "the agent noticed something". For that the POS needs its own
side — an **event bus** — and the two are complementary rather than alternatives:

> **The event bus tells the agent THAT something happened. The MCP server tells the agent
> WHAT it may do about it.**

An event carries **no power and almost no data** — a name, a tenant, an outlet, an object id, a
timestamp. The agent reacts by calling the tools over MCP, with its own token, and the server
answers under the tenant's plan and the tenant's outlet scope. So the bus cannot leak what
the tools would refuse, and the tools cannot be reached without a credential.

#### 3.5.1 The four parts

**1. The emitters — in the write path, never a poller.**

| Event | Emitted when | A manager agent would… |
|---|---|---|
| `order.placed` | an order is created | flag a table that has been open too long |
| `order.paid` | the money settles | close the shift count |
| `order.stalled` | an order sits past the kitchen's reminder | tell the kitchen |
| `stock.low` | an ingredient falls to its threshold | draft a purchase order |
| `staff.clocked_in` / `shift.ended` | the shift starts and ends | compare the actual to the roster |
| `table.turned` | a table is settled | suggest the next seating |
| `payment.failed` | a gateway webhook says no | alert the counter |
| `refund.issued` | a refund is written | flag it for the security review |

The delivery module already settled the house rule: **the server owns the decision, and the
enforcement lives where the data is written.** An event emitted next to the order insert is
*truthful*; an event inferred by a cron that scans for rows is a *guess* — it double-fires,
and it cannot see a transaction that has not committed.

**2. The outbox — `domain_events`, written in the same transaction.**

The event row is written **in the same DB transaction as the business change**. That is what
makes it true: either the order exists and the event exists, or neither does. There is no
window where an agent saw an order that was rolled back. The row carries
`event_id`, `event_type`, `customer_id`, `outlet_id`, `payload` (ids only),
`created_at`, `delivered_at`, `attempts`, `state`.

**3. The dispatcher — one worker, the same pattern as the delivery sweep.**

The box already runs a cron worker (`scripts/sweep_delivery_entitlement.py`, 03:23 daily).
The dispatcher is the same shape: a script that reads the undelivered `domain_events`, asks
the **subscribers** which ones they want, and delivers. It is **not** a synchronous call from
the order insert — an event that blocks an order because a tenant's webhook is slow is a
self-inflicted outage on the live payment path. The order commits; the event is queued; the
dispatcher retries with a backoff and drops into a dead-letter log after N attempts.

**4. The subscriptions — per tenant, per outlet, per event type.**

A row saying *this tenant, this outlet, wants these events, delivered this way*:

| Subscription field | Example | Why |
|---|---|---|
| `customer_id` / `outlet_id` | 22 / 3 | The tenant — **never** from the payload |
| `event_types` | `["stock.low", "order.stalled"]` | What this agent cares about |
| `channel` | `in_app` / `telegram` / `webhook` | Where the answer goes |
| `endpoint` / `chat_id` / `bot_token_ref` | a chat id, a SecretRef | Where exactly |
| `runtime` | `pos_frontend` / `n8n` / `telegram_bridge` | Which client runs the agent |
| `quiet_hours` | `23:00–07:00` | From the tenant profile (§3.4) |
| `enabled` | true | The off switch a tenant can pull |

#### 3.5.2 The two shapes of a trigger

**Push (proactive).** The POS notices something.

```
order insert ──▶ domain_events row (same transaction)
                      │
                 dispatcher (cron / worker)
                      │  asks the subscribers
                      ▼
              tenant's agent runtime  ──▶ MCP tool calls (with the tenant's token)
                      │
                      ▼
              the answer lands on the channel
```

**Pull (reactive).** A human says something.

```
manager types in Telegram ──▶ the channel's bridge ──▶ the agent runtime
                                                              │
                                                              ▼
                                                  MCP tool calls (same token)
                                                              │
                                                              ▼
                                                   the answer goes back
```

Both shapes end at the **same MCP server, with the same token, under the same plan and outlet
scope**. That is the point of the split: the bus is a *notification mechanism*, the MCP server
is the *authority*. A tenant's Telegram agent and our own POS chatbot have exactly the same
powers.

#### 3.5.3 The channels, concretely

**Channel A — the frontend POS app (we already have it).**

The staff app's **notification bell** already polls `GET /api/inventory/notifications/`
every **30 seconds** (`frontend/src/components/NotificationBell.jsx`) and shows a badge — but
it is an **inventory** bell. The router is mounted at `/api/inventory/notifications`, the
table is `inventory_notifications`, and every row carries an `ingredient_id` with a
`notification_type` of low stock / out of stock / critical low. The bell is also hidden
entirely for a tenant whose plan has no Inventory feature (`INVENTORY_FEATURES` in the
component). It is an alert feed about ingredients, not a queue about decisions.

So the native channel needs **one new, generic, tenant-scoped table** — `agent_notifications`
(§5.1) — carrying the agent's briefings, its alerts and its pending approvals, each row
addressed to an outlet with a read state. One table, three kinds, one unread count. The
existing inventory notifications are untouched; the bell grows a second source rather than
being bent into a shape it was never built for.

For a phone, `delivery_push.py` already speaks **VAPID web push** — the transport is
reusable. The **subscription is not**: `push_subscriptions.dining_customer_id` is `NOT NULL`
and `subscribe()` takes a dining member's id, so every row in the table is a customer's phone
for delivery news. A manager's phone is a new subscription (a staff-keyed row, or a sibling
table) — new work in Phase C, not a re-use of an existing one.

**Channel B — Telegram (the tenant's own channel).**

This is the case Kens named, and it is the one that makes the runtime swappable:

- **The tenant connects Telegram** — a bot token stored as a **SecretRef** (never a plain
  value, never in the workflow JSON), the chat id bound to `customer_id` + `outlet_id` in the
  subscription row. One subscription = one tenant + one outlet + one chat.
- **Inbound** — Telegram posts the message to a webhook; the bridge resolves the chat id to
  the tenant, then the agent runtime calls our MCP server with that tenant's token. The
  bridge never touches the database — it is a client, exactly like n8n.
- **Outbound** — the dispatcher delivers the event to the runtime; the runtime calls the
  tools and sends the answer to the chat.
- **The channel is not the identity.** The chat id is a *routing* fact. Every tool call still
  arrives with a token that resolves to the tenant, so a misrouted or spoofed message cannot
  reach another restaurant's data — the token's scope is what decides.
- **The POS backend has no Telegram code today.** `grep -rn telegram backend/app` returns
  nothing; the only Telegram in the house is the OpenClaw gateway's own channel. So this
  channel is new code, and it lives in the *bridge*, not in the POS.

**Channel C — a signed webhook (the tenant's own runtime).**

The dispatcher POSTs the event to the tenant's endpoint with a signature over the body, a
timestamp and the tenant id, scoped to that tenant's key — the pattern
`backend/app/routes/internal.py` already uses for `/plan-changed` and `/order-paid`. This is
the channel n8n consumes, and the channel any other runtime consumes.

#### 3.5.4 The rules that keep the bus honest

- **The event carries no money and no personal data.** An event says *which* order, not what
  it cost and who it belonged to. The agent fetches the detail through a tool, under the
  gate. A webhook payload that carried the order total would leak it to whatever endpoint the
  tenant pointed at.
- **At-least-once, and the receiver must be idempotent.** The dispatcher may deliver twice
  (it crashed after the push and before the mark). Every event carries a stable `event_id`, and
  a consumer that acts on it must record what it has already acted on.
- **A failed delivery is a recorded failure, not silence.** Dead-lettered events are visible
  in the admin app. The house already lives by this — the unattended watcher rule: *silence
  must never mean "healthy."*
- **The plan gate applies to the events too.** A tenant on Pro must not receive a
  `stock.low` event, because `Inventory` is an Enterprise row. The dispatcher asks the same
  feature list the tools ask, and drops an event whose module the tenant does not hold.
- **Quiet hours are the tenant's, and they are enforced here.** An event that arrives at 02:00
  is held, not dropped — it is delivered when the tenant's day starts.
- **One event, one tenant.** The dispatcher never fans an event out across tenants, and the
  tenant id on the row is the tenant the event belongs to.

### 3.6 The surface (Phase D)

**Where this lives: the FRONTEND POS STAFF APP.** Not the website admin app, not the
customer app, not a separate agent console. Concretely, it is the staff app's **existing
`/ai-tools` route** — `frontend/src/App.jsx:496` → `frontend/src/pages/AI/index.jsx` —
which Kens has decided the AI Manager **replaces** rather than sits beside.

That is the answer to "where is the §3.6 surface implemented?": the same React app, under the
same `/api` base, with the same session cookie, behind the same nav gating. **One page
changes. The app does not gain a second front door.** The chatbot at **`/chatbot`** stays
where it is — it remains the conversational surface, and the approval cards of §3.3.1 appear
inside it.

The page carries four sections:

- **Today** — the briefing: sales against the same hour yesterday, orders waiting, tables
  occupied, anything the agent thinks the manager should know, in the outlet's timezone.
- **Needs you** — the approvals. A draft purchase order, a proposed campaign, a price change.
  Approve, edit, or reject — each one an audit row, and the same three controls the chat
  offers (§3.3.1). The chat card and the page card are two views of **one** proposal, not
  two queues.
- **Alerts** — the agent's findings, next to the existing AI alerts, with the same
  acknowledge path (`AIAlert` already has one).
- **Agent** — the profile from §3.4, the working hours, the allowed actions, the escalation
  thresholds, the channel the briefing arrives on, and the **agent token** the tenant hands to
  their own runtime.

**What happens to the five tabs the page carries today.** The current AI Tools page is five
read-only tabs — Insights, Menu Analytics, Campaigns, Competitor Discover, Competitor
Analysis — each behind its own feature row and plan. The Manager keeps that material; what
it adds is the trigger and the personality. **Proposal, for Kens to confirm in the design
review:** Insights and Menu Analytics are what the agent reads to build *Today* and *Alerts*,
so they become sections rather than tabs; Campaigns becomes the surface the agent drafts
into; and the two competitor tabs stay as they are, under their own feature rows, because
competitor data is not the tenant's own store and does not belong inside an agent that
manages an outlet.

**The nav and the plan do not move.** `navItems.js` keeps one AI entry — the `/ai-tools`
entry, still behind the `AI Tools` feature row — instead of two. A tenant on a plan without
`AI Tools` does not see the page today and does not get the Manager page later. The
`AI Tools` row is what the page is called and what it is gated by; the content underneath it
is what Phase D replaces.

### 4.4 The model proxy — a Phase F question, not a Phase 0 one

In an MCP setup the *client* holds the LLM. For a **foreign** runtime — n8n, a Telegram
bridge, a tenant's own agent — that means per-tenant token cost is invisible to us, because
their model key, their bill. The proxy closes that: the backend exposes a tenant-scoped,
OpenAI-compatible model endpoint, the client's model node points at it, and the server logs
tokens per tenant, enforces the model, caps spend, and refuses a tenant whose plan lapsed.
The same trick the house already uses for the plan read (`plan_features.py` over the
house's loopback path).

**But our own runtime does not need it, and that changes the priority.** Our chatbot calls
MiniMax from our own backend, on our own key — `ai/chatbot.py` posts to
`settings.MINIMAX_BASE_URL` with `settings.MINIMAX_API_KEY`. The browser never holds a model
key; it posts to `/api/chatbot/` and the backend does the rest. So for the runtime Kens
picked first, the cost is **already ours, already attributed to a tenant by the request, and
already gated** by `require_plan_feature("AI Chatbot")`. There is nothing for a proxy to
discover.

That is why the proxy is **Phase F**, where it belongs: it exists for the tenant who brings
their own runtime, and it is only worth building once that tenant actually exists. For the
proactive agent, the cheaper and more direct instrument is **§4.6** — record the `usage`
block the response already carries, at the call site we already own.

### 4.5 The gate every tool carries

Every tool above declares **one feature row** — the row of the module it touches. That row
is the tool's plan gate. Three rules follow from it.

**Rule 1 — the gate is data, never a tier name.** The tool does not know what "Pro" or
"Enterprise" is. It knows it touches `Inventory`. The plan row for `Inventory` is read live
from the website API's `features` / `plan_features` tables, through the machinery the house
already has:

- `backend/app/services/plan_features.py` — `get_plan_features(tenant_id, fetch)` reads the
  plan's feature **names** and caches them. The name it collects is the row's `tab_name`
  (the website API's customer-features route returns `tab_name` under the key `name`), so
  that string — not `display_name` — is what the gate compares. Today all 44 live rows have
  the two identical, which is why the source comment calls it "the display name"; a new row
  must set both to the same string, or the gate compares a string that was never put in the
  plan.
- `backend/app/core/plan_cache.py` — the cache distinguishes three states, and the third one
  is the one that matters:
  - a **fresh or stale known list** — the tenant bought these features;
  - an **empty known list** — the tenant bought no paid feature (a Starter tenant);
  - **`None`** — the plan could not be read and was never known.

`None` is not "no features". It is "we could not ask". The delivery entitlement pattern
already draws this line: it checks the plan includes delivery, then that the subscription is
active, then that the outlet's own delivery switch is on. **We could not ask is not the same
as not allowed** — a lookup failure must never be reported to a tenant as a refusal, because
the tenant *has* the feature and we simply could not confirm it.

**Rule 2 — no tier names in code.** The catalogue never says "Pro-only" or "Enterprise-only".
It says "`Inventory`". If the admin later moves the `Inventory` row from Enterprise to Pro —
which is exactly what Kens said could happen — the tools that touch inventory become
available to Pro tenants **with no code change and no redeploy of the catalogue**. The tier
names in the tables in §4.1–4.3 are annotations of *today's* plan assignment, not the rule.
They are marked as such.

**Rule 3 — the gate is checked on every call, not only when listing.** Two checks, both
required:

1. **At catalogue time** — `list_tools` (MCP) / the tool-schema registry returns only the
   tools whose feature rows are in this tenant's live feature list. A Pro tenant's agent is
   never even *offered* `get_inventory_levels`.
3. **At call time** — every tool body re-checks the gate before it runs. The plan can change
   mid-session: the tenant upgrades, downgrades, lapses, or an admin moves a feature row
   between plans while the agent is holding a session. The listing was true when it was made;
   the call-time check is what makes it true *now*. The read is served from
   `plan_cache`, so it is cheap — and a cache miss costs one live read, not a refusal.

**And the check has to be ours on the agent's path.** `require_plan_feature` is a **no-op for
a key caller**: it returns the credential untouched unless `key_type == "user"`, because a
session is what carries a plan (the route dependency's own docstring says server-to-server
callers "are not governed by a browser session and are not checked here"). The chatbot is a
session, so its route gate works. The MCP transport is **not** — it presents a key — so a
tool reached only through the route dependency would be **ungated**. The MCP layer checks the
plan itself, from the same `plan_cache`, with the same three states (§8, Phase 0).

**What a refusal looks like.** When a tool is called and the gate fails, the tool returns a
**module-level refusal**, in the same shape as every other answer (the `data` field):

> `This restaurant's plan does not include the Inventory module.`

It does **not** return an empty result, and it does **not** invent plausible data. An empty
result would be read by the model as "there is no stock" — a refusal is the only answer that
cannot be misread.

**Why this matters more than it looks.** Today the chatbot's ten tools are gated **once, at
the route**, by `require_plan_feature("AI Chatbot")` — no tool carries its own module gate.
Two consequences follow:

- A tenant with `AI Chatbot` can ask the agent about AI alerts, the demand forecast and the
  order insights, whose own routes (`ai_security.py`, `ai_forecast.py`, `ai_orders.py`) carry
  **no plan gate at all** — only `ai:read`. The features are paid for elsewhere; the agent
  reaches them anyway.
- Several modules are gated in the **frontend only**. `frontend/src/config/navItems.js` hides
  Promotions, Loyalty, Vouchers and every Inventory page by feature row, but
  `promotions.py`, `vouchers.py` and `loyalty.py` carry **no `require_plan_feature`**. The
  screen hides what the API does not refuse — hiding a menu item is a usability decision, not
  an authorisation boundary.

Per-tool gating closes both, and it is the difference between an agent that is *about the
business* and an agent that is *about the plan*.

### 4.6 The metering we do not have

The MiniMax API returns a `usage` object with every response — prompt tokens, completion
tokens, and for a reasoning model like `MiniMax-M3`, the thinking tokens as well. **Today the
chatbot discards it.** The parser keeps `choices[0].message` and nothing else
(`ai/chatbot.py`), so there is no token count anywhere in the product — `grep` for
`prompt_tokens` across the backend returns nothing.

That is acceptable while the model is only ever called because a human asked something, and
the `AI Chatbot` plan row is the price. It stops being acceptable the moment the agent
speaks **on its own**, because then two questions become unanswerable: which tenant spent
the tokens, and when to stop.

The fix is deliberately small, and it belongs at the call site rather than behind a proxy:

- Read `usage` off the response and log it with the tenant, the outlet and the model.
- One row per call is enough to start.
- **Size the cap with the amplification in mind.** `MAX_TOOL_ROUNDS = 3` means one question
  can cost up to three round-trips, each up to `max_tokens: 800`, and `MiniMax-M3` is a
  *reasoning* model — it spends part of the budget thinking before it answers. One question
  is not one token count. (The translator already learned this the hard way:
  `TRANSLATION_MAX_TOKENS = 16000`, with the comment *"With a small ceiling the response
  comes back empty and nothing gets translated."*)

- `outlet_settings.bot_name` / `bot_language` / `bot_greeting` / `ai_enabled` — the profile
  **seeds** from these, so a tenant that has already named its bot sees its name carried over.
- The feature row and the plan gate — unchanged; the AI Manager rides the existing
  `require_plan_feature` machinery (§6).

### 5.3 The model

MiniMax, as today (`settings.MINIMAX_MODEL`, the `ai/minimax.py` helper). One change worth
making: the agent's calls should go through **one** client with a **cost log** — the number of
calls, the tokens and the tenant they belong to. Without that, a proactive agent that runs
every morning for every outlet is an unbounded bill and nobody knows whose it is.

## 6. Plan and role gating

The house has two independent gates, and the agent needs both:

- **The role** says what a *person* may do with a kind of data.
- **The plan** says what the restaurant *bought*. `require_plan_feature` compares a
  **feature name** against the tenant's list, which is read from the website API over the
  house's loopback path. That name is the row's `tab_name` (§4.5) — so a new feature row has
  to carry the right `tab_name`, or the gate compares a string the plan does not hold.

**Plan rows.** The live feature table holds 44 rows, of which the AI category is:

| Row | Display name | Pro | Enterprise |
|---|---|---|---|
| `ai_chatbot` | AI Chatbot | yes | yes |
| `ai_tools` | AI Tools | yes | yes |
| `ai_customer_insights` | AI Insights | yes | yes |
| `ai_menu_analytics` | Menu Analytics | yes | yes |
| `ai_campaigns` | AI Campaigns | yes | yes |
| `ai_competitor_analysis` | Competitor Analysis | no | yes |
| `Competitor Discover` | Competitor Discover | no | yes |

Plus the settings row `ai_chatbot_setting` → **AI Chatbot Settings** (Pro and Enterprise).
Starter and Basic carry **no** AI row at all.

**The proposal:** two new rows.

| Row | Display name | Plan |
|---|---|---|
| `ai_agent` | AI Agent | Pro — read-only agent (MCP read tools, profile, briefing, inbox) |
| `ai_agent_actions` | AI Agent Actions | Enterprise — the agent may also *act* (draft + action tools) |

The two-row split is deliberate: **the agent that reports is a different purchase from the
agent that writes**, and the write one is the one that needs the audit, the approval queue and
the review. Splitting them also means a tenant can buy the briefing on Pro and not be
refused at runtime for a missing entitlement — the plan gate refuses a *route*, and an action
is a route.

**The per-tenant exception already exists.** `customer_feature_overrides` lets the admin grant
or refuse a feature for one customer with a reason and a `created_by`. So the "AI Manager" can
be sold to a single tenant on a plan that does not include it, without a new billing path —
the row is written, the POS cache is notified (`notify_pos_plan_changed`), and the tenant's
agent switches on.

**The agent's authority is its token, not a role.** `ROLE_PERMISSIONS` maps **session roles**
to permissions — the browser's signed-in user is looked up there by role
(`get_auth_context`), and an API key carries its own permission list instead. The agent holds
a token, not a session, so giving it an entry in `ROLE_PERMISSIONS` would describe nothing
that exists. Its authority is the token's **scope**:

- `read` — everything today's tools already need.
- `draft` — the draft tools, and nothing else.
- `action` — the action tools, and nothing else.

**The human's authority is a new permission.** `ai:approve` is added to `manager`; the
`admin` already covers it through its existing `ai:*` wildcard, and `staff` has neither — so
a waiter cannot approve a price change. The agent's token **never** carries `ai:approve`:
the scope has no such value, and the approval is a human's. A human who approves an action is
recorded as the approver, with their own permissions checked **at that moment**, in their own
session — the manager's approval and the admin's approval are separate records with separate
permissions behind them.

**The MCP token's scope is a third, separate axis.** A token's scope (`read` / `draft` /
`action`) is checked **at the transport**, before the tool body runs — so an agent that
somehow tries an action tool with a read token is refused without the tool ever seeing the
request.

**Where the gate sits today, and where it moves.** The route-level gate is what the house
uses today, and it works — but it is one gate for a whole route. The chatbot's route carries
`require_plan_feature("AI Chatbot")` and that is the **only** gate on it: the ten tools
inside have no gate of their own, so a tenant with `AI Chatbot` can ask the agent about
alerts, forecasts and order insights whose own routes carry no plan gate at all, and about
Promotions, Loyalty and Vouchers, whose routes carry none either — those are hidden in the
frontend only (`navItems.js`). Hiding a menu item is a usability decision; refusing a call is
an authorisation boundary.

The proposal moves the gate **down to the tool** (§4.5):

| | Today | Proposal |
|---|---|---|
| The gate | one per route, `require_plan_feature` | one per tool, carrying the feature row of the module it touches |
| Where it is checked | at the route, once, at request entry | at catalogue time **and** at call time, per tool |
| What a refusal says | the route returns 403 | `This restaurant's plan does not include the Inventory module.` |
| A tier change | a code change per route | a row move in `plan_features` — no code change |
| A lookup failure | the route refuses | **never** reported as a refusal — "we could not ask" is not "not allowed" |

The route gate stays — it is still the coarse boundary for the page. The tool gate is the
fine one, and the two are not redundant: the route gate answers *"may this tenant open the
AI Manager at all?"*, the tool gate answers *"may this agent read stock?"*.

## 7. Where n8n fits — and where it does not

*(v1.1: this section was rewritten. In v1.0 n8n was the proposed agent runtime; Kens pushed
back on that and proposed MCP instead. The verdict is now the opposite: n8n is one client
among many.)*

### 7.1 What n8n is good at

- Letting a **tenant** wire their own automations without us building each one: WhatsApp
  broadcasts, a delivery aggregator, an accounting export, a Google Sheet, a Telegram channel.
- Surviving the long tail of integrations we would never ship.
- Being **visible** to the tenant — the flow is in a UI they can open and read.

### 7.2 What n8n is bad at, for this job

| Problem | Why n8n does not solve it |
|---|---|
| **Tenant isolation** | A flow runs with the credentials it was given. Getting "this flow may only ever read this tenant's data" right means re-implementing the isolation the POS already has in `require_outlet_access` and the tenant scope on every tool. |
| **The money rules** | The agent must never be able to write a price the pricing engine would not have written. A workflow that calls the POS API is subject to the POS's rules; a workflow that writes to the database directly is not. |
| **Plan gating** | `require_plan_feature` refuses a route for a tenant that did not buy it. A tenant's n8n flow is outside that gate unless we make it call our gated routes — at which point n8n is a caller, not the brain. |
| **The agent's own identity** | The agent needs a tenant profile, a working-hours rule, an escalation threshold and an audit trail. That is data the POS must own; it cannot live in a workflow JSON. |
| **Cost** | A proactive agent that runs every morning for every outlet is a per-tenant bill (model calls + n8n executions). That has to be priced deliberately, not discovered later. |
| **The licence, if the tenant ever logs in** | n8n is under the **Sustainable Use License**, which restricts hosting n8n as a service to clients and embedding it in a product without a commercial agreement. Running n8n internally, one instance, one workflow per tenant, is ordinary internal use and is fine. Giving the tenant a login into our n8n is selling access to n8n — that needs a commercial licence, and the per-project RBAC that isolates one tenant's workflows from another's is an Enterprise feature (Community Edition has no project isolation at all). |

### 7.3 The shape that works

**The POS owns the agent's tools and identity; n8n is a client.**

n8n has an **MCP Client Tool** node — an MCP client that attaches to an AI Agent node's
tools — so n8n consumes our MCP server as-is, with no bespoke integration code. A tenant's
n8n workflow becomes: *a trigger (schedule or our webhook) → the AI Agent node → the MCP
Client Tool pointing at our server → our tools → the answer.* The tenant's own runtime, the
tenant's own connectors, and **not one line of our code in the loop**.

But the same shape serves a Telegram bridge, a WhatsApp bot, or a future OpenClaw agent with
no change to the server. That is the whole point of the MCP decision.

**If n8n is not installed, nothing above changes.** The product does not depend on it.

## 8. The phases

*(v1.6: this section was re-audited against the live code and re-ordered. The phase letters
are unchanged — §3.2 is still Phase 0, §3.3 Phase A, and so on — but four things moved, and
they are listed first because they are the reason the order is what it is.)*

### 8.1 What the re-audit changed

**1. The two feature rows move to Phase 0.** The plan gate compares a **string** — the row's
`tab_name` — against the tenant's live feature list, and that list is read from the website
API's `features` and `plan_features` tables. A gate can only be satisfied by a row that
exists. So if `AI Agent` and `AI Agent Actions` are created in Phase E, then through Phases 0
to D the gate reads "not in your plan" for every tenant including us, every gated tool
refuses, and none of the phases can be proven at all. The rows are **data, not code**: they
go in Phase 0, with their plan assignment, and Phase E keeps only the commercial packaging —
the price, the tiering decision, the per-tenant override for the design partners, and the
cost report over the usage log.

The row has **three** places to be written, and all three are needed:

- `website_api/app/core/seed_features.py` — for a fresh install. This file is **not** the
  source of truth for the live database: it holds 20 rows and the live `features` table holds
  44, so 30 live rows exist only in the database. A new row goes into the seed **and** into
  the live table.
- the live `features` table — `name` (`ai_agent`, `ai_agent_actions`), `display_name` (`AI
  Agent`, `AI Agent Actions`), `tab_name` (the same string), `category` (`ai`), `is_active`.
- the live `plan_features` table — `AI Agent` to Pro and Enterprise, `AI Agent Actions` to
  Enterprise, per §6.

**The gate string is `tab_name`, not `display_name`.** The POS reads the list from
`/api/admin/customer/{id}/features`, and that route returns the row's `tab_name` under the
key `name` — which is the key `fetch_plan_features` collects. Today the two are identical for
all 44 live rows, so the distinction is invisible; a new row must set both to the same
string, or the gate compares a string that was never put in the plan.

**2. The metering and the cap move forward, into Phase D.** The push side is the unbounded
side (§9.2): the pull path is bounded by a human asking, the proactive path is bounded by
nothing. So the `usage` log and the daily briefing cap ship **with** the briefing that first
spends a token without being asked — not after. A cost log added the morning after the first
unmetered briefing is a bill you can attribute but not prevent.

**3. Phase A's delivery target is a new table.** The "existing notification inbox" is the
**inventory** feed: `inventory_notifications`, every row carrying an `ingredient_id`, the
router mounted at `/api/inventory/notifications`, and the bell hidden entirely for a tenant
without an Inventory feature. It is an alert feed about ingredients, not a queue about
decisions. The proposals get the new generic `agent_notifications` table (§5.1).

**4. The agent's authority is its token, not a role.** `ROLE_PERMISSIONS` is a map of
**session** roles to permissions — the browser's signed-in user is looked up there by role.
The agent holds a token, so an entry in `ROLE_PERMISSIONS` would describe nothing that
exists. Its authority is the token row: a **scope** (`read` / `draft` / `action`) checked at
the transport, and a **permissions list** the tool bodies check (`ai:read`, `ai:act`).
`ai:approve` is only ever on a human session, and the human roles gain it explicitly
(`manager`; `admin` already covers it through its `ai:*` wildcard).

### 8.2 The dependency graph

```
Phase 0 ──> Phase A ──> Phase B ──> Phase C ──> Phase D ──> Phase E ──> Phase F
(MCP +    (the action  (the tenant  (the      (the       (the     (the
feature   layer)        profile)    trigger)  surface)  money)   connectors)
rows)
```

The edges that are not obvious from the list:

- **C depends on A** — the native channel writes into the `agent_notifications` table Phase A
  creates.
- **D depends on A, B and C** — the page shows A's proposals, B's profile and C's events.
- **E depends on nothing new in code** — it is pricing and packaging, and it can ship any
  time after Phase 0's rows exist.
- **F depends on A's registry and Phase 0's transport** — a foreign runtime is a client of
  what Phase 0 already built.

Nothing in Phase A depends on Phase C or Phase D. The **metering and the cap land in
Phase D**, with the briefing that first spends a token unasked.

### 8.3 What Phase A's implementation settled

The design left four questions open. The code answered them, and this is the record of how —
so the next reader does not have to re-derive them from the diff.

**1. A draft tool also waits for a human.** §4.3's table had the draft rows at "—" for
approval, while §3.3 had the draft producing "a *proposal*, nothing changes" and Phase A's
own proof section had a manager approving a *drafted* purchase order into a real one. The
implementation reads those together as: the *tool call* needs no approval — it changes
nothing — and the **approval is what creates the thing**. So both kinds produce a stored
proposal, both wait for a human, and both write an `ai_actions` row when they are decided.
The table's "Approval" column now reads `required` on every row.

**2. Draft against action is *what it asks for*, not *whether it needs approval*.**

| | The draft asks for | The action asks for |
|---|---|---|
| `purchase_order` | the order, in `pending` | the order, **sent** to the supplier |
| `promotion` | the promotion, **not running** | the promotion, **running** |
| `campaign` | the campaign, **not active** | the campaign, **executed** — vouchers sent |
| `price` | a price **derived from the live cost** at the margin asked for | a price **somebody chose** — the money action |
| `voucher` | the house **template's** terms — the draft may not invent the money | **bespoke** terms |
| `shift_swap` | the handover, drafted | — (the clock *is* the roster) |

The two that share a route — a promotion, a voucher — differ in exactly that way: the draft
takes the house's standard form and the action takes the bespoke one. That is what stops a
`draft` token from being a quieter `action` token.

**3. The approval runs the house's own routes, with the approver's session.** The approved
operation is executed by calling the POS backend's own endpoints over the loopback, with the
**approver's signed session cookie** forwarded. So the route's own permission, its own plan
gate, its own outlet tenancy and the pricing path all run *with that person's authority* —
and the agent never writes business data. It also means the permission the tool needs is
the route's own: `record_stock_waste` needs `inventory:write`, which the `manager` role does
not hold, so a manager is refused that one and the refusal is recorded.

**4. The approver must present a signed session, not merely hold the permission.** The
shared frontend API key carries an `ai:*` wildcard, so a plain `require_permission` check
would have let that shared secret approve a purchase order. `require_human_approver` demands
`key_type == "user"` **and** the permission, so the shared key, the agent token and the
`staff` role are all refused — and only a person in their own session decides.

**What was proven.** `backend/scripts/test_mcp_actions.py` — 53 checks against the live
server — covers the scope ladder at the transport, that a proposal changes nothing, that
only a person approves (agent token, shared key and staff session each refused), that the
approval runs the house's own route, that the `ai_actions` row was written **before** the
operation ran, that an edit creates a new proposal and never patches the old one's
arguments, that a refusal is recorded as a refusal, that the tenant is the session's
tenant, and that a failed operation is still on the record. Phase 0's three proofs still
pass unchanged (18 / 35 / 10).

### Phase 0 — the MCP server (read-only), and the two feature rows

**Does:** the MCP transport on the existing FastAPI app, mounted at `/api/mcp` so the
deny-by-default middleware covers it (§10.1); the tenant-scoped token — the new
`agent_tokens` table and the new lookup that resolves it into the same `key_info` shape the
house already understands, beside the three hardcoded keys in `PERMISSIONS`; the ten read
tools of §4.1 exposed through one registry; the **plan gate enforced by the MCP layer
itself**, because `require_plan_feature` is a no-op for a key caller (§4.5); the two feature
rows and their plan assignment, written into the seed **and** the live tables (§8.1).

**Does not:** write anything; call a model; change the chatbot's behaviour; involve n8n;
**carry the model proxy** — that is Phase F, and §4.4 says why.

**Proves:** one tenant, one outlet, one token — a client outside the POS calls `get_sales`
and gets that outlet's numbers, and a second tenant's token gets a different tenant's
numbers. The identity model is proven before anything risky is built on it. And the gate is
proven in the same phase: a tenant whose plan does not hold the row is refused **by name** —
*"This restaurant's plan does not include the Inventory module."* — and not by an empty
result, because an empty result is read by the model as "there is no stock".

**The two traps this phase must not walk into.** Both are live-code facts, and both are
silent when they are wrong:

- **`require_plan_feature` does not gate a key caller.** It returns the credential untouched
  unless `key_type == "user"`, because a session is what carries a plan. The chatbot is a
  session, so its route gate works; an MCP token is not, so the route dependency would let
  it through untouched. The MCP layer checks the plan itself, from the same `plan_cache`,
  with the same three states (§4.5). The token's `key_info` must also carry
  `website_customer_id`, or the shared routes' own plan gate cannot read this tenant's plan
  either.
- **A key type the shared routes do not know is treated as a customer.**
  `is_customer_caller` treats any credential whose `key_type` is not `frontend` or `user` as
  a customer caller, and `require_shared_permission` accepts only `frontend`, `customer`
  and `user`. An agent token typed `agent` would therefore be **refused by the shared
  routes** and **served the public menu payload** by `menu.py` — the public half, without the
  costing or the recipe links. The token's type is chosen with both functions in mind, and
  that choice is part of this phase, not an afterthought.

### Phase A — the action layer

**Status: BUILT** (POS `main` at `5fc7983`; proven by `backend/scripts/test_mcp_actions.py`,
53 checks, against the live server).

**Does:** extend the tool registry with the draft and action tools of §4.3; the `ai_actions`
audit table and the `ai_action_proposals` queue; the three explicit approval controls of
§3.3.1 and the dedicated routes `POST /api/ai/proposals/{id}/approve|edit|reject`; the
token's `draft` and `action` scopes and `ai:act` on its permission list; the **new**
`agent_notifications` table and its service — the proposal queue's delivery target; the
`ai:approve` permission added to the human roles; the approver's own session and permissions
checked at approval time.

**Does not:** emit events; run on a schedule; introduce n8n; invent a second approval
channel — the words in a chat message approve nothing, ever.

**Proves:** the agent can propose a purchase order from the inventory suggestion the AI
already makes; a manager sees the proposal **as a card with Approve / Edit / Reject**, the
manager clicks Approve, a purchase order exists, and `ai_actions` holds the whole story —
the audit row written **before** the action ran. And the negative proof, which is the one
that matters: a message in the chat that says "yes, approve it" approves nothing, because
the only path to approval is a signed request from a human's own session.

### Phase B — the tenant profile

**Does:** `tenant_agent_profiles`; the profile screen; the profile seeds from the outlet's
existing bot settings (`bot_name`, `bot_language`, `bot_greeting`, `ai_enabled` — the four
knobs that exist today); the profile's `allowed_actions` narrows what the agent may call;
the `runtime` field names the client.

**Does not:** introduce new capabilities — it configures the ones Phase A built.

**Proves:** two tenants with different personas, hours and allowed actions get visibly
different behaviour from the same engine, and no code changed between them.

*(One wrinkle to settle in the design review: the profile is one row per **tenant**, while the
bot settings it seeds from are per **outlet** — so a group seeds from its default outlet and
then diverges per outlet.)*

### Phase C — the trigger layer

**Does:** the `domain_events` outbox, written in the same transaction as the business change;
emit the §3.5 events from the write paths; the dispatcher with its retry and dead-letter
log, claiming rows atomically rather than relying on being the only worker (§10.1); the
subscription rows; the **native** channel — the `agent_notifications` rows Phase A created,
read by the app; the **staff web push** — a new subscription, because `push_subscriptions`
is a customer's phone for delivery news and not a manager's (§3.5.3); the signed,
tenant-scoped outbound webhook; the Telegram bridge (a client, like n8n).

**Does not:** require n8n — the events are consumed by the native agent in Phase D; n8n is
one possible consumer. Nor does it build a queue broker: the outbox is a table in the POS's
own database, read by a worker. Nor does it deliver to a customer's push subscription.

**Proves:** an order placed in one tenant produces an event that reaches that tenant's
subscriber, and a second tenant's subscriber never sees it. A second proof: a Pro tenant
receives no `stock.low` event at all, because `Inventory` is not in that tenant's feature
list (§4.5).

### Phase D — the AI Manager surface, the metering and the cap

**Does:** the briefing, the approvals queue, the alerts, the profile screen, the channel
settings, the agent-token screen; the native agent consumes the Phase C events and produces
the §3.6 briefing; the **usage log** — the `usage` block MiniMax already returns, read and
recorded with its tenant, outlet and model, at the call site (§4.6); the **daily briefing
cap** per outlet, and what happens at the cap (§9.2).

**Does not:** invent a new notification system — `agent_notifications` from Phase A and the
`ai_alerts` table are reused as they are; nor start a proactive briefing before the usage
log and the cap are live.

**Proves:** the manager opens `/ai-tools` and sees today's briefing, the proposals waiting
for them, and the agent's own settings — and every proactive call is attributed to a tenant
and counted against that outlet's daily allowance. The cap is exercised before it is relied
on: the allowance is reached, the agent goes quiet, and the quiet is a **recorded**
decision, not a silence.

### Phase E — the money

**Does:** the price and the tiering decision for the two rows; the per-tenant override path
used for the first design partners — `customer_feature_overrides` already exists and already
applies, because the website API's feature endpoint reads the override map over the plan
default, so a tenant can be granted `AI Agent` on a plan that does not carry it, with a
reason and a `created_by`, and the POS cache is notified; the cost report over the usage log
Phase D writes.

**Does not:** change how any other plan row is priced; meter tokens per call for the pull
path — the `AI Chatbot` row *is* that price (§9.2).

### Phase F — the connectors (optional, and last)

**Does:** the documented setup for a tenant's own runtime — n8n with the MCP Client Tool, a
Telegram bridge, the signed webhook, the token; and the model proxy of §4.4, which exists
only for a runtime we do not control holding its own LLM.

**Does not:** make any runtime a dependency of the agent. If n8n is not installed, nothing
above changes.

### 9.1 The approval question in full

### 9.2 The cost question — re-scoped

*(v1.5: Kens pushed back on the original version of this section — "if the channel is our
frontend POS, it should call our MiniMax model as existing." He is right, and this is now
the narrower question that survives his answer.)*

**What the answer already settles.** For our frontend POS channel there is no new decision
here. The model call is the one we already make:

- The call is **server-side, on our key, in our own backend** — `ai/chatbot.py` posts to
  `settings.MINIMAX_BASE_URL` with `settings.MINIMAX_API_KEY`. The browser never holds a
  model key; it posts to `/api/chatbot/` and the backend does the rest.
- The route is **already gated** — `require_permission("ai:read")` and
  `require_plan_feature("AI Chatbot")`, and `ai_chatbot` is a Pro+ row. A tenant without
  the feature cannot spend a token.
- Only the roles that need it reach the model at all — `admin` and `manager`. `staff` and
  `customer` are answered from the intent handlers and never call MiniMax.

So **"who pays for the model calls" is answered for the pull path: we do, on our own
account, and the tenant has already bought the row that lets them spend it.** The model
proxy (§4.4) therefore drops to Phase F — it only matters when a runtime we do not control
is holding the LLM.

**What genuinely remains — the push side, and it is a different question.** The pull path is
bounded by human behaviour: the cost scales with how often the staff ask. The proactive
agent is not. A morning briefing for every outlet, every tenant, whether or not anyone
reads it, is O(tenants × outlets × briefings × tool-rounds × tokens), and nothing in the
current design bounds it. Two decisions, both small:

1. **Attribution — which tenant spent the tokens?** This is **not** answered today, and it
   is not a proxy problem: the `usage` block comes back in every MiniMax response and the
   chatbot throws it away. Recording it is a few lines at the call site (§4.6).
2. **The cap — how many proactive briefings per outlet per day, and what happens at the
   cap?** The agent goes quiet, or the tenant is told it has reached its allowance? Quiet
   hours (§3.5.4) is the first throttle; a daily briefing cap is the second.

**And the thing that is *not* a question.** Nobody has to decide whether a tenant is
charged per token. We do not meter tokens for the pull path today and we should not start:
the `AI Chatbot` row *is* the price. If a tenant wants the proactive agent, that is a **new
feature row** (`AI Agent` — created in Phase 0, priced in Phase E) that says what they get —
not a meter on every call.

## 10. Impact on the existing apps

*(v1.3: Kens asked the blunt question — if we build the MCP server, does the POS frontend or
the backend API app break? This section is the answer, verified against the running code.)*

The short answer: **the backend barely moves, and the frontend does not move at all until
Phase D** — when the AI Manager replaces the AI Tools page in the staff app (§3.6) — but two
traps will bite if the MCP server is mounted carelessly, and one of them is a plan-gate
regression that would change what a paying tenant's chatbot says to them today.

### 10.1 The backend API app — four things, and one of them is a trap

**The existing tools are reusable as-is. Zero edits to `chatbot_tools.py`.**

`backend/app/chatbot_tools.py` (really `backend/app/ai/chatbot_tools.py`) already exposes
everything an MCP server needs:

| It already has | Why it matters for MCP |
|---|---|
| `TOOLS` — a dict of ten name → function | The registry the MCP `list_tools` enumerates |
| `tool_schemas()` — the OpenAI-style function schemas | The MCP tool schemas, same source |
| `run_tool(ctx, name, arguments)` | The MCP tool dispatcher, unchanged |
| `ToolContext(db, tenant_id, default_outlet_id)` | The credential → tenant binding |
| `ToolError` | The refusal shape the MCP layer returns |
| `MAX_ROWS = 15`, `PERIODS` | The existing rails, inherited for free |

The decisive detail: **`ToolContext` takes the tenant as a constructor argument.** The tenant
is not read from the session *inside* the tool — the caller supplies it. So an MCP server
builds the same `ToolContext` from a token's tenant and calls the same functions. The rule
"the tenant comes from the credential, never from the model's arguments" is not something
MCP has to re-implement; it is already the shape of the code.

**Trap 1 — the mount path decides whether MCP is authenticated at all.**

`backend/app/main.py` denies by default, but only for one prefix:

```python
if path.startswith("/api/") and not _is_public_api_path(path):
    ...  # 401 without a credential
```

MCP's conventional path is `/mcp`. **Mount it there and the authentication middleware never
runs.** The `SubscriptionAccessMiddleware` has the same `/api` prefix test, so it would skip
as well. The endpoint would be open.

The fix is a prefix, not a rewrite: **mount at `/api/mcp`**, so the existing deny-by-default
covers it — and still verify the token explicitly inside the MCP layer, because the
middleware proves *a credential exists*, not *the credential is an agent token*. Two checks,
two different jobs.

**Trap 2 — per-tool plan gating changes the live chatbot's behaviour.**

Today the chatbot's ten tools are gated **once, at the route**, by
`require_plan_feature("AI Chatbot")` — no tool carries its own module gate. The moment the
gate moves down into the tool bodies (§4.5), a tenant whose plan holds `AI Chatbot` but not
`AI Insights` starts getting `get_alerts` refused — **inside the chatbot they use every
day**. That is a plan-gate regression shipped alongside a new transport, and it is invisible
until a tenant notices.

The rule this section proposes:

> **Phase 0 ships the tool-level gate on the MCP path only.** The chatbot's behaviour changes
> in a later, deliberate step — with its own note, its own test, and its own release.

Note also that `get_alerts` reads the AI alerts, and `ai_security.py`, `ai_forecast.py` and
`ai_orders.py` carry **no plan gate at all** today — only `ai:read`. So the chatbot is
already reaching past the tenant's paid features. That is the bug §4.5 fixes, but the fix
must not be a surprise.

**The key system needs one new lookup, not a change.**

`middleware/auth.py` holds a **hardcoded three-tier key table** (`PERMISSIONS`: the frontend
key, the customer key, the external key) and `get_key_info()` matches a literal string
against it. A tenant-scoped, revocable, per-outlet MCP token cannot live there — that table
is static config, not data. So the `agent_tokens` table (§5.1) is read by a **new function**
that returns the same `key_info` dict shape the rest of the app already understands. The
three existing keys are untouched.

**New tables need no migration.** `main.py` runs `Base.metadata.create_all(bind=engine)` at
boot, plus the idempotent `_ensure_added_columns()` and `_ensure_push_schema()` belt-and-braces.
New models are created automatically — the house pattern. `ai_actions`, `agent_tokens`,
`agent_notifications`, `domain_events` and `event_subscriptions` all follow it.

**One worker.** The backend runs **one uvicorn worker** — the prepay expiry sweep depends on
it (`main.py`: *"the backend runs ONE uvicorn worker, so there is exactly one sweep"*). MCP
over HTTP is stateless, so a second worker is not required and not harmful. But the **event
dispatcher must claim rows atomically** (`SELECT … FOR UPDATE SKIP LOCKED`, or a
compare-and-set on the row's `state`) rather than relying on being the only worker. The
one-worker assumption is a convenience we may lose, not a guarantee we may build on.

### 10.2 The frontend POS — nothing until Phase D, then one page

- **Nothing in Phases 0–C.** The frontend is a REST client against `/api/*`; MCP is
  server-to-server. The nav gating (`frontend/src/config/navItems.js`), the feature hook
  (`frontend/src/hooks/useFeatures.jsx`) and the notification bell
  (`frontend/src/components/NotificationBell.jsx`) are untouched.
- **In Phase D, one page changes** — the `/ai-tools` page is replaced by the AI Manager
  page (§3.6), and the chat gains the proposal card and its three controls (§3.3.1). Both
  are ordinary React work against our own REST routes. The frontend still never speaks
  MCP.
- **The browser should not become an MCP client.** MCP over streamable HTTP with SSE and
  custom auth headers is awkward in a browser, and it would put a credential where the
  session cookie already works. The **AI Manager** page (Phase D) keeps calling our own
  REST routes; the backend is what speaks MCP. The browser stays inside the cookie model it
  already understands.
- **The one behavioural change reaches the frontend indirectly** — through the chatbot's
  answers. That is Trap 2 above, and it is why the gate change is staged.

### 10.3 The do-not-touch list

Things that look like they should change, and must not:

| Do not | Why |
|---|---|
| Move or rename `app/ai/chatbot_tools.py` | `ai/chatbot.py` imports `ToolContext`, `run_tool` and `tool_schemas` from it (line 1157). Add `app/ai/mcp_server.py` **beside** it and import from it — one registry, two consumers, no move. |
| Change the three hardcoded keys in `PERMISSIONS` | They serve the frontend, the customer app and the external developer. The agent token is a **fourth, separate** path. |
| Change `require_authentication`'s behaviour | It is deny-by-default and correct. The MCP mount simply has to live under the prefix it already guards. |
| Re-gate the chatbot's existing ten tools in Phase 0 | A plan-gate regression in the product a paying tenant uses today (§10.1, Trap 2). |
| Add an Alembic migration | There is no Alembic. `create_all` at boot is the pattern. |
| Add an MCP client to the browser bundle | The session cookie is the browser's credential. |

### 10.4 A security note found while reading

`main.py` imports `TrustedHostMiddleware` (line 13) but **never adds it** — `add_middleware`
is called only twice, for CORS and for `SubscriptionAccessMiddleware`. The app therefore
accepts any `Host` header today.

That is pre-existing and unrelated to MCP. But it becomes relevant the moment the MCP
server is reachable from outside the box: the `Host` header is the cheapest way to bind a
virtual host to an app that does not check it. **When the MCP server is exposed, add the
middleware** — it is a two-line change and it should not wait for the exposure.
