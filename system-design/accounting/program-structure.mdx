## What this document is

**The other seven documents say what to build. This one says where it goes and what may not touch what.**

The accounting program touches three existing things, and each of them is touched differently and for a different reason. **Most of the confusion about this program's risk comes from collapsing those three into one word, "the POS".** They are not the same thing, and the distinction is the whole answer to "does this change our POS?".

| The thing | What it is | When accounting touches it |
|---|---|---|
| **the POS backend** (`backend/`) | the product the counter runs on | **Phase 2 only**, and only as the nine prerequisites that make the binding honest |
| **the website API** (`website_api/`) | the shared billing and entitlement spine | **Phase 0b**, and it is a *shared* spine - the accounting product changes it, and so does every future product |
| **the host** (Caddy, pm2, systemd, Postgres) | the machine everything runs on | **Phase 0a**, additively - a new process, a new port, a new database |

## 1. The short answer to "does this touch our POS?"

**Three separate answers, because there are three separate surfaces.**

**1. The accounting service never touches the POS database.** Not reads, not writes, not a join. The accounting service has its own Postgres database. The POS keeps its SQLite file (`database/pos_ai.db`). There is no shared table, no shared connection, no cross-database query, and no migration that spans both. **A tenant's books live in the accounting database and only there.**

**2. Phases 0 and 1 change the POS backend ZERO times.** This is the load-bearing fact, and it is what makes Option C possible. The accounting service in Phase 0 and Phase 1 is a **complete, sellable, standalone double-entry ledger with manual entry** - chart of accounts, journals, fiscal periods, trial balance, P&L, balance sheet. It does not read a sale, does not import a sale, and does not know the POS exists. **If we stopped the program at the end of Phase 1, the POS backend would have no accounting code in it at all** - and we would still have a product we could sell, because the ledger is horizontal.

**3. Phase 2 changes the POS backend - and that is the point.** The binding is where the value is, and it costs ten specific things in the POS, listed in `pos-integration.mdx` §"The POS prerequisites" and repeated in §5 below. Nine of them are **filling gaps the POS has today** - the frozen settlement, the tax breakdown that is computed and thrown away, the settlement timestamp that does not exist, the payment row missing from the commonest sale path, the refund path the POS does not have. The tenth is the snapshot API the accounting service reads money from.

**So the honest one-liner:** the accounting program does not change how the POS sells a coffee, and it does not change the POS's data model for anything the POS already has. **It adds to the POS** - a settlement table, a set of event types, an emitter, a refund path, a read-only internal API - and every one of those additions is a thing the POS was missing.

**And the one shared surface that genuinely carries POS risk is not the POS backend - it is the website API's entitlement route.** Section 4 is about that, and it is the most important compatibility rule in this document.

## 2. The repository layout

**Two questions, and they are separate: where the design documents live, and where the accounting source lives.**

### 2.1 The design documents live in `Kiens8/IDEAZESPOSAI` - decided

**The eight (now nine) accounting design documents live in the `Kiens8/IDEAZESPOSAI` repository, under `system-design/accounting/`.** That is decided and it is not revisited here.

**This is where the house already keeps its design documents, and the live code already points at them.** `website_api/scripts/send_notifications.py:595` carries the comment *"The promotion (system-design/plan-promotion.mdx)"*, and `website_api/scripts/test_promotion.py:1` opens with *"The promotion, end to end (system-design/plan-promotion.mdx)"* - the running code references a design document by that path. **The design documents are a first-class artifact of the product, not a folder inside a code repository**, and they sit in the repository that publishes them.

**A practical consequence, and it is the reason the split is clean:** the design repository is a **documentation site** (`docs.json`, `index.mdx`, Mintlify) and the accounting source is **a service with a database, a systemd unit, a backup job and a port**. Those are different kinds of repository, and the accounting source does not belong in a Mintlify site repository any more than it belongs in the POS's code repository.

### 2.2 Where the accounting source lives - OPEN, and the recommendation is a dedicated repository

**This is still open, and it is Kens's decision.** It is recorded here with the recommendation and the reasoning, so that the decision is made once, in the open, rather than by drift.

**The recommendation: a dedicated `IDEAZES_Accounting` repository** for the accounting service, the accountant-facing web app, and the accounting deploy/ and tests.

**The reason the shared spine does not argue for one repository.** The billing and entitlement spine is shared between the POS product and the accounting product, and Phase 0b changes it. **But the spine is shared as an HTTP contract, not as code.** The accounting service calls the website API's entitlement route over HTTP, with its own server key; it must never `import` from `website_api/`, for the same reason it must never import from `backend/` (§6.1). **Once that rule holds, a shared spine gives no reason to share a repository - and several reasons not to.**

**What a separate repository actually buys:**

- **An independent release and rollback unit.** The accounting service is a different deployable on a different port (`8100`), a different domain, its own database, its own systemd unit and its own backup job. One repository means one tag, one release train, one rollback - so a broken accounting release at 2am holds the POS's release hostage.
- **An independent CI pipeline.** Neither repository has a workflow today (verified: no `.github/` in `Kiens8/POS_AI` and none in `Kiens8/IDEAZESPOSAI`). When one is added, a separate repository means accounting can go green and ship without the POS's test suite running, and the POS release does not wait on accounting's.
- **A licensing boundary.** The design repository's `LICENSE` is the Mintlify template's **MIT with `Copyright (c) 2026 Mintlify`** on it, and `Kiens8/POS_AI` has **no `LICENSE` file at all** (both verified 27 Nov 2026). **The accounting product is a commercial product and needs its own explicit licence**, and it cannot have one if it shares a repository with something that has none.
- **An operational boundary.** The accounting service's backup, restore drill, alerting and runbooks are its own (`operations.mdx`). A repository boundary is where those live, and where a future operator looks for them.

**The honest counter-argument, stated so the decision is made against it:** the shared spine is a real coupling, and a repository boundary does not remove it. If the entitlement route changes shape and the accounting service does not change with it, the accounting service breaks. **That is why the rule is a contract and not a folder:** the spine's shape is pinned by a **test** (the union returns byte-identical output for every existing customer, §4 Rule 1), not by the two consumers living in the same tree. A monorepo makes the coupling *visible in a diff*; a contract makes it visible in a *failing test*. **The second is a stronger guarantee, because it cannot be skipped by a merge.**

**What holds whichever way Kens decides it** - and these are the rules the code must obey regardless:

1. **The accounting service imports nothing from `backend/` and nothing from `website_api/`.** The tenant module and the money module are *patterns to copy*, not libraries to import.
2. **Nothing imports anything from the accounting service.** The dependency arrow points one way, and only as HTTP.
3. **The accounting source is its own deployable**, with its own working directory, its own process, its own database and its own backup unit - in a monorepo as well as in its own repository.
4. **The design documents live in `Kiens8/IDEAZESPOSAI`**, in either case, and they are versioned with the program rather than with the code that does not exist yet.

**The recommendation is a dedicated repository, on the strength of independent release, independent CI, the licensing boundary and operational isolation - with the shared spine held by a contract and a test rather than by a folder.**

### The four decisions in this tree that matter

**★ `services/ledger.py` must be unit-testable with no database.** This is the single most important structural decision in the service, and it is what makes the audit rule provable rather than asserted. The engine takes a list of lines and either balances them or raises. It takes a session, it does not create one. It has no HTTP in it and no import of `core.database`.

The consequence: **the test suite can prove "debits equal credits or the journal is refused" on a laptop in two seconds**, with no Postgres running, and can prove it across every edge case - a negative amount, a zero line, a line on a closed account, a line on a locked period, a currency that does not match the book. **This is how the whole ledger's central claim gets tested, and it is only possible because the engine does not own its own persistence.** A ledger engine that reaches for the database session itself cannot be tested this way, and a ledger whose balance rule is only tested through an API is a ledger whose balance rule is tested slowly.

**★ `core/money.py` is the only module allowed to convert.** Every amount in the service is an integer in minor units. The conversion from the source's representation happens once, at the boundary, in one file. Every other module takes minor units and returns minor units. This is the rule from `ledger-and-money.mdx` §3.4, and it is enforced by structure - one module, one function, one place to look.

**★ `core/tenant.py` is the isolation boundary, and it is the POS's own pattern.** The POS already has this exact idea in `backend/app/core/tenant.py` - a tenant claim that a key cannot pick (`KEY_CANNOT_PICK_TENANT`, `:41`), `get_tenant_claim` (`:56`), `require_tenant_claim` (`:77`), `require_outlet_tenant` (`:188`). The accounting service gets **the same shape, a different subject**: the tenant is an accounting tenant (a legal entity), not a POS tenant (a restaurant group). The rule is the one the house already lives by:

> **A caller-supplied tenant id is never authorisation. The tenant comes from a signed credential, and every outlet, order and accounting entity is verified to belong to it.**

The accounting service's version is in `core/tenant.py`, it is used by every route, and **no route reads a tenant id from the request body.**

**★ `connectors/base.py` defines one interface, so adding Xero does not touch the ledger.** Every connector implements the same shape: pull a window of source facts, map them to journal lines, hand them to `services/ledger.py`. **The journal mapping lives in the connector. The money rules live in the ledger.** So the Xero connector in Phase 6 is a new directory, a new route module, and a new set of tests - **and it changes nothing in `services/ledger.py`.** If adding a connector ever requires editing the ledger, the boundary has failed.

## 4. The compatibility rules that keep the POS untouched

**This is the section that matters most for risk.** The accounting program changes the website API, and the website API is shared with the POS. The POS reads two things from the website API that the accounting program touches.

### The shared surface, exactly

| What the POS reads | Where | What accounting does to it |
|---|---|---|
| **the entitlement route** - the plan's features merged with the customer's overrides | `website_api/app/routes/admin.py:1216` (`GET /api/admin/customer/{customer_id}/features`), read by the POS at `backend/app/services/plan_features.py:71` and `backend/app/routes/customer_bff.py:194` | **its output becomes a union - but it stays byte-identical for every existing customer** |
| **the plan-change push** - a notification that a tenant's plan changed, so the POS drops its cache | `website_api/app/services/plan_notify.py:25` -> `POST /internal/plan-changed` -> `backend/app/routes/internal.py:70` | **the existing push is reused**, with the union's feature list. No new POS endpoint |

### Rule 1 - the entitlement union changes no existing output

The entitlement read today is: the plan's features, plus the customer's overrides. It becomes: **the plan's features for the requested product, plus active feature subscriptions for that product, plus the enabled overrides.**

**Why this is invisible to the POS today.** The union adds a source that contributes **nothing** for any existing customer, because **no feature subscription exists yet** and none can exist until the Phase 0b checkout route is built. For every customer in the live database right now, the union's output equals the old route's output. **That is a property that can be asserted in a test**, not a hope: *the union, run against the live data, returns exactly the old route's rows.*

**The scoping rule.** The union is **product-scoped**. The existing admin route defaults to `product='pos'` - so it answers for the POS product, exactly as it does today - and a **new** internal route answers for `product='accounting'`:

| Route | Who calls it | Product | Status |
|---|---|---|---|
| `GET /api/admin/customer/{id}/features` | the POS (`plan_features.py:71`, `customer_bff.py:194`) | `pos` (default) | **response shape unchanged** |
| `GET /api/internal/entitlements/{platform_customer_id}?product=accounting` | the accounting service | `accounting` | **NEW** |

**Why a new route rather than a parameter on the old one.** A new route means **the POS's call site does not change at all** - not the URL, not the parameters, not the response shape. A parameter on the old route means every existing caller has to keep working with a default, which is a rule that decays. **The accounting service gets its own door, and the POS's door stays exactly as it is.**

### Rule 2 - the guard that has to become product-scoped

`website_api/app/routes/subscription.py:227` refuses a second subscription:

```
existing = db.query(Subscription).filter(
    Subscription.customer_id == current_user.id,
    Subscription.status.in_(["active", "trial"])
).first()
if existing:
    raise HTTPException(status_code=400, detail="Already has active subscription")
```

**This is a real blocker for the second revenue path, and it is one line.** A POS tenant on a `pos` plan who wants the standalone `accounting` plan is refused - correctly, under the old rule, because today one customer has one subscription. With two products, the rule has to be "already has an active subscription **for this product**". The customer's subscription count stays unlimited; the count *per product* is one.

**The feature checkout does not hit this guard at all**, because a feature purchase creates a `feature_subscriptions` row and never a `Subscription` row.

### Rule 3 - the conditional POS provisioning

Every website customer is auto-provisioned a POS account, at three call sites: `website_api/app/routes/auth.py:143` (signup), `website_api/app/routes/subscription.py:577` (subscribe), `website_api/app/routes/webhooks.py:683` (the Stripe webhook). All three call `provision_pos_account` (`website_api/app/services/pos_provisioning.py:40`), which POSTs to the POS's own `POST /api/auth/register-customer` and `POST /api/auth/register` over `http://127.0.0.1:8000/api/auth` with the staff key.

**All three become conditional on the product:** provision a POS tenant only when `account_type == 'pos'` or the plan's `product == 'pos'`. An accounting-only customer gets a `website_customers` row with `customer_id = NULL` and **no POS tenant is created** - which is the point of the standalone product.

**The POS backend changes zero times for this.** The two POS endpoints stay exactly as they are. The website API simply stops calling them for accounting-only customers. **This is the clearest example in the whole program of the difference between "the accounting program touches the POS" and "the accounting program changes the POS".**

### Rule 4 - the cache stays fresh through the push that already exists

The POS caches a tenant's feature list for **300 seconds** (`backend/app/core/plan_cache.py:41`), and the website API's push is what makes an upgrade visible immediately - the TTL is only the safety net for a lost notification (`plan_cache.py:15-16`). So when a feature subscription is granted or cancelled, the website API calls the **existing** `notify_pos_plan_changed` (`website_api/app/services/plan_notify.py:25`) with the union's feature list, and the POS drops its cache entry through the route it already has (`backend/app/routes/internal.py:70`).

**No new POS endpoint. No new cache. No new TTL.** The push is the house's own mechanism, used for a new reason.

## 5. What Phase 2 adds to the POS - precisely

**This is the complete list. Nothing else in the POS backend changes, in any phase, for any reason.**

| # | What is added to the POS | Where | Why it cannot be avoided |
|---|---|---|---|
| **P1** | the frozen settlement row - the figures as they were at settlement | a new table beside `Order` | the live order row is mutable; a cancellation erases the totals |
| **P2** | the tax breakdown on the frozen row | the same new table | the POS computes the tax and throws it away (`services/order_pricing.py:61`) |
| **P3** | the settlement time on the frozen row | the same new table | an ordinary sale has no settlement timestamp anywhere today |
| **P4** | a payment row on **every** settlement path | `services/order_service.py:1235`, `routes/order.py:1368`, `routes/delivery_tracking.py:501`, `routes/internal.py:206` | the commonest sale of the day writes no payment row |
| **P5** | the accounting event types, with **their own** base feature | `services/domain_events.py:97`, `:146`, `:349` | the existing events are gated behind `"AI Agent"` (`BASE_FEATURE`, `:146`) - an accounting-only tenant would have every sale **silently skipped** |
| **P6** | the emitters, beside the existing ones | `services/event_emitters.py` | the signal has to exist before anything can consume it |
| **P7** | a refund path - a refund record, a payment row, the emitter | new | a settled sale cannot be taken back today |
| **P8** | the snapshot API and the reconciliation endpoint | a new router beside `routes/internal.py`, under the existing `require_internal_key` (`:44`) | this is where the money comes from |
| **P9** | a reversing stock movement when an order is voided | `routes/order.py:1540` (the void), against `:236` (the stock usage) | the stock usage is never reversed, so a voided order leaves the stock short |
| **P10** | a purchase emitter | `routes/purchase_orders.py:238` | the purchase side is silent today |

**P1-P4 are one table and one writer.** They are the same fact written once: *what was sold, for how much, taxed how, paid how, and when.*

**P5 is the one that would have been a silent disaster.** The POS's domain events all hang off `BASE_FEATURE = "AI Agent"` (`domain_events.py:146`), and the feature list is read from the entitlement route at `domain_events.py:333-341`. **An accounting tenant that was not an "AI Agent" subscriber would have had every one of its sales skipped without an error** - the books would just quietly not fill. The accounting events need their own types and their own gate.

**Every one of these is an addition.** No existing POS route changes its behaviour. No existing POS table changes its shape. The sale path writes one extra row per settlement and emits one extra event - **and the floor never waits for the books.**

## 6. The isolation boundary, structurally

**The rules that keep one tenant's books out of another's, expressed as code structure rather than as intent.**

**6.1 The accounting service imports nothing from `backend/`.** Not the tenant module, not the money module, not a model. The POS's `core/tenant.py` is a *pattern* to copy, not a library to import - and copying it is the right call, because **a shared import is a shared failure**: a change to the POS's tenant helper would silently change the accounting service's isolation. **The rule is checked in CI** (a grep for `from backend` / `import backend` in `accounting/`), and it is cheap to check because the POS and the accounting service are separate deployables with separate working directories.

**6.2 Nothing from `backend/` imports anything from `accounting/`.** The dependency arrow points one way, and it points from the POS *to* the accounting service only in Phase 2 - and then only as an HTTP call the POS makes to itself.

**6.3 The tenant never comes from the request.** Every route resolves the tenant from the signed credential via `core/tenant.py`. A tenant id in a path, a query string, or a body is **read as a filter, never as authority** - and the filter is applied to a set the caller is already entitled to, so a wrong id returns nothing rather than someone else's books.

**6.4 Every accounting row carries the accounting tenant id.** Not the POS tenant, not the platform customer. The tenant of the books. Every query filters on it, and **there is no code path that reads a table without a tenant filter** - enforced by a repository helper that takes the tenant as a required argument, so the filter cannot be forgotten.

**6.5 The provider credentials are per tenant and per legal entity.** They are encrypted at rest, they never appear in a log line, and an alert carries a tenant id rather than a credential.

**6.6 The accounting service asks, it does not decide.** Entitlement comes from the website API (`services/entitlement.py`). **The service never decides its own entitlements** - the same rule the POS already lives by at `backend/app/services/plan_features.py:71`.

## 10. The build order, in the order a developer should type it

**Because a structure that is right but built in the wrong order costs more than one that is slightly wrong and built right.**

1. **`core/money.py` and `services/ledger.py` first, with the unit tests, before the database exists.** The engine is the product. If the balance rule is right, everything above it is plumbing. **This is the step that makes the whole service testable in two seconds instead of two minutes.**
2. **`core/tenant.py` next**, before any route exists. The isolation boundary is a module, not a middleware, and it is written once and used by every route that follows.
3. **The models**, then `migrations/`, then the health surfaces. The database appears in Phase 0a with nothing in it but the tenant, the chart of accounts and the money rules.
4. **The statements** (Phase 1) - because a trial balance and a P&L are what the product *is*, and they are what a standalone customer in Phase 1 is actually buying.
5. **The website API changes** (Phase 0b) - the purchase path, after the ledger exists and can be provisioned into.
6. **The operations** (Phase 0c) - the backup, the drill, the alerting. **After there is something worth backing up, and before there is a customer whose books depend on it.**
7. **The POS binding** (Phase 2) - last, because it is the only phase that touches the POS, and it needs a ledger that is already proven.

## What this document does NOT claim

- **It does not claim any of this is built.** The tree above is a proposal. The `accounting/` directory does not exist.
- **It does not claim the POS is untouched forever.** It is untouched in Phases 0 and 1, and touched additively in Phase 2, in ten named places.
- **It does not claim the entitlement union is free.** It changes a shared route. **Rule 1's test - the union returns byte-identical output for every existing customer - is what makes it safe, and that test has to exist.**
- **It does not claim Postgres is free to add.** It is not installed on this host. It is a Phase 0a prerequisite with its own backup method.
- **It does not claim a separate repository would be wrong.** It would be defensible on the permission boundary. The argument here is that the shared spine and the shared deploy conventions matter more, and that a repository boundary is the wrong place to enforce an API boundary.

## The open questions

1. **Does the accountant-facing app go in `accounting-web/` or inside `accounting/`?** The house's pattern says top-level. But the accounting service is a *product*, not a feature of the POS, and a self-contained directory is easier to move out later if it becomes its own repository. **The honest answer is that it does not matter much and should be decided by whoever writes the first screen.**
2. **Which repository holds the accounting source?** §2 has the argument; **the recommendation is a dedicated `IDEAZES_Accounting`**, and the decision is Kens's. **The design documents' home is not part of this question - they stay in `Kiens8/IDEAZESPOSAI` either way.**
3. **Is one Postgres instance enough, and where does it live?** The host runs everything on one box today. The accounting service gets its own database on it. **The first account needs more than one box, and the backup story changes when it does.**
4. **Does the accounting API get a public API key model like the POS's, or is it session-only?** The public API is the displacement play - a third-party POS or a payroll system posting in. **The key model, its scopes, and its tenant binding are a Phase 2b decision.**
5. **Does the accountant-facing app live at `books.ideazes.com` or inside `site.ideazes.com`?** The marketing site is Next.js and the accountant app is a React SPA. **One domain or two is a branding decision with a technical consequence, and it should be made before the first screen is built.**
6. **What licence does the accounting source carry?** The accounting product is commercial, so it needs an explicit licence - and `Kiens8/IDEAZESPOSAI` currently carries the Mintlify template's MIT with Mintlify's copyright on it, while `Kiens8/POS_AI` has no `LICENSE` at all (both verified 27 Nov 2026). **This is decided together with the repository question, and it is decided before the first commit.**
