## What this document is

**A service is not a service until it can be restarted at 2am without a human holding its hand.** The accounting service is a multi-tenant ledger: it holds a tenant's profit, their payroll and their bank balance. It is the most sensitive data in the product, and the blast radius that stops the counter taking an order is not acceptable - which is why it is a separate service (`accounting-service.mdx` §"The service boundary").

This document is Phase 0c: **the operations that turn a deployable into something that can be trusted with a tenant's books.** The phase plan in `accounting-service.mdx` says it in one line - "the operations that make it a service" - and this document is that line written out.

**The standard exists, and it is already running.** This host already keeps a verified nightly backup of the two databases that hold the POS and the website API, with a failure path that reaches a human instead of a log file nobody reads. **The accounting service's Postgres cannot be added to that script, and the reason is the method** - so the third database needs its own backup, its own proof, and its own restore drill.

**Five things are specified here:**

1. **The database lifecycle** - the schema revision, the nightly verified backup, and the **restore drill**
2. **Readiness and dependency checks** - the difference between a process being up and a service being able to serve
3. **Monitoring and alerting** - what is measured, and what reaches a human
4. **The scheduled work** - the dispatcher, the nightly reconciliation, the renewal
5. **The runbooks** - the two questions a customer asks at 2am, answered by something

## 1. The database lifecycle

**The live facts.**

- `scripts/pos_backup.py` takes a consistent snapshot via **SQLite's online backup API**, runs `PRAGMA integrity_check`, compares the **row counts of every representative table** before and after the copy, and only then renames the file into place. The two databases it protects are `database/pos_ai.db` and `website_api/website_api.db`.
- `posai-backup.timer` schedules it at `OnCalendar=*-*-* 22:00:00 UTC` - 06:00 in Kuala Lumpur - **written in UTC on purpose**, because the unit must not depend on the host's local time zone. `Persistent=true`, so a backup missed while the machine was off runs when it comes back: **the point of the backup is the state of the data, not the hour it was taken.**
- `posai-backup.service` is `Type=oneshot` with `Nice=10` and `IOSchedulingClass=idle` - **the backup is a background chore and must never compete with the POS.** It has `TimeoutStartSec=1800` and exits non-zero when any proof fails, so a failed backup is a failed unit and not a silent success.
- `OnFailure=posai-backup-notify.service` runs `/usr/local/sbin/posai-backup-notify.sh` - **a failure is reported to the owner instead of disappearing into the journal.**
- The accounting service's database is **Postgres**, not SQLite. That is a design decision (`ledger-and-money.mdx`), and it has an operational consequence: **the script's whole method is SQLite's online backup API, which has no Postgres equivalent.** `pg_dump` is not the same thing and does not give the same guarantees for free.

**The specification.**

**The schema revision is written in Phase 0a, and it is the only migration in the accounting service's life.** The service is greenfield - nothing is being migrated, so this is a `CREATE` script and a `schema_version` table, not a tool. **There is no Alembic in the accounting service at the start, and that is a deliberate choice**: a greenfield service with one schema and a version table is simpler than a migration framework, and it is the shape the ledger's own audit rule wants - a books system that can say which revision it is at.

**The nightly backup has three proofs, and it is not a backup without all three.**

| The proof | What it answers |
|---|---|
| **The dump restores** | the file is a usable database, not a truncated one |
| **The row counts are right** | the restore has the data the production database had |
| **The restore is atomic** | a half-restored environment is never a usable environment |

The Postgres equivalents: `pg_dump --format=custom` (or a base backup), a restore into a scratch database, and the same row-count comparison against the representative tables - **the charts of accounts, the journals, the accounts, the tenants.** The third proof, atomicity, is a property of how the restore is performed: **the restore lands in a scratch environment and the environment is promoted only after the counts pass.** A restore that fails halfway leaves the scratch environment broken and production untouched.

**The rotation is per-day and per-week, and the retention is written down.** The existing SQLite backup rotates; the accounting service's backup rotates the same way, with a longer tail - a ledger is worth more than a POS and loses more, so the retention window is longer and the backups are copied off the host. **A backup that is only on the machine it protects is not a backup.** It survives disk failure, not a host loss.

**And the restore drill is part of Phase 0, not an afterthought.** Once a month, in a staging environment, the backup is restored and a tenant's books are read back - a trial balance, a P&L, a bank reconciliation - and the numbers are compared against production. **A backup that has never been restored is a hypothesis.** The drill's output is a date and a pass/fail, and a failure is an alert like any other.

**The two questions the drill answers, before any customer asks them:** *can you restore me?* and *was the thing you restored actually my books?*

## 2. Readiness and dependency checks

**The live facts.**

- `backend/app/main.py:619` and `website_api/app/main.py:71` both return `{"status": "healthy"}` **without touching a database**.
- That is **correct for a liveness probe** - it answers "is the process up" - and **useless for readiness**, because a service whose Postgres is unreachable is still "healthy" and would still be sent traffic.

**The specification: three surfaces, not two.**

| Surface | Question | Checks |
|---|---|---|
| **`/livez`** | is the process up? | nothing - it returns immediately. **It must not check a dependency, or a database blip restarts every replica at once** |
| **`/readyz`** | can this instance serve a request? | the Postgres connection, the schema version, and the write path |
| **`/healthz`** | what is the service's own state? | the full picture for a human: database latency, the last successful reconciliation, the depth of the dead-letter queue, the entitlement cache age |

**Readiness checks the write path, not just the connection.** A service that can read but cannot write is not ready for a tenant's first journal - and the ledger's audit rule means a posting that half-succeeded is worse than one that never started. So the readiness probe **writes and reads back a scratch row**, in a scratch table, on a schedule - not on every probe, which would be its own write storm.

**The dependency that matters most is the billing spine.** The accounting service cannot serve a book without Postgres, and **cannot know a tenant's entitlement without the website API.** So readiness has a rule about that dependency specifically:

- **The entitlement dependency is soft at runtime and hard at provisioning.** A running tenant's books must stay available when the website API has an incident - the books are the tenant's, and taking them away because a billing call timed out would be a worse failure than the incident. But **a new tenant must never be provisioned on a stale or failed entitlement read.** So the service serves what it knows and refuses to create what it cannot confirm.
- **The entitlement cache has a stated age.** The service re-reads entitlement on every request, and a cached answer is never older than the cache TTL. **A cache that serves an unknown age is a cache that serves a lie.**

**The dependency checks are explicit, because "it works on my machine" is not a monitoring strategy.** The service checks, on start and on a schedule: Postgres reachable and writable; the schema revision is the one this build expects; the website API is reachable and the internal key is accepted; the object store for attachments is reachable; the clock is synchronised - **because the ledger's period boundaries are clock-dependent, and a drifting clock closes a fiscal period at the wrong time.**

## 3. Monitoring and alerting

**The live facts.**

- The host runs a **failed-unit notifier**: `posai-backup.service` -> `OnFailure=posai-backup-notify.service`.
- The POS runs a **minute-level event dispatcher** (`* * * * * ... backend/scripts/dispatch_events.py`) and a **nightly entitlement sweep** (`23 3 * * * ... backend/scripts/sweep_delivery_entitlement.py`).
- The website API runs a **nightly notification job** (`0 9 * * * ... website_api/scripts/send_notifications.py`) and a **ten-minute reconciliation** (`*/10 * * * * ... --reconcile-only`).

**The accounting service follows the same shape, and the shape is the point.** The dispatcher delivers the POS's events in; the nightly reconciliation catches what the dispatcher could not; the failure path reaches a human instead of a log file nobody reads.

**What is measured, and what alerts.**

| Signal | Why it is measured |
|---|---|
| **Journal rejection rate** | the ledger refuses an unbalanced journal. A rising rejection rate is not a metric - it is **a tenant's data not getting in**, and it is the earliest sign that a mapping broke |
| **Event lag** | how far behind the dispatcher is. The books are correct but late, which reads to a tenant as "the numbers are wrong" |
| **Dead-letter depth** | events that could not be processed. A non-zero depth is a queue that is not empty, and it is the difference between a five-minute delay and a permanent gap |
| **Entitlement cache age** | how stale the answer to "is this customer entitled" can be. A cache that is too old means a customer who cancelled may still have access - and, worse, one who paid may not |
| **Unbalanced-journal attempts** | a rejected journal is a security property working. **A spike of rejections that succeed is an attack** |
| **Backup age and restore-drill age** | the backup is only worth the last successful drill. The alert fires on the **drill's** age, not the backup's - a backup that has not been restored is a hypothesis |
| **Postgres connection pool saturation and query latency** | the ledger's writes are small and frequent; a saturated pool is a service about to stop accepting journals |

**What alerts, and what does not.** A metric without an alert is a chart. The rule:

- **Page a human** when money is wrong, when a tenant cannot write, when the backup or the drill has failed, and when the entitlement is wrong in the direction that gives service away.
- **Log and trend** everything else - a slow query, a retried event, a large dead-letter queue that is draining.
- **Never alert on something nobody will act on.** An alert that fires every night and is ignored is worse than no alert: it teaches the team that alerts are noise. **Every alert in this service has a named response, and the runbook is the response.**

**The alerting channel is the same one the backup failure already uses** - `OnFailure=` into a notifier that reaches the owner. A new alerting stack is not a Phase 0 deliverable; **reusing the mechanism that is already proven to reach a human is.**

## 4. The scheduled work

**The three jobs, and why each one exists.**

**The dispatcher** - every minute, the accounting service takes what the POS has emitted and turns it into journals. This is the live in-bound path, and it is the shape the POS already runs (`dispatch_events.py`, every minute). It is idempotent, because the POS may deliver twice, and a journal posted twice is a tenant's revenue wrong.

**The nightly reconciliation** - every night, the service compares what it has recorded against what the source says, and names the difference. This is the job that answers the second 2am question, and it is the one that must run **before** anyone asks. It is the accounting service's counterpart to the website API's ten-minute payment reconciliation, on a slower clock because a day of books is what needs checking, not ten minutes of it.

**The renewal and dunning sweep** - the service's copy of the website API's nightly notification job. It reads the entitlement, finds the purchases whose period has ended, generates the next invoice, and moves the ones whose payment failed into the dunning path. **This is where `purchase-path.mdx` Decision 6 lands:** a purchase outside the `subscriptions` table is never renewed and never dunned unless this job knows about it.

**The sweeps are cheap to run and expensive to skip.** Each is idempotent and each reports a count, so "zero" is a meaningful answer - **the same way the website API's notification job reports `Renewal invoices generated: 0`** (`website_api/app/routes/notifications.py:273`). A job that reports nothing cannot be distinguished from a job that did nothing.

**One rule for all three: they never compete with the tenant's work.** The backup is `Nice=10` and `IOSchedulingClass=idle` for exactly this reason, and the accounting service's jobs take the same shape. A tenant writing a journal at 9am does not wait for a sweep.

## 5. The runbooks

**The two questions a customer asks at 2am are always the same, and they are answered by something, not by a person improvising.**

### "Can you restore me?"

**The answer is the restore drill.** One command, a scratch environment, a restored database, and the tenant's numbers read back. The runbook is the drill written down: how to restore, how to point an environment at the restored database, how to verify a tenant's books are intact (trial balance, P&L, the bank reconciliation), and how to promote the restored environment.

**What the runbook does NOT say:** "it should work." **A restore is an operation with steps, and the steps are only known because the drill ran them.** The drill runs monthly, in staging, against a real backup - not a synthetic one.

**And the honest limit is written down too:** what is restored is the **database**, not the running service. A restore does not restore a Stripe subscription, a HitPay payment request, a queued event, or a customer's session. **Those are re-derived from the restored state** - and the runbook says which, so that nobody discovers it at 2am.

### "Why is my revenue wrong?"

**The answer is the reconciliation screen in Phase 2c** - and that is why the reconciliation is a product feature and not only a support tool. The tenant sees, side by side, what the books say and what the source says, and the difference is named.

**Before Phase 2c exists, the runbook is manual** and it says so: how to re-pull a window from the POS snapshot API, how to see the events that were rejected and why, how to identify a single order whose money landed in the wrong place, and how to post the correction - **which is never an edit of a posted journal.** The ledger is append-only for a reason, and the runbook's correction path is a reversal, exactly as `pos-integration.mdx` defines it.

**Three more runbooks, because there are three more questions.**

**"I paid and I have no books."** This is the failure the purchase path can produce, and it is the most embarrassing one: the customer paid, the entitlement is granted, and the accounting tenant was not created. The runbook: check the entitlement read, check whether the accounting service saw the grant, and if it did not, re-trigger the provisioning by re-reading the entitlement. **Provisioning is idempotent by construction** (`purchase-path.mdx` Decision 2), so re-triggering is safe.

**"Your service was down."** The runbook: what the incident was, what the data state is, whether any journal was half-written, and what the tenant needs to know. **The ledger's audit rule is the answer here:** the books are either balanced or they were refused. There is no third state, because an unbalanced journal never gets written.

**"I want out, and I want my books."** The runbook: the export, the retention rule, and what is deleted and what is kept. **The export path is defined in `purchase-path.mdx` Decision 6**, and this runbook says where the export lives and how long the read-only window lasts.

**Every runbook has an owner, a trigger and a "how do we know it worked".** A runbook without those three is a document, and a document does not get anyone their books back at 2am.

## 6. The tenant isolation rules the operations must preserve

**These are operational, not just architectural, because an operations mistake is a tenant-isolation breach.**

- **Backups are per-tenant by construction, not by filtering.** A backup contains every tenant's books, so the backup is as sensitive as the most sensitive tenant's data and is encrypted and stored the same way. **A restore into a shared environment is a production environment.** There is no "staging copy" that is less confidential than production.
- **A support engineer reading a tenant's books does it through the tenant-scoped interface, with the tenant's own credentials, and it is audited.** There is no operator login that bypasses the tenant check, because the moment there is one, it is the thing everyone uses.
- **The reconciliation job is tenant-scoped.** It compares one tenant's books against one tenant's source. A reconciliation that ran across all tenants and reported a single number would be a leak.
- **A restore of one tenant's data is not a thing.** Either the whole database is restored or nothing is. **Partial restores of a multi-tenant ledger are how a tenant's books end up in another tenant's dashboard.**
- **Provider credentials are encrypted at rest and never appear in a log line, a backup manifest, or an alert.** An alert that carries a credential is a credential in a chat app.

## What this document does NOT claim

- **It does not claim the service is built.** Nothing here exists.
- **It does not claim the drill has been run.** The drill is what Phase 0c delivers. Until it has run once end to end, "we can restore you" is a claim, not an answer.
- **It does not claim the alerting is complete.** The specification is the signal set, the page/no-page rule, and the runbook per alert. The thresholds are set when there is real traffic to threshold against.
- **It does not claim a second region, a point-in-time recovery target, or a high-availability Postgres.** Those are the right answers for a mature ledger and the wrong ones for Phase 0. **A verified backup, a proven restore and an honest RTO are worth more than an untested multi-region design.**
- **It does not claim the POS's operations are insufficient.** They are good, for what they protect. **This service protects different data with a different database engine, so it gets its own.**

---

## The open questions

1. **The restore RTO.** How fast must a restore be? The answer depends on the size of the database, which does not exist yet. **The drill measures it** - and the target is set from the measurement, not before it.
2. **The retention window for the backups.** The longer the tail, the more disk and the more exposure. A ledger's tax years may require seven years of records in some jurisdictions; the *backups* need a different answer from the *books*.
3. **Who receives the 2am page.** The live notifier reaches the owner. As the tenant count grows, that is one person. **The honest answer is that the alerting needs a rotation before the tenant count needs it** - and it is worth deciding when, not discovering it.
4. **Whether the dead-letter queue is tenant-visible from day one.** It should be, and it is the same queue the POS already has. The open question is whether it is tenant-visible in Phase 0 or Phase 2c.
