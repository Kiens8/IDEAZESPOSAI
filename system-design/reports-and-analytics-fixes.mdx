## 1. The summary — one page

The **Reports & Analytics** screen (`/reports`, `frontend/src/pages/Reports.jsx`) has
**six tabs** — Sales, Orders, Walk-in vs Registered, Items, Payments, Loyalty — one
shared date filter, a CSV export and a print button.

The review (Nov 8, 2026) drove the live screen in a browser, read every line behind it
and measured the numbers against the database. The result:

**The screen looks right. Three of the six tabs quietly ignore the date filter, one of
them is arithmetically wrong for every tenant but the demo, and three backend routes
hand another tenant's loyalty data to anyone who asks.**

| # | The finding | The measure |

**The order of the work:** the three tenancy holes (§5.1) first — they are a data leak,
not a polish item. **They are closed** (Nov 8, 2026): the gate is live, the probes pass
(33 of them, `scripts/pos_loyalty_gate_test.sh`) and the guest app still works. The
**vouchers** carried the same hole (A4) — **they are closed too** (§5.8, the same day).
While the vouchers were being closed, a bigger hole came with them: **a guest could
post its own price and its own discount** (§5.9). Both are closed. Then the accuracy fixes
(§5.2–§5.5), because a report that is wrong is worse than no report. Then the export
and the print (§5.6–§5.7), which are already solved on the Order History screen and
can be reused.

**The additions** (§6) are the value on top: the comparison against the previous
period, today's pace, the busiest hour, the gross margin, the void report, and a daily
takings sheet that arrives by itself.

## 3. The findings, with the evidence

### A. The tenancy holes (the serious ones)

Three routes in `backend/app/routes/loyalty.py` take the tenant as a **path parameter**
and never check the session. The audit recipe says the tenant comes from the session
and the parameter is only a claim — these three are the claim.

```
GET /api/loyalty/report/{customer_id}      no dependency at all
GET /api/loyalty/customers/{customer_id}    no dependency at all
GET /api/loyalty/stats/{customer_id}        optional_permission("loyalty:read")
```

Measured on the live site:

```
$ curl -b adminOfTenant1.jar  .../api/loyalty/report/3        -> 200   (tenant 3's data)
$ curl -H "X-API-Key: customer_app_key" .../api/loyalty/report/1
  -> {"total_customers":7, "total_revenue":2367.7268,
      "top_customers":[{"name":"Cust 1","phone":"60161234567","loyalty_points":540, ...}]}
$ curl -H "X-API-Key: customer_app_key" .../api/loyalty/customers/1
  -> [{"name":"Cust 1","phone":"6060161234567", ...}]
```

The **customer app key is public** — it ships in the PWA bundle, so anyone can extract
it. With it, a reader gets any tenant's customer names, phone numbers, revenue and
loyalty balances.

**The sibling routes** in the same file deserve the same pass: `/customer/{id}`,
`/customer/{id}/points`, `/customer/{id}/transactions`, `/walkin-customer/{id}`.

### B. The accuracy defects

**B1 — the walk-in tab is wrong for every tenant but the demo.**
`Reports.jsx` calls `calculateReportStats(filteredOrders, activeReport, 7, …)` — the
walk-in customer id **7**, hardcoded. The walk-in row is id 7 **only for tenant 1**;
for tenant 3 (AES Restaurant) it is id **9**, and 31–37 for tenants 4–10. Measured on
the last 7 days of tenant 3:

```
with the id 7 (today)  ->  46 registered /  0 walk-in
with the id 9 (truth)  ->   0 registered / 46 walk-in
```

So the AES account would report *"Good news! Registered customers account for 100.00%
of orders"* — for a restaurant where **every** order was a walk-in. The insight box
below the table flips with it.

**The house convention is already written down**: the walk-in customer is the row with
the phone `'WALKIN'` — the backend uses it in this very report and in `vouchers.py`.
The id is not stable, so it must not be hardcoded.

**B2 — the date filter is UTC; the Order History screen is the outlet's time.**
`filterOrdersByDate` compares `now.toISOString()` (UTC) against the order's UTC date.
The `created_at` is stored naive-UTC, so the filter is *self-consistent* — but it is
**not the outlet's day**, and the Order History screen (`OrderHistory.jsx`) *is* the
outlet's day. For the demo outlet (Asia/Phnom_Penh, UTC+7), six of the sixteen orders
in the last 7 days fall on a different local day:

```
ORD-20261108-3683   2026-11-07 21:48 UTC  =  2026-11-08 04:48 in Phnom Penh
ORD-20261107-4964   2026-11-06 19:08 UTC  =  2026-11-07 02:08 in Phnom Penh
```

So **"today's takings" differ between two screens of the same app.** The Inventory
Reports screen (`pages/Inventory/Reports.jsx`) has its own from/to picker and a
timezone helper — the main Reports screen is the odd one out.

**B3 — the chart ignores the range.** `calculateSalesStats` always builds the last
seven days from `now`. The title says "Revenue (Last 7 Days)" whatever the range is.

**B4 — the Payments tab: no range, and a different source from the Sales tab.**

```
range          Sales tab        Payments tab
Today          $14.24           $5,393.61
Last 30 days   $487.24          $5,393.61
All time       $5,049.82        $5,393.61      <- a $343.79 gap
```

Two faults. The payments route has **no date filter** (identical numbers for every
range). And it is built on the **tender rows** (`order_payments`) while the Sales tab
sums the **order totals**. Those tender rows are not clean: twenty orders carry a row
of **3.50** against totals of 20.03 / 13.67 / 8.90, and one order carries **two** rows
of 3.50 (a retried payment counted twice).

**The rule that fixes it:** the **order total is the ledger** and the tender rows are
the **split of that ledger**. The total comes from the order; the shares come from the
tender rows. Then the Payments tab and the Sales tab must agree — to the cent.

**B5 — the Loyalty tab ignores the range** as well: always all-time, sitting next to a
Sales tab that follows the range, both labelled "Total Revenue" ($2,367.73 vs $14.24).

**B6 — the pending-payment KPI is hardcoded to 0** in the branch that uses the server
stats (`pendingPayment: 0`), so it always reads $0.00.

**B7 — "Items Sold" counts line items, not quantities.** The Sales KPI sums
`items.filter(...).length`; the Items tab sums `item.quantity`. They agree today only
because every demo order has one item of quantity one.

**B8 — the payment methods are raw keys** (`card`, `khqr`, `cash`, `duitnow_qr`,
`duitnow`). The app already has the mapping — `paymentMethodLabel(method, t)` in
`frontend/src/utils/paymentMethods.js` (`duitnow_qr` → the DuitNow label, and so on) —
and the KPI cards only cover Cash / Card / KHQR, so the DuitNow money is in the table
but in no KPI.

### C. The export

`components/reports/ExportButtons.jsx` builds the CSV by hand:

```js
const headers = columns.map(col => col.label).join(',')   // the ENGLISH label
const rows = data.map(row => columns.map(col => { ... }).join(',')).join('\n')
const csv = `${headers}\n${rows}`
const blob = new Blob([csv], { type: 'text/csv;charset=utf-8;' })
```

- **C1** the buttons are rendered **inside the `currentReport.table` block** — the
  Sales report has no table, so **the Sales tab has no export and no print button**
  (measured: 0 and 0).
- **C2** `col.label` is the English fallback, not `col.labelKey` → the headers stay
  English in Khmer and Chinese while the cells are translated.
- **C3** no BOM, no CRLF → Excel mangles the non-ASCII headers. The order export
  (`utils/orderExport.js`) has had both since Nov 8.
- **C4** no formula guard → a guest or item name starting with `=`, `+`, `-` or `@`
  runs as a formula when the file is opened.
- **C5** no report header block — the file does not say which outlet, which period, or
  when it was generated.

### D. The print

`handlePrint` is `window.print()`. There is **no `@media print` rule for this screen**
(the only one in the app is in `pages/Inventory/PurchaseOrders.jsx`), so the printed
page keeps the **sidebar, the header, the tab row, and both buttons — including the
Print button itself**. Measured in print media: the nav, the header, the six tab
buttons, "Download CSV" and "Print" are all still visible; the output is two A4 pages
with the navigation down the left.

### E. The quiet ones

- **E1** `GET /api/orders/` has `limit: int = 10000` and the screen shows no notice if
  it was truncated — a busy tenant's "All Time" would be silently short.
- **E2** the whole order list travels to the browser to be filtered there. The screen
  should ask for aggregations, the way the export route does.

## 4. The decisions (for Kens)

These are the choices the fixes turn on. Each one has a recommendation.

1. **The day is the outlet's day, everywhere.** Every report, every screen, the export
   and the print use the **outlet's timezone**. *Recommendation: yes — one rule, one
   helper.* The alternative (UTC everywhere) means the manager's "today" never matches
   the till's "today".
2. **The ledger is the order total.** The Payments tab is built from the paid order
   totals; the tender rows only decide **how to split** a total, never how much it is.
   *Recommendation: yes — then the Sales tab and the Payments tab must agree to the
   cent, and a test asserts it.*
3. **The date filter either works or it is not shown.** A tab that cannot honour the
   range must **hide the range control** (and say "all time" in its title) rather than
   show a control that does nothing. *Recommendation: make them honour it — the loyalty
   and payments data are cheap to re-aggregate per range.*
4. **The walk-in is the `WALKIN` phone, decided by the backend.** The frontend must
   not know an id. *Recommendation: the backend returns `is_walkin` on the order rows
   (and on the export rows).*
5. **Which role may read the loyalty report?** It carries the customers' names, phones
   and balances. *Recommendation: `loyalty:read` with the **manager** and **admin**
   (the same roles the Reports screen itself is for) — not the floor, and never the
   public PWA key.*
6. **The comparison period.** *Recommendation: every KPI gets a **"vs the previous
   period"** line — the same length, immediately before. It is the single most
   requested number in a restaurant report and it needs no new data.*

## 5. The fix designs

### 5.1 The tenancy gate on the loyalty routes — **BUILT (Nov 8, 2026)**

> **What was built:** every route in `backend/app/routes/loyalty.py` is gated; the guest
> app proves who it is with a signed guest token; the walk-in member travels with the
> venue's settings; the register and the login derive the tenant from the venue. The
> probes: `scripts/pos_loyalty_gate_test.sh` — **33 probes, 0 failing**.
> The mechanism (the guest token) is in §5.1.1, the walk-in move in §5.1.2, and the
> **vouchers**, which carry the same hole, in §5.8.

The shape every route follows (the audit recipe):

```python
from app.core.tenant import caller_tenant, require_tenant_claim

@router.get("/report/{customer_id}")
def get_loyalty_report(
    customer_id: int,
    request: Request,
    db: Session = Depends(get_db),
    key_info: dict = Depends(require_permission("loyalty:read")),
):
    tenant_id = caller_tenant(request, key_info)      # the tenant of the SESSION
    if customer_id != tenant_id:
        raise HTTPException(status_code=403, detail="This restaurant group is not yours")
    ...
```

- **the tenant comes from the session**, never from the path parameter;
- the parameter is only a **claim**, and a mismatch is a **403**;
- the permission is **required**, not optional — the customer app key must not pass;
- the same treatment for `/customers/{id}`, `/stats/{id}`, `/customer/{id}`,
  `/customer/{id}/points`, `/customer/{id}/transactions`, `/walkin-customer/{id}`.

**The probe** (log in as two tenants):

```bash
curl -s -b tenantA.jar "…/api/loyalty/report/<B>"      # must be 403
curl -s -H "X-API-Key: customer_app_key" "…/api/loyalty/report/1"   # must be 403
curl -s -b tenantB.jar "…/api/loyalty/report/<B>"      # must be 200
```

#### 5.1.1 The guest token (the new piece)

The customer app's key is **public** — it ships in the PWA bundle — and it carries
`loyalty:read`, so a plain `loyalty:read` would not have stopped it. A guest needs a
**proof of identity**, and the proof is a signed token:

```python
# backend/app/core/guest_session.py
create_guest_token(dining_customer_id, customer_id)   # HS256, the SESSION_SECRET
read_guest_token(token)                               # the claims, or None
```

- The login and the register **hand the token out** (it travels in the answer's
  `token` field).
- The guest app keeps it (`pos_guest_token_<restaurant group>`) and sends it in the
  **`X-Loyalty-Token`** header.
- The token has **no `uid` claim**, so `read_session_token()` does not accept it — a
  guest token can never be used as a staff session, and the two cannot be mixed up.
- It is signed with the same secret as the staff session but carries a `pur` claim
  (`loyalty_guest`) and lives 30 days.

The new dependency (`middleware/auth.py`):

```python
require_guest_or_staff("loyalty:read")
# → the staff path (the signed session or the frontend key) with the permission,
# → or the guest path (a valid guest token),
# → otherwise 401.
```

The member routes then ask one more question — **is this the member?** — and a member
of another restaurant group gets the same answer as a member that does not exist
(**404**), so a guest cannot probe for other guests' ids.

#### 5.1.2 The walk-in member travels with the venue

`GET /api/loyalty/walkin-customer/{customer_id}` was used by the guest app and by the
staff-order screen. Both of them were asking about a **restaurant group** when they
actually wanted to know about **their venue** — so the id now travels with the
venue's settings:

- `GET /api/settings/{outlet_id}` (the POS) and `GET /api/customer/settings/{outlet_id}`
  (the guest app) carry **`walk_in_customer_id`** — the member whose phone is
  `'WALKIN'`, of that venue's tenant. The id is **never hardcoded** (it is 7 for
  tenant 1 and 9 for tenant 3 — §5.2).

#### 5.1.3 The venue decides the tenant (the register and the login)

The register and the login took the restaurant group from the body. They now take the
**venue** and derive the group from it — the same **venue trust boundary** the order
route uses:

```python
tenant_id = _tenant_of_outlet(db, data.outlet_id)      # the venue decides
if data.customer_id is not None and data.customer_id != tenant_id:
    raise HTTPException(400, "This customer does not belong to that restaurant")
```

A guest can no longer sign up inside somebody else's restaurant group.

#### 5.1.4 The version bump (the guest app)

The guest app's assets are cached by the CDN **by URL**, so a new build needs a new
version query — the SW comment in `customer-app/sw.js` says so, and the service worker's
own comment calls the old behaviour "a nightmare to debug". The build stamps it:
`python3 customer-app/scripts/build_pwa.py` (the `VERSION` file). Without the bump the
guests keep running the old code — and the old code sends no token.

### 5.2 One walk-in rule

The backend already knows the tenant's walk-in row (the one with the phone `WALKIN`).
The order rows carry the flag:

```python
# backend/app/routes/order.py — OrderResponse
is_walkin: Optional[bool] = None
```

computed from the tenant's walk-in customer id (never a constant), and the frontend
uses it instead of the number 7:

```js
// frontend/src/components/reports/reportsConfig.js
const registered = orders.filter(o => !o.is_walkin)
const walkin     = orders.filter(o =>  o.is_walkin)
```

### 5.3 One date rule, one helper

```js
// frontend/src/utils/dateRange.js
export const RANGE_DAYS = { today: 1, week: 7, month: 30, all: null }

/** The window of a range, as the LOCAL dates of the outlet (YYYY-MM-DD). */
export function rangeWindow(dateRange, tz, now = new Date()) {
  const today = now.toLocaleDateString('en-CA', { timeZone: tz })
  const shift = (d, days) => {
    const dt = new Date(`${d}T00:00:00Z`)
    dt.setUTCDate(dt.getUTCDate() + days)
    return dt.toISOString().slice(0, 10)
  }
  if (dateRange === 'today') return { from: today, to: today }
  if (dateRange === 'week')  return { from: shift(today, -6), to: today }   // 7 days
  if (dateRange === 'month') return { from: shift(today, -29), to: today }  // 30 days
  return { from: null, to: null }                                          // all
}

/** Is an order inside the window, in the outlet's day? */
export function inWindow(createdAt, tz, from, to) {
  if (!from && !to) return true
  const local = new Date(createdAt).toLocaleDateString('en-CA', { timeZone: tz })
  if (from && local < from) return false
  if (to && local > to) return false
  return true
}
```

The window is then sent to the server (`date_from`, `date_to`) for the tabs that are
aggregated there — **the same parameters the export route already takes**
(`GET /api/orders/export`), so the report and the file always cover the same period.

**The "week" range is seven days** (today and the six before). The old code used
`now - 7 days`, which is **eight** calendar days — the label said seven.

### 5.4 The Payments tab on the ledger

The total comes from the order; the tender rows only split it:

```sql
SELECT o.payment_method, COUNT(*) AS count, SUM(o.total) AS revenue
FROM orders o
WHERE o.customer_id = :tenant AND o.outlet_id = :outlet
  AND o.payment_status = 'paid'
  AND o.created_at >= :from AND o.created_at < :to
GROUP BY o.payment_method
```

For a **split** order the tender rows give the **shares**, and the order's total is
split by those shares (so the parts still add up to the total):

```
order 42.00, tender rows 30.00 card + 12.00 cash
-> card 28.00, cash 14.00   (the shares, scaled to the order total)
```

**The rule to test:** the Payments tab's total **equals** the Sales tab's total for the
same range, to the cent. One assertion, and it catches every future drift.

### 5.5 The chart follows the range

The chart's series is built **for the selected window**: today → the hours so far,
7 days → seven daily bars, 30 days → thirty daily bars, all time → the months. The
day labels come from the outlet's timezone and are translated like the rest.

### 5.6 The export, on every tab

The order export already solved the file rules (`utils/orderExport.js`: the BOM, the
CRLF, the formula guard, the bare money cells). The reports exporter should **reuse
them**, not re-implement them:

```js
import { buildCsv, downloadCsv, csvMoney } from '../../utils/orderExport'

const csv = buildCsv(columns, rows)   // the columns carry the TRANSLATED labels
downloadCsv(csv, `report_${reportId}_${from || 'all'}_${to || 'all'}.csv`)
```

And every tab gets the buttons — including the Sales tab, which needs **a table**
(the daily series) to export, not just a chart. That table is also what makes the
chart readable: a chart cannot be summed in a spreadsheet.

The file gets a **header block**: the outlet, the period, the report, and the moment
it was generated — the three lines an accountant asks for first.

### 5.7 The print

A `@media print` block for the screen:

- the sidebar, the header, the tab row and the buttons are **hidden**;
- a **report header** appears: the outlet, the report, the period, the generated-at,
  and who printed it;
- the table keeps its rows whole (no row split across a page) and repeats its header
  row on every page;
- a footer with the page number.

### 5.8 Phase 1b: the vouchers (built, Nov 8, 2026)

The loyalty router was not the only file with the same shape. **`routes/vouchers.py`**
had it too, and worse — some of its routes are **writes**:

| Route | Guard before | The gate now |
|---|---|---|
| `GET /vouchers/all/{customer_id}` | **none** | `require_staff_permission("staff:vouchers:read")` + the tenant from the session |
| `GET /vouchers/stats/{customer_id}` | **none** | the same |
| `GET/POST /vouchers/templates/{customer_id}` | **none** | read / write + the tenant from the session |
| `PUT/DELETE /vouchers/templates/{template_id}` | **none** | write + **the template's own** tenant (the url's id is only a claim) |
| `POST /vouchers/issue` | **none** | the guest token (**its own member only**) or the staff (its own group) |
| `POST /vouchers/issue-bulk` | **none** | write + the tenant from the session |
| `GET /vouchers/my-vouchers/{dining_customer_id}` | **none** | the guest token (**its own member**) or the staff (its own group) |
| `POST /vouchers/redeem` | **none** | the guest token or the staff — the member's group has to match |
| `DELETE /vouchers/{voucher_id}` | **none** | write + the tenant of the **member** the voucher belongs to |
| `GET /vouchers/validate/{code}` | **none** | read + the tenant of the member the voucher belongs to |

Three things are worth naming:

- **the staff namespace.** The gate is `staff:vouchers:read`, not `vouchers:read`. The
  customer app's key **carries** `vouchers:read` (it ships in the PWA bundle), so the
  plain permission would have stopped nothing. The `staff:` namespace is what the
  customer key cannot satisfy.
- **the voucher's tenant comes from the voucher's member**, not from the url. A
  voucher has no tenant of its own — it belongs to a member, and the member belongs
  to a restaurant group.
- **the guest app's two routes take the guest token** (`my-vouchers`, `issue`). The
  token is what proves the device is that member; the API key alone is public.

**The probes:** `scripts/pos_voucher_gate_test.sh` — 23 of them, all passing (the
cross-tenant reads, the guest's own member, the guest's price and discount, and the
staff at the till).

### 5.9 The hole that came with them: the money of a guest order (built, Nov 8, 2026)

While the vouchers were being closed, the order route was read again — and the same
question was asked of it: **who owns the money of this order?**

The answer was: **the client**. A guest could post an order with

```json
{"items": [{"menu_item_id": 2, "quantity": 1, "unit_price": 0.01}], "discount": 50}
```

and the server took it. The probe order came out at **-53.99** — the restaurant owes
the guest 53.99. The voucher was applied the same way: the client sent the discount
it liked.

**The rule now:** the server owns the money of a **guest's** order.

- **the price** is the menu's price (`OrderService.create_order(..., trust_client_money=False)`);
- **the discount** is 0 unless a voucher is applied — and then it is the **validated**
  voucher's discount (the code is checked against the member, the group, the expiry
  and the minimum spend) or, without a voucher, the **promotions engine's** best
  discount (a bundle is a promotion, and the app shows the bundle price in the cart);
- **the redemption** happens in the same transaction as the order (the order route
  marks the voucher used and tells the campaign behind it), so the app no longer
  redeems the voucher itself after the order.

**The staff at the till keep their power:** a manual price and a manual discount are
normal things at a counter, so the staff's order is still theirs (`trust_client_money`
stays on). The two are one parameter, and the probes prove both sides.

The **percentage bug** in the guest app went with it: the cart computed a 10% voucher
as `subtotal * 10 / 100` and then **threw the result away** and used the percentage as
an amount (10% became 10). Two places, both fixed.

The promotions engine moved out of the route into
`backend/app/services/promotion_service.py`, because the order needs it now. Its
answer does not change.

## 10. What we are **not** doing (yet)

  by itself every day is worse than no report.

  if that day comes.
