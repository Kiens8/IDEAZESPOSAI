# Language Switching System

**Date:** October 13, 2026

---

## Overview

This document outlines the language switching system to support 4 languages across the IDEAZES ecosystem.

### Apps Covered

| App | Routes | Database |
|-----|--------|----------|
| **Site App** (Public + Portal) | `/`, `/login`, `/signup`, `/portal/*` | `website_api.db` |
| **Frontend POS** | All POS routes | `pos_ai.db` |
| **Customer Order App** | `/order/*` | `pos_ai.db` |

### Languages Supported

| Code | Language | Display Name |
|------|----------|--------------|
| `en` | English | English |
| `zh` | Chinese | 简体中文 |
| `ms` | Malay | Bahasa Melayu |
| `kh` | Khmer | ភាសាខ្មែរ |

## Priority System

| App | Priority Order | Storage |
|-----|---------------|---------|
| **Frontend POS** | User setting > Outlet setting > Default (en) | Database |

## Translation Files Structure

Each app has its own `i18n` folder with the same structure:

```
src/
├── i18n/
│   ├── index.js              # Export translation hook
│   ├── LanguageContext.jsx   # React context provider
│   ├── useTranslation.js     # Custom hook: t('key.subkey')
│   └── locales/
│       ├── en.json
│       ├── zh.json
│       ├── ms.json
│       └── kh.json
```

### Translation File Format

All translation files use **flat key naming** with dot notation:

```json
{
  "common.save": "Save",
  "common.cancel": "Cancel",
  "common.delete": "Delete",
  "common.edit": "Edit",
  "common.loading": "Loading...",
  "common.error": "Error",
  "common.success": "Success",
  "menu.dashboard": "Dashboard",
  "menu.orders": "Orders",
  "menu.settings": "Settings",
  "auth.login": "Login",
  "auth.logout": "Logout",
  "auth.email": "Email",
  "auth.password": "Password",
  "settings.language": "Language",
  "settings.outlet": "Outlet Settings"
}
```

## How to Add New UI Strings (Future UI Changes)

This is the **key workflow** for maintaining translations when you add new features or UI.

### Step 1: Add Key to All Translation Files

When adding new UI text, you must add the key to **all 4 language files**:

```json
// en.json
{
  "newFeature.title": "New Feature",
  "newFeature.description": "This is a new feature"
}

// zh.json
{
  "newFeature.title": "新功能",
  "newFeature.description": "这是一个新功能"
}

// ms.json
{
  "newFeature.title": "Ciri Baharu",
  "newFeature.description": "Ini adalah ciri baharu"
}

// kh.json
{
  "newFeature.title": "មុខងារថ្មី",
  "newFeature.description": "នេះគឺជាមុខងារថ្មី"
}
```

### Step 2: Use the Translation Hook in Components

```jsx
import { useTranslation } from '../i18n/useTranslation';

function NewFeaturePage() {
  const { t } = useTranslation();
  
  return (
    <div>
      <h1>{t('newFeature.title')}</h1>
      <p>{t('newFeature.description')}</p>
    </div>
  );
}
```

### Step 3: Fallback is Automatic

If a key is missing in the selected language, it falls back to English:

```javascript
// If 'newFeature.title' is missing in zh.json, it returns "New Feature"
```

### Translation Key Naming Conventions

| Rule | Example |
|------|---------|
| Use **dot notation** for hierarchy | `menu.dashboard`, `auth.login` |
| Use **camelCase** for keys | `orderHistory`, `tableNumber` |
| Use **lowercase** for top-level categories | `common`, `menu`, `auth`, `settings` |
| Be **descriptive** | `error.invalidPassword` not `err.1` |

### Category Reference

Use these standard categories to keep keys consistent:

| Category | Purpose |
|----------|---------|
| `common` | Shared elements (buttons, labels, messages) |
| `menu` | Navigation menu items |
| `auth` | Login, logout, registration |
| `settings` | Settings pages |
| `orders` | Order-related UI |
| `reports` | Report labels |
| `errors` | Error messages |
| `validation` | Form validation messages |

| `backend/app/routes/outlet_settings.py` | Add language field |

### API Endpoints

#### PUT /api/users/{id}/language
Update user language preference.

```json
{
  "language": "en|zh|ms|kh"
}
```

#### GET /api/users/{id}
Returns user info including `language` field.

#### GET /api/outlet-settings
Returns outlet settings including `language` field.

### Database Changes (pos_ai.db)

```sql
ALTER TABLE outlet_settings ADD COLUMN language VARCHAR(10) DEFAULT 'en';
ALTER TABLE users ADD COLUMN language VARCHAR(10) DEFAULT NULL;
```

## Menu Items & Categories Translation

### Approach: Manual Input via Menu Management

Menu items and categories support manual translation via Menu Management screen.

### Database Changes (pos_ai.db)

**menu_items Table:**
```sql
ALTER TABLE menu_items ADD COLUMN name_zh VARCHAR(255);
ALTER TABLE menu_items ADD COLUMN name_ms VARCHAR(255);
ALTER TABLE menu_items ADD COLUMN name_kh VARCHAR(255);
```

**categories Table:**
```sql
ALTER TABLE categories ADD COLUMN name_zh VARCHAR(255);
ALTER TABLE categories ADD COLUMN name_ms VARCHAR(255);
ALTER TABLE categories ADD COLUMN name_kh VARCHAR(255);
```

### Display Logic

```javascript
function getItemName(item, language) {
  switch(language) {
    case 'zh': return item.name_zh || item.name;
    case 'ms': return item.name_ms || item.name;
    case 'kh': return item.name_kh || item.name;
    default: return item.name;
  }
}
```

## Future Considerations

### Adding a New Language

1. Create new `xx.json` in `locales/` folder
2. Copy structure from `en.json`
3. Translate all keys
4. Add language to LanguageSelector dropdown
5. Update `useTranslation.js` to include new language

### RTL Support

Khmer may need RTL support in the future. When implementing:
- Add `dir="rtl"` attribute to `<html>` or relevant container
- CSS should handle mirrored layouts

### Translation Key Auditing

When adding new UI, maintain a translation key checklist:

```
✓ Key added to en.json (base)
✓ Key added to zh.json
✓ Key added to ms.json
✓ Key added to kh.json
✓ Component uses t('key') not hardcoded string
✓ Fallback works when key is missing
```
