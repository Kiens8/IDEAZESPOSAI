# Language Switching System

**Date:** October 13, 2026  
**Last Updated:** October 28, 2026 (design review — status corrected, stack updated to 2026 standards; Phase 3 Site App implemented and live)

## Overview

This document outlines the language switching system to support **3 languages** across the IDEAZES ecosystem.

### Apps Covered

| App | Routes | Database | Stack |
|-----|--------|----------|-------|
| **Site App** (Public + Portal) | `/`, `/login`, `/signup`, `/portal/*` | `website_api.db` | Next.js 16 + React 19 + Tailwind v4 |
| **Frontend POS** | All POS routes | `pos_ai.db` | Vite + React 18 (SPA) |
| **Customer Order App** | `/order/*` | `pos_ai.db` | Vanilla JS (PWA) |

> **Out of scope:** the **Admin App** (`admin.ideazes.com`) is intentionally excluded from this document and from this phase of work. It can be added later as its own phase — see [Future Considerations](#future-considerations).

## Languages Supported

| Code | BCP-47 Tag | Language | Display Name | Direction |
|------|-----------|----------|--------------|-----------|
| `en` | `en-US` | English | English | LTR |
| `zh` | `zh-Hans` | Chinese (Simplified) | 简体中文 | LTR |
| `km` | `km-KH` | Khmer | ភាសាខ្មែរ | LTR |

### Locale Code Correction (October 28, 2026)

The earlier draft used `kh` for Khmer. That was incorrect.

- `kh` is the ISO 639-2 **bibliographic** code for Khmer. The BCP-47 / ISO 639-1 language subtag is **`km`**.
- `ms` (Malay / Bahasa Melayu) has been **removed** from the supported set — Malay is no longer required.
- Chinese is pinned to Simplified (`zh-Hans`) rather than the generic `zh`, so a future Traditional Chinese locale can be added without breaking existing users.

Use the **short code** (`en`, `zh`, `km`) in the database column and in `Intl`/library calls; use the **full BCP-47 tag** in `<html lang>`, `hreflang`, and locale-prefixed URLs.

### Text Direction (October 28, 2026)

The earlier draft stated that "Khmer may need RTL support". That was incorrect.

- **Khmer is a left-to-right (LTR) script.** Khmer, Chinese and English are all LTR.
- RTL support is only required if we later add **Arabic, Hebrew, Persian or Urdu**. Until then, no `dir="rtl"` handling is needed.
- To make a future RTL locale cheap, use **CSS logical properties** from the start (Tailwind: `ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`, `text-start`/`text-end`) instead of `ml-`/`mr-`/`left-`/`right-`.

**i18n key-parity guardrail** — `site/scripts/check-i18n-parity.mjs`:

- every locale has the same namespaces as `en`
- every namespace has an identical leaf-key set in every locale (804 keys × 3 locales)
- no translation value is empty where the English source has content
- ICU placeholders (`{count}`, `{name}`) match the English source exactly, so a missing placeholder cannot silently drop data
- exits non-zero on any drift

Wired into `package.json`:

```json
{
  "lint": "eslint",
  "i18n:check": "node scripts/check-i18n-parity.mjs",
  "verify": "npm run lint && npm run i18n:check",
  "prebuild": "npm run verify"
}
```

`prebuild` means a production build **fails** when the locales drift apart or the code has a lint error. A GitHub Actions workflow (`site/.github/workflows/site-ci.yml`) runs lint → parity → `tsc --noEmit` → build.

#### Auto-translated database content (added October 28, 2026)

The admin app stays English and stays the single source of truth for database
content. The site app auto-translates that content into the visitor's language
when they switch.

```
Admin app (English)          website_api                     Site app
─────────────────────   ─────────────────────────   ─────────────────────
PUT /api/admin/plans/3  →  save → background job   →  GET /api/plans/published
  description = "…"            translate → zh, km         ?locale=zh
  feature_tags = "…"                 │                       │
                                     ▼                       ▼
                             content_translations      renders zh/km copy
                             (cached + hashed)         (English fallback)
```

**Storage** — one generic table, so the same machinery later serves the
feature catalogue, menu items, categories and modifiers:

```sql
content_translations(
  content_type TEXT,      -- plan | feature | menu_item
  content_id   INTEGER,
  field        TEXT,      -- tagline | bullets | description
  locale       TEXT,      -- zh | km
  source_hash  TEXT,      -- hash of the English source
  source_text  TEXT,
  translated_text TEXT,
  provider     TEXT,
  status       TEXT,      -- done | failed
  created_at / updated_at
)
```

The `source_hash` is the key: editing a plan in the admin app changes the hash,
the cached translation is invalidated automatically and re-translated in the
background. No manual re-translate step, no forgotten translations.

**Two triggers**
1. *Write time* — `POST/PUT /api/admin/plans/...` schedules a background
   translation, so the content is already translated before anyone switches.
2. *Read time* — `GET /api/plans/published?locale=xx` translates anything
   missing or stale on the spot and caches it.

**Provider** — MiniMax (`MiniMax-M2.7`, Anthropic-compatible
`https://api.minimax.io/anthropic/v1/messages`), configured in
`website_api/.env` as `MINIMAX_API_KEY`. A prompt pins down brand names,
plan names, product acronyms, numbers, currency and placeholders so they are
never translated; the result is validated (empty or identical-to-source
output is rejected and falls back to English).

**Never translated** — plan names and slugs, prices, currency codes, outlet
and staff limits, feature keys, API values, HTML structure.

**Site-side** — the pricing card renders, in order of precedence:
1. the API's localized copy (admin-owned),
2. the curated static copy in `home.json` (fallback if the API is down),
3. the raw English source.

Limits are rendered from the API numbers with localized labels and proper ICU
plurals (`1 outlet` / `3 staff members` / `1 个门店` / `1 សាខា`).

**Pre-warming** — `website_api/scripts/prewarm_translations.py` fills the
cache for every plan, so a first-time visitor never waits on the model
(Khmer is the slow one, ~10s per plan when cold).

**Limitations**
- Machine translation is good, not perfect. Khmer quality is noticeably weaker
  than Chinese (e.g. "Online Ordering" was rendered as "voice ordering" in one
  pass). Because every translation is stored in `content_translations`, the
  copy can be hand-corrected later from the database, and an admin-side
  translation editor can be added later.
- `subscription_plans.description` and `feature_tags` are denormalized copies
  of what the `features` / `plan_features` tables already model, and they had
  drifted (a stray "Staff Managementaaa" typo, missing bullets). They are now
  translated as-is; the source-of-truth cleanup is a separate task.
- The Admin App itself is still English-only and stays out of scope.

#### Mobile UI fixes caused by the added language button (October 28, 2026)

Adding the language selector widened the portal header, which pushed the
notification bell and the sign-out button off the screen on small viewports.
Found by a Playwright sweep of every route at 375 px and 640 px.

| Symptom | Cause | Fix |
|---|---|---|
| Clicking the bell showed only part of the notification list | The panel was `absolute right-0 w-80` anchored to the bell. On a 375 px screen the bell sat far enough right that the 320 px panel started at **x = -108** — a third of it was off-screen | The panel is now `fixed` and centred on small screens (`left-1/2 -translate-x-1/2 w-[min(20rem,calc(100vw-1.5rem))]`), and reverts to `absolute right-0` anchored to the bell from `sm` up |
| The whole page scrolled sideways | The portal header (logo + bell + language selector + sign-out) was wider than a 375 px viewport | Tighter gaps on mobile (`gap-2 sm:gap-4`), smaller logo tile, and the sign-out button collapses to a 34 px icon button below `sm` |
| The signup phone field overflowed the page | The `flex-1` input could not shrink below its intrinsic width | Added `min-w-0` to the phone input |

Verification: every route (`/en`, `/about`, `/contact`, `/login`, `/signup`,
`/portal`, `/portal/billing`, `/privacy-policy` in en/zh/km) now reports
`scrollWidth === innerWidth` at both 375 px and 640 px, and the notification
panel is fully inside the viewport in all three languages.

## Technology Stack (revised October 28, 2026)

The original plan used a hand-rolled `LanguageContext` + flat JSON files. That approach is a generation behind current practice. The revised plan uses the standard 2026 libraries:

| App | Library | Version | Why |
|-----|---------|---------|-----|
| **Frontend POS** | `i18next` + `react-i18next` | v26.x / v17.x | ICU plurals, namespaces, typed resources, lazy loading |
| **Customer Order App** | `i18next` (core only) | v26.x | No framework in this app — `data-i18n` attributes on DOM nodes |
| **Site App** | `next-intl` | 4.14.x | Native Next.js App Router support: locale routing, RSC, `hreflang`, static generation per locale |

### What we gain over the hand-rolled approach

- **Compile-time key safety** — with i18next v25+ `CustomTypeOptions`, a mistyped key (`t('menu.dishes')` when the key is `menu.dish`) is a **TypeScript error**, not a silent English string in front of a customer.
- **Namespaces** — split by feature area (`common`, `menu`, `settings`, `orders`, …) so each bundle loads only the keys it needs instead of one monolithic JSON.
- **ICU plurals & gender** — `"{{count}} item"` / `"{{count}} items"` handled by `Intl.PluralRules` instead of manual `count === 1` checks. Chinese and Khmer each use a single plural form; the API stays correct if Arabic is added later.
- **Lazy loading** — locale JSON is fetched on demand, keeping the customer app's first paint fast on low-end Android.
- **Per-namespace fallback** — a missing `km` key falls back to `en` for that namespace only.
- **Managed platform** — `i18next-parser` extracts keys from source, `eslint-plugin-i18n` flags missing/unused keys, and a CI parity check fails the build when locales drift apart.

### Key Management

```
locales/
├── en/
│   ├── common.json
│   ├── menu.json
│   └── ...
├── zh/
│   ├── common.json
│   └── ...
└── km/
    ├── common.json
    └── ...
```

Adding a new language means adding **one folder** — there is no need to copy `en.json` and prune it, because fallback is handled per key by the library.

## Locale Detection & Persistence

| App | Detection | Persistence |
|-----|-----------|-------------|
| **Frontend POS** | User setting → Outlet setting → Default (`en`) | Database (`users.language`, `outlet_settings.language`) |
| **Customer Order App** | Browser `navigator.language` → `Accept-Language` → Default (`en`) | `localStorage` (+ PWA cache) |
| **Site App** | `Accept-Language` header → cookie → Default (`en`) | **Cookie** (not `localStorage`) |

**Why a cookie for the Site App:** the locale must be readable on the server so the first HTML response is already in the correct language. With `localStorage` the page renders in English and then swaps — a visible flash, a hydration mismatch, and wrong text for search crawlers. `next-intl` handles this with a locale-prefixed route plus a cookie.

## Number, Currency & Date Formatting

**This is a critical separation and was missing from the original design.**

`outlet_settings` already carries business formatting settings:

- `currency_symbol`, `currency_code`
- `decimal_places`
- `date_format`, `timezone`

These are **business locale** and must be driven by `outlet_settings`, **not** by the UI language. Switching the UI to Chinese or Khmer must never reformat prices or change the timezone.

Implementation:

- Prices → `Intl.NumberFormat(locale, { style: 'currency', currency: currencyCode, minimumFractionDigits: decimalPlaces })`
- Dates → `Intl.DateTimeFormat(locale, { timeZone: outletTimezone, ... })`
- `locale` here is the **UI locale** (affects digit grouping and separators); `currencyCode` / `timezone` / `decimalPlaces` come from the **outlet settings**.

For the Site App, `next-intl` provides `useFormatter()` (client) and `getFormatter()` (server) for exactly this.

## SEO (Site App)

The Site App has `sitemap.ts` and `robots.ts` but no locale story. With multi-language support:

- Use **locale-prefixed routes**: `/en/about`, `/zh/about`, `/km/about` (next-intl `defineRouting` supports custom pathnames per locale too, e.g. `/zh/about` / `/km/about-about`)

## Phase 1 — implementation notes and traps (28 October 2026)

**Two traps that cost real debugging time — both are now documented in the code:**

1. **react-i18next v17 returns a wrapper, not the instance.** `useTranslation()` returns an object whose own property descriptors are copied from the instance. Calling `changeLanguage()` on it mutates only the wrapper's private copy of `language` — the shared instance never sees the change, no component re-renders, and the UI silently stays in the old language. Always drive language changes through the imported instance (`import i18n from './i18n'`). Symptom: `document.documentElement.lang` says the new locale while the text is still the old one.

2. **`parseMissingKeyHandler` swallows `defaultValue`.** i18next calls it as `(key, defaultValue, options)` and **replaces** the resolved value with its return. A handler of `(key) => key` therefore discards any `defaultValue` the caller supplied — which is exactly how unknown API enum values (a status or payment method the server has never sent) are kept from rendering a raw key path. The handler is now `(key, defaultValue) => defaultValue ?? key`.

**Build-time guards in place:**

- `scripts/check-i18n-parity.mjs` → wired to `prebuild`, so `npm run build` fails on locale drift, empty values or ICU placeholder mismatch
- `i18next.d.ts` → typed keys, activates automatically when the app moves to TypeScript
- Vite `import.meta.glob` discovers namespaces from the filenames — no registry to forget

**Verified:** 23 routes × 3 locales = 69 browser renders, zero untranslated keys, zero console errors. The admin account was left on `en`.

## Phase 1 (cont.) — business formatting and fonts (28 October 2026)

The last two Phase 1 items, completed after the page migration.

### Business formatting — `src/utils/format.js`

**The rule the module exists to enforce:** the *UI language* and the *business locale* are two different things and never move together. Switching the interface to Chinese or Khmer must not reformat prices, change the currency symbol, or shift the timezone.

A concrete trap: `Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'MYR' }).format(1234.5)` returns `"MYR 1,234.50"` while `en-MY` returns `"RM 1,234.50"`. Using the UI locale with `style: 'currency'` therefore silently swaps the symbol the moment a staff member switches language. The module instead formats the **number** with the outlet's business locale and prints the outlet's own `currency_symbol`.

| Concern | Source | Affected by UI language? |
|---|---|---|
| Currency symbol | `outlet_settings.currency_symbol` | **No** |
| Decimal places | `outlet_settings.decimal_places` | **No** |
| Digit grouping / separators | business locale, derived from `currency_code` / `country` | **No** |
| Date pattern (`DD/MM/YYYY`, `MM/DD/YYYY`, `YYYY-MM-DD`) | `outlet_settings.date_format` | **No** — the identifier is a business setting and is never translated |
| Timezone | `outlet_settings.timezone` | **No** |
| Month names, AM/PM marker | UI language | **Yes** — these are words |

`formatCurrency` / `formatDate` / `formatDateTime` / `formatTime` / `formatNumber` live in one module; `src/hooks/useSettings.js` re-exports them so existing call sites keep working.

**Pre-existing bugs found and fixed while consolidating:**
- `OrderQueue.jsx` passed a *currency symbol string* where the formatter expected a settings object, so receipts fell back to `$` instead of the outlet's symbol.
- `OrderHistory`, `MenuManagement`, `OrderHistory` order totals and the reports KPI/table components hardcoded `$` — a Malaysian outlet would have shown dollars on every report.
- `MenuManagement`, `Reports` and `Dashboard` each defined a **local** `formatCurrency`/`fmtCurrency` that shadowed the shared one, so the outlet's decimal places and grouping were ignored.
- The inventory pages formatted money with `toFixed(2)` instead of the outlet's `decimal_places`.
- All of it is now one code path: prices, receipts, the ESC/POS printer stream, CSV exports, dashboards, reports and the AI widgets.

**Deliberately left alone:** CSV cells stay bare numbers (`1234.50`, no symbol, no thousands separator) — one CSV builder does not escape commas, so a grouped value would break the column layout. A spreadsheet should receive a number, not a price.

### Fonts

- **Noto Sans Khmer** is self-hosted in three subsets (`khmer`, `latin-ext`, `latin`) with `unicode-range` on each and `font-display: swap`. A device downloads the ~59 KB Khmer subset only once Khmer characters actually appear — the Latin subsets stay unloaded.
- **Chinese** uses the system CJK stack (PingFang SC → Hiragino Sans GB → Microsoft YaHei → Noto Sans SC → Noto Sans CJK SC). A self-hosted SC font is several megabytes and is not worth the bandwidth.
- The stack is Latin → Khmer → CJK → system, so Latin text stays on the OS UI font while Khmer and Chinese pick up a proper face.

**Symptom:** on the Purchase Orders page the AI panel showed *Loading AI predictions…* and then disappeared, leaving no trace.

**Two separate causes, one visible symptom:**

1. **Backend logic flaw (`backend/app/services/inventory_prediction_engine.py`).** `predict_stockout_date()` checked consumption history *before* checking whether stock had already fallen to or below the minimum level. An ingredient with no stock movements in the last 7 days returned `status: "unknown"` and `days_until_stockout: None`, and `get_urgent_ordering_list()` filtered those out. The result: an outlet with sparse movement history showed **zero** AI warnings while sitting on **11 ingredients already at or below their minimum stock level** (Rice 8.8/20 kg, Milk 0.8/5 L, Tomato 2/4 kg, Salmon 1.5/3 kg …).

   The minimum-stock check now runs first: an ingredient at or below its minimum level is `critical` regardless of consumption history, and `critical` items are always included in the urgent list. The endpoint now returns **11 items, $182.86 estimated cost** (previously 0).

2. **Frontend feedback (`frontend/src/components/AIInventoryAlerts.jsx`).** When there were no alerts the component did `return null`, so a spinner was replaced by nothing — which reads as a broken feature rather than a completed check. It now renders a calm, muted *Stock levels checked — all stock levels are healthy* strip instead of vanishing.

**Lesson worth keeping:** an empty result is only reassuring if you can tell it apart from a failure. Both halves of this bug were "silence" — one from a filter that was too strict, one from a `return null`.

Verified in the browser: the alert banner shows *11 items need ordering* with a working *View AI Suggestions* modal (11 rows), and the empty state renders correctly in English, Chinese and Khmer. Regression re-run: 23/23 routes clean, zero page errors.

## UI fix — the language switcher and notification bell covered the page's own buttons (28 October 2026)

**Symptom (reported by Kens with a screenshot):** on the Purchase Orders page the blue language button sat directly on top of the page's own *订单* button, hiding it. The notification bell was hidden behind the language button.

**Root cause:** both controls lived in a `fixed top-4 right-4 z-50` cluster that floated *over* the page content, while `<main>` reserved no space for it. It was not just the Purchase Orders page:

| Route | Button that was covered |
|---|---|
| /orders | 餐桌 (table card action) |
| /tables | 新增餐桌 (Add table) |
| /menu | 新增菜品 (Add dish) |
| /staff | 新增员工 (Add staff) |
| /settings | 保存设置 (Save settings) |
| /inventory/orders | 新建订单 (New order) |
| /inventory/ingredients | 新增食材 (Add ingredient) |

| /promotions | 新增促销 (Add promotion) |
| /vouchers | 创建模板 (Create template) |

**10 of 13 audited routes had a primary action button covered.**

**Why the "just add some padding" fix is not enough:** the cluster was pinned to the *viewport*, so even with top padding on `<main>`, page content scrolled underneath it while scrolling. The controls had to stop floating.

**The fix (`frontend/src/App.jsx`):** the language switcher and the notification bell now live in a real app top bar — `sticky top-0 h-16`, white with a bottom border, offset by `lg:ml-64` to align with the content area. It occupies layout space, so nothing can ever end up underneath it, at any scroll position. The mobile hamburger button moved into the bar as well (it was a second floating `fixed top-4 left-4` overlay) and gained a translated `aria-label` (`layout:header.menu`).

**Verified:**
- Header-overlap audit across 14 routes: **0 overlaps**, and every page's top-right action button is visible below the bar.
- Language dropdown and notification dropdown open fully inside the viewport on both desktop (1440px) and mobile (390px); the bell dropdown stays viewport-pinned on mobile and bell-anchored on desktop.
- Full functional regression: 23/23 routes clean, 55 mutations attempted and blocked, zero uncaught exceptions; every tab on all 7 tabbed pages renders a distinct panel.

**One trap worth recording:** the first attempt used `t('header:menu')` inside `App()`, which had no `t` in scope. Plain JavaScript gives no compile-time error for this — the build passed and the app rendered a blank screen with `t is not defined` in the console. The header audit caught it immediately, but it would have been invisible in a build log.

| AI Tools tab | Endpoint | Figures & structure | Narrative |
|---|---|---|---|
| AI Insight | `POST /api/ai/insights` | program (SQL) | **MiniMax M3** |
| Menu Analytics | `GET /api/ai/menu-analytics` | program only | – |

The AI Insight tab is therefore **hybrid**: every number it shows is computed by the program, and only the written summary comes from the model. MiniMax M3 is called through `https://api.minimax.io/v1/chat/completions` with a 30-second timeout; the response's `<think>` reasoning tags are stripped before display.

**Two risks worth closing later:**
1. Every LLM call site swallows its errors. If MiniMax is unreachable, over quota, or the key is invalid, the AI Insight tab silently shows the program-generated template sentence ("During this period, you had N orders totaling $X") which reads like an insight but is not one. The fix is a `summary_source` field (`llm` / `fallback`) returned by the API and shown as a badge in the UI — the same rule that came out of the AI prediction bug: silence must never be ambiguous.
2. Two MiniMax endpoints are in use — `/v1/chat/completions` in `app/ai/minimax.py` and `app/routes/ai/__init__.py`, and the legacy `/v1/text/chatcompletion_v2` in `app/routes/competitors.py`, which also repeats the API key inline. Both still work, but they should be consolidated onto one endpoint with the key in the environment only.

**Hardening applied:** `app/ai/minimax.py` `generate_text()` now strips `<think>` reasoning tags centrally, so no caller can leak raw model reasoning into the UI.

## Phase 4 — Translating AI-generated content (28 October 2026)

The language switch previously covered only **hand-written UI copy**. Everything the
backend *generates* stayed in English, so the dashboard read as a Chinese app with an
English AI layer bolted on:

- Order Insights sentences ("Quiet day with 1 orders.")
- AI Security Alert titles and messages ("Order outside operating hours")
- Demand Forecast recommendations ("📦 Stock up on popular ingredients…")
- The weather description ("light rain") and the holiday name ("King's Coronation Day")
- The AI Tools → AI Insight narrative summary

### How it works

> **Update — 29 October 2026.** The AI Tools were added to this list: the competitor
> discovery insight and the AI pricing insights are now localized as well. Two new
> `kind` values (`competitor_insight`, `competitor_pricing`) reuse the same service.
>
> For the AI Tools the model is asked to **write the answer in the outlet's language
> directly**, instead of writing English and translating afterwards. That is one AI
> call instead of two, and it produced a noticeable speed-up. The translation service
> is kept as a safety net: if the answer still comes back in English (detected by
> checking for characters of the target script), it is translated after all.
>
> A second table, `ai_insight_cache`, caches the finished answer itself against a
> hash of the data it was derived from, so re-opening a screen or re-analysing the
> same restaurant is instant instead of another model round trip:
>
> | Column | Purpose |
> |--------|---------|
> | `kind` | `competitor_analysis` \| `competitor_pricing` |
> | `source_hash` | sha256 of the data the answer was derived from (plus a prompt version, so a prompt change invalidates the old answers) |
> | `locale` | `en` \| `zh` \| `km` |
> | `result` | the json answer |
>
> One more finding worth recording: **MiniMax-M3 is a reasoning model**, and for
> structured output it spent ~2,600 characters of `<think>` reasoning before every
> answer. Sending `"thinking": {"type": "disabled"}` with the request cut the call
> from 8.8 s to 3.5 s, with identical output. The translation service uses the same
> switch (2.3 s → 1.0 s).

The same approach the **Site App** already uses for plan and feature copy
(`website_api/app/services/translation.py`): the text is machine-translated by
**MiniMax**, cached, and falls back to the English source if the provider is
unavailable.

**Translatable text travels as a template plus values.** The dynamic values never
reach the model as prose - they are referenced by `{{placeholder}}` tokens that the
prompt pins down:

```
"High cancel rate by {{user_name}}"  +  {"user_name": "Ahmad"}
```

The model only ever sees the sentence, so staff names, menu item names, prices,
times and counts come back byte-identical. The translated template is cached in
`ai_content_translations` and the values are substituted back in per alert.

| Column | Purpose |
|--------|---------|
| `kind` | `alert` \| `insight` \| `forecast` |
| `source_hash` | sha256 of the English template |
| `locale` | `zh` \| `km` |
| `source_text` / `translated_text` | the template and its translation |
| `provider` | `MiniMax-M3` |

Because the hash is of the *template*, one sentence is translated once and reused for
every alert of that type in every outlet, and editing the template automatically
invalidates the stale translation.

### Safety rules

1. **Placeholder validation** - a translation is rejected and the English source used
   if any `{{placeholder}}` was dropped, renamed or reordered.
2. **Deduplication before the call** - 22 alerts usually share a handful of
   templates, so only the unique templates are sent to the model.
3. **English is always a valid answer** - if MiniMax is unreachable, over quota, or
   the key is invalid, the English source is returned and `translation_source` is
   reported as `fallback`, so the UI can tell a real translation from the fallback.
4. **Batch, one call** - the whole request is translated in a single provider call.

### Endpoints

| Endpoint | Parameter | Behaviour |
|----------|-----------|-----------|
| `GET /api/ai/orders/insights` | `lang=en\|zh\|km` | translates `ai_insight` |
| `GET /api/ai/security/alerts` | `lang=en\|zh\|km` | translates every alert `title` and `message` |
| `GET /api/ai/forecast/daily` | `lang=en\|zh\|km` | translates the recommendations, the weather description and the holiday name |
| `POST /api/ai/insights` | `language` in the body | MiniMax writes the summary **in that language**; the response now carries `summary_source` (`llm` or `fallback`) |

The POS authenticates with an API key, so the backend cannot tell which staff member
is browsing - the language is always passed explicitly by the client.

### Frontend

- The AI components re-fetch when `i18n.language` changes, so the content follows the
  switch immediately without a page reload.
- A request-sequence guard drops superseded responses, so a slow response from the
  previous language can no longer overwrite the new one.
- `src/utils/dateLocale.js` formats dates per locale. Khmer is handled explicitly
  because it is not present in every Chromium ICU build and silently falls back to
  English; Khmer month and weekday names are written out directly.
- The forecast confidence level ("low" / "medium" / "high") is localised through
  `forecast.confidence_<level>`.
