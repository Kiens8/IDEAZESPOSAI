## Bug Fixes (September 23, 2026)

### 1. Email Verification Status Not Updating (Critical Fix)
**Issue:** When logging in without email verification, portal showed "Active" status incorrectly  
**Root Cause:** `fetchSubscription()` was setting `emailVerified = true` whenever API returned 200 OK  
**Fix:** Fetch email verification status from `/api/auth/me` FIRST, before setting subscription state  
**File:** `/root/.openclaw/workspace/mydoc/Projects/POS_AI/site/src/app/portal/page.tsx`

**Code Change:**
```javascript
// Before (Wrong - always set emailVerified to true)
if (res.ok) {
    setEmailVerified(true)  // ❌ Wrong
}

// After (Correct - check from profile API)
const profileRes = await fetch('/api/auth/me')
if (profileRes.ok) {
    const profileData = await profileRes.json()
    const emailVerified = profileData.user?.email_verified || false
    setEmailVerified(emailVerified)  // ✅ Correct
}
```

### 2. Subscription API Endpoint Fixed
**Issue:** Frontend calling `/api/subscriptions/create` but backend endpoint is `/api/subscriptions/`  
**Fix:** Changed frontend to call correct endpoint  
**File:** `/root/.openclaw/workspace/mydoc/Projects/POS_AI/site/src/app/portal/page.tsx`

### 3. Trial/Condition Detection Fixed
**Issue:** Backend expected `trial: true` boolean but frontend sends `choice: "trial"` string  
**Fix:** Changed backend to check `sub_data.choice == "trial"`  
**File:** `/root/.openclaw/workspace/mydoc/Projects/POS_AI/website_api/app/routes/subscription.py`

### 4. Plan Display Fixed
**Issue:** Plan showing as "Plan" instead of actual plan name  
**Root Cause:** Frontend using `user.plan?.name` from localStorage instead of `subscription.plan?.name`  
**Fix:** Changed to use `subscription.plan?.name` and fixed API to return full plan object  
**Files:**
- `/root/.openclaw/workspace/mydoc/Projects/POS_AI/site/src/app/portal/page.tsx`
- `/root/.openclaw/workspace/mydoc/Projects/POS_AI/website_api/app/routes/subscription.py`

### 5. Billing Cycle Selection Reset
**Issue:** Changing billing cycle didn't reset choice selection  
**Fix:** When changing billing cycle, `choice` is now reset to `null`

## Email Verification Flow

```
1. User logs in
   ↓
2. fetchSubscription() called
   ↓
3. FIRST: Call /api/auth/me to check email_verified status
   ↓
4. THEN: Call /api/subscriptions/current to get subscription
   ↓
5. Set states:
   - emailVerified = true only if profile API confirms it
   - hasSubscription = true only if subscription exists and is active
   ↓
6. UI renders based on states:
   - !emailVerified → Show "🔒 Email Verification Required"
   - hasSubscription → Show current plan details
   - !hasSubscription && emailVerified → Show subscription wizard
```

## Upgrade Flow Restrictions (September 23, 2026)

### 1. Upper Plans Only
**Implementation:** When upgrading, only plans with higher price are shown.

**Logic:**
```javascript
// Filter plans - show only upper plans for upgrades
availablePlans.filter(plan => {
  if (hasSubscription && subscription?.plan) {
    const currentPrice = subscription.billing_cycle === 'annual'
      ? subscription.plan.price_annual
      : subscription.plan.price_monthly
    const newPrice = selectedPlan.billingCycle === 'annual'
      ? plan.price_annual
      : plan.price_monthly
    return newPrice > currentPrice  // Only show higher priced plans
  }
  return true  // Show all plans for new customers
})
```

### 2. Payment Method Lock for Stripe Customers
**Rule:** If customer is on Stripe subscription, they CANNOT switch to Pay Later when upgrading.

**Reason:** To prevent double billing - Stripe would still auto-charge even if manual invoice is created.

**Backend Protection:**
```python
# In /api/subscriptions/upgrade endpoint
if upgrade_data.payment_method == "pay_later":
    if sub.stripe_subscription_id:
        raise HTTPException(
            status_code=400, 
            detail="Cannot change from Stripe to Pay Later. Please keep Stripe for upgrades or cancel your Stripe subscription first."
        )
```

**Frontend Behavior:**
- Pay Later option is HIDDEN if `subscription.payment_method === 'stripe'`
- Shows warning notice:
  ```html
  <div class="bg-amber-50 border border-amber-200 rounded-xl p-4">
    <p class="font-semibold">⚠️ Payment Method Locked</p>
    <p>Your subscription is managed via Stripe. Upgrades must also use Stripe payment.</p>
  </div>
  ```

### 3. Upgrade vs New Subscription Detection
**Frontend Logic:**
```javascript
const isUpgrade = hasSubscription && subscription?.id

if (isUpgrade) {
  // Call upgrade endpoint
  POST /api/subscriptions/upgrade
} else {
  // Call create endpoint
  POST /api/subscriptions/
}
```

### Upgrade Flow Summary

| Scenario | Plans Shown | Payment Methods |
|----------|-------------|-----------------|
| New customer (no subscription) | All plans | Pay Later, Stripe |
| Upgrade from Pay Later | Upper plans only | Pay Later, Stripe |
| Upgrade from Stripe | Upper plans only | Stripe only (Pay Later hidden) |

### Upgrade Redirect Behavior

**Before:** For existing Stripe customers, upgrade modified subscription directly without showing checkout.

**After:** All Stripe upgrades redirect to Stripe checkout with prorated amount displayed.

**Flow:**
1. Customer selects upgrade plan + Stripe payment
2. Redirects to Stripe checkout with prorated charge shown
3. Customer sees "Upgrade to {Plan} - Proration" line item
4. After payment → webhook updates invoice with Stripe URLs
5. Customer can view/download Stripe invoice in billing page

## Reactivation Flow (September 23, 2026)

### Overview

When a customer with a cancelled or expired subscription returns, they can **reactivate** by creating a new subscription. This follows Option 2 design - a NEW subscription is created (not resume old one).

### Backend Changes

**File:** `/root/.openclaw/workspace/mydoc/Projects/POS_AI/website_api/app/routes/subscription.py`

**Reactivation detection:**
```python
# Check for cancelled/expired subscription (for reactivation)
old_subscription = db.query(Subscription).filter(
    Subscription.customer_id == current_user.id,
    Subscription.status.in_(["cancelled", "expired"])
).first()

is_reactivation = old_subscription is not None
```

**Key points:**
- Old subscription is NOT modified (stays cancelled/expired)
- New subscription is created with fresh period dates
- POS data is PRESERVED (outlets, orders, menu items intact)
- Customer can choose same or different plan

### Admin API Changes

**File:** `/root/.openclaw/workspace/mydoc/Projects/POS_AI/website_api/app/routes/admin.py`

## $0 Invoice Cron Job (September 23, 2026)

### New Cron Job: `mark_zero_paid`

**Purpose:** Mark all $0 pending invoices as paid (for trials and free plans).

**Location:** `/root/.openclaw/workspace/mydoc/Projects/POS_AI/website_api/scripts/send_notifications.py`

**Function:**
```python
def mark_zero_invoices_paid(db: Session):
    """
    Mark all $0 pending invoices as paid.
    Per renewal system design:
    - Trial and Free plan invoices are $0
    - Cron marks these as paid automatically
    """
    pending_zero = db.query(Invoice).filter(
        Invoice.status == 'pending',
        Invoice.amount == 0
    ).all()
    
    for invoice in pending_zero:
        invoice.status = 'paid'
    
    db.commit()
```

**Cron Execution Order:**
1. `mark_zero_invoices_paid` - Marks $0 pending invoices as paid
2. `process_trial_end` - Process trial endings
3. `generate_renewal_invoices` - Generate renewal invoices
4. Other checks (expired, cancelled, reminders...)

**CLI Flag:** `--mark-zero`

### Updated Renewal System Flow

```
1. Trial/Free Plan Subscription Created
   ↓
2. $0 invoice created (status: pending)
   ↓
3. Cron runs → marks $0 invoice as PAID
   ↓
4. Trial ends → generates first paid invoice
```

This aligns with the documented renewal system where cron job handles $0 invoice status updates.
