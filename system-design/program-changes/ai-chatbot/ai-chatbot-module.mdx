# AI Chatbot Module

## Overview

The AI Chatbot module provides intelligent customer and staff assistance within the POS system. It supports multiple languages, custom greetings, and configurable behavior.

## Features

- **Multi-language Support**: English, Chinese, Malay, Khmer, Multilingual
- **Custom Bot Identity**: Configurable bot name and greeting message
- **Enable/Disable Control**: Toggle chatbot availability per outlet
- **Role-based Responses**: Different behavior for customer, staff, manager, admin
- **Intent-based Processing**: Recognizes orders, menu requests, reservations, etc.
- **AI Fallback**: Uses MiniMax for complex queries (admin mode)

## API Endpoints

### POST /api/chatbot/

Send a message to the chatbot.

**Request Body:**
```json
{
  "message": "string",           // User message
  "chatbot_type": "string",     // "customer", "staff", "manager", "admin"
  "outlet_id": "number",        // Outlet ID for settings lookup
  "language": "string"          // Language code (optional, overrides settings)
}
```

**Response:**
```json
{
  "intent": "string",           // Detected intent
  "response": "string",         // Bot response text
  "action": "string|null",      // Optional action hint
  "data": "object|null"        // Optional additional data
}
```

**Error Responses:**
- `403`: Chatbot is disabled for this outlet

### GET /api/chatbot/greeting

Get translated greeting message.

**Query Parameters:**
- `outlet_id` (required): Outlet ID for settings lookup
- `language` (optional): Language code (default: "en")

**Response:**
```json
{
  "greeting": "string",         // Translated greeting text
  "bot_name": "string"          // Bot name from settings
}
```

### GET /api/chatbot/quick-replies

Get localized quick reply buttons.

**Query Parameters:**
- `language` (optional): Language code (default: "en")

**Response:**
```json
{
  "quick_replies": [
    {"label": "string", "message": "string"},
    ...
  ]
}
```

### GET /api/chatbot/test

Test endpoint to verify chatbot is running.

## The intents, the roles and the outlet (fixed Nov 4, 2026)

Kens clicked the **"🪑 Tables Served"** chip as a **manager** and the bot answered
*"🙃 I'm not sure I understand that question."* - as the **admin** the same question was
answered fine.

**It was not the role.** The chip sends **"How many tables are served?"** - and that string
matched **no pattern**: the old `tables_served` pattern only knew *"tables served"* and *"tables
is served"* (no **"are"** ✗). The intent fell through to `general` ✗, and from there the two
roles diverged:

| Role | `general` | What the customer saw |
|---|---|---|
| **admin** | the **AI fallback** ✓ | MiniMax answers it (with the outlet's data ✓) |
| **manager** | the **canned help** ✗ | *"I'm not sure I understand that question."* ✗ |
| **staff** | the canned help ✓ | (the chatbot is manager+ only ✓ - `ai:read` ✓) |

So the admin's chatbot worked **because of the AI fallback**, not because the admin can do
more - the intent never matched for anybody ✓.

### The fixes

1. **The patterns speak like people.** Every management intent now matches the natural
   phrasing - *"how many tables are served?"* ✓, *"how many tables are occupied?"* ✓,
   *"occupied tables"* ✓, *"how many orders are pending?"* ✓, *"how many orders are in the
   kitchen?"* ✓, *"how many orders are ready?"* ✓, *"how many did we make today?"* ✓.
2. **The order-count intents outrank the generic `order` intent** (score 0.9 ✓) - otherwise
   *"how many orders are ready?"* matched `order` (the bare word *"order"*) ✗.
3. **The manager gets the AI fallback too** ✓ - a manager has `reports:*` ✓, so the data in
   the fallback is data they may see ✓. The **staff must not** ✗ (the fallback carries the
   sales ✗ and they have no `reports:*` ✓).
4. **The customer app has its own intent list** ✓ - it used to inherit the **staff's** list ✓,
   and the staff may now ask about the tables ✓ - a guest may not ✗.
5. **The counts are the outlet's.** `_handle_tables_served` ✓, `_handle_pending_orders` ✓,
   `_handle_kitchen_status` ✓, `_handle_ready_orders` ✓ and `_handle_completed_orders` ✓
   counted **every tenant's** orders ✗ - a restaurant saw another one's numbers ✗. They are
   filtered by `outlet_id` now ✓ (`Table.outlet_id` for the tables ✓).

## The admin's chatbot gets the group's data (fixed Nov 4, 2026)

The admin asked *"Now we have how many outlets?"* and the bot answered *"The number of outlets
isn't available in the current data"* - and then quoted the **tables**, which it did have.

**Why:** the AI fallback's context held **one outlet's** numbers (today's sales, the pending
orders, the tables, the popular items) - **nothing about the group** ✓. The outlet count was
never in it ✓, so the model said so ✓ (it did NOT invent a number ✓ - it quoted the tables it
really had ✓).

### What the admin's chatbot knows now

| In the context | What it is |
|---|---|
| **the outlets** | the count, the names and **per outlet**: the tables, the staff, today's sales and today's orders ✓ |
| **the staff count** | the group's active staff accounts ✓ |
| today's sales | the revenue, the orders, the average order value ✓ |
| 7 days / 30 days | the same three ✓ |
| the pending orders | the outlet's ✓ |
| the tables | occupied / total / available ✓ |
| the popular items | the top five of the last 7 days ✓ |

The **tenant** is the outlet's `customer_id` ✓ (the restaurant group ✓) - the same rule the
rest of the backend uses ✓.

### A new intent: `outlets`

*"How many outlets do we have?"* is answered **exactly** ✓ - the count, and each outlet with
its tables, its staff and today's sales ✓ (the manager may ask ✓, the staff may not ✓).

A **comparison** (*"which outlet is doing better?"*) is deliberately **not** an intent ✓ - it
goes to the AI ✓, which has the per-outlet numbers and can reason about them ✓:

> *"Neither outlet is outperforming the other today - both have $0 sales and 0 orders. However,
> Demo Cafe 1 is more operational, with 14 tables and 2 staff, while Kens SS17 has 0 tables."* ✓

### The prompt's rules about the data

The system prompt now says ✓:
1. the numbers are the whole truth - if the answer is not in them, say it is not available ✓,
   never estimate, never guess, never invent a number ✓;
2. a question about the **group** uses the OUTLETS lines ✓ - not the single outlet's numbers ✓;
3. a zero is a zero ✓ - do not soften it ✓.

### Two more traps

- **`"hi"` matched `"which"`.** The greeting pattern was the bare word `hi` ✓, so *"which
  outlet is doing better?"* was a **greeting** ✓ (and so were *"this"* ✓ and *"chips"* ✓). The
  patterns have word boundaries now ✓ (`\bhi\b` ✓, `\bhello\b` ✓, `\bhey\b` ✓).
- **The `staff` intent was the guest's.** *"I need a waiter"* is a **guest's** request ✓, but
  the admin's *"How many staff do we have?"* got the guest's reply (*"just wave and our team
  will assist you"* ✗). The intent now answers **both shapes** ✓: a **count** (*"how many"*)
  gets the group's staff count ✓; a **request** gets the guest's reply ✓. The staff role no
  longer has the intent ✓ (the guest keeps it ✓).

## The tool layer - the chatbot queries the database (Nov 4, 2026)

Kens' decisions ✓:

1. **Tenant wide with an outlet filter** ✓
2. **Read only** ✓
3. **Admin only** ✓ (the manager's chatbot keeps the intents and the AI fallback ✓)
4. **Aggregated** ✓ (counts and sums ✓ - never a guest's name ✓)

### The shape

```
the question
   ↓
the intents (fast, free, exact) - "how many tables are served" ✓
   ↓ (no intent matched, or the question is analytical)
MiniMax-M3 gets a CATALOGUE of read-only tools ✓
   ↓
the model calls them: get_sales({period, outlet}) ✓
   ↓
the backend runs them (tenant-scoped ✓) and hands the JSON back ✓
   ↓
the model writes the answer in plain English ✓ - with the numbers it actually queried ✓
```

MiniMax-M3 **does** support function calling ✓ (the OpenAI-compatible `tools` + `tool_calls`
shape ✓) ✓.

### The tools (`backend/app/ai/chatbot_tools.py` ✓)

| Tool | Answers |
|---|---|
| `get_sales` | the revenue and the order count of a period ✓ |
| `get_orders` | the counts by status, by type and by hour ✓ |
| `list_outlets` | the outlets: their name, their currency, their size ✓ |
| `compare_outlets` | the same numbers for every outlet ✓ |
| `get_tables` | the occupancy right now ✓ |
| `get_menu_performance` | the best and the worst sellers ✓ |
| `get_staff` | the headcount per outlet and per role ✓ |
| `get_customers` | the guests served - counts only ✓ |
| `get_payments` | the payment mix ✓ |
| `get_alerts` | the recent AI alerts ✓ |

### The rails

- **The tenant comes from the session** ✓ - the model may ask for an **outlet** ✓, and the
  outlet must belong to the tenant ✓. *"VARMAN"* (another tenant's outlet ✗) is **refused**
  with the group's outlet names in the refusal ✓.
- **Read-only** ✓ - there is no tool that writes anything ✓; the model picks a tool and passes
  parameters ✓ - it never writes SQL ✓.
- **Aggregated** ✓ - the tools return counts and sums ✓ - no guest's name ✓, no staff's name ✓.
- **The money is grouped per currency and never added up** ✓ - Demo Cafe 1 bills in USD ✓ and
  Kens SS17 in MYR ✓, and they are in the **same group** ✓ - so every figure carries its own
  currency ✓ and the two are never summed ✓. The AI says so ✓:
  *"the two outlets run in different currencies (USD vs MYR), so I can't rank them head-to-head
  on revenue"* ✓.
- **The answer is traceable** ✓ - the tools that ran come back in the API's `data.tools_used` ✓.

   matched and the handler always reported today ✓. The sales and the completed-orders
   handlers now **parse the period** from the question ✓ (today ✓, yesterday ✓, last 7 days ✓,
   this week ✓, last 30 days ✓, this month ✓, this year ✓).
2. **The currency** ✓ - the chatbot follows the **outlet's own** settings ✓ (Demo Cafe 1 is `$`
   ✓, Kens SS17 is `RM` ✓) and every figure now names its currency code ✓.
