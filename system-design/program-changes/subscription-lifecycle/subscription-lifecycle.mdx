# Subscription Lifecycle and Access

**Date:** November 2, 2026  
**Status:** Approved — **all five phases are done and live** (November 2, 2026)  
**Scope:** the website API (the billing system) and the POS login gate  
**Files:** `website_api/app/services/subscription_access.py` (new), `website_api/app/services/payment_providers.py` (new), `website_api/app/services/subscription_notify.py` (new), `website_api/app/routes/admin.py`, `website_api/app/routes/subscription.py`, `website_api/app/routes/webhooks.py`, `website_api/scripts/send_notifications.py`, `backend/app/services/subscription_gate.py` (new), `backend/app/core/subscription_cache.py` (new), `backend/app/middleware/subscription.py` (new), `backend/app/routes/internal.py`, `backend/app/routes/auth.py`

## Overview

A restaurant may use the POS when its **subscription says it may**. The plan
lives in the website API (the billing system's database); the POS backend asks
it at every login and refuses the login when the answer is no.

The intent is simple and correct:

> **When the paid period ends and the subscription is not renewed, the user
> must not be able to sign in to the POS again.**

So the design is already right — **the POS login gate is what does not
implement it.** This document describes the current behaviour, the
disagreements between the billing system and the POS, and the model that
fixes them.

## The decisions (Kens, November 2)

| # | The question | The answer | The source |
|---|---|---|---|
| 1 | **The trial** — the trial invoice is due immediately, or the trial gets the grace? | **Scenario 12 — Trial: Not Paid.** At the trial end the first paid invoice is created, `status` stays `trial`, **the access continues for the grace**, and when the grace runs out the invoice is forgiven → `expired` → **blocked** | `renewal-system.mdx` → Scenario 12 |
| 2 | **A cancellation** — when does the access actually stop? | **Scenario 7 — Cancel: Without Payment (Within Grace Period).** The cancellation is recorded, but it does **not** protect from non-payment: with a paid period the access lasts **until the period end**, without a payment it lasts only **until the grace ends**, then the subscription becomes `expired` and the access is blocked | `renewal-system.mdx` → Scenario 7 + the Cancellation Decision Table |
| — | **The grace period** | the admin app's setting **`payment_due_days`** (14 today) — read live, never hardcoded | `renewal-system.mdx` → Grace Period Settings |
| — | **The frontend POS login checking** | it implements the renewal system's **Access Decision Table** — the POS gate is not allowed to have its own rules | `renewal-system.mdx` → Access Control Logic |

**The one rule behind all of it:** the invoice's `due_date` already contains
the grace (a subscription on day 0 has an invoice due on day 14). The access
is allowed while the invoice is unpaid **and** its due date has not passed;
when the due date passes unpaid, the cron forgives the invoice, the
subscription becomes `expired` and the access is blocked.

**Two things the renewal system said that the code did not do** *(both fixed on November 2, 2026)*

- *"Cancellation does NOT protect from non-payment. At Day 14, the
  subscription becomes EXPIRED."* — the cron **skipped** the cancelled
  subscriptions, so they never reached `expired`. → phase 3
- *"Payment extends nothing — the period end date stays fixed."* — a resume
  must not invent a new period. → the resume route never moves
  `current_period_end` ✓ (verified: the period end stayed 2026-12-02)

## How it works now (after the five phases)

### The stored state

`subscriptions` (the website API's database):

| Field | Meaning |
|---|---|
| `status` | `active` · `trial` · `cancelled` · `expired` |
| `payment_status` | `not_required` · `pending` · `paid` · `failed` |
| `current_period_end` | when the paid period ends |
| `trial_ends_at` | when the trial ends |
| `cancelled_at` | when the customer cancelled |
| `payment_due_date` | when a "pay later" invoice is due |

`invoices` carry their own `status` (`pending` / `paid` / `forgiven`) and
`due_date`. **The invoice's `due_date` is the grace:** it is
`period_start + payment_due_days`, so an unpaid invoice blocks the access
exactly when the grace runs out.

### The daily cron (09:00, `send_notifications.py`)

Runs in this order:

1. `mark_zero_invoices_paid` — a $0 invoice (a trial, a free plan) counts as paid
2. `process_trial_end` — a trial that ended gets its first paid invoice;
   **the status stays `trial`**; the invoice's `due_date` is
   `trial_ends_at + payment_due_days` → the grace ✓ (Scenario 12)
3. `generate_renewal_invoices` — an **active** subscription whose `current_period_end` has passed gets its next invoice (due at `period_end + grace`) and the period rolls forward
4. `check_expired_subscriptions` — a pending invoice past its due date → the invoice is forgiven and the subscription becomes **`expired`** — the **cancelled** subscriptions are **not** skipped any more ✓ (phase 3)
5. `check_cancelled_subscriptions` — a cancelled subscription past its period end → it becomes **`expired`** ✓ (phase 3)
6. the notices (the trial-ending notices, the billing reminders, the final reminders)

### The login gate (the POS backend, `backend/app/routes/auth.py`)

At login the POS backend asks the website API for the tenant's **effective
access** (`GET /api/admin/customer/{id}/subscription` → the `access` object)
and enforces that answer. The gate has **no rules of its own** any more.

The seven conditions it used to apply are still in the code — as the
**fallback** for an older website API that answers without an `access`
object:

| # | Condition | Result |
|---|---|---|
| 1 | no subscription, or `status == "none"` | **blocked** — "No active subscription found" |
| 2 | `status == "cancelled"` | **blocked** — "Your subscription has been cancelled" |
| 3 | `status == "expired"` | **blocked** — "Your subscription has expired" |
| 4 | `payment_status == "overdue"` (a pending invoice past its due date) | **blocked** — "Account suspended due to overdue payment" |
| 5 | a `trial` whose `trial_ends_at` has passed | **blocked** — "Your trial period has ended" |
| 6 | a `pending` payment past its due date | **blocked** — "Payment is overdue" |
| 7 | a trial ending within 3 days, a payment due soon | a **warning**, the login goes through |
| — | the website API cannot be reached | **allowed with a warning** (fail-open — availability wins) ✓ |

So the end-of-period path today is:

```
period ends → the renewal invoice is created (14-day grace)
             → the subscription stays "active" and the login works
             → the invoice is unpaid after the grace
             → the cron sets "expired"
             → the login is blocked  ✓
```

**That part is right.** Both live tenants are healthy: Demo until 2027-09-17,
AES until 2026-11-30 (its renewal invoice lands on the 30th, the grace runs to
December 14).

### What the gate could not see before (it can now)

Before phase 1 the website API's endpoint returned `status`,
`payment_status` (`active` / `pending` / `overdue`), `due_date`,
`overdue_invoices` and `latest_invoice_due_date`. It did **not** return:

- **`trial_ends_at`** → the gate's condition 5 was **dead code**: it never
  fired, so a trial was never blocked by the gate (the trial was blocked
  later, when the cron flipped the status to `expired` — which is why the
  trial accidentally behaved like Scenario 12).
- **`current_period_end`** → the gate could not know when the paid period
  ends, so it could not implement "cancelled + paid → the access lasts until
  the period end" (Scenario 6).
- the **real payment state of the period** → `payment_status` was `active`
  for a paid subscription, never `paid`, so the gate could not tell
  Scenario 6 (cancel with payment) from Scenario 7 (cancel without payment).

**Now it returns** `access`, `payment_state`, `current_period_end`,
`trial_ends_at` and `grace_days` — so the gate asks one question and gets
one answer. That is why the decision belongs in the website API, not in the
gate.

## The disagreements (all resolved)

> This section describes what was wrong **before** the five phases. Every
> item below was fixed on November 2, 2026 — the text is kept so the reason
> for the model stays readable.

### 1. A cancellation cuts the access off immediately — the renewal system says otherwise

`POST /cancel` sets `status = "cancelled"` the moment the customer clicks.
The login gate blocks on `cancelled` → **instant lockout**. But the renewal
system's Cancellation Decision Table says:

| Payment | Cancel when | Result |
|---|---|---|
| **Paid** | any time | **the access lasts until the period end**, then blocked (Scenario 6) |
| **Not paid** | before the grace ends | **the access lasts until the grace ends**, then the subscription becomes **EXPIRED** and the access is blocked (Scenario 7) |
| **Not paid** | after the grace ended | already EXPIRED, the cancellation has no effect (Scenario 8) |

The route's own docstring, its response body and its cancellation email say
*"Access continues until period end"* — the same wording as Scenario 6, but
without Scenario 7's **"cancellation does not protect from non-payment"**.

The two halves of the product disagree with each other. A customer who
cancels on day 20 of a 30-day period loses the ten days they have already
paid for. And a customer who cancels without paying keeps the access for the
**whole grace** — which today they do not get either: they are locked out on
the cancellation day.

The cron makes it worse: `check_expired_subscriptions` **skips** the cancelled
subscriptions (*"letting expire naturally"*), so a cancelled subscription
never becomes `expired` — it stays `cancelled` forever, and the "expired"
reporting and the admin's own state never see those tenants.

### 2. The trial: the billing code already follows Scenario 12 — the gate does not

Scenario 12 says:

```
Day 30:  Trial ends
           Invoice #2 created for the paid version: $XX, status = pending
           subscription_status = trial  (the grace period starts)
Day 44:  Grace period ends, no payment
           Invoice #2 status → forgiven
           subscription_status = expired
           Access = BLOCKED
```

The billing code does exactly this: `process_trial_end()` creates the invoice
with `due_date = trial_ends_at + payment_due_days` (14) and keeps the status
`trial`; the cron forgives the invoice when the due date passes and flips the
status to `expired` → the gate blocks ✓.

So the trial case is **right today** — but only because condition 5 is dead
code (the endpoint does not return `trial_ends_at`). The moment somebody
"fixes" the endpoint to return `trial_ends_at`, the gate starts blocking the
trial on the trial-end day and Scenario 12 breaks.

> **Note:** the renewal design's prose line *"On trial end: … invoice due
> immediately"* is superseded by Scenario 12 — the invoice is due immediately
> **and the access lasts for the grace**. Both are true: the invoice is
> created and payable at once, the lockout waits for the grace to end.

### 3. The status is only checked at login

The subscription was read once, when the user signed in. An open session kept
working for up to **12 hours** after a cancellation or an expiry.

This was the same weakness the plan features had until November 2 (see
`ai-feature-gating.mdx`): the entitlement was a snapshot. The features came
from a pushed cache — the subscription status did not.

**Now:** the subscription state is a pushed cache too, and the middleware
checks it on **every** request (phase 5) — an open session is affected
within seconds.

### 4. A cancelled subscription never becomes "expired"

`check_cancelled_subscriptions` found the cancelled subscriptions past their
period end and **only printed a line**. The status stayed `cancelled`
forever, so the "expired" reporting and the admin's own state never saw
those tenants.

**Now:** it writes `expired` (phase 3).

### Also worth knowing: cancelling does not cancel the Stripe subscription

`POST /cancel` never called Stripe. The webhook *did* handle
`customer.subscription.deleted` ✓ — but nothing ever cancelled the Stripe
subscription, so the event never fired and **the customer kept being
charged** after cancelling in the app.

**Now:** the cancel route tells the payment provider to cancel at the period
end, and the resume route tells it to charge again (phase 4). The Stripe
webhook learned `customer.subscription.updated`, so the two sides agree even
when the change came from the Stripe dashboard.

## The proposed model

### One place decides access

A single function computes the tenant's **effective access** from the stored
state. The login gate asks it; the cron asks it; the admin panel can show it.
Nobody decides on their own.

```python
def effective_access(subscription, invoices, now) -> Access:
    """active | trial | grace | blocked - and the reason why."""
```

The rules — **the renewal system's Access Decision Table**, with the grace
from the admin setting:

| Stored state | Payment | Effective access | Why |
|---|---|---|---|
| no subscription | — | **blocked** | they never subscribed |
| `expired` | — | **blocked** | the grace ran out |
| `active` | paid | **active** | ✓ |
| `active` | pending, the invoice not yet due | **active** + a warning | the renewal is pending |
| `active` | pending, the invoice past its due date | **blocked** | the grace ran out (the cron forgives the invoice → `expired`) |
| `cancelled` | **paid** | **active** until `current_period_end` + a warning ("your plan ends on the 30th") | they paid for the period (Scenario 6) |
| `cancelled` | **not paid** | **active** until the invoice's due date (the grace end), then **blocked** | the cancellation does not protect from non-payment (Scenario 7) |
| `trial` | — | **trial** + a warning near the end; **active** during the grace after the trial end | the invoice is created at the trial end and the grace starts (Scenario 12) |
| `trial`, the grace has ended, the invoice unpaid | — | **blocked** | the cron forgives the invoice → `expired` |
| `expired` **and a new active subscription exists** | — | **active** | reactivated (Scenario 9/10) |

**One grace rule for everything, and it is the admin's setting.** The grace
period is `payment_due_days` from the admin app's settings (14 today) — read
live, never hardcoded. The renewal grace, the trial grace and the grace after
a cancellation are the same value.

### The cancellation records the intent, the state stays honest

No schema change is needed:

- the cancellation keeps writing `status = "cancelled"` and `cancelled_at` ✓
- the **effective** access reads the payment and the invoice's due date →
  a paid period lasts until the period end (Scenario 6), an unpaid one only
  until the grace ends (Scenario 7) ✓
- the cron forgives the unpaid invoice of a cancelled subscription at the
  grace end and flips the status to **`expired`** ✓ (the missing step, and it
  makes the reporting correct)

The Stripe subscription is cancelled with `at_period_end=True` ✓ → the
customer is not charged again, and the billing stops at the same moment the
access stops.

### A resume does not invent a period

`POST /resume` today flips `status` back to `active` and leaves
`current_period_end` alone — which may be in the past. That is a subscription
in name only: the renewal cron immediately invoices a period that has already
ended.

Following Scenario 7 and the renewal system's *"payment extends nothing — the
period end date stays fixed"*:

- a **resume** restores the access to the period that was paid for; it does
  **not** create a fresh period and it does **not** move `current_period_end`
  ✓
- the outstanding invoice stays as it is, with its due date (the grace) — the
  resume does not buy the customer extra time
- if the grace has already run out (the subscription is `expired`), the
  customer is **reactivated**, not resumed: a **new** subscription with a
  fresh period, the old one archived, and the POS data preserved
  (Scenarios 9/10 and the Reactivation Flow)

### The status is checked live, like the features

The same pushed-cache pattern as the plan features:

- the website API pushes `POST /internal/subscription-changed/{customer_id}`
  after every state change (cancel, resume, upgrade, the Stripe webhook, the
  cron)
- the POS backend keeps a small cache of the subscription state per tenant
- the login gate reads the cache ✓ → an open session is affected within
  seconds, not within 12 hours

The login gate stays the place where the decision is **enforced** — the cache
only tells it what the truth is now.

### What phase 1 and 2 built

**The website API — `app/services/subscription_access.py` (new)**

```python
effective_access(subscription, invoices, now, grace_days, warning_days) -> Access
```

One function, one place. It reads the stored state and returns the answer:

| Field | Meaning |
|---|---|
| `state` | `active` · `trial` · `grace` · `blocked` |
| `allowed` | may the tenant use the POS? |
| `reason` | the machine code (the gate logs it) |
| `message` | what the user is told when it is blocked |
| `warning` | the soft warning (a trial ending, a payment due, a plan ending) |
| `access_until` | when the access ends |
| `grace_days` | the grace that was applied |

The grace and the warning window are **read live** from the admin app's
settings (`payment_due_days`, `overdue_warning_days`) — the caller passes
them in, the function never hardcodes them.

**The endpoint** — `GET /api/admin/customer/{id}/subscription` now also
returns `access`, `payment_state`, `current_period_end`, `trial_ends_at` and
`grace_days`. The old fields (`status`, `payment_status`, …) stay exactly as
they were, so nothing else breaks.

**The POS gate — `app/services/subscription_gate.py` (new)**

```python
check_subscription_access(data, warning_days, warning_days_fetcher) -> GateResult
```

The gate reads the answer and enforces it. The old seven conditions are the
**fallback** inside the same function — they are only reached when the
website API answers without an `access` object (an older website API).

### Two bugs the rewrite found

1. **The eight-hour skew.** The website API stores its dates in **UTC**
   (`datetime.utcnow()`); the gate compared them with `datetime.now()` — the
   server's **local** time, which is `+08` in Malaysia. Every deadline was
   eight hours early: the login was refused eight hours before the payment
   was actually due. The decision now happens in the website API, in UTC,
   once.
2. **The truncated days.** `(due_date - now).days` truncates — a payment due
   in **two hours** has `0` days left, so the old code treated it as
   **overdue** and refused the login. The same bug applied to a trial that
   was about to end. The days are now rounded **up**, and the "is it over"
   test is an exact comparison.

### What phase 3, 4 and 5 built

**Phase 3 — the cron keeps the state honest**

`check_expired_subscriptions` no longer skips the cancelled subscriptions:
a cancelled subscription whose invoice is unpaid past its due date is
**forgiven** and becomes **`expired`** (Scenario 7 — the cancellation does
not protect from non-payment).

`check_cancelled_subscriptions` no longer only prints: a cancelled
subscription whose **paid** period has ended becomes **`expired`**
(Scenario 6). A cancelled subscription whose invoice is still inside the
grace is left alone — the access continues.

**Phase 4 — the cancellation reaches the gateway**

`app/services/payment_providers.py` (new) — one interface, three gateways:

```python
provider = get_provider(sub.payment_provider)   # stripe | hitpay | payway
provider.cancel_at_period_end(sub)
```

The subscription code never talks to a gateway directly. `subscriptions`
gained a **`payment_provider`** column (default `stripe`).

The cancel route tells the provider; the resume route tells it to charge
again. A gateway that could not be reached is **logged, not fatal** — the
local state is already correct (the customer keeps the access until the
period end), so a Stripe outage must not fail a cancellation.

The Stripe webhook learned the `customer.subscription.updated` event: the
`cancel_at_period_end` flag sets the local status to `cancelled` (and back
to `active` when the customer comes back). Without it the POS and Stripe
disagreed about whether the customer was still subscribed.

**Phase 5 — the pushed cache**

The website API pushes the change; the POS backend refreshes what it knows:

- `website_api/app/services/subscription_notify.py` (new) — the notifier
  (fire and forget, it never breaks the billing flow).
- `backend/app/core/subscription_cache.py` (new) — the cache, filled **on
  demand** and pushed. The TTL (2 minutes) is only the safety net for a
  lost notification.
- `backend/app/services/subscription_state.py` (new) — the reader (the
  website API over loopback).
- `backend/app/routes/internal.py` — `POST /internal/subscription-changed`
  and `GET /internal/subscription-cache`. The plan notification invalidates
  the subscription cache too — a plan change is usually a subscription
  change.
- `backend/app/middleware/subscription.py` (new) — **every** request of a
  signed-in member of staff checks the tenant's access from the cache. An
  open session is affected within seconds, not within twelve hours.

Two rules keep the middleware safe: it **never** calls the website API (a
request must not wait for the network) and it **never** blocks a request it
cannot answer (the cache is empty → the request goes through).

### The payment providers (phase 4)

The cancellation has to reach the **payment provider**, and there will be
more than one:

- **Stripe** — the current one.
- **HitPay** — Malaysia.
- **PayWay** — Cambodia.

So the cancellation must not be written against one gateway's API. The
phase 4 design keeps the provider behind one interface — "cancel the
subscription at the period end" — and each provider implements it. The
subscription's `stripe_subscription_id` becomes a provider reference with a
provider field, and the renewal/webhook code reads it the same way.

That is how it is built: `payment_providers.py` has a `StripeProvider`
(implemented), a `HitPayProvider` and a `PayWayProvider` (the interface is
there, the gateway call is not — they say so instead of pretending).

**The HitPay and PayWay integration itself is a separate task** — it comes
with the site apps.

## The risks

| Risk | Mitigation |
|---|---|
| A customer loses access earlier than intended | the effective access is **never stricter** than the stored state today — every change makes it *more* permissive for the cancellation and trial cases |
| The grace becomes a free window | one rule, measured from the moment the period ends, and the trial case now matches the billing system's own design |
| The live cache locks someone out on a technicality | the cache falls back to the last known state, and the login gate keeps its fail-open behaviour when the website API is unreachable |
| The Stripe change double-charges or stops the billing wrongly | the cancellation is `at_period_end=True` — the billing stops exactly when the access ends ✓ |
| The gate and the billing system disagree | the gate has **no rules of its own** any more — it enforces the website API's answer, and the old conditions are only a fallback for an older website API ✓ |
| A deadline is read in the wrong timezone | the decision happens in the website API, in UTC, once — the POS no longer does date math ✓ |

## The decisions (all of them)

1. **The trial** — **Scenario 12**: the invoice is created at the trial end,
   the status stays `trial`, the access continues for the grace
   (`payment_due_days`), and the grace running out forgives the invoice →
   `expired` → blocked ✓
2. **A cancellation** — **Scenario 7** + Scenario 6: paid → the access lasts
   until the period end; unpaid → the access lasts until the grace ends and
   the subscription then becomes `expired` ✓
3. **A resume** — no fresh period, the period end stays fixed; a reactivation
   (after the grace) is a **new** subscription with the POS data preserved ✓
4. **The grace period** — the admin app's setting `payment_due_days` (14
   today), read live. One value for the trial, the renewal and the
   cancellation ✓
5. **The warning period** — the admin app's setting `overdue_warning_days`
   (7 today), the same window the billing reminders already use ✓
6. **The POS login checking** — it implements the renewal system's **Access
   Decision Table**; the gate does not have rules of its own ✓

**Noted, not changed:** the renewal design contradicts itself on one line —
*"Payment received during grace: extend period from the original end date"*
against *"Payment extends nothing — the period end date stays fixed"* in the
same box. The implemented behaviour is **the period end stays fixed** (per
`proposed-renewal-updates.mdx`, DONE) ✓.
