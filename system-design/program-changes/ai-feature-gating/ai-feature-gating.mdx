# AI Feature Gating and Tenant Isolation

**Date:** November 2, 2026  
**Status:** Approved — the four plan rules are decided (November 2); ready for implementation  
**Scope:** `backend/app/routes/ai/*`, `ai_chatbot.py`, `ai_forecast.py`, `ai_orders.py`, `ai_search.py`, `ai_security.py`, `competitors.py`, `chatbot.py` — 61 routes

---

## Overview

The POS AI family is the last part of the API that answers *"who may call this, and whose data may it touch?"* with only half an answer. The inventory family was fixed on November 1 (52 routes, 7 routers). The AI family was left behind.

Two gates exist in the system today:

| Gate | Question it answers | Source of truth |
|---|---|---|
| **Role / permission** | May this *person* (or key) touch this kind of data? | `ROLE_PERMISSIONS` in `backend/app/middleware/auth.py` |
| **Plan / feature** | Did this *restaurant* buy this capability? | the subscription plan, stamped into the session as `feat` at login |

A third, equally important question has no answer at all on these routes:

| Missing gate | Question it answers | Today |
|---|---|---|
| **Tenant / resource** | Whose *rows* may this request read or write? | **not implemented on any of the 61 AI routes** |

This document proposes closing all three gaps as **one change set (A + B + C)**.

---

Live evidence — a tenant on the **Starter** plan (AES, tenant 3):

```
GET  /api/ai/insights              -> 403  This feature is not included in your plan: AI Insights
GET  /api/ai/forecast/daily        -> 200  ← should be refused

GET  /api/ai/customer-insights/1   -> 200  ← should be refused
```

The 14 competitor-analysis routes are the sharpest case: **Competitor Analysis** is an Enterprise-plan feature, and a Starter tenant can call it today.

### Finding 2 — the AI family has no tenant isolation at all

None of the six AI routers import `app.core.tenant`. The `outlet_id` arrives as a query parameter and is used to read data directly.

Live evidence — AES (**tenant 3**) reading Demo (**tenant 1**) data by asking for `outlet_id=1`:

```
GET /api/ai/forecast/daily?outlet_id=1   -> 200   Demo's sales forecast
GET /api/ai/orders/insights?outlet_id=1  -> 200   Demo's order insights
GET /api/ai/security/alerts?outlet_id=1  -> 200   Demo's security alerts (alert id 66)
GET /api/ai/customer-insights/1          -> 200   Demo's customer insights (89 orders)
```

**The plan gate would not have caught this.** Demo is on the Enterprise plan, so its plan legitimately includes every AI feature. This is a pure isolation failure, and it is the more serious of the two findings.

## Scope — A, B and C ship together

| Step | What it does | Why it cannot ship alone |
|---|---|---|
| **A** | The tenant check on all 61 AI routes | Without B, a Starter tenant still gets a friendly 403 instead of a 403 — but the *other* tenant's data is still exposed to a Starter tenant on any route that is not gated |
| **B** | The plan gate on the AI family | Without A, an Enterprise tenant can read a Starter tenant's data — the plan gate says nothing about ownership |
| **C** | The verification pass | Without C, neither A nor B can be trusted — the customer app is the shared path and must keep working on every plan |

**All three are one change set.** A without B leaves the plan half-enforced; B without A leaves the isolation hole open; C exists because both A and B touch routes the customer app uses.

## A — The tenant check

### A1. The two-caller problem

The AI routes have two very different callers:

| Caller | Credential | Tenant source | Strictness |
|---|---|---|---|
| POS staff (browser) | signed session | the session (`key_info.customer_id`) | strict — the session wins, a browser can never claim another tenant |
| Customer app (PWA) | shared API key | the `customer_id` claim, **which the PWA often omits** | the outlet itself is the scope |

The customer app calls these routes **without** a `customer_id` claim in most cases:

```
GET  /api/ai/search?q=coffee&outlet_id=1          → no customer_id
GET  /api/ai/recommendations/cart?outlet_id=1     → no customer_id
GET  /api/ai/recommendations/frequently-bought     → no customer_id
POST /api/ai/chat/order?outlet_id=1&customer_id=…  → claim present, but optional
```

So a strict `require_tenant_claim()` would answer **400** and break the guest ordering flow. The check has to work for both callers.

### A2. The helper

A new helper in `backend/app/core/tenant.py`:

```python
def require_outlet_access(db: Session, request: Request, key_info: dict, outlet_id: int) -> int:
    """Fail unless the caller may read the outlet's data.

    The tenant of the outlet is always derived from the outlet itself.

    * A signed-in staff member: the outlet's tenant must equal the
      session's tenant, or the request is refused (403).
    * An API-key caller: when it sends a customer_id claim, the outlet's
      tenant must equal that claim (403). Without a claim the outlet is
      the scope - the same rule the customer app already relies on for
      the menu and the cart.
    """
```

The rule stays: **the tenant of a resource is derived from the resource.** The claim is only ever a cross-check, never an authority.

### A3. The mapping

| Route shape | Check | Example |
|---|---|---|
| takes `outlet_id` | `require_outlet_access(...)` | `/api/ai/forecast/daily` |
| takes `customer_id` (the POS tenant) | `require_customer_tenant(customer_id, tenant)` | `/api/competitors/{customer_id}` |
| takes a row id (alert, campaign, competitor, item) | load the row, then `require_resource_tenant(db, row, tenant)` → 404 unknown, 403 foreign | `/api/ai/security/alerts/{alert_id}` |
| row id + a body payload that carries another tenant | the row wins; a mismatch in the payload is a 403 | `POST /api/ai/campaigns` |
| no tenant at all (pure config) | none needed, but the write still needs the role gate | `/api/ai/campaigns/suggest` |

## B — The plan gate

### B1. The rule, in one table

**The AI at the dashboard is a free benefit for every plan. The AI Tools follow the subscription. The AI in the customer app is free for every plan. The "you might also like" in Staff Order is free for every plan.**

That gives every AI route exactly one home:

| Route family | Where it shows | Plan rule | Feature that grants it |
|---|---|---|---|
| `/api/ai/insights` (GET + POST) | AI Tools → Insights | follows the plan | **AI Insights** |
| `/api/ai/menu-analytics` | AI Tools → Menu Analytics | follows the plan | **Menu Analytics** |
| `/api/ai/campaigns/*` | AI Tools → Campaigns | follows the plan | **AI Campaigns** |
| `/api/ai/chat/order`, `/api/ai/chat/search-and-order`, `/api/ai/chat/suggest` | the POS chatbot | follows the plan | **AI Chatbot** |
| `/api/ai/search/suggestions` | the AI search suggestions | follows the plan | **AI Tools** |
| `/api/competitors/analyze`, `/api/competitors/ai-insights/*`, the competitor CRUD | AI Tools → Competitor Analysis | follows the plan | **Competitor Analysis** |
| `/api/competitors/discover-places`, `/analyze-discovered`, `/save-discovered` | AI Tools → Competitor Discover | follows the plan | **Competitor Discover** |
| `/api/chatbot/*` | the legacy chatbot | follows the plan | **AI Chatbot** |
| `/api/ai/customer-insights/*` | **the Dashboard** | **all plans** | — |
| `/api/ai/forecast/*` | **the Dashboard** | **all plans** | — |
| `/api/ai/orders/*` | **the Dashboard** | **all plans** | — |
| `/api/ai/security/*` | **the Dashboard** (the AI alerts panel) | **all plans** | — |
| `/api/ai/recommendations/*` | **Staff Order** ("you might also like") + the customer app | **all plans** | — |
| `/api/ai/customer/*` | the customer app | **all plans** | — |
| `/api/ai/search` | the staff menu search + the customer app | **all plans** | — |
| `/api/ai/inventory/*` | the Inventory page | the Inventory feature | **Inventory** (already done) |

The names are the display names of the `features` catalogue — the same names the AI Tools tabs already carry in `frontend/src/pages/AI/index.jsx` (`feature: 'AI Insights'`, `'Menu Analytics'`, `'AI Campaigns'`, `'Competitor Discover'`, `'Competitor Analysis'`). The sidebar and the API therefore cannot disagree.

### B2. The asymmetry that matters

**The same route can be free for the customer app and paid for the POS.** `/api/ai/chat/order` is the AI order chat in both places:

- the **customer app** calls it with the shared API key → never plan-gated → free on every plan ✓
- the **POS** calls it with a staff session → gated on **AI Chatbot** → follows the subscription ✓

That is the plan gate doing its job: it prices the *staff tools*, and the customer-facing benefit stays open. The tenant check (step A) applies to both callers, always.

### B3. What the customer app keeps, whatever the plan

The customer app's calls are never refused by the plan, because `require_plan_feature` only inspects a **browser session** (`key_type == "user"`) and the customer app authenticates with the shared API key:

```
GET  /api/ai/search?q=…&outlet_id=…            free on every plan
GET  /api/ai/customer/{id}/greeting?outlet_id=… free on every plan
POST /api/ai/recommendations/cart?outlet_id=…   free on every plan
POST /api/ai/chat/order?outlet_id=…             free on every plan
```

This is structural, not a special case: any route gated in the future is free for the customer app, and any route left free is free for the POS staff too.

### B3. The customer app carve-out — the AI stays available on every plan

**Decision: the customer app's AI is a customer benefit and is available on every plan, Starter included.**

The mechanism already guarantees this, structurally:

```python
# app/middleware/auth.py — require_plan_feature
if key_info.get("key_type") != "user":
    return key_info          # a server-to-server caller is not plan-gated
```

Only a **browser session** is plan-gated. The customer app calls with the shared API key, so it is never refused by the plan — on any plan, for any route, including the ones this document gates. The same carve-out covers the routes the PWA shares with the POS (`/api/ai/chat/order`, `/api/ai/search`, `/api/ai/customer/*`, `/api/ai/recommendations/*`).

One consequence to keep in mind: the plan gate and the tenant check are **independent**. Gating the staff side of a shared route never closes the customer app, and the tenant check applies to both callers.

## C — The verification pass

C is not a code change; it is the proof that A and B are correct and that nothing was broken.

### C1. The probe matrix

| # | Probe | Expected |
|---|---|---|
| 1 | Enterprise tenant, own outlet | **200** on every route |
| 2 | Starter tenant, own outlet, **a plan-gated route** | **403** with `This feature is not included in your plan: <name>` |
| 3 | Starter tenant, own outlet, **a free route** (the dashboard AI, the recommendations, the menu search) | **200** — the free benefit stays free |
| 4 | Starter tenant, **another tenant's** outlet | **403** (isolation) on every route that takes an outlet |
| 5 | Enterprise tenant, **another tenant's** outlet | **403** (isolation) — the plan does not grant ownership |
| 6 | Unknown row id (alert, campaign, competitor) | **404** |
| 7 | The public customer key, the customer app's routes | **200** on every plan — the guest ordering flow |
| 8 | The public customer key, the staff-only routes | **403** |

### C2. The customer app smoke test

The guest flow is checked end to end on a **Starter** plan, because that is the plan where a mistake would show up:

```
menu → search → AI chat → add to cart → place the order → the receipt
```

### C3. The regression

- The 24-route POS sweep (`/tmp/regress_all.js`) → `routes with problems: 0 / 24`
- The PWA regression (`scripts/pwa_check.js`)
- The browser check per role (admin / manager / staff) → no console errors

Each phase is independently revertable — the helper is additive and the gate is a single dependency per route.

## Risk and rollback

| Risk | Mitigation |
|---|---|
| The customer app breaks (the PWA sends no claim) | the helper accepts a key caller without a claim; the smoke test runs on every phase |
| The staff menu search breaks on a Starter plan | `/api/ai/search` is excluded from the gate by design (B1) |
| The dashboard AI is refused on a Starter plan | the dashboard AI is free on every plan by decision 1 — the gate must not be applied to it (the probe matrix row 3) |
| The Staff Order upsell is refused on a Starter plan | the recommendations are free on every plan by decision 4 |
| A session issued before the feature list existed | `require_plan_feature` already lets an empty `feat` list through — an old cookie never locks anybody out |
| The gate blocks a plan that *should* have the feature | the feature list comes from the same website API the frontend uses, so the sidebar and the API can never disagree |

**Rollback:** remove the `Depends(require_plan_feature(...))` / `Depends(require_outlet_access(...))` from a route. No schema change, no data migration.

---

## Decisions (Kens, November 2, 2026)

The four rules that settled the plan gate:

| # | Decision | Effect on the plan gate |
|---|---|---|
| 1 | **The AI at the dashboard is allowed on every plan** | the dashboard AI (`customer-insights`, `forecast`, `orders`, `security`) is **not** plan-gated |
| 2 | **The AI Tools follow the plan subscription** | the AI Tools page (Insights, Menu Analytics, Campaigns, the chatbot, Competitor Analysis and Discover, the AI search suggestions) **is** plan-gated, on the catalogue feature each tab already declares |
| 3 | **The AI in the customer order app is allowed on every plan** | the customer app's calls are never plan-gated (the shared key is not a session) |
| 4 | **The Staff Order "you might also like" is allowed on every plan** | `/api/ai/recommendations/*` is **not** plan-gated |

**The tenant check (step A) applies to every route in every case.** None of these four decisions weakens the isolation — they only decide what a restaurant *pays for*, not what it may *read*.
