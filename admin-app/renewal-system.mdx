# Subscription Renewal System

IDEAZES POS AI implements a unified renewal system with clear payment deadlines and access control.

:::info
**Applies to Both Billing Cycles**

This renewal system applies to **both monthly and annual** billing subscriptions:
- **Monthly Billing:** 30-day subscription period, 14-day grace period
- **Annual Billing:** 365-day subscription period, 14-day grace period

All logic is identical for both billing cycles. Only the period length differs.

**Trial Subscriptions**

All trial subscriptions follow the **30-day standard trial period**:
- Trial invoice ($0) is auto-created and auto-marked as paid by cron job
- At trial end (Day 30), first paid invoice is generated
- Customer has 14-day grace period to pay the first paid invoice
- If not paid by Day 44, subscription expires and access is blocked
:::

---

## Core Concepts

### Key Rule

**Access is blocked when grace period ends (Day 14) if payment is not received.**

### Subscription Period vs Grace Period

| Item | Definition | Duration |
|------|------------|----------|
| Subscription Period | Active service time | 30 days (monthly) / 365 days (annual) |
| Grace Period | Time to pay invoice | 14 days (default) |

**Important:** If grace period ends without payment, subscription becomes EXPIRED regardless of cancellation status.

## Timeline: Monthly Subscription

```
Day 0:  Subscribe / Renew
         |
         subscription_period_start = Day 0
         subscription_period_end = Day 30
         invoice_created = Day 0
         invoice_due_date = Day 14
         |
Day 7:  Warning email
         |
Day 14: Grace period ends (invoice due)
         |
Day 15+: If NOT paid - ACCESS BLOCKED, Invoice = forgiven, Subscription = expired
         |
Day 30: Subscription period technically ends
         (Access already blocked since Day 15)
```

```

         |
         |--- Paid within 14 days ---> PAID
         |
         |--- Not paid by Day 14 ---|
                   |
                   v

                   |
                   v
         Access BLOCKED
         Subscription EXPIRED
```

## Subscription Status Flow

```
ACTIVE
         |
         |--- Paid ---> ACTIVE (next cycle)
         |
         |--- Not paid by Day 14 ---|
                   |
                   v
              EXPIRED (blocked immediately)
```

## Cancellation Logic

### Key Points

1. **Cancellation is recorded** but does NOT override payment obligation
2. **If grace period ends without payment, subscription becomes EXPIRED** regardless of cancellation status
3. **With payment before grace period:** Access continues until period end
4. **Without payment:** Access blocked at grace period end

### Cancellation Decision Table

| Payment | Cancel When | Result |
|---------|-------------|--------|
| Paid | Any time | Access until period end, then blocked |
| Not Paid | Before Day 14 | Cancelled at Day 14 becomes EXPIRED |
| Not Paid | After Day 14 | Already EXPIRED, cancellation has no effect |

- **POS data is PRESERVED** - outlets, orders, menu items, tables all remain
- Customer can self-reactivate via portal or admin can do it
- Reactivation creates NEW subscription (not resume old one)

**Result:** Old subscription expired, New subscription active, Full access restored, POS data preserved

### Scenario 13: Trial - Upgrade Plan During Trial

```
Day 0:   Trial starts
           subscription_status = trial
           plan = Starter (default or selected)
           billing_cycle = null/pending
           Invoice #1 created: $0, status = trial

Day 0:   Cron job runs (daily)
           Invoice #1 status → paid (auto-marked for trial)

Day 7:   Trial warning email #1 sent
Day 12:  Trial warning email #2 sent
Day 14:  Grace period ends
           ✓ No issue — Invoice #1 already paid

Day 15:  Customer UPGRADES plan AND selects billing cycle
           subscription plan updated: Starter → Pro
           subscription billing_cycle stored: annual (365 days)
           Invoice #1: unchanged ($0, already paid)
           No new invoice created yet ✓

Day 30:  Trial ends
           subscription plan: Pro (already updated on Day 15)
           subscription billing_cycle: annual (already stored on Day 15)
           subscription status → active
           subscription period_start = Day 30
           subscription period_end = Day 395 (30 + 365)
           Invoice #2 created: $XX (Pro annual price), status = pending

Day 30:  Customer pays Invoice #2
           Invoice #2 status → paid ✓
           subscription continues as active
           Next invoice (Invoice #3) due at Day 395

Day 44:  Grace period ends
           ✓ No issue — Invoice #2 already paid
```

**Key Points:**
- During trial, customer can upgrade plan AND select billing cycle anytime (Day 0-29)
- Both `plan` and `billing_cycle` are stored in the subscription record when customer commits
- Invoice #2 at Day 30 reflects the upgraded plan AND selected billing cycle
- No prorated billing during trial — keeps it simple
- After trial converts to paid, normal prorated upgrade rules apply for mid-cycle changes

**Result:** Plan upgraded during trial, billing cycle selected, Invoice #2 generated for Pro annual at Day 30, Trial converts to active, Access full

## Paid to Paid Upgrades

### Key Rules

| Rule | Description |
|------|-------------|
| Upgrade only | No downgrade allowed |
| Period unchanged | period_end stays the same |
| Prorated billing | Pay difference for remaining days |
| Immediate effect | Plan upgraded upon payment |

### Plan Pricing (Current)

| Plan | Monthly | Annual |
|------|---------|--------|
| Starter | Free ($0) | Free ($0) |
| Basic | $10/mo | $100/yr |
| Pro | $20/mo | $200/yr |
| Enterprise | $50/mo | $500/yr |

### Scenario 15: Paid - Upgrade Mid-Cycle (Monthly Billing)

**Starting State:**
- Plan: Starter (Free $0/month)
- Period: Day 0 - Day 30
- Invoice #1: paid ($0)

**Upgrade on Day 15 (Starter → Basic $10/month):**

```
Day 15:  Customer UPGRADES Starter → Basic ($10/month)
           Since Starter is $0, full Basic monthly price applies
           Days remaining = 30 - 15 = 15 days
           Full monthly price = $10
           Invoice #2 created: $10.00, status = pending
           subscription plan updated: Starter → Basic
           subscription period_end: unchanged (Day 30)

Day 15:  Customer pays Invoice #2
           Invoice #2 status → paid ✓
           subscription continues as Basic

Day 30:  Period ends
           Invoice #3 created: $10 (Basic monthly), status = pending
           Auto-renew continues
```

**Result:** Plan upgraded from free to paid, full $10 charged (no prorated since old plan was $0), subscription continues as Basic

### Scenario 16: Paid - Upgrade Mid-Cycle (Monthly Billing with Proration)

- Plan: Basic ($10/month)
- Period: Day 0 - Day 30
- Invoice #1: paid ($10)

```
Day 15:  Customer pays Invoice #2
           Invoice #2 status → paid ✓
           subscription continues as Pro

           Auto-renew continues
```

**Result:** Plan upgraded mid-cycle, prorated charge $5 collected, subscription continues as Pro

## Reactivation Flow

### Overview

When a customer with a cancelled or expired subscription returns, they can **reactivate** by creating a new subscription.

**Key Design Decision:** Reactivation creates a **NEW subscription** (not resume old one). This ensures:
- Clean billing history
- Proper invoice tracking
- Customer can choose different plan
- Clear lifecycle audit trail

### Reactivation Methods

| Method | Who | How |
|--------|-----|-----|
| **Self-service** | Customer | Via customer portal (simplified flow) |
| **Admin-initiated** | Admin | Via admin panel |

### Self-Service Reactivation (Customer Portal)

```
Customer visits portal (cancelled/expired status)
         |
         v
Sees "Reactivate Subscription" button
         |
         v
Simplified subscription flow:
1. Select plan (can be same or different)
2. Choose billing cycle
3. Select payment method
         |
         v
Creates NEW subscription
         |
         v
POS Login RESTORED
POS data: PRESERVED
```

### Admin Reactivation

```
Admin views cancelled/expired customer in Admin Panel
         |
         v
Clicks "Reactivate" button
         |
         v
Chooses plan (same or different)
         |
         v
Creates NEW subscription
         |
         v
Customer notified via email
POS Login RESTORED
POS data: PRESERVED
```

### POS Data Preservation

| Data Type | Preserved on Reactivation? |
|-----------|---------------------------|
| Customer record | ✅ Yes (same customer_id) |
| Users | ✅ Yes |
| Outlets | ✅ Yes |
| Menu Items | ✅ Yes |
| Categories | ✅ Yes |
| Tables | ✅ Yes |
| Orders | ✅ Yes |
| Subscriptions (old) | ❌ Archived (status preserved) |
| Invoices (old) | ❌ Archived (historical record) |

**All POS operational data is preserved.** Only subscriptions and invoices are treated as new records.

### Reactivation and Payment

| Old Status | Payment Required? |
|------------|-------------------|
| Expired (unpaid) | Old invoices remain forgiven on record |
| Cancelled (paid) | Old subscription was paid - no payment needed |
| Both cases | New subscription requires new payment |

Reactivation always creates a fresh subscription with new invoices. Old unpaid invoices stay on record as forgiven.

## Access Control Logic

### Login Flow

```
Customer attempts login
         |
         v
Check subscription status
         |
    _____|_____
   |           |
   v           v
ACTIVE      NOT ACTIVE
   |           |
   |       ____|____
   |      |         |
   |      v         v
   |    EXPIRED   CANCELLED
   |      |         |
   |      v         v
   |    BLOCK    Check grace period
   |             ____|____
   |            |           |
   |            v           v
   |         GRACE        GRACE
   |         ENDED        ACTIVE
   |            |           |
   |            v           v
   |          BLOCK      ALLOW
   |                       (with warning)
   v
Check for NEW active subscription (reactivated)
   |
   v
Has new active subscription - ALLOW
No new subscription - BLOCK
         |
         v
Check payment (if active)
   |
   v
Paid - ALLOW
Pending - WARNING if due soon
Overdue - BLOCK
```

### Access Decision Table

| Status | Payment | Access |
|--------|---------|--------|
| active | paid | ALLOW |
| active | pending (due soon) | WARNING |
| active | overdue | BLOCK |
| trial | - | ALLOW |
| cancelled | paid | ALLOW until period end |
| cancelled | no payment | BLOCK at grace period |
| expired | - | BLOCK |
| cancelled/expired | has NEW active subscription | ALLOW (reactivated) |

| 7 days | First warning email |
| 3 days | Second warning email |
| 1 day | Final reminder email |
| 0 days | Grace period ends |
| 1+ days | Access BLOCKED |

| Rule | Description |
|------|-------------|

| Access blocked at Day 15 | If grace period ends without payment |
